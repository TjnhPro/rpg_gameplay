### Two independent storage candidates

The fixture checks actual Inventory membership, quantity1, exact Item, matching
owner and absence from Equipment. It requests removeInventoryEntry and
equipEquipmentItem from the original snapshots. A local publish closure replaces
one in-memory pair only if both results accepted and the original pair is still
current; uniqueness is checked before publication. Rejected equip leaves the source
bag untouched; stale baseline cannot republish. Exact success: bag empty, gear has
A once, same properties, no Equipment quantity field.

On return, unequip releases A, addInventoryEntry stages quantity1 on the current
bag; only both accepted are published. maxEntries0, a physically occupied one-entry
bag and Inventory eligible:false each refuse publication, keeping A equipped.
Successful return restores the exact original pair. A valid stackable quantity2
source is rejected by the L4 staging guard before requesting either transition;
no split, generated ID or duplicated Item is introduced.

Replacement crossing storage is also executed: initial bag[B]/gear[A]; stage
remove B, replace A with B, then add released A into the staged bag. maxEntries0
rejects and publishes neither; maxEntries1 yields exact bag[A]/gear[B], each once,
with original properties. Old snapshots remain unchanged. No variant is deferred.
These are single-process caller fixtures, not DB/durable/distributed transactions,
MMO concurrency, global ownership authority or production transfer APIs.
