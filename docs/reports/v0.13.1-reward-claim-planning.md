## API delta and canonical authority

Append only prepareRewardClaim(state:RewardClaimState,admission:RewardClaimAdmission):
RewardClaimPreparationResult; two readonly types, exactly as supplied in the task.
Admission is eligible:boolean. Accepted status narrows reason:none, complete candidate
and readonly RewardLine[]; rejected narrows already_claimed|ineligible, candidate:null
and readonly empty tuple. No redundant inspection or grant-intent type.

All old Foundation types and function signatures remain exact. Root native ESM names
equal baseline plus prepareRewardClaim; type names equal baseline plus the two new types
(observed195 runtime/311 types). Registry and old graph unchanged, optional reward->[].
Reward still has zero imports; no Core/sibling calls, new runtime dependency or handler.

Implementation validates the whole state through validateRewardClaimState, then admission
via the existing strict descriptor helper. Claimed status never bypasses admission or
nested validation. Structural errors throw TypeError; ordinary priority is already_claimed,
then ineligible. Acceptance shallowly wraps the already-detached canonical snapshot with
claimed status; grant lines are separately captured through validateRewardPackage, ensuring
their identities detach from both input and candidate. Empty/repeated/opaque/fractional
lines retain Foundation meaning. Every wrapper, nested record and array is frozen/fresh.

L2 only prepares data. L3 resolves policy/kind semantics; L4 checks authoritative claimId,
recipient/current state, content availability and consumer compatibility, then atomically
commits all grant candidates together with claim state. eligible:true is not entitlement
proof. Two calls on the original available snapshot can both succeed. A supplied claimed
snapshot rejects, but no global/concurrent/distributed exactly-once guarantee exists.
No Item/Inventory/Progression call, actual delivery, events, receipt, store, clock or RNG.
