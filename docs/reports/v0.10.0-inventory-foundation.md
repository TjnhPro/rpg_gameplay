## 1. Research and actual Item ownership

Actual accepted Item API inspected before implementation:
`validateItemDefinition(definition): ItemDefinition`,
`validateItemInstance(definition, instance): ItemInstanceState`,
`validateItemStackPolicy(policy): ItemStackPolicy`, and
`assessItemStackCompatibility(leftDefinition, leftInstance, rightDefinition, rightInstance, policy)`.
Item definitions contain definitionId/categoryId/tagIds/rarityId/properties;
instances contain instanceId/definitionId/properties; stack policy has stackable.
Item alone validates/captures recursive property data. Inventory passes the original
instance to the canonical Item validator after safely reading only its binding key.
Compatibility remains advisory in Item; this milestone does not merge instances.

Architecture references, not copied implementations:

- [Epic Lyra Inventory and Equipment](https://dev.epicgames.com/documentation/en-us/unreal-engine/lyra-inventory-and-equipment-in-unreal-engine)
  separates inventory/equipment and definitions/instances, with multiple instances or stack counts.
  The project retains the separation without a controller or manager runtime.
- [Unity Game Foundation historical preview](https://docs.unity3d.com/ru/current/Manual/com.unity.game.foundation.html)
  lists Inventory, Wallet, Stats and Transaction domains; this is a historical reference,
  not a recommendation to install its preview manager architecture.
- [Unity Economy player data](https://docs.unity.com/en-us/economy/player-data) and
  [custom data](https://docs.unity.com/en-us/economy/custom-data) distinguish instance
  identity/data from configuration metadata. Cloud storage and authority remain L4 here.
- [Godot 4.4 Resource](https://docs.godotengine.org/en/4.4/classes/class_resource.html)
  provides data containers. No claim that Godot core supplies a standard inventory.
  [Expresso Inventory](https://github.com/expressobits/inventory-system) illustrates
  separate logic/UI and extensible items/stacks; Nodes, editors and multiplayer are not adopted.

Project choice: Inventory owns membership/quantity; Item owns Item data and identity
validation. These sources do not prescribe the identical model used here.

## 2–3. Boundaries and frozen contracts

L1 numerical Kernel unchanged. L2 Inventory owns only snapshot identity, neutral owner,
ordered entry membership and quantity validation. L3 supplies stack policy/caps and
complete definitions explicitly. L4 owns IDs, authorization, state commits, persistence,
concurrency and global uniqueness. No stores, clocks, RNG or independent engine.

Additive root API: two functions `createInventoryState`, `validateInventoryState`;
six types `InventoryOwnerReference`, `InventoryEntry`, `InventoryState`,
`InventoryItemContext`, `InventoryValidationContext`, `InventoryTransitionResult`.
Signatures match the approved task. Inventory is optional, depends only on Item;
Item remains optional with no dependencies. Existing registry entries are unchanged.
Malformed data throws TypeError. Both functions return fresh detached deeply frozen
snapshots, preserve opaque IDs and entry order, and never freeze caller input.
All context entries are validated, including unused definitions; duplicates reject.
`null` maximum removes only the extra cap, never the safe integer bound.

## 4. Design-only future stress assessment

These are feasibility assessments, not implemented operations or runtime test claims.

| Case | Same foundation shape and future owner |
| --- | --- |
| Unique item | One canonical Item instance, quantity 1, explicit nonstackable policy |
| Potion stack | One Item instance plus quantity 9; explicit cap 20 |
| Merge | Future operation checks canonical Item compatibility; retains destination ID, retires source membership; global identity retirement is L4 |
| Split | Caller supplies new ID through canonical Item creation; two resulting entries |
| Full/partial transfer | Paired source/destination candidates; L4 must atomically commit and authorize |
| Equipment handoff | External L4 handoff of canonical Item snapshot; no equipment fields in Inventory |
| Chest/bank/ownerless | Neutral ownerKind/ownerId or null; no Entity dependency |
| UI slots/grid | Companion state keyed by instance ID; array order is not a grid coordinate |
| Hydration | Complete caller snapshot plus context can be validated; persistence format/migration remains external |
| Capacity/weight | L3 policy evaluates external facts; no built-in game capacity or weight calculator |

No breaking shape gap found for these cases. Future operations/policies still require
separate approved tasks; no placeholders or future implementation added.
