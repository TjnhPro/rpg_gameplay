## Exact additive public API and invariants

Runtime: `createEquipmentState(input,context):EquipmentState` and
`validateEquipmentState(state,context):EquipmentState`.
Types: `EquipmentOwnerReference`, `EquippedEntry`, `EquipmentState`,
`EquipmentItemContext`, `EquipmentValidationContext` (five, all readonly fields).
The exact shapes match the task and `src/modules/equipment/index.ts`.

IDs are exact nonblank strings; owner may be null. Required dense ordered entries
have unique local Item instance IDs. Required nonempty dense ordered slot IDs cannot
repeat within/across entries. Context has unique complete canonical definitions,
including valid unused ones; every equipped Item resolves and validates its binding.
Closed own-data structures reject extra/symbol/accessor/custom-prototype/inherited
required data; canonical Item validation rejects unsafe nested values/cycles.
Getters are not invoked. Invalid supplied data throws TypeError. Successful calls
always create fresh detached deeply frozen snapshots without freezing caller input.
Nonempty rehydration is structural validation, not proof of lawful equipping.

Static registry adds only `{id:'equipment',optional:true,dependencies:['item']}`.
No Inventory/Entity/Skill/Effect/Core import or new numerical operation. L4 still
owns authority, freshness and cross-storage uniqueness. No quantity, default slot
catalog, generated ID, equip/unequip/query/admission operation, global store or engine.
