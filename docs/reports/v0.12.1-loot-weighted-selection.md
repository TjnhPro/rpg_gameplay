## Implementation and contract freeze

One additive operation: `rollLootTable(table:LootTableDefinition,sample:number):LootRollResult`.
No new public types. Entire v0.12.0 Loot source remains an unchanged prefix, preserving
all old validation/helpers/signatures/error behavior. Root adds only this function.
Final Loot inventory: createLootTableDefinition, validateLootTableDefinition,
validateLootRollResult, rollLootTable; LootTableEntry, LootTableDefinition, LootDropIntent,
LootRollResult. Exact release comparison against baseline names finds190 runtime root
exports and304 type exports, with exactly one function added and no removed/retyped name.
This is scoped release evidence, not a new daily inventory/count gate.

The operation first calls canonical table validation, then rejects non-number/nonfinite/
out-of-range sample with TypeError. It sums the validated weights and calculates
`ticket = Math.min(total - 1, Math.floor(sample * total))`. No-drop first, then input
entry order; each bucket uses `< end`. Selected entry ID/definition/quantity is projected
through canonical result validation, or an empty result is validated for no-drop.
Outputs are newly detached and recursively frozen. No retries, sorting, normalization,
providers, generator, clock, IDs, catalog lookup, Item creation or storage commit.

Graph remains11 optional modules with `loot -> []`; no imports in Loot. L3 supplies
resolved tables/weights; L4 supplies sample, event and delivery authority; Item/Inventory/
Equipment retain their canonical responsibilities. Bounded weight bookkeeping is the
approved Loot operation, not an alternative Kernel or general numerical calculator.
