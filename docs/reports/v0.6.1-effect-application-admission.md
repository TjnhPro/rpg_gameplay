## 6–9. Source-agnostic requests, canonical context and caller policy

Entity source existence and target existence use getEntity, which validates the
entire closed collection and its identities/uniqueness before lookup. Effect does
not scan/copy private collections. System source IDs are never looked up as Entity;
no fake Entity is created. Source life is not hardcoded; sourceEligible supplies
caller assessment consistent with D17. Stable sourceKey remains exact and opaque.

Life has canonical EntityLifeState/EntityLifeStatus shape/values. The Effect
boundary checks its two own-data fields, exact binding and alive/dead status; it
neither infers nor transitions life, creates another enum, nor fabricates an Entity
when the target is missing. Explicit nonempty unique allowedTargetLifeStatuses can
permit alive, dead, or both. No automatic revive or universal alive-only default.

sourceEligible and targetEligible must be explicit booleans. L3/L4 resolve gameplay
permissions/relations and current eligibility. Effect does not copy Skill admission
or Combat targeting, inspect source-key meaning or authenticate assertions.
Admission is not a credential/durable token. L4 retains freshness, concurrency,
authoritative state and commit/retry policy. No cross-domain transaction is claimed.

## 10–13. Priority, duplicate semantics and immutable candidates

All Definition/Request/Instance/Source/State/Collection/Life/Policy contracts and
cross-contract identities validate before ordinary rejection selection. Malformed
inputs/associations throw TypeError, including when source and target are missing.
Closed own-data validation rejects missing/extra/symbol/accessor/inherited required
fields; invalid nested/dense-array/unique-status inputs reject with getter count0.

Ordinary reason priority:
source_not_found > target_not_found > target_life_not_allowed > source_ineligible
> target_ineligible > instance_already_present > none.
Admission status is admitted iff reason=none. Policy property order does not matter.

Duplicate identity is scoped only to the supplied target EffectState, including
same-ID retry with another valid Effect/source payload. No overwrite, generated ID,
implicit idempotent success or global ledger exists. Distinct IDs for the same
Effect/sourceKey can append; this does not implement stacking. Same ID can be
accepted in another target state or against the original uncommitted empty state.

applyEffect reevaluates admission using full caller context; it accepts no receipt
for bypass. Applied result appends in original order through validateEffectState;
rejected result always has state=null. Nested request/admission/candidate records
are detached/frozen, including previous instances. Caller objects remain unchanged
and unfrozen; mutation after return cannot change captured snapshots. No partial
state, implicit commit, clock/RNG/ID reads, scheduling or events occur.
