  must not become Inventory or Equipment storage/instance ownership.

  data do not establish authoritative grant execution. No Unity service or integer-only
  currency policy is ported.
- [Godot resources](https://docs.godotengine.org/en/stable/tutorials/scripting/resources.html)
  separates data containers from node behavior. Inference: immutable Reward snapshots
  need no engine, node, callback manager or runtime.

## Future contract stress — design only

| Future request | Existing extension point; deferred behavior |
| --- | --- |
| Currency/unlock/reputation | Opaque grantKindId/referenceId/amount; no handler or wallet implemented |
| Quest/boss/achievement | Neutral source kind/id; no world or quest listener |
| Multiple recipients | Separate caller-issued claim IDs and recipient snapshots sharing resolved content; no party distributor |
| Repeatable/daily claims | L4 issues distinct entitlement IDs; no clock, cadence or registry |
| Catalog edits | Embedded detached reward retains original values; later catalog changes affect later captures |
| Multi-line atomic delivery | Ordered lines support a later plan; L4 commits owners together, no transaction engine |
| Explicit no-op | Empty lines valid; L4 decides issuance policy |
| Scaling/random amounts/context | L3 resolves concrete package before capture; no DSL/random generation |
| Partial/expiry/compensation | Would need separately approved companion state with provenance; not overloaded into base status |
| Distributed exactly once | L4 unique authority and DB atomic commit; no locks/queues/receipt in Reward |

No known supplied use case requires breaking the five canonical types. Foundation
does not claim to implement these future behaviors or Item/EXP delivery.
