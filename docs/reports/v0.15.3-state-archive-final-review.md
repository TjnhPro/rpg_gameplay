## Public composition and independent oracle

The new root-import integration fixture creates actual canonical snapshots, captures
four exact records at one explicit point, then performs test-local JSON serialization
and parsing. Item instances live inside Inventory/Equipment snapshots; there is no
second authoritative Item store. Independent literals specify bag-blade quantity 3,
gems [2], gear-blade power 7/slot hand, gold 23/silver explicit 0, and a claimed Reward
with recipient player/p1. Definition blade, stackable=true and maximum 10 are independent
L3 facts, never reconstructed from archive payload claims.

Public signatures exercised (unchanged; canonical types in [API](../API.md)):

```ts
assembleGameplayStateArchive(formatVersion: number, records: readonly GameplayStateRecord[]): GameplayStateArchive;
validateGameplayStateArchive(archive: GameplayStateArchive): GameplayStateArchive;
prepareGameplayStateRestore(archive: GameplayStateArchive, policy: GameplayStateRestorePolicy): GameplayStateRestorePreparation;
createInventoryState(input: InventoryState, context: InventoryValidationContext): InventoryState;
validateInventoryState(state: InventoryState, context: InventoryValidationContext): InventoryState;
createEquipmentState(input: EquipmentState, context: EquipmentValidationContext): EquipmentState;
validateEquipmentState(state: EquipmentState, context: EquipmentValidationContext): EquipmentState;
createCurrencyWalletState(input: CurrencyWalletState): CurrencyWalletState;
validateCurrencyWalletState(state: CurrencyWalletState): CurrencyWalletState;
createRewardClaimState(input: RewardClaimState): RewardClaimState;
validateRewardClaimState(input: RewardClaimState): RewardClaimState;
prepareRewardClaim(state: RewardClaimState, admission: RewardClaimAdmission): RewardClaimPreparationResult;
```

Parsed data remains untrusted/mutable until complete structural revalidation. Preparation
ready is only metadata compatibility. The fixture next calls real owner validators,
including canonical Item validation through Inventory/Equipment with caller definitions.
It checks payload IDs against exact record IDs, current owner and recipient bindings,
cross-storage Item uniqueness and current baseline identity before its sole assignment.
Every failed case preserves holder identity and serialized pre-state. Returned nested
state is frozen and detached from parsed data, validated archive and initial state.
Repeated equivalent inputs give value-equal, separately allocated results.

No event/tick/grant interface is wired into restoration, and source inspection shows
these owner validators only validate/capture data. Claimed status and balances are
preserved; a separate explicit prepareRewardClaim replay returns already_claimed with
null candidate and empty grants. This is state-preservation/pure-call evidence, not
an instrumented production event bus or proof of historical reward delivery.

## Evidence-driven gaps and limits

Representative portable snapshots only; no claim every valid domain value has a JSON
encoding (the archive explicitly rejects -0 and nonportable data). No targeted
representative owner shape required a production change.

NOT_EVALUATED for archive rehydration: Entity separate attributes/resource/life states;
Progression rank/point/cursor states; Combat operations; Skill separate costs/cooldowns/
loadouts; Effect duration/periodic state; Actor AI timing/decision/feedback ledgers;
Encounter membership/completion/recovery state. Their separate owner/context/clock/
lifecycle contracts need explicit snapshot completeness, binding and recovery evidence.
Loot content definitions and Foundation private callback capabilities were not restored.
Their existing direct regression tests still ran; those tests do not imply save/restore coverage.

No DB/file adapter, durable atomicity, distributed CAS, crash/runtime recovery, autosave,
clock origin/catch-up, permission policy, schema migration, event sourcing or exactly-once
delivery is proven. L4 baseline identity comparison is only synchronous in-memory
freshness. No storage API, global manager, domain-validator registry or second engine.

CI configuration remains one Ubuntu/Node22 PR job checking out the exact head. No push
workflow or Windows/Node24 CI matrix is configured; Windows Node24 evidence here is local.
CI result and delivery SHA must be observed after push in the linked supplement.
