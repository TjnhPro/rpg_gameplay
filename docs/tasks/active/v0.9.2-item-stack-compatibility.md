## 4. Minimal additive public API — two functions and two types

All v0.9.0/v0.9.1 functions/types and semantics are **protected**. If the accepted installed declarations differ from examples, STOP with an exact API delta report rather than altering earlier accepted contracts.

```ts
export interface ItemStackPolicy {
  readonly stackable: boolean;
}

export type ItemStackCompatibilityResult =
  | {
      readonly compatible: true;
      readonly reason: 'none';
    }
  | {
      readonly compatible: false;
      readonly reason:
        | 'same_instance'
        | 'different_definition'
        | 'definition_conflict'
        | 'not_stackable'
        | 'different_properties';
    };

export function validateItemStackPolicy(
  policy: ItemStackPolicy,
): ItemStackPolicy;

export function assessItemStackCompatibility(
  leftDefinition: ItemDefinition,
  leftInstance: ItemInstanceState,
  rightDefinition: ItemDefinition,
  rightInstance: ItemInstanceState,
  policy: ItemStackPolicy,
): ItemStackCompatibilityResult;
```

No `ItemStack`, `ItemQuantity`, `maxStack`, `InventoryEntry`, merged candidate, combined store, public deep-equality helper, `getStackKey` or `ItemStackEngine`.

### 4.1. IT09: explicit policy

- Only valid closed own-data `{stackable:boolean}`; no unknown/symbol fields, getters/accessors or class/custom prototype; no truthy coercion or default.
- `validateItemStackPolicy` returns **fresh detached frozen** exact object; caller input unchanged.
- A valid `stackable:true` **only** allows Item's *structural* compatibility check, not automatic merge, L3 content admission or capacity. `stackable:false` is structurally valid; it means no merge eligibility.
- No rarity, category, price/weight or property named `unique` automatically implies stackability.

### 4.2. IT10: complete structural validation before comparison

**Must validate all five inputs**, even if an early condition is incompatible:

1. `validateItemDefinition(leftDefinition)` and `validateItemDefinition(rightDefinition)` using Foundation.
2. `validateItemInstance(leftDefinition,leftInstance)` and `validateItemInstance(rightDefinition,rightInstance)` using Foundation, including exact binding.
3. `validateItemStackPolicy(policy)` on the complete own-data record.
4. Invalid nested input/prototype, accessor/symbol field, cycle, sparse array, mismatched ID, wrong policy type → **TypeError** (not `compatible:false`), even for `{stackable:false}` or obviously different definitions.
5. Compare only canonical safely captured snapshots, no arbitrary object value methods, getters, external callbacks or JSON stringification.

**Exact deterministic reason priority for structurally valid operands:**

| Order | Condition | Result |
| --- | --- | --- |
| 1 | Same exact instance ID | `{compatible:false,reason:'same_instance'}` |
| 2 | Different exact definition IDs | `{compatible:false,reason:'different_definition'}` |
| 3 | Same definition ID but different **full definition contents** | `{compatible:false,reason:'definition_conflict'}` |
| 4 | `policy.stackable === false` | `{compatible:false,reason:'not_stackable'}` |
| 5 | Different **full instance properties** | `{compatible:false,reason:'different_properties'}` |
| 6 | Otherwise | `{compatible:true,reason:'none'}` |

**Definition equality:** exact `definitionId`, `categoryId`, ordered tag IDs, exact rarity ID and deeply equal nested definition properties. **Instance equality for compatibility:** complete instance **properties** equal; different `instanceId`s are required, but are not themselves payload inequality.

**Nested data equality:** array element order is meaningful; record own key/value equality is independent of record insertion order; recursively compare exact own keys. `Object.is` numeric equality (notably `-0` versus `0`); strings case-sensitive, bool/null exact. Property objects with `__proto__` or `constructor` are ordinary safe own records. No lossy hashes, JSON stringification, normalization, approximate numerical matches, type coercion or field whitelist. Definition content equality includes metadata, not just IDs.

**Why conservative:** Two instances with different mutable properties (e.g., durability) cannot be considered stack-compatible simply because L3 sets `stackable:true`; an Inventory merge cannot silently discard distinct payload. Future policies can become richer only with a real use case **and lossless representation**.

### 4.3. IT11: safe identity/outcome semantics

- Same exact instance ID => `same_instance`, even if two *objects* carry equal data. Validate operands first.
- Two distinct instance IDs prove only two **references**, not global uniqueness or ownership. L4/Inventory will guard local/global duplicate storage and concurrent updates.
- `stackable:false` rejects otherwise equal distinct items. Do not infer item uniqueness from rarity, category or arbitrary L3 property keys.
- Return exactly `{compatible:boolean,reason:...}`; all outcomes fresh, detached, frozen. Compatible/incompatible is a **read-only advisory assessment**, never an Item state mutation, quantity change, merge receipt, split or commit.
- Malformed input fails with `TypeError`; valid but incompatible returns a normal immutable result, not an exception.

### 4.4. Literal examples

```ts
const def = createItemDefinition(
  createItemDefinitionReference({definitionId:'fixture-potion'}),
  {categoryId:'consumable',tagIds:[],rarityId:null,properties:{marker:'v1'}},
);
const a = createItemInstance(def,{instanceId:'potion-A',properties:{grade:1,tag:null}});
const b = createItemInstance(def,{instanceId:'potion-B',properties:{tag:null,grade:1}});
const yes = assessItemStackCompatibility(def,a,def,b,{stackable:true});
// exact {compatible:true,reason:'none'} despite property insertion order
const no = assessItemStackCompatibility(def,a,def,b,{stackable:false});
// exact {compatible:false,reason:'not_stackable'}
const same = assessItemStackCompatibility(def,a,def,a,{stackable:true});
// exact {compatible:false,reason:'same_instance'}
```

Fixture `consumable` does not configure L2 behavior; only the supplied policy does.
