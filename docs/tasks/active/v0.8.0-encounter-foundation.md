## 1. Objective and execution boundary

Implement the **Encounter Foundation**, a reusable, headless L2 contract for the identity and structural state of one encounter, without introducing an Encounter runtime or changing canonical gameplay owners.

| ID | Feature | Required capability |
|---|---|---|
| **EN01** | Encounter Identity | Exact encounter ID, opaque identity, deterministic validation |
| **EN02** | Encounter Definition Reference | Opaque L3 definition/template reference, not a copied content catalog |
| **EN03** | Encounter State Contract | Closed immutable snapshot, explicitly `prepared` at creation, generic lifecycle status type |
| **EN04** | Side & Participant Contracts | Generic side IDs, canonical Entity references, one side per participant within one encounter |
| **EN05** | Validation & Module Boundary | Fail-closed invariants, optional `encounter → [entity]`, public installed-package checks |

**Successful v0.8.0 consumer:** Creates an immutable encounter snapshot with caller-supplied identity, definition reference, side declarations and an optional *initial structural roster*. The snapshot starts `prepared`. It may be inspected and structurally validated against a canonical `EntityCollection`. It **cannot** activate, join/leave dynamically, spawn, run Combat, resolve victory, close, give rewards or commit to an authoritative World.

The *initial structural roster* is an input to this factory, **not** EN11 dynamic participation and **not** proof of activation. v0.8.1 adds activation readiness and game-policy validation; it must not reimplement EN04 identity/membership validation.

Example input:

```text
Encounter ID:  forest-fight-001
Definition ID: forest-wolves
Sides:         party, enemies
Participants:  player-001 → party; monster-001 → enemies
EntityCollection: contains player-001, monster-001
```

Expected `createEncounterState(...)`:

```text
status: prepared
participants: [player-001→party, monster-001→enemies]
side IDs: [party, enemies]
frozen/detached: true
world spawn: none
combat/AI execution: none
```

Do not declare v0.8.0 complete based on a passing unit function alone: installed artifact, strict declarations, historical regression, negative guards and exact-head CI are mandatory.

## 4. Ownership by L1–L4

### L1 — `@rpg/core/kernel` (numerical owner)

No Encounter-specific numerical algorithm; no new Core API or legacy import. Combat uses Core for hit, crit, damage and mitigation; Entity uses Core for resource/stat arithmetic. Encounter must not copy them.

### L2 — `@rpg/gameplay` Encounter

Owns **structural encounter identity, definition references, immutable side/participant membership records, prepared-state factory and deterministic validation**. Later milestones may add reusable lifecycle transitions. It does not own global current World state or multi-Encounter exclusivity.

### L2 canonical siblings

- **Entity:** only owner of `Entity.id`, `Entity.kind`, `EntityCollection`, HP/resources and Life.
- **Combat:** action admission, target relation policy, attack result/damage.
- **Skill:** activation, resource payment, cooldown and execution outcome.
- **Effect:** lifecycle/status/restrictions.
- **Actor AI:** perception, target selection, FSM, intents and timing.
- **Progression:** EXP/rank/upgrade ownership.

Do not add another owner for these capabilities into Encounter.

### L3 — game policy/content

Supplies opaque Encounter definition IDs; names/types of sides; future spawn, join/leave, objectives, wave, victory/defeat, difficulty and loot/reward policies. No catalog/registry data is embedded in L2.

### L4 — Game Application/World

Owns physical spawn/despawn; event triggers; timing/turn order; current Entity and Encounter storage; replay/concurrency-safe authoritative commit; World membership and placement; cross-Encounter exclusivity; Combat/Skill/Effect/AI orchestration; rewards/cleanup execution. L2 validation is not a transaction or admission permit.

### Dependency graph

```text
entity      → []
progression → [entity]
combat      → [entity]
skill       → [entity]
effect      → [entity]
actor-ai    → [entity]
encounter   → [entity]      // add in v0.8.0; optional, disabled by default
```

**Forbidden:** `encounter → combat`, `encounter → actor-ai`, `encounter → skill`, `encounter → effect`, `combat → encounter`, `actor-ai → encounter`, World/Movement import, mutual edges, global Gameplay Engine.

## 5. EN01 — Encounter Identity

### Contract

- Caller provides `encounterId`; L2 does not generate it.
- Exact opaque, nonblank string identity: case-sensitive, no trimming, lowercasing, parsing or canonicalization.
- IDs with leading/trailing spaces retain those bytes after validation if not entirely whitespace, consistent with accepted Entity/Actor AI identity conventions.
- Within one L2 Encounter snapshot, `encounterId` is a single scalar identity.
- Across encounters, L4 owns ID uniqueness/registration. A deterministic L2 factory cannot claim to enforce global uniqueness.
- Distinguish **Encounter instance ID** from **Encounter definition/template ID**.

Example:

```text
encounterId: "forest-fight-001"       // one runtime engagement identity
definitionId: "forest-wolves"        // reusable L3 definition reference
```

Do not identify encounters using a Monster Entity ID, World zone ID, party ID or Skill ID.

### Rejection

`null`, numbers, empty/whitespace-only strings, missing fields and accessor identity fields are invalid; throw `TypeError` before returning any snapshot.

Proposed public interface:

```ts
export interface EncounterDefinitionReference {
  readonly definitionId: string;
}
```

Proposed factory:

```ts
export function createEncounterDefinitionReference(
  input: EncounterDefinitionReference,
): EncounterDefinitionReference;
```

Required:

- Exactly one own data property `definitionId`.
- Validate as exact opaque nonblank ID.
- Return new detached, frozen data object.
- Do not load or validate actual L3 content/catalog, spawn list, objective policy, wave definitions or difficulty.
- Different Encounter IDs may use the same `definitionId`.
- No global registration, cache or side effects.

Example:

```ts
const reference = createEncounterDefinitionReference({ definitionId: 'forest-wolves' });
// Object.isFrozen(reference) === true
```

**No `EncounterDefinition` content schema in EN02.** Content belongs to L3; this is a reference contract only.

## 7. EN03 — Immutable Encounter State Contract

### Status names — structure only

Proposed public type:

```ts
export type EncounterStatus =
  | 'prepared'
  | 'active'
  | 'resolved'
  | 'closed'
  | 'cancelled';
```

The names reserve the agreed lifecycle vocabulary **without implementing transitions**. The factory **always creates `prepared`**. v0.8.0 must not export a `startEncounter`, `resolveEncounter`, `closeEncounter` or `cancelEncounter` function.

**Important:** `validateEncounterState` is a *structural* validator. Accepting a structurally valid `active`/`resolved`/`closed`/`cancelled` snapshot is **not proof** that the state was reached through an authorized lifecycle transition. L4 owns current authoritative state and v0.8.1+ provides actual transition/evidence contracts. Do not treat a client-submitted status as an authorization to dispatch Combat.

### Proposed state shape

```ts
export interface EncounterState {
  readonly encounterId: string;
  readonly definitionId: string;
  readonly status: EncounterStatus;
  readonly sides: readonly EncounterSide[];
  readonly participants: readonly EncounterParticipant[];
}

export interface EncounterInitialState {
  readonly encounterId: string;
  readonly sides: readonly EncounterSide[];
  readonly participants: readonly EncounterParticipant[];
}
```

`EncounterInitialState` intentionally contains no lifecycle status. `createEncounterState` supplies `prepared` unconditionally. All state fields are required; an explicit empty list is allowed, no ambiguous optional fields.

### Factory

```ts
export function createEncounterState(
  reference: EncounterDefinitionReference,
  initial: EncounterInitialState,
  entities: EntityCollection,
): EncounterState;
```

Invariants:

1. Validate the complete reference/initial record and canonical `EntityCollection` before producing a result.
2. Copy only `definitionId` from reference; do not embed L3 objects.
3. Require `initial.encounterId` valid.
4. Validate side/participant records and their cross-references (see EN04/EN05).
5. All participant `entityId` references must exist in `entities` at creation.
6. Produce `status:'prepared'` deterministically.
7. Return new frozen/detached arrays and nested records; never freeze caller input.
8. Do not capture timestamp, entity HP/Life, World location, RNG/ID provider, spawn receipts or runtime handles.
9. Do not mutate `EntityCollection` or any other input.
10. Support empty `sides:[]`/`participants:[]` as structurally **prepared** state; **readiness to activate is intentionally deferred to EN08**. Participants may not exist without a declared side.

### Validator

```ts
export function validateEncounterState(
  state: EncounterState,
  entities: EntityCollection,
): EncounterState;
```

- Validate exact closed state shape, IDs, allowed status, dense arrays, unique side IDs and participant Entity IDs, membership side links and canonical Entity existence.
- Return a newly captured frozen/detached snapshot; do not return caller object directly.
- All five status strings are structurally valid. **This is not a transition validator** and must not synthesize missing outcome data.
- Validation of a `resolved`/`closed` snapshot does not imply a winner exists and does not authorize rewards.
- Revalidate the referenced EntityCollection on each call; do not rely on a prior cached verdict.
- Do not infer member Life from their `Entity.kind` or infer completion from zero participants.

**Future evolution guard:** Do not append outcome/winner, wave cursor, retry counters, HP, timestamps, revision, combat log or arbitrary metadata fields to `EncounterState` in this milestone. Future lifecycle/outcome companions must be designed in the approved milestone without silently breaking this public five-field contract.

## 8. EN04 — Generic Side & Participant Contracts

### 8.1. Side

```ts
export interface EncounterSide {
  readonly sideId: string;
}

export function createEncounterSide(input: EncounterSide): EncounterSide;
```

- Only structural identity; no hardcoded `players`, `monsters`, `allies`, `enemies`, `teamA`, `teamB` enum.
- No side name, allegiance or PvP relationship inferred from `Entity.kind`.
- No side priority/turn order stored.
- A side may have zero participants in `prepared` state.
- Side IDs must be unique within one Encounter state; independent encounters may reuse the same side IDs.

### 8.2. Participant

```ts
export interface EncounterParticipant {
  readonly entityId: string;
  readonly sideId: string;
}

export function createEncounterParticipant(
  input: EncounterParticipant,
): EncounterParticipant;
```

- The record is a *reference*, not a new Entity or Actor AI state.
- It may be constructed structurally without an `EntityCollection`, but it **does not admit** the actor or prove existence until contained in a validated Encounter snapshot.
- `entityId` is exact canonical Entity.id, `sideId` links to one declared EncounterSide.
- One participant ID can occur **at most once per Encounter**, including across different sides.
- One side may have many Entity IDs.
- The same Entity may appear in **different encounters' structural snapshots**; cross-encounter exclusivity and authoritative membership are L4 responsibilities, not global L2 lookup.
- Do not embed EntitySnapshot/Resource/Life/Stats/Skill/Effect/AI or gameplay actor-kind discrimination.

### 8.3. Illustrative mapping

```text
Encounter: arena-001
Side A: player-001, pet-001
Side B: player-002, summon-002
Side C: monster-001
```

`sideId` is membership grouping only. It does not automatically define a Combat `enemy`/`ally` relationship; L3 supplies a relation policy and L4 applies it to Combat/AI when appropriate in later phases.

### 8.4. No membership transition yet

A fully specified **initial roster** may be provided when constructing a prepared state. But there is no `joinEncounter`, `leaveEncounter`, `switchSide` or automatic participant deletion until EN11–EN15. The factory and structural validator cannot serve as authoritative Join/Leave admission: L4 must never accept an arbitrary forged new array as evidence of a permitted live roster change.

## 9. EN05 — Validation, invariants and fail-closed handling

### 9.1. Closed data schemas

Every new public record must have **exactly** its specified own string-named data properties:

- Reject extra/missing/unknown fields, symbol keys, inherited fields, accessors/getters, arrays used as records and nonplain prototypes.
- Reject invalid type/value combinations; no repair, coercion, auto-ID generation or normalizing whitespace.
- Do not execute caller getter code while validating.
- Validate complete input before publishing a returned result.
- Validate dense proper arrays, no holes or inherited array entries; reject custom enumerable/symbol props and unsafe array shapes, consistent with existing project conventions.
- Never reuse input arrays or records by reference in returned snapshots.

### 9.2. Aggregate invariants

| Invariant | Requirement |
|---|---|
| Unique side identity | No duplicate `sideId` within one Encounter |
| Unique participant identity | No duplicate `entityId` within one Encounter, even on different sides |
| Membership | Every participant `sideId` must match a declared side |
| Entity existence | Every participant `entityId` must resolve via canonical `getEntity`/EntityCollection API |
| Exact matching | Case-sensitive, no normalization for encounter, side, participant, definition IDs |
| Empty state | Empty sides/participants valid as `prepared`, **not** evidence of readiness or winner |
| Entity type | No whitelist by `Entity.kind`; Player/Monster/NPC/Pet/Summon/custom are references |
| Life | Dead Entity may be structurally referenced; **activation eligibility deferred**, no life read required here |
| Ordering | Capture caller's `sides` and `participants` order, do not sort |
| Cross-encounter | No global duplicate/entity-exclusive policy within L2 |

### 9.3. Validation and error model

Structural invalidity → `TypeError`, no partial result, no mutation, no auto-recovery. Do not invent `EncounterAdmissionResult`/`EncounterOutcomeResult` at foundation stage; structured rejection outcomes belong to later admission/transition milestones.

### 9.4. Determinism

Same initial records + equivalent canonical EntityCollection membership produce exactly equivalent semantic snapshots regardless of unrelated global state. No `Date.now()`, `Math.random()`, timers, random IDs, filesystem, environment variables, network, global registry or implicit callback calls.

### 9.5. Immutability

Use full recursive snapshot isolation for the exposed structural graph. Both factories and validator return deeply frozen owned records/arrays. Caller input must remain unchanged and unfrozen. Frozen output cannot be modified to alter subsequent evaluation.

### 9.6. No false authority

Validating `EncounterState` **does not**:

- verify L3 readiness/win policy;
- authorize Combat or Skill execution;
- prove World spawn, actual zone membership, single active encounter per actor or persistence commit;
- prove a claimed `active`/`closed` status was reached legitimately;
- authorize loot, rewards or automatic state cleanup.

Document these limitations next to the API.
