# 1. Objective

Triển khai **Effect Duration & Lifecycle** cho RPG Gameplay L2, bổ sung vòng đời thời gian vào các Effect Instances đã được chấp nhận bởi v0.6.1.

Hệ thống phải hỗ trợ:

1. Timed effects có thời hạn xác định.
2. Persistent effects tồn tại cho tới khi được remove.
3. Bắt đầu lifecycle sau accepted Effect Application.
4. Sử dụng Foundation Execution Clock.
5. Advance simulation time bằng explicit caller action.
6. Expire đúng những effects hết hạn.
7. Remove một Effect Instance theo explicit reason.
8. Trả immutable lifecycle state candidates và events.
9. Deterministic replay, không timer hoặc scheduler.
10. Không tạo Effect Instance store thứ hai.

| ID | Feature | Responsibility |
|---|---|---|
| EF11 | Effect Duration Contracts | Timed/persistent duration, lifecycle timestamps, validation |
| EF12 | Effect Lifecycle Initialization | Foundation Clock, accepted-application binding, immutable lifecycle state |
| EF13 | Effect Expiration | Advance timeline, expiration selection, deterministic ordering |
| EF14 | Effect Removal | Explicit removal, dispel, cleanup reasons, no cascade |
| EF15 | Lifecycle Outcomes & Verification | Immutable events, state consistency, replay, installed package, regressions |

## 2.4. Existing Effect State Remains Canonical

v0.6.1 defines:

```ts

  readonly entityId: string;
  readonly instances: readonly EffectInstanceState[];
}
```

**This remains the canonical collection of Effect Instance identities.**

Do not replace its `instances` with an unrelated collection.

Do not add lifecycle timestamps to `EffectDefinition` or `EffectInstanceState`.

Do not change accepted EF01–EF10 public signatures.

## 2.5. Lifecycle Metadata Is Not a Second Effect Store

Lifecycle metadata may reference existing Effect Instance IDs, but must not contain duplicate Effect Instance objects.

Approved model:

```text
EffectLifecycleState
  ├── effectState
  │     └── canonical Effect Instances
  │
  ├── lifetimes
  │     └── timing metadata by instance ID
  │
  └── observedAtMs
```

Invariants:

- One canonical Effect Instance collection.
- Exactly one lifetime record per included instance.
- No orphaned lifetime records.
- No duplicated lifetime identifiers.
- All instances belong to one Entity.
- Lifecycle transition updates membership and timing records together.
- L4 retains only the current authoritative lifecycle snapshot after commit.

Older immutable snapshots and historical application results may remain available for replay, but are not separate live authorities.

No global active-effect store.

# 5. EF11 — Effect Duration Contracts

## 5.1. Objective

Represent an Effect Instance lifetime without embedding duration into Effect Definition or Instance identity.

## 5.2. Duration Contract

Proposed:

```ts
export type EffectDuration =
  | {
      readonly mode: "timed";
      readonly durationMs: number;
    }
  | {
      readonly mode: "persistent";
    };
```

L3 supplies duration configuration for concrete effects.

Example:

```ts
{
  mode: "timed",
  durationMs: 5000
}
```

or:

```ts
{
  mode: "persistent"
}
```

## 5.3. Timed Duration Rules

`durationMs` must be:

- Number.
- Finite.
- Strictly greater than zero.
- Expressed in milliseconds.
- Fractional milliseconds allowed.
- Caller-supplied.

Reject:

```text
0
negative
NaN
Infinity
-Infinity
numeric string
null
```

Do not impose an arbitrary integer-only requirement.

Do not round duration.

Do not introduce a default duration.

## 5.4. Persistent Duration Rules

Persistent mode contains no duration field.

Valid:

```ts
{
  mode: "persistent"
}
```

Invalid:

```ts
{
  mode: "persistent",
  durationMs: 5000
}
```

Expected TypeError.

Persistent means:

```text
No automatic time-based expiration.
```

It does not mean:

```text
Cannot be explicitly removed.
```

## 5.5. No Instant Effect

Do not support:

```text
mode = instant
durationMs = 0
```

Instant effects remain outside the current MVP scope.

Do not reinterpret zero-duration effects as immediate expiration or one tick.

## 5.6. Lifetime Metadata

Proposed:

```ts
export interface EffectLifetimeState {
  readonly effectInstanceId: string;

  readonly mode: "timed" | "persistent";

  readonly startedAtMs: number;
  readonly expiresAtMs: number | null;
}
```

Meaning:

```text
Timed:
  expiresAtMs > startedAtMs

Persistent:
  expiresAtMs = null
```

No remaining-duration counter stored.

No mutable timer object.

No cached `isExpired` field.

## 5.7. Expiration Arithmetic

For timed effects:

```text
expiresAtMs = startedAtMs + durationMs
```

This is timestamp bookkeeping, not a game numerical balance calculation.

L2 may perform this addition.

Do not call cooldown calculation to compute Effect lifetime.

`calculateCooldownDurationMs()` belongs to cooldown semantics and must not be repurposed for Effect Duration.

If addition produces:

```text
Infinity
NaN
expiresAtMs <= startedAtMs
```

reject malformed/unrepresentable timing.

Do not clamp or silently repair.

## 5.8. No Effect Modifier Snapshot

Lifetime metadata does not contain:

```text
damage
healing
stat modifiers
stacks
restrictions
tickInterval
```

Those belong to later milestones.

# 6. EF12 — Effect Lifecycle Initialization

## 6.1. Objective

Connect accepted Effect Application to its explicit lifetime without creating a second instance store.

## 6.2. Lifecycle State Contract

Proposed:

```ts
export interface EffectLifecycleState {
  readonly effectState: EffectState;

  readonly lifetimes: readonly EffectLifetimeState[];

  readonly observedAtMs: number;
}
```

This is the single lifecycle envelope.

`effectState` contains the canonical Effect Instances.

`lifetimes` contains timing metadata only.

No copied Effect Instance records inside `lifetimes`.

## 6.3. State Invariants

Required:

```text
effectState.instances.length
  === lifetimes.length
```

The two arrays must have exact one-to-one membership and matching order by `effectInstanceId`.

Example:

```text
effectState.instances:
  A
  B

lifetimes:
  A → expiresAt 5000
  B → persistent
```

Reject:

```text
Missing lifetime
Extra lifetime
Duplicate lifetime
Wrong instance identity
Order mismatch
Malformed timestamps
```

No silent rebuilding.

## 6.4. Lifecycle Factory

Proposed:

```ts
export function createEffectLifecycleState(
  state: EffectState,
  context: GameplayExecutionContext
): EffectLifecycleState;
```

Initialization requires an empty Effect State.

Expected:

```ts
{
  effectState: {
    entityId: "monster-1",
    instances: []
  },
  lifetimes: [],
  observedAtMs: 1000
}
```

Why empty?

v0.6.1 Effect State records contain no lifetime metadata.

Assigning arbitrary start times to already-populated states would invent lifecycle history.

Do not silently treat existing structural instances as active timed effects.

Migration/restoration of historical instances requires explicit source data and is outside v0.6.2.

## 6.5. Foundation Clock

Reuse:

```ts
createExecutionContext()
readExecutionTime()
```

Existing type:

```ts
GameplayExecutionContext
```

Time semantics:

- Finite.
- Nonnegative.
- Milliseconds.
- Caller-chosen origin.
- No requirement for Unix epoch.
- No wall-clock dependency.

Use the actual Foundation Clock, not a second clock wrapper.

## 6.6. Start Lifetime API

Proposed:

```ts
export function startEffectLifetime(
  lifecycle: EffectLifecycleState,
  application: EffectApplyResult,
  duration: EffectDuration,
  context: GameplayExecutionContext
): EffectLifecycleStartResult;
```

Preconditions:

1. Complete structural input validation PASS.
2. `application.status === "applied"`.
3. `application.reason === "none"`.
4. Admission result is consistent with applied status.
5. `application.state` contains exactly the previous canonical instances followed by one new instance.
6. Previous instances are unchanged in identity and content.
7. New instance is not already present in lifecycle.
8. Duration is valid.
9. Current execution time equals lifecycle `observedAtMs`.

The full candidate comparison must be by validated values, not by object-reference identity.

An application result remains a caller-supplied assessment/candidate, not an authenticated capability.

## 6.7. Example — Start Timed Effect

Current:

```text
Lifecycle:
  entityId = monster-1
  observedAtMs = 1000
  instances = []
```

Accepted v0.6.1 application:

```text
effect-instance-001
effectId = poison
```

Duration:

```text
timed
durationMs = 5000
```

Expected:

```text
status = started
reason = none

Lifecycle:
  observedAtMs = 1000

Effect Instances:
  effect-instance-001

Lifetime:
  effect-instance-001
  mode = timed
  startedAtMs = 1000
  expiresAtMs = 6000
```

Original lifecycle unchanged.

## 6.8. Example — Start Persistent Effect

Accepted application:

```text
effect-instance-002
effectId = frost-shield
```

Duration:

```text
persistent
```

Expected:

```text
startedAtMs = 1000
expiresAtMs = null
mode = persistent
```

No automatic expiration.

## 6.9. Multiple Applications

Consumer flow:

```text
Create empty EffectLifecycleState
        ↓
applyEffect(A, lifecycle.effectState)
        ↓
startEffectLifetime(A)
        ↓
Commit lifecycle candidate
        ↓
applyEffect(B, currentLifecycle.effectState)
        ↓
startEffectLifetime(B)
```

Expected:

- A retained.
- B appended.
- Original A timestamps unchanged.
- Each instance has one lifetime record.
- No parallel active instance registry.
- No replacement of accepted application rules.

## 6.10. Stale Application Candidate

If the application result was produced from a different Effect State baseline:

```text
rejected / stale_application
state = null
```

No implicit merge.

No overwrite.

No partial membership changes.

L4 must rerun admission/application against the current authoritative state when appropriate.

## 6.11. Invalid Application

If supplied application is a valid rejected result:

```text
rejected / application_rejected
state = null
```

If malformed:

```text
TypeError
```

Never start a lifetime for a rejected Effect Application.

## 6.12. Timeline Admission

For lifecycle mutation at current simulation time:

```text
readExecutionTime(context)
  === lifecycle.observedAtMs
```

If current time is newer, caller must advance the lifecycle first.

Expected valid rejection:

```text
lifecycle_not_advanced
```

If current time regresses, reject:

```text
time_regressed
```

No automatic time advancement inside `startEffectLifetime()`.

This prevents starting effects against an obsolete timeline without silently expiring previous ones.

# 7. EF13 — Effect Expiration

## 7.1. Objective

Advance the Effect timeline and remove expired timed effects deterministically.

## 7.2. Public API

Proposed:

```ts
export function advanceEffectLifecycle(
  lifecycle: EffectLifecycleState,
  context: GameplayExecutionContext
): EffectLifecycleTransitionResult;
```

## 7.3. Time Validation

Read current simulation time from:

```ts
readExecutionTime(context)
```

Require:

```text
nowMs >= lifecycle.observedAtMs
```

If clock regresses:

```text
rejected / time_regressed
state = null
```

Malformed/nonfinite clock output:

```text
TypeError
```

No hidden time correction.

No clock rewind.

## 7.4. Expiration Condition

A timed instance expires when:

```text
expiresAtMs <= nowMs
```

A persistent instance never expires automatically.

No floating-point epsilon adjustment.

No rounding.

No expiration before the exact boundary.

## 7.5. Basic Timeline

Effect:

```text
startedAtMs = 1000
durationMs = 5000
expiresAtMs = 6000
```

At:

```text
nowMs = 5999
```

Expected:

```text
Effect remains.
```

At:

```text
nowMs = 6000
```

Expected:

```text
Effect removed from next lifecycle state.
Expiration event returned.
```

At:

```text
nowMs = 7000
```

Effect must not remain active.

## 7.6. Delayed Advancement

If caller advances directly:

```text
1000 → 8000
```

and effects expired at:

```text
3000
5000
7000
```

Expected:

- All three expire.
- No timers needed.
- No step-by-step interval loop.
- One terminal event per expired instance.
- Next lifecycle state excludes the three instances.

Expiration event `atMs` records the actual expiration deadline, not the delayed observation time.

Next lifecycle `observedAtMs` is `8000`.

## 7.7. Deterministic Expiration Ordering

Sort expiration events by:

```text
1. expiresAtMs ascending
2. effectInstanceId lexical ascending
```

Do not use:

- Input iteration order as an implicit tie-breaker.
- Object property enumeration.
- Random ordering.
- Runtime scheduling order.

The resulting Effect State preserves the relative order of surviving instances.

Do not sort surviving canonical instances.

## 7.8. Persistent Effects

Input:

```text
Effect A:
  timed, expiresAtMs = 6000

Effect B:
  persistent, expiresAtMs = null
```

Advance to `100000`.

Expected:

```text
Effect A expired.
Effect B retained.
```

No arbitrary maximum persistent duration.

## 7.9. Repeated Advancement

After expiration at `6000`:

```text
advance(6000)
```

again.

Expected:

```text
No second expiration event.
No resurrected instance.
No duplicate terminal outcome.
```

A successful same-time advance with no due expiration may return a semantically identical new immutable snapshot and empty events.

## 7.10. No Tick Execution

Expiration must not:

- Calculate DoT damage.
- Calculate HoT healing.
- Generate periodic ticks.
- Modify resource state.
- Update target life.
- Read Combat data.

EF31–EF35 will own periodic tick scheduling/intent.

## 7.11. Future Tick/Expire Ordering — D15

Reserved integration rule:

At an expiration boundary shared with a periodic tick:

```text
1. Resolve due periodic tick intent.
2. Apply caller-approved canonical resource/life outcome.
3. Resolve expiration.
```

v0.6.2 does not implement step 1 or step 2.

`advanceEffectLifecycle()` is the expiration boundary and must be called after due tick processing when periodic support is later introduced.

Do not hardcode a new tick scheduler now.

# 8. EF14 — Effect Removal

## 8.1. Objective

Explicitly remove one Effect Instance from the canonical lifecycle state.

Both timed and persistent effects are removable.

## 8.2. Removal Reason

Proposed:

```ts
export type EffectRemovalReason =
  | "explicit"
  | "dispel"
  | "target_defeated"
  | "source_removed"
  | "session_cleanup";
```

These are caller-supplied reasons, not automatically evaluated game rules.

Examples:

```text
Player dispels Poison:
  dispel

Equipment unequipped:
  source_removed

Target defeat:
  target_defeated

Combat session ends:
  session_cleanup
```

Do not create Item/Equipment/Combat integrations in L2 Effect.

## 8.3. Public API

Proposed:

```ts
export function removeEffectLifetime(
  lifecycle: EffectLifecycleState,
  effectInstanceId: string,
  reason: EffectRemovalReason
): EffectLifecycleTransitionResult;
```

Removal operates at:

```text
lifecycle.observedAtMs
```

No clock read inside removal.

Caller must explicitly advance lifecycle before requesting removal at a later simulation time.

## 8.4. Successful Removal

Current:

```text
Effect A:
  timed

Effect B:
  persistent
```

Remove B:

```text
effectInstanceId = B
reason = explicit
```

Expected:

```text
status = applied

Next Effect Instances:
  A

Next Lifetimes:
  A

Event:
  type = removed
  effectInstanceId = B
  reason = explicit
  atMs = lifecycle.observedAtMs
```

Previous lifecycle unchanged.

## 8.5. Unknown Instance

Input:

```text
effectInstanceId = unknown
```

Expected:

```text
rejected / effect_not_found
state = null
events = []
```

No implicit creation.

No removal from another Entity.

## 8.6. Duplicate Removal

After successfully removing an instance, remove same instance again.

Expected:

```text
rejected / effect_not_found
```

No duplicate terminal event.

No idempotency receipt store.

## 8.7. Expired Instance Removal

If an instance has already expired and been removed by `advanceEffectLifecycle()`:

```text
rejected / effect_not_found
```

Do not emit `removed` after an earlier `expired` terminal event.

## 8.8. No Automatic Source Death Cleanup

D17:

```text
Source dies
```

does not imply:

```text
Remove all effects from source
```

L2 Effect does not inspect source life automatically.

Future L4 policies decide what to do.

## 8.9. Target Defeat Cleanup

L4 may observe canonical Entity defeat and request removal with:

```text
reason = target_defeated
```

Effect performs the requested single-instance removal.

Do not implement automatic cross-module death listeners.

Do not introduce a hidden Entity life observer.

## 8.10. No Group Removal Yet

Do not implement:

```text
removeEffectGroup()
consumeEffectStacks()
removeEffectsBySource()
```

Group removal and consumption are reserved for EF16–EF20.

L4 may explicitly invoke single-instance removals when needed, but v0.6.2 does not promise an atomic group transaction.

No automatic cascades.

## 8.11. No Numerical Rollback

Removal does not:

- Subtract buff modifiers.
- Restore HP.
- Refund resources.
- Reset cooldown.
- Undo Combat.
- Recalculate stats.
- Cancel Skill instances.

Effect has no numerical contributions in v0.6.2.

Later modifier resolution must derive active contributions from the current Effect State rather than maintaining a reversible numerical cache.

# 9. EF15 — Lifecycle Outcomes

## 9.1. Objective

Return structured immutable lifecycle outcomes without introducing event-bus or runtime ownership.

## 9.2. Lifecycle Events

Proposed:

```ts
export type EffectLifecycleEvent =
  | {
      readonly type: "started";
      readonly effectInstanceId: string;
      readonly effectId: string;
      readonly targetEntityId: string;
      readonly atMs: number;
    }
  | {
      readonly type: "expired";
      readonly effectInstanceId: string;
      readonly effectId: string;
      readonly targetEntityId: string;
      readonly atMs: number;
    }
  | {
      readonly type: "removed";
      readonly effectInstanceId: string;
      readonly effectId: string;
      readonly targetEntityId: string;
      readonly atMs: number;
      readonly reason: EffectRemovalReason;
    };
```

`started` means lifetime establishment after an accepted EF09 application.

It does not mean the Effect caused stat/resource/gameplay changes.

These events are returned as values.

They are not automatically published.

## 9.3. Start Result

Proposed:

```ts
export type EffectLifecycleStartResult =
  | {
      readonly status: "started";
      readonly reason: "none";
      readonly state: EffectLifecycleState;
      readonly events: readonly EffectLifecycleEvent[];
    }
  | {
      readonly status: "rejected";
      readonly reason:
        | "application_rejected"
        | "stale_application"
        | "lifecycle_not_advanced"
        | "time_regressed";
      readonly state: null;
      readonly events: readonly [];
    };
```

## 9.4. Transition Result

Proposed:

```ts
export type EffectLifecycleTransitionResult =
  | {
      readonly status: "applied";
      readonly reason: "none";
      readonly state: EffectLifecycleState;
      readonly events: readonly EffectLifecycleEvent[];
    }
  | {
      readonly status: "rejected";
      readonly reason:
        | "effect_not_found"
        | "time_regressed";
      readonly state: null;
      readonly events: readonly [];
    };
```

If an operation produces no expiration, `advanceEffectLifecycle()` still returns:

```text
applied / none
events = []
```

because simulation time has been explicitly observed/advanced.

## 9.5. Result Invariants

Successful operations:

- Contain complete new immutable state.
- Contain detached frozen events.
- Never mutate input state.
- Preserve unaffected instances and lifetimes.

Rejected operations:

```text
state = null
events = []
```

No partial candidate.

No implicit state commit.

## 9.6. Complete Validation Before Rejection

Validate all supplied contracts before ordinary rejection.

Examples:

- Malformed lifecycle plus unknown instance.
- Malformed duration plus rejected application.
- Invalid context plus stale application.
- Malformed removal reason plus missing instance.

Expected:

```text
TypeError
```

Do not mask malformed contracts with ordinary rejection.

## 9.7. Closed Records

Reject:

- Missing fields.
- Unknown fields.
- Symbol keys.
- Accessor fields.
- Inherited required fields.
- Sparse arrays.
- Invalid timestamps.
- Duplicate lifetime IDs.
- Orphaned lifetime records.
- Instance/lifetime ordering mismatch.
- Invalid mode/expiry combinations.
- Invalid event/result shape when supplied as input.

No getter invocation.

No silent normalization.

## 9.8. Immutable Snapshot Isolation

All returned states/events:

- Frozen.
- Detached.
- Readonly at TypeScript level.
- No writable nested aliases.
- No mutation of caller input.
- No mutation of historical snapshots.

Do not freeze caller-owned inputs as a side effect.

## 9.9. Rejection Is Not Exception

Malformed contracts:

```text

```

Valid lifecycle rejection:

```text

reason = exact reason
```

Examples:

```text

```

Do not throw exceptions for normal rejected transitions.

## 9.10. No Automatic Event Publication

Do not call:


from Effect module.

No hidden event bus or subscriber list.

## Final Architecture Rule

```text
            L3 — EFFECT CONTENT
             Duration Configuration
                 Timed/Persistent
                       │
                       ▼
                L4 — APPLICATION
               Current Effect State
              Explicit Clock Context
                       │
                       ▼
                  L2 — EFFECT
             Accepted EF09 Application
                       │
                       ▼
               EffectLifecycleState
                       │
           ┌───────────┴───────────┐
           ▼                       ▼
      Timed Effects          Persistent Effects
           │                       │
           ▼                       ▼
     Expire at Time          Explicit Removal
           │                       │
           └───────────┬───────────┘
                       ▼
             Immutable State + Events
                       │
                       ▼
                 L4 — COMMIT
```

**L1 Core:** Remains sole numerical owner. No new Core capability is required.

**L2 Foundation:** Owns execution clock and time validation.

**L2 Entity:** Owns Entity identity, resources and life state.

**L2 Effect:** Owns lifecycle timing, expiration, explicit removal and immutable candidate transitions.

**L3:** Owns concrete Effect duration configuration.

**L4:** Owns authoritative state, simulation advancement, commit, external death handling and event publication.
