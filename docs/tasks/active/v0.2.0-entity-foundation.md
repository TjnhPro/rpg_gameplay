# 5. EC01 — Entity Identity

## 5.1. Objective

Mỗi actor có một identity được cung cấp rõ ràng.

Entity identity không phụ thuộc:

- Gameplay Module ID.
- Character name.
- Player account ID.
- Monster template ID.
- Scene/GameObject ID.
- Database primary key.
- Rendering instance.
- Runtime-generated counter.

Ví dụ:

```ts
const player = createEntity({
  id: "player-001",
  kind: "player"
});

const monster = createEntity({
  id: "monster-001",
  kind: "monster"
});
```

Cả hai sử dụng cùng Entity contract.

## 5.2. Identity Contract

Yêu cầu:

- `id` là một nonblank string.
- Không tự động tạo ID.
- Không tự trim/normalize ID.
- Không tự thêm prefix/suffix.
- Không dùng random hoặc global counter.
- Không lấy ID từ system clock.
- Không mặc định ID là UUID.
- Không áp đặt module-ID kebab-case lên entity IDs.

ID phải được lưu chính xác như caller cung cấp.

Blank/malformed values phải bị reject.

Nếu caller có ID provider từ GF15, caller chủ động gọi `nextExecutionId()` trước rồi truyền kết quả vào Entity Creation.

Entity module không tự tạo Execution Context.

## 5.3. Identity Semantics

Hai entity snapshots có cùng ID biểu diễn cùng một logical identity theo contract của consumer, nhưng chưa có collection authority để reject duplicate IDs giữa các snapshots độc lập.

**Collection-level uniqueness thuộc EC04 — v0.2.1.**

Không tạo global Entity ID Registry để kiểm tra uniqueness ở v0.2.0.

Không sử dụng identity equality bằng object reference làm thay thế ID equality.

# 6. EC02 — Entity Contract

## 6.1. Objective

Thiết lập một entity data contract tối thiểu, tái sử dụng được.

Đề xuất public contracts định hướng:

```ts
interface EntityDefinition {
  readonly id: string;
  readonly kind: string;
}

interface EntitySnapshot {
  readonly id: string;
  readonly kind: string;
}
```

`EntityDefinition` là đầu vào, `EntitySnapshot` là dữ liệu đầu ra đã được validate/detach.

Agent có thể tránh định nghĩa hai interfaces trùng lặp bằng type alias hoặc một canonical contract nếu điều đó không làm mất ý nghĩa public API.

## 6.2. Entity Kind

`kind` là caller-defined classification.

Ví dụ:

- `player`
- `monster`
- `npc`
- `summon`
- `companion`
- `neutral-actor`

Những giá trị này **không phải built-in enum bắt buộc**.

Requirements:

- Giá trị phải là nonblank string.
- Không tự gán mặc định là `player`.
- Không khóa hệ thống vào một danh sách actor types.
- Không biến `kind` thành game-specific class.
- Không tự suy ra combat eligibility từ `kind`.
- Không tự suy ra HP/MP từ `kind`.

Không thiết kế subclass hierarchy như `PlayerEntity extends CharacterEntity`.

## 6.3. Entity Snapshot Boundary

Snapshot v0.2.0 chỉ mô tả:

1. Entity identity.
2. Actor classification.

Nó **chưa phải gameplay state đầy đủ**.

Không thêm sớm:

- Attributes.
- Stats.
- HP/MP.
- Alive/dead.
- Effects.
- Equipment.
- Position.
- Current skill.
- Target.
- EXP/level.
- AI state.

Những dữ liệu đó thuộc milestone/capability riêng.

Đặc biệt, không tạo một `Record<string, unknown>` state bag có thể chứa mọi dữ liệu mà không có validation và ownership rõ ràng.

EC05/EC06 sau này sẽ bổ sung state semantics theo approved contracts.

## 6.4. Contract Stability

- Entity snapshots là immutable data.
- Không chứa callbacks/functions.
- Không có database model coupling.
- Không có render engine references.
- Không chứa Runtime hoặc Messaging Context.
- Không giữ global Entity state.
- Không phụ thuộc concrete Player/Monster implementations.

Dữ liệu đầu vào không được bị mutate/freeze ngoài ý muốn.

Unknown gameplay fields không được âm thầm trở thành state được chấp nhận. Agent phải chọn và tài liệu hóa validation behavior rõ ràng; ưu tiên closed foundation input shape trong v0.2.0.

Không mở rộng arbitrary metadata schema nếu chưa có use case được duyệt.

# 7. EC03 — Entity Creation & Validation

## 7.1. Required Public Function

Cung cấp public function tương đương:

```ts
createEntity(definition)
```

Ví dụ:

```ts
const actor = createEntity({
  id: "actor-100",
  kind: "player"
});
```

Expected:

```ts
{
  id: "actor-100",
  kind: "player"
}
```

Output phải là immutable Entity Snapshot.

Không bắt buộc public validator function riêng nếu `createEntity()` đã là canonical validation boundary.

Nếu cần dùng chung validation nội bộ, chỉ có **một** canonical implementation.

## 7.2. Validation

Reject tối thiểu:

- `null`.
- `undefined`.
- Arrays.
- Non-object input.
- Missing ID.
- Missing kind.
- Blank ID.
- Blank kind.
- Non-string ID.
- Non-string kind.
- Malformed foundation definition.

Invalid input phải tạo một failure rõ ràng, nhất quán với Foundation TypeError conventions.

Không silently convert number IDs thành strings.

Không tự sửa malformed input rồi báo success.

## 7.3. Creation Semantics

`createEntity()` phải:

1. Validate input.
2. Tạo một snapshot có dữ liệu đúng contract.
3. Bảo toàn exact ID/kind values.
4. Không mutate input.
5. Không phụ thuộc global state.
6. Không đọc Clock/RNG ngầm.
7. Không register entity vào collection.
8. Không phát event.
9. Không gọi lifecycle hooks.
10. Không thực hiện Kernel numerical calculations.

Creation phải deterministic với cùng input hợp lệ.

## 7.4. Immutability

Chứng minh:

- Caller sửa input sau khi tạo entity không làm đổi snapshot.
- Caller không thể mutate snapshot.
- Hai snapshots độc lập không chia sẻ mutable Entity state.
- Không expose internal writable records.

Nếu snapshot chỉ có scalar fields, không tạo deep cloning framework không cần thiết.

Không sử dụng một global Entity Store chỉ để quản lý snapshots.

## 7.5. Creation Failure Atomicity

Invalid input không được:

- Đăng ký partial entity.
- Tăng global ID counter.
- Phát sự kiện.
- Sửa Runtime Context.
- Tạo Entity Collection.
- Để lại hidden state.

Creation failure không tạo một partial successful entity.

# 8. Integration With Gameplay Foundation

## 8.1. Entity as a Real Gameplay Module

Lần đầu tiên bổ sung gameplay module implementation tại:

`src/modules/entity/`

`src/modules/entity/index.ts`

- `src/modules/player/`
- `src/modules/monster/`

chỉ để đại diện cho các actor types.

## 8.2. Static Architecture Registry

Cập nhật `harness/modules.json` theo schema hiện có.

Thêm đúng một entry:

```json
{
  "id": "entity",
  "optional": true,
  "dependencies": []
}
```

Giữ `schemaVersion: 1` và các fields metadata hiện có.

Đây là static module ownership declaration.

Không thêm Entity Foundation functions vào `src/foundation/modules/` chỉ vì chúng dùng module contracts.

Không thay đổi boundary checker nếu registry hiện tại đã hỗ trợ module mới.

## 8.3. Module Registration

Module `entity` phải có thể được consumer khai báo thông qua accepted GF01 contract:

```ts
const registry = registerModule(
  createModuleRegistry(),
  {
    id: "entity",
    optional: true,
    dependencies: []
  }
);

const configuration = configureModules(registry, {
  enable: ["entity"]
});

const composition = composeModules(registry, configuration);
```

Expected:

- `entity` được lựa chọn.
- Composition chứa Entity module.
- Không phát sinh dependency giả.
- Không khởi chạy engine.
- Không tự tạo Player hoặc Monster.

**Gameplay module ID `entity` khác với actor ID như `player-001`.**

Không yêu cầu Foundation tự discovery entity module.

Không thay đổi GF01–GF05 registration semantics.

## 8.4. Foundation Integration Boundary

Entity module được phép sử dụng các public Foundation contracts khi cần.

Nhưng EC01–EC03 không cần tạo:

- Runtime lifecycle bindings riêng.
- Command handlers.
- Event subscribers.
- Execution context.
- Entity store.
- World/session context.

Một installed consumer scenario có thể kết hợp Entity Creation với GF01–GF05 module composition để chứng minh module được tích hợp đúng.

Không tạo integration code không có functional behavior cần thiết.
