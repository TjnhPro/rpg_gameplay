Triển khai **Effect Stacking & Refresh** dựa trên canonical Effect Application và Lifecycle đã được phê duyệt ở v0.6.0–v0.6.2.

# 5. EF16 — Effect Stack Identity & Grouping

## 5.1. Objective

Derive stack groups from current canonical EffectLifecycleState without storing duplicate collections.

## 5.2. Group Identity

Approved D06:

```text
targetEntityId
+ effectId
+ sourceKey
```

Proposed:

```ts
export interface EffectStackGroupKey {
  readonly targetEntityId: string;
  readonly effectId: string;
  readonly sourceKey: string;
}
```

All identifiers are opaque exact strings.

Do not normalize:

```text
Poison
poison
```

or:

```text
Source-A
source-a
```

These remain distinct identities.

## 5.3. Grouping Examples

### Same Effect, Same SourceKey, Same Target

```text
Target:
  monster-1

Effect:
  poison

SourceKey:
  player-1/poison-weapon

Instances:
  poison-001
  poison-002
  poison-003
```

Expected:

```text
One group.
Three stacks.
```

### Same Effect, Different SourceKey

```text
player-1/poison-weapon
player-2/poison-skill
```

Expected:

```text
Two independent groups.
```

### Same SourceKey, Different Effect

```text
poison
burning
```

Expected:

```text
Two independent groups.
```

### Same Effect/SourceKey, Different Target

```text
monster-1
monster-2
```

Expected:

```text
Two independent groups.
```

## 5.4. Source Identity Consistency

D06 defines grouping by sourceKey, but a sourceKey must not silently merge distinct source identities.

For existing group:

```text
source.kind = entity
source.sourceId = player-1
source.sourceKey = poison-source-001
```

Incoming:

```text
source.kind = entity
source.sourceId = player-2
source.sourceKey = poison-source-001
```

Expected:

```text
rejected / source_identity_conflict
```

Likewise for `entity` versus `system`.

No implicit source rebinding.

For malformed existing lifecycle data containing conflicting origins within the same group, structural/group validation fails with TypeError.

L4 is responsible for allocating globally meaningful sourceKeys.

Do not create a source registry.

## 5.5. Group View

Proposed:

```ts
export interface EffectStackGroupView {
  readonly key: EffectStackGroupKey;
  readonly source: EffectSourceReference;
  readonly instanceIds: readonly string[];
  readonly stackCount: number;
}
```

`stackCount` is derived from `instanceIds.length`.

No stored count.

No `currentStacks` field inside EffectInstanceState.

## 5.6. Public Inspector

```ts
export function inspectEffectStackGroups(
  lifecycle: EffectLifecycleState
): readonly EffectStackGroupView[];
```

Required:

- Validate lifecycle snapshot.
- Group by exact D06 key.
- Verify same-group source identity consistency.
- Preserve instance order within each group.
- Preserve first-appearance order across groups.
- Return deeply frozen detached views.
- Do not mutate lifecycle.
- Do not calculate modifiers.
- Do not advance time.

Do not include `maxStacks` in the group view: it is L3 policy, not stored Effect state.

## 5.7. Empty State

Input:

```text
instances = []
```

Expected:

```text
groups = []
```

Frozen array.

## 5.8. No Global Stack Registry

Do not create:

```text
Map<GroupKey, ActiveStackGroup>
StackStore
StackRegistry
StackCache
```

Local temporary lookup structures inside a pure function are allowed.

Do not retain them between calls.

# 6. EF17 — Stack Admission & Addition

## 6.1. Objective

Apply explicit L3 stack policy to an already accepted Effect application without bypassing EF06–EF10.

## 6.2. Stack Policy

Proposed:

```ts
export type EffectStackPolicy =
  | {
      readonly mode: "refresh";
      readonly maxStacks: 1;
    }
  | {
      readonly mode: "stack";
      readonly maxStacks: number;
    };
```

Validation:

- `refresh`: maxStacks must equal exactly `1`.
- `stack`: maxStacks must be positive safe integer.
- No missing fields.
- No unknown fields.
- No implicit defaults.
- No `replace` or `extend` mode.
- No `overflowPolicy` extension.

The combination `stack` with `maxStacks:1` is valid but differs from `refresh`:

```text
stack/1:
  second apply rejected at capacity

refresh/1:
  second apply renews existing timed instance
```

## 6.3. Policy Ownership

L3 selects:

```text
mode
maxStacks
```

L4 supplies the selected policy to L2.

Effect does not infer policy from:

```text
effectId
sourceKey
Skill ID
Equipment ID
```

No hardcoded Poison/Burning/Buff behavior.

L4 must keep a group's policy consistent during its lifecycle.

Since v0.6.3 does not store a policy catalog, a historical policy change cannot always be inferred from existing instances. Do not fabricate a guarantee that arbitrary L3 policy changes are detected.

## 6.4. Stack Admission Input

Reuse actual accepted:

```ts
EffectApplyResult
EffectLifecycleState
EffectDuration
GameplayExecutionContext
```

Proposed assessment API:

```ts
export function evaluateEffectStackAdmission(
  lifecycle: EffectLifecycleState,
  application: EffectApplyResult,
  duration: EffectDuration,
  policy: EffectStackPolicy,
  context: GameplayExecutionContext
): EffectStackAdmissionResult;
```

## 6.5. Admission Prerequisites

Required:

1. Complete structural input validation.
2. Application was accepted by EF09.
3. Application candidate matches current canonical Effect State plus exactly one incoming instance.
4. Current lifecycle is aligned with execution time.
5. No pending expiration at or before current observed time.
6. Incoming source/group identity is consistent.
7. Policy and duration are valid.
8. Group mode/capacity conditions permit the operation.

The EF09 application result is not an authenticated authorization token.

No bypass of existing Effect admission.

## 6.6. Admission Outcomes

Proposed:

```ts
export type EffectStackAdmissionResult =
  | {
      readonly status: "admitted";
      readonly reason: "none";
      readonly operation: "add" | "refresh";
      readonly group: EffectStackGroupKey;
    }
  | {
      readonly status: "rejected";
      readonly reason: EffectStackRejectionReason;
      readonly operation: null;
      readonly group: EffectStackGroupKey;
    };
```

Only actual implementation outcomes are returned.

No candidate state from assessment.

## 6.7. Stack Mode — Below Maximum

Current:

```text
Poison group:
  stacks = 2
  maxStacks = 5
```

New valid application:

```text
effect-instance-003
```

Expected:

```text
admitted
operation = add
```

After execution:

```text
stacks = 3
```

Use canonical v0.6.2 `startEffectLifetime()` behavior.

Do not create a separate lifetime addition engine.

## 6.8. Empty Group

With no matching group:

```text
stacks = 0
```

Both `stack` and `refresh` policies permit the first application.

Operation:

```text
add
```

The first instance is created with its supplied duration.

## 6.9. Refresh Mode — Existing Group

When group has exactly one instance:

```text
mode = refresh
maxStacks = 1
```

Incoming EF09 application may contain a new attempt instance ID.

Expected:

```text
operation = refresh
```

The new attempt does **not** become an additional stored instance.

The existing canonical instance remains the group anchor.

No new stack is created.

## 6.10. Existing Group With Multiple Instances

If `refresh` policy is supplied to a group already containing multiple instances:

```text
rejected / group_policy_conflict
```

Do not silently remove existing stacks to satisfy the new policy.

No migration of historical stack policy in this milestone.

## 6.11. Pending Expiration

If lifecycle contains effects whose deadline is already due at the observed time, the caller must first resolve the lifecycle boundary using the approved advance operation.

Expected:

```text
rejected / pending_expiry
```

Do not silently expire effects inside stack admission or stack mutation.

This preserves D15's future tick-before-expire ordering.

## 6.12. No Admission Bypass

Incorrect:

```text
New Effect Instance
  → append directly into EffectState
  → increment stack
```

Required:

```text
EF09 Apply
  → EF17 Stack Admission
  → EF12 Lifecycle Addition
  → Immutable Candidate
```

For refresh, EF17 validates EF09's accepted candidate but preserves the original instance rather than appending the incoming one.

# 7. EF18 — Effect Refresh

## 7.1. Objective

Renew an existing Effect's duration without creating a new Effect Instance or changing its payload.

## 7.2. Refresh Identity Rule

Existing:

```text
effectInstanceId:
  poison-001

effectId:
  poison

sourceKey:
  player-1/poison-skill
```

After refresh:

```text
effectInstanceId:
  poison-001
```

Must remain unchanged.

Do not replace with the incoming attempt's instance ID.

## 7.3. Timed Refresh Semantics

Current:

```text
startedAtMs = 1000
expiresAtMs = 6000
```

Refresh at:

```text
nowMs = 4000
durationMs = 5000
```

Expected:

```text
startedAtMs = 1000
expiresAtMs = 9000
```

Use:

```text
newExpiresAtMs =
  max(existingExpiresAtMs, nowMs + durationMs)
```

This is timestamp bookkeeping, not Core numerical gameplay calculation.

**Refresh cannot shorten an existing timed lifetime.**

Do not alter:

- Original `startedAtMs`.
- Effect Instance ID.
- Effect Definition ID.
- Source identity.
- Target association.
- Other stack lifetimes.

## 7.4. Shorter Renewal

Current:

```text
expiresAtMs = 9000
```

Refresh at `4000` with duration `1000`.

Candidate deadline:

```text
5000
```

Expected final:

```text
expiresAtMs = 9000
```

The operation may be accepted as a refresh without shortening the lifetime.

Do not return a newly created stack.

## 7.5. Timestamp Overflow

If:

```text
nowMs + durationMs
```

is nonfinite or cannot represent a strictly later expiry:

```text
TypeError
```

No clamping.

No fallback to Infinity.

No hidden rounding.

## 7.6. Snapshot Preservation — D09

Refresh must preserve the original Effect Instance value.

Future modifier snapshots are likewise retained.

Do not replace:

```text
source
effectId
targetEntityId
effectInstanceId
```

with incoming values.

At v0.6.3, there are no numerical modifier payloads to refresh.

Tests must prove identity/payload preservation now; later v0.6.4 will verify modifier snapshot preservation.

## 7.7. Explicit Single-Stack Refresh

Proposed:

```ts
export function refreshEffectStackLifetime(
  lifecycle: EffectLifecycleState,
  effectInstanceId: string,
  duration: EffectDuration,
  context: GameplayExecutionContext
): EffectStackMutationResult;
```

Required:

- Exactly one existing instance selected.
- Timed duration.
- Existing lifetime must be timed.
- Current time aligned with lifecycle.
- No pending expiry.
- Preserve other stacks.
- Immutable state candidate.

This allows a caller to refresh one selected stack in a multi-stack group while preserving D08 independent expiration.

## 7.8. Independent Stack Durations

Current:

```text
Poison group:

Stack A:
  expiresAt = 5000

Stack B:
  expiresAt = 7000

Stack C:
  expiresAt = 9000
```

Refresh B at `4000` with duration `6000`.

Expected:

```text
A expiresAt = 5000
B expiresAt = 10000
C expiresAt = 9000
```

No shared expiration timestamp.

No group-wide automatic renewal.

## 7.9. Persistent Effect Refresh

Persistent effects have:

```text
expiresAtMs = null
```

They do not have a timed deadline to renew.

An explicit refresh attempt on a persistent lifetime returns:

```text
rejected / not_timed
```

For an incoming application under `refresh` policy when an existing persistent instance is already present:

```text
rejected / persistent_already_present
```

The persistent instance remains unchanged.

Do not emit a misleading refreshed event for a no-op persistent duration.

For an empty group, the first persistent application is valid.

For `stack` mode, persistent instances may be stacked up to the configured limit.

## 7.10. Duration Mode Conflict

An existing timed anchor cannot be silently converted to persistent by a refresh request.

Likewise, an existing persistent anchor cannot be converted to timed.

Expected:

```text
rejected / duration_mode_conflict
```

when attempting incompatible automatic group refresh.

Changes of duration mode require an explicit removal and new approved application.

Do not silently migrate existing lifecycle data.

# 8. EF19 — Stack Overflow & Rejection

## 8.1. Objective

Enforce maximum stack capacity with deterministic rejection and no partial state.

## 8.2. Default Overflow Rule — D10

For:

```text
mode = stack
maxStacks = 5
```

If:

```text
currentStacks = 5
```

Then incoming application:

```text
rejected / max_stacks_reached
```

No:

- Automatic replacement.
- Oldest-stack removal.
- Newest-stack removal.
- Overflow refresh.
- Partial append.
- Alternate stack group.

## 8.3. No Overflow Policy Engine

Do not introduce:

```text
replace_oldest
replace_weakest
extend_all
merge_damage
increase_max_stacks
```

These are outside the approved MVP.

## 8.4. Rejection Reasons

Proposed:

```ts
export type EffectStackRejectionReason =
  | "application_rejected"
  | "stale_application"
  | "lifecycle_not_advanced"
  | "time_regressed"
  | "pending_expiry"
  | "source_identity_conflict"
  | "group_policy_conflict"
  | "max_stacks_reached"
  | "duration_mode_conflict"
  | "persistent_already_present"
  | "effect_not_found"
  | "not_timed"
  | "group_not_found"
  | "insufficient_stacks";
```

Malformed contracts throw TypeError; they are not ordinary gameplay rejections.

## 8.5. Stable Priority

**First:** validate all supplied contracts.

For application-based stacking, apply priority:

```text
1. application_rejected
2. stale_application
3. time_regressed
4. lifecycle_not_advanced
5. pending_expiry
6. source_identity_conflict
7. group_policy_conflict
8. duration_mode_conflict
9. persistent_already_present
10. max_stacks_reached
11. admitted
```

For explicit refresh/consume/remove, evaluate only relevant branches while preserving full structural validation first.

Do not use JavaScript field enumeration or incidental loop order to choose a reason.

## 8.6. Candidate Rejection Invariant

All rejected stack operations:

```text
state = null
events = []
```

No mutation.

No implicit retry.

No implicit fallback to refresh.

## 8.7. Group Policy Consistency

L3 owns group policy.

If caller changes policy during a live group, L4 is responsible for compatibility and migration decisions.

L2 must reject detectable conflicts, e.g. refresh policy applied to a group with multiple existing stacks.

Do not introduce persistent policy registry solely to detect every historical L3 policy change.

Record this explicitly as a lifecycle boundary.

# 9. EF20 — Stack Consumption & Group Removal

## 9.1. Objective

Support exact-N stack consumption and full-group removal using canonical immutable EffectLifecycleState transitions.

No extra stack store.

## 9.2. Stack Consumption Request

Proposed:

```ts
export interface EffectStackConsumeRequest {
  readonly group: EffectStackGroupKey;
  readonly count: number;
}
```

Rules:

- `count` must be a positive safe integer.
- Group identity must be exact.
- No implicit default count.
- No partial consumption.
- Caller explicitly selects the group.

## 9.3. Deterministic Stack Selection

When consuming N stacks, select instances in the following order:

```text
1. Earliest expiresAtMs
2. Then lexical effectInstanceId
3. Persistent instances after timed instances
```

Persistent lifetime is treated as having no expiration deadline, not converted into a numeric `Infinity` field.

Example:

```text
Stack A expires at 7000
Stack B expires at 5000
Stack C persistent
Stack D expires at 5000
```

Consume 2:

```text
B
D
```

Assuming lexical `B < D`.

The resulting canonical Effect State preserves the relative order of surviving instances.

Do not reorder survivors.

## 9.4. Public Consumption API

Proposed:

```ts
export function consumeEffectStacks(
  lifecycle: EffectLifecycleState,
  request: EffectStackConsumeRequest
): EffectStackMutationResult;
```

Consumption takes place at:

```text
lifecycle.observedAtMs
```

No extra clock read.

Caller must advance lifecycle first if the intended operation occurs at a later time.

## 9.5. Successful Consumption

Current:

```text
Poison group:
  A
  B
  C

count = 3
```

Request:

```text
consume 2
```

Expected:

```text
status = applied
action = consumed

consumed IDs = [selected two IDs]
remainingStacks = 1
```

Candidate state:

- Removes selected Effect Instance records.
- Removes corresponding lifetime records.
- Retains C.
- Preserves unrelated groups.
- Original lifecycle unchanged.

## 9.6. Insufficient Stacks

Current:

```text
stacks = 2
```

Request:

```text
consume 3
```

Expected:

