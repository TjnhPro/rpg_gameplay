# 1. Objective

Triển khai **Periodic Effects** cho Effect System, cho phép Effect tạo các periodic tick intents theo thời gian, phục vụ:

- Damage-over-Time (DoT).
- Heal-over-Time (HoT).
- Các periodic resource effects được Core/Entity hỗ trợ.

Periodic Effects phải sử dụng canonical Effect Lifecycle từ v0.6.2, Stacking từ v0.6.3, Modifier snapshots từ v0.6.4 và Restrictions từ v0.6.5.

Sau milestone này:

1. Effect có thể cấu hình periodic interval.
2. First tick được xác định từ thời điểm Effect bắt đầu.
3. Mỗi Effect Instance sở hữu periodic cursor độc lập.
4. Caller có thể advance simulation qua nhiều tick.
5. Tick intents được trả theo thứ tự deterministic.
6. Tick tại expiration boundary được xử lý trước khi expire.
7. L4 sử dụng canonical Entity Resource transitions để thực hiện DoT/HoT.
8. L4 sử dụng canonical Entity Life resolution khi damage dẫn tới defeat.
9. Effect có thể xử lý stack/refresh/expire/remove mà không nhân đôi periodic engine.
10. Không tự triển khai numerical Damage/Healing Calculator.
11. Không tạo Timer/Scheduler hoặc background gameplay loop.
12. Deterministic replay và installed package verification PASS.

| ID | Feature | Responsibility |
|---|---|---|
| EF31 | Periodic Effect Contracts | Periodic configuration, DoT/HoT classification, immutable cursor |
| EF32 | Periodic Timeline & Tick Planning | First tick, due selection, catch-up, ordering |
| EF33 | DoT Resolution Integration | Canonical resource decrease, optional supported Core damage resolution |
| EF34 | HoT Resolution Integration | Canonical resource increase and life boundary |
| EF35 | Tick Completion & Outcomes | Exactly-once cursor progression per committed L4 tick, death/expiry ordering, replay, verification |

# 6. EF31 — Periodic Effect Contracts

## 6.1. Objective

Introduce periodic configuration without modifying existing Effect Definition, Instance, Lifecycle or Stack contracts.

## 6.2. Proposed Capture Contract

```ts
export type EffectPeriodicCapture =
  | {
      readonly mode: "none";
    }
  | {
      readonly mode: "periodic";

      readonly kind: "dot" | "hot";

      readonly intervalMs: number;

      readonly resourceId: string;
    };
```

`none` explicitly identifies an Effect without periodic behavior.

Every newly active Effect Instance must have a periodic companion entry, including nonperiodic effects.

This prevents missing captures from becoming silent defaults.

## 6.3. DoT Semantics

```text
kind = dot
```

Means:

```text
Periodic resource decrease intent.
```

L3 defines which Entity resource represents health.

Effect must not hardcode:

```text
hp
health
life
```

as required resource IDs.

## 6.4. HoT Semantics

```text
kind = hot
```

Means:

```text
Periodic resource increase intent.
```

No automatic revival.

No implicit bypass of minimum-resource restrictions.

No custom healing formula.

## 6.5. Interval Validation

`intervalMs` must be:

- Number.
- Finite.
- Strictly greater than zero.
- Milliseconds.
- Representable as a strictly advancing timestamp.
- Caller-supplied.

Fractional milliseconds are allowed.

Reject:

```text
0
negative
NaN
Infinity
-Infinity
numeric strings
null
```

No silent rounding.

No implicit tick frequency.

## 6.6. First Tick — D15

For a periodic Effect starting at:

```text
startedAtMs = 1000
```

with:

```text
intervalMs = 1000
```

First tick:

```text
2000
```

No tick at application time.

No hidden immediate-tick policy.

## 6.7. Periodic Entry

Proposed:

```ts
export type EffectPeriodicEntry =
  | {
      readonly effectInstanceId: string;
      readonly mode: "none";
    }
  | {
      readonly effectInstanceId: string;

      readonly mode: "periodic";

      readonly kind: "dot" | "hot";

      readonly intervalMs: number;

      readonly resourceId: string;

      readonly nextTickAtMs: number;
    };
```

Each active Effect Instance has one periodic entry.

No duplicated Effect Instance payload.

`nextTickAtMs` is the next scheduled tick candidate.

For a timed Effect, it may be later than the current expiry. Such a tick is **not due** unless a permitted refresh extends the lifetime.

Do not clamp it to the old expiry or restart its cadence on refresh.

## 6.8. Periodic State

Proposed:

```ts
export interface EffectPeriodicState {
  readonly entityId: string;

  readonly observedAtMs: number;

  readonly entries: readonly EffectPeriodicEntry[];
}
```

This is a companion progress state, not another lifecycle authority.

It must be paired with the actual canonical `EffectLifecycleState`.

## 6.9. State Invariants

For current lifecycle:

```text
Each Effect Instance:
  exactly one Periodic Entry

Each Periodic Entry:
  refers to one current Effect Instance
```

Required:

- Exact Entity identity.
- Matching observedAtMs.
- Same instance ordering.
- No duplicate IDs.
- No orphan entries.
- No missing entries.
- Valid interval.
- Valid next scheduled timestamp.
- No invented numerical amount.
- No duplicated lifetime metadata.

## 6.10. Initialization

Proposed:

```ts
export function createEffectPeriodicState(
  lifecycle: EffectLifecycleState
): EffectPeriodicState;
```

Only an empty lifecycle can initialize an empty periodic companion.

Expected:

```text
entityId = monster-1
observedAtMs = 1000
entries = []
```

No fabrication of periodic history for already-active effects.

# 7. EF32 — Periodic Timeline & Tick Planning

## 7.1. Objective

Plan due periodic ticks deterministically, independently of runtime scheduling.

## 7.2. Time Authority

Reuse:

```ts
readExecutionTime()
```

through existing Foundation Execution Context.

The caller owns the clock.

No:

```text
Date.now()
performance.now()
setTimeout()
setInterval()
```

No background worker.

No periodic scheduler process.

## 7.3. Tick Eligibility Window

For a timed Effect:

```text
startedAtMs < tickAtMs <= expiresAtMs
```

For a persistent Effect:

```text
tickAtMs > startedAtMs
```

A tick is due only if:

```text
tickAtMs <= requested simulation time
```

No tick is due after expiration.

## 7.4. Expiration Boundary — D15

Example:

```text
Started = 1000
Interval = 1000
Expires = 6000
```

Expected order:

```text
Tick 2000
Tick 3000
Tick 4000
Tick 5000
Tick 6000
Expire 6000
```

Not:

```text
Expire 6000
Skip Tick 6000
```

Existing EF13 expiration must remain canonical.

Do not build a second expiration mechanism.

## 7.5. Catch-Up

If the simulation advances directly:

```text
1000 → 6000
```

All due ticks must be processed in the canonical order before expiration.

Do not skip ticks because the caller advanced through a large interval.

Do not multiply:

```text
amount × missedTickCount
```

inside Effect.

Each tick is independently resolved through its own resource transition.

This matters because HP caps, life state and other effects can change between ticks.

## 7.6. One Tick at a Time

Use incremental planning rather than allocating an unbounded list of all due ticks.

Proposed:

```ts
export interface EffectPeriodicTickIntent {
  readonly effectInstanceId: string;

  readonly effectId: string;

  readonly targetEntityId: string;

  readonly kind: "dot" | "hot";

  readonly resourceId: string;

  readonly dueAtMs: number;
}
```

Proposed API:

```ts
export function getNextDueEffectTick(
  lifecycle: EffectLifecycleState,
  periodic: EffectPeriodicState,
  targetLife: EntityLifeState,
  context: GameplayExecutionContext
): EffectPeriodicTickAssessment;
```

Return at most one due tick.

This supports large simulation jumps without materializing an unlimited tick array.

## 7.7. Deterministic Global Ordering

When multiple instances have due ticks:

```text
1. Earliest dueAtMs
2. Lexical effectInstanceId
```

No priority based on:

```text
Buff/Debuff classification
Source kind
Effect ID
Application order
Stack strength
```

Unless an explicit future contract is approved.

## 7.8. Same-Time Example

```text
Poison A:
  dueAt = 3000

Poison B:
  dueAt = 3000

Regeneration C:
  dueAt = 3000
```

If IDs are:

```text
A
B
C
```

Expected tick order:

```text
A
B
C
```

This matters if A or B causes target defeat.

## 7.9. Time Regression

If caller time is earlier than lifecycle observedAtMs:

```text
rejected / time_regressed
```

No tick candidate.

No state mutation.

## 7.10. No Due Tick

If no tick is due:

```text
status = idle
intent = null
```

This is not a failure.

The caller may proceed to canonical lifecycle advancement after confirming that all relevant due ticks have been resolved.

## 7.11. No Automatic Execution

Planning does not:

- Change HP.
- Heal Entity.
- Consume Resource.
- Update Life.
- Modify Effect duration.
- Remove Effect.
- Advance periodic cursor.
- Publish gameplay events.

It only returns an immutable tick intent.

# 8. EF33 — DoT Resolution Integration

## 8.1. Objective

Support Damage-over-Time using existing canonical Resource/Life mechanics.

## 8.2. Required L4 Flow

```text
Effect Tick Intent
       │
       ▼
kind = dot
       │
       ▼
L4 resolves Damage Amount
       │
       ▼
Canonical Entity Resource Decrease
       │
       ▼
Canonical Entity Life Resolution
       │
       ▼
L4 commits outcomes and periodic progress
```

## 8.3. Supported MVP Amount

The caller supplies:

```text
resolvedAmount
```

Requirements:

- Finite.
- Nonnegative.
- Explicit.
- Already resolved by L3 configuration or supported Core calculations.
- No string coercion.
- No silent rounding.

Zero amount is valid.

Effect must not reinterpret zero amount as a missing tick.

## 8.4. Canonical Damage Application

L4 consumer uses:

```ts
transitionEntityResource(
  resourceState,
  resourceId,
  {
    maximum,
    amount: resolvedAmount,
    operation: "decrease",
    rule: {
      minimum,
      currentAboveMaximum,
      allowIncreaseFromMinimum: false
    }
  }
);
```

The values `resourceId`, `minimum`, `maximum` and current-above-maximum policy come from L3/L4 authoritative configuration.

Do not hardcode HP maximum or minimum.

No direct manipulation of EntityResourceState.

## 8.5. Correct Applied Damage

Core's `ResourceTransitionResult` includes:

```text
before
after
applied
reachedMinimum
```

Use canonical `transition.applied` for actual applied magnitude.

Do not universally reconstruct damage using:

```text
before - after
```

because Core has specific above-maximum resource semantics.

No duplicate damage cap logic.

## 8.6. Entity Defeat

For DoT affecting the configured life resource, after applying the resource transition, L4 calls:

```ts
resolveEntityDefeat()
```

using the updated Entity Resource State.

Expected:

```text
HP reaches minimum
       ↓
Entity Life becomes dead
       ↓
Future periodic ticks stop
       ↓
L4 performs approved Effect cleanup
```

Effect does not implement another death resolver.

Do not assume every resource decrease causes Entity defeat.

## 8.7. No Attack Resolution

DoT does not automatically perform:

```text
Hit
Dodge
Critical
Attack targeting
Combat attack execution
```

Do not call `resolveCombatAttack()` as a workaround merely to obtain damage.

If L3 requires supported mitigation calculations, L4 may use the correct existing Core Kernel APIs.

If the desired periodic damage formula is unsupported, defer that variant.

## 8.8. Source Death

If the Effect source dies, an already-applied DoT may continue.

D17 remains in force.

Do not revalidate source Life on every tick.

Do not automatically delete the Effect.

Example:

```text

HoT amount = 10
```

Expected:


```text
HP = 100
Maximum = 100
HoT amount = 10
```


No automatic resurrection through HoT.

```text
DoTEngine
HoTEngine
```

# 10. EF35 — Tick Completion & Outcomes

## 10.1. Objective

Advance periodic cursor only after L4 has successfully performed the intended canonical gameplay operation.

## 10.2. Two-Step Boundary

Required:

```text
Step 1:
  Plan next due tick.

Step 2:
  L4 executes canonical Entity operation.

Step 3:
  Produce next periodic cursor candidate.

Step 4:
  L4 atomically commits authoritative Entity/Effect state.
```

Do not consume the tick before its resource operation succeeds.

## 10.3. Completion API

Proposed:

```ts
export function completeEffectPeriodicTick(
  lifecycle: EffectLifecycleState,
  periodic: EffectPeriodicState,
  intent: EffectPeriodicTickIntent,
  targetLife: EntityLifeState,
  context: GameplayExecutionContext
): EffectPeriodicCompletionResult;
```

Requirements:

- Validate complete inputs.
- Verify intent matches next due tick.
- Verify instance remains active.
- Verify target Entity identity.
- Verify target is alive.
- Verify tick is due within current horizon.
- Reject stale/duplicate tick intent.
- Advance only the selected instance cursor.
- Preserve unrelated cursors.
- Return immutable candidate.

**This API does not prove that Entity damage/healing was applied.**

It creates a cursor candidate based on L4's completion decision.

L4 must not commit that cursor unless the corresponding canonical Entity transition was executed successfully.

Do not claim exactly-once execution across crashes or concurrent requests.

## 10.4. Cursor Advancement

For:

```text
dueAtMs = 2000
intervalMs = 1000
```

After successful completion:

```text
nextTickAtMs = 3000
```

Do not derive the next tick from wall-clock now.

Incorrect:

```text
nextTickAtMs = currentTime + intervalMs
```

Correct:

```text
nextTickAtMs = previousDueAtMs + intervalMs
```

Use strictly advancing finite timestamp checks.

Do not silently clamp, round or skip timestamps.

## 10.5. Missed Tick Recovery

If L4 fails to execute a tick:

- No periodic cursor candidate is committed.
- No authoritative resource transition is committed.
- Same due tick remains pending on retry.

L4 coordinates both states.

No hidden retry loop.

No exception swallowing.

## 10.6. Repeated Completion

After completing tick at `2000`, attempt to complete the same intent again against updated state.

Expected:

```text
rejected / stale_tick
```

No duplicate cursor advance.

No duplicate tick completion event.

## 10.7. Tick Progress Event

Proposed:

```ts
export interface EffectPeriodicTickEvent {
  readonly type: "tick-completed";

  readonly effectInstanceId: string;

  readonly effectId: string;

  readonly targetEntityId: string;

  readonly kind: "dot" | "hot";

  readonly atMs: number;
}
```

This is a scheduling/progress event only.

It does not contain invented damage/healing results.

Actual numerical outcome belongs to the canonical Entity transition returned to L4.

## 10.8. L4 Composite Tick Outcome

External consumer must demonstrate a composite outcome using actual Entity and Effect results.

Example:

```text
Tick:
  effectInstanceId = poison-001
  dueAtMs = 2000

Resource:
  before = 100
  after = 90
  applied = 10

Life:
  alive → alive

Periodic:
  nextTickAtMs = 3000
```

L4 may assemble this outcome for game runtime.

No new L2 damage receipt schema is required.

## 10.9. Deterministic Target Death Behavior

If a tick defeats the target:

```text
1. Execute canonical resource transition.
2. Resolve canonical Entity defeat.
3. Stop planning/executing further ticks.
4. L4 explicitly requests canonical Effect cleanup.
5. Commit final Entity and Effect state together.
```

No further tick at the same timestamp after death.

Even if another Effect has a due tick at that timestamp, it must not execute on the defeated target.

## 10.10. Dead Target Planning

The planner receives canonical `EntityLifeState`.

If target is dead:

```text
status = blocked
reason = target_dead
intent = null
```

No periodic tick execution.

Do not automatically remove active effects inside the planner.

Cleanup remains L4-owned through canonical Effect removal.

## 10.11. End-of-Life Ordering

At expiration boundary:

```text
Due tick
  → canonical Entity execution
  → tick cursor completion
  → possible defeat handling
  → canonical Effect expiration
```

If target survives, EF13 performs expiration after all due ticks have been processed.

If target is defeated, L4 follows target-defeat cleanup policy instead of executing further ticks.

## 10.12. No Silent Pending-Tick Loss

When synchronizing a later lifecycle advancement into the periodic companion:

- Reject if mandatory due ticks remain unresolved in the advanced interval.
- Do not silently drop pending ticks because the canonical lifecycle has expired.
- Explicit target-defeat cleanup is allowed to terminate future work according to D17.
- Do not fabricate completed ticks during cleanup.

This is essential to preserve D15.
