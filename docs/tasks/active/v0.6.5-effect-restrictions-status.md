# 1. Objective

Triển khai **Effect Restrictions & Status** dựa trên canonical Effect Application, Lifecycle, Stacking và Modifier systems đã được phê duyệt trong v0.6.0–v0.6.4.

Effect System phải cho phép một Effect đang active đóng góp các status và restriction identities. Những contributions này có thể được L3/L4 sử dụng để điều khiển gameplay admission.

Sau milestone này, consumer phải có khả năng:

1. Gán status identities cho một Effect Instance.
2. Gán restriction identities cho một Effect Instance.
3. Capture immutable status/restriction snapshot tại thời điểm apply.
4. Query những status đang active trên Entity.
5. Query những restrictions đang active trên Entity.
6. Phân biệt nhiều nguồn tạo cùng status.
7. Đánh giá một explicit restriction policy.
8. Chuyển kết quả restriction thành existing Skill/Combat admission policies.
9. Sử dụng restriction để từ chối một Effect Application.
10. Bảo toàn status/restriction snapshot khi refresh.
11. Loại bỏ contributions khi Effect expire, remove hoặc consume stack.
12. Hỗ trợ Stun, Silence và Immunity thông qua L3 configuration mà không hardcode chúng thành engine riêng.
13. Giữ deterministic behavior và immutable candidate state.
14. Không sửa existing Skill, Combat, Entity hoặc Core implementations.

# 4. EF26 — Effect Status & Tags

## 4.1. Objective

Allow active Effects to provide generic status identities.

Status identity is metadata, not a gameplay implementation.

Examples:

```text
stunned
silenced
poisoned
burning
frozen
poison-immunity
shielded
regenerating
```

These are L3 examples, not predefined L2 status enums.

## 4.2. Status Identity

`statusId`:

- Opaque nonblank string.
- Exact/case-sensitive.
- Caller-supplied.
- No ID generation.
- No normalization.
- No built-in vocabulary.
- No gameplay behavior inferred from the name.

Example:

```text
stunned
Stunned
```

These remain different identities.

## 4.3. Status Does Not Equal Restriction

A status answers:

```text
What status is currently present?
```

A restriction answers:

```text
What restriction contribution is present?
```

Example:

```text
Status:
  poisoned

Restrictions:
  []
```

Valid.

Example:

```text
Status:
  silenced

Restrictions:
  [disable-magic-skill]
```

Valid.

Example:

```text
Status:
  []

Restrictions:
  [block-physical-action]
```

Also structurally valid.

Do not require one-to-one status/restriction mapping.

## 4.4. No Hardcoded Status Logic

Do not write:

```ts
if (statusId === "stunned") {
  return false;
}
```

Do not create internal tables mapping:

```text
stunned → cannot act
silenced → cannot cast
poison-immunity → cannot receive poison
```

That interpretation belongs to L3.

## 4.5. Status Provenance

A status can be contributed by multiple Effect Instances.

Example:

```text
Effect Instance A:
  status = poisoned

Effect Instance B:
  status = poisoned
```

Expected:

```text
poisoned:
  contributors = [A, B]
```

Removing A must not remove status contributed by B.

Do not maintain a separate mutable status counter.

Count must be derivable from active instance membership.

# 5. EF27 — Restriction Contributions

## 5.1. Objective

Capture immutable restriction identities associated with an accepted Effect Instance.

## 5.2. Restriction Identity

`restrictionId` is an opaque nonblank string.

Examples:

```text
disable-all-actions
disable-magic-skill
disable-melee-action
immune-poison
immune-burning
block-teleport
```

L2 does not assign semantics to these strings.

No wildcard syntax.

No prefix interpretation.

No automatic hierarchy.

No special treatment of `all` or `any`.

If an action should be blocked by multiple restriction identities, L3 supplies those identities explicitly.

## 5.3. Proposed Capture Contract

```ts
export interface EffectStatusCapture {
  readonly statusIds: readonly string[];
  readonly restrictionIds: readonly string[];
}
```

Both arrays required.

Empty arrays allowed.

No implicit default status.

No implicit default restriction.

No automatic Buff/Debuff classification.

## 5.4. Proposed Snapshot

```ts
export interface EffectStatusSnapshot {
  readonly effectInstanceId: string;

  readonly statusIds: readonly string[];

  readonly restrictionIds: readonly string[];
}
```

One snapshot per active Effect Instance.

The snapshot stores no second Effect Instance object.

It does not contain:

```text
effectId
sourceKey
duration
stacks
modifiers
stats
```

Those remain owned by earlier Effect contracts.

## 5.5. Snapshot Rules

Within each snapshot:

- Duplicate status IDs rejected.
- Duplicate restriction IDs rejected.
- IDs preserve exact case/content.
- Arrays preserve caller order.
- Nested arrays detached and frozen.
- Caller inputs remain unchanged and unfrozen.
- Invalid or accessor properties rejected.
- No getter invocation.

The same status/restriction may appear in different Effect Instances.

That is valid and must preserve contributor provenance.

## 5.6. Apply-Time Snapshot — D09

Capture occurs when an Effect Instance is accepted into lifecycle.

Example:

```text
Effect A:
  statusIds = [silenced]
  restrictionIds = [disable-magic-skill]
```

If L3 later changes the definition, A retains its original snapshot.

Refresh A's duration:

```text
statusIds unchanged
restrictionIds unchanged
```

No recapture.

No replacement.

No extra contribution.

# 6. Canonical Status State

## 6.1. Objective

Associate status/restriction snapshots with existing Effect lifecycle without creating another active Effect store.

## 6.2. Proposed Contract

```ts
export interface EffectStatusState {
  readonly entityId: string;

  readonly observedAtMs: number;

  readonly snapshots: readonly EffectStatusSnapshot[];
}
```

**EffectStatusState is a companion payload index, not lifecycle authority.**

It does not duplicate the canonical Effect Instance collection.

The authoritative active membership is supplied separately through `EffectLifecycleState`.

## 6.3. State Invariants

For a matching lifecycle and status state:

```text
lifecycle.effectState.entityId
  == statusState.entityId

lifecycle.observedAtMs
  == statusState.observedAtMs
```

Every lifecycle instance must have exactly one status snapshot.

Every status snapshot must reference one existing lifecycle instance.

Snapshot ordering must follow canonical Effect Instance ordering.

Reject:

- Missing snapshot.
- Orphan snapshot.
- Duplicate effectInstanceId.
- Wrong Entity.
- Time mismatch.
- Snapshot ordering mismatch.
- Unknown fields.
- Malformed arrays.

No silent repair.

## 6.4. Initialization

Proposed API:

```ts
export function createEffectStatusState(
  lifecycle: EffectLifecycleState
): EffectStatusState;
```

Initialization requires an empty lifecycle.

Expected:

```text
entityId = player-1
observedAtMs = 1000
snapshots = []
```

Do not fabricate status snapshots for existing active Effect Instances.

Historical state migration is out of scope.

## 6.5. Coexistence With Modifier State

v0.6.4 already introduces modifier snapshots.

v0.6.5 introduces status/restriction snapshots.

Both must reference the same canonical Effect lifecycle.

```text
Canonical EffectLifecycleState
          │
          ├── Modifier Companion
          │     └── numerical snapshot payloads
          │
          └── Status Companion
                └── status/restriction payloads
```

No additional lifetime engine.

No duplicate Effect Instance authority.

No global status registry.

L4 is responsible for coordinating their transitions against the same authoritative lifecycle candidate.

**Do not perform one successful authoritative commit while silently leaving the other companion at a different lifecycle version.**

If a multi-companion commit cannot be completed by L4, no partial commit is authorized.

This is a caller orchestration invariant, not a new L2 transaction manager.

# 7. Status State Transitions

## 7.1. Objective

Follow canonical Effect lifecycle transitions without reproducing their application, expiration, stacking or removal logic.

## 7.2. Proposed API

```ts
export function applyEffectStatusTransition(
  current: EffectStatusState,
  previousLifecycle: EffectLifecycleState,
  transition:
    | EffectLifecycleStartResult
    | EffectLifecycleTransitionResult
    | EffectStackMutationResult,
  capture?: EffectStatusCapture
): EffectStatusTransitionResult;
```

The accepted EF12–EF20 types remain authoritative.

Do not recreate their public result schemas.

## 7.3. New Effect Instance

Flow:

```text
EF09 Apply
    ↓
EF12 / EF17 Accepted Lifecycle Addition
    ↓
New Effect Instance
    ↓
EffectStatusCapture
    ↓
Status Transition
    ↓
Immutable Candidate
```

Requirements:

- Exactly one new canonical instance.
- Capture required, even when both arrays are empty.
- Snapshot associated with new instance ID.
- Existing snapshots preserved.
- No fabricated status.
- No second Effect application.

## 7.4. Refresh

When canonical stack mutation reports:

```text
action = refreshed
```

Expected:

- Status snapshot unchanged.
- Restriction snapshot unchanged.
- No new Effect Instance.
- No additional contribution.
- No new snapshot.
- No supplied replacement capture.

If capture is provided on refresh:

```text
TypeError
```

Do not silently overwrite the original snapshot.

## 7.5. Expiration

When EF13 removes an expired Effect Instance:

- Remove exactly its status snapshot.
- Preserve unrelated snapshots.
- Update observedAtMs to the canonical lifecycle time.
- Do not emit status-specific expiration events.
- Do not duplicate EffectLifecycleEvent.

## 7.6. Explicit Removal

When EF14 removes an Effect Instance:

- Remove its status snapshot.
- Preserve remaining contributors to the same status.
- Do not generate a numerical rollback.
- Do not alter other Entity state.

## 7.7. Stack Consumption

When EF20 consumes N stacks:

- Remove exactly those snapshots.
- Preserve unconsumed stacks.
- Preserve shared status if another contributor remains.
- No partial cleanup.

## 7.8. Group Removal

When EF20 removes an entire group:

- Remove every snapshot belonging to removed instances.
- Preserve unrelated groups.
- Do not perform an independent group search using status IDs alone.

## 7.9. No Membership Change

For a successful lifecycle advance with no expiration:

- Preserve snapshots.
- Advance companion observedAtMs.
- Return immutable candidate.
- No new contribution.

## 7.10. Transition Validation

Validate before returning an accepted candidate:

1. Complete previous lifecycle.
2. Complete current status state.
3. Same Entity and observation time.
4. Canonical transition result shape.
5. Old instance identities preserved where unaffected.
6. Exactly matching added/removed membership.
7. Correct capture presence.
8. No snapshot overwrite.
9. No orphan snapshots.
10. No unexpected duplicate identities.

A forged transition receipt must not bypass structural checks.

L4 still owns authoritative freshness and state commit.

# 10. EF28 — Action Restriction Assessment

## 10.1. Objective

Assess whether active restriction identities match an explicit caller-provided policy.

Effect must not know which Skill or Combat action is being executed.

## 10.2. Proposed Policy

```ts
export interface EffectRestrictionPolicy {
  readonly blockedByRestrictionIds:
    readonly string[];
}
```

The list is provided by L3/L4.

Empty list is valid and means no restriction IDs selected by this policy.

Entries must be unique opaque nonblank strings.

No implicit defaults.

## 10.3. Proposed Assessment

```ts
export interface EffectRestrictionAssessment {
  readonly entityId: string;

  readonly status: "allowed" | "blocked";

  readonly reason:
    | "none"
    | "active_restriction";

  readonly matches:
    readonly EffectRestrictionView[];
}
```

Invariant:

```text
matches.length = 0
  → allowed / none

matches.length > 0
  → blocked / active_restriction
```

This is an Effect restriction assessment, not a Skill/Combat admission result.

## 10.4. Public API

```ts
export function evaluateEffectRestrictionGate(
  lifecycle: EffectLifecycleState,
  state: EffectStatusState,
  policy: EffectRestrictionPolicy
): EffectRestrictionAssessment;
```

The evaluator must:

1. Validate lifecycle/status alignment.
2. Validate complete policy.
3. Read current active restrictions.
4. Match exact restriction IDs.
5. Preserve all matching contributor provenance.
6. Return immutable deterministic assessment.
7. Avoid gameplay side effects.

No action execution.

No Skill invocation.

No Combat invocation.

## 10.5. Matching Semantics

Match exact IDs only.

No:

```text
wildcards
prefixes
regular expressions
case folding
implicit inheritance
severity
priorities
```

Existing public Core `matchesAnyTag()` may be reused for suitable exact boolean matching, but it is not authorization to introduce new interpretation semantics.

Returning contributor provenance must still use canonical active restrictions.

## 10.6. Stun Example

L3 defines:

```text
Effect:
  stun

Status:
  stunned

Restriction:
  disable-all-actions
```

Combat action policy:

```ts
{
  blockedByRestrictionIds: [
    "disable-all-actions"
  ]
}
```

Expected:

```text
blocked / active_restriction
```

L3 decides which actions use that policy.

Effect does not hardcode that every action must be blocked.

## 10.7. Silence Example

L3 defines:

```text
Effect:
  silence

Status:
  silenced

Restriction:
  disable-magic-skill
```

Magic Skill policy:

```ts
{
  blockedByRestrictionIds: [
    "disable-all-actions",
    "disable-magic-skill"
  ]
}
```

Expected:

```text
blocked / active_restriction
```

Physical action policy:

```ts
{
  blockedByRestrictionIds: [
    "disable-all-actions",
    "disable-physical-action"
  ]
}
```

Expected:

```text
allowed / none
```

This example must be driven by the supplied policies, not an L2 hardcoded distinction between physical and magic.

## 10.8. Multiple Restrictions

If two active instances contribute the same blocking restriction:

```text
A → disable-magic-skill
B → disable-magic-skill
```

Expected two matches with distinct instance IDs.

Removing A must not incorrectly change the assessment to allowed while B remains.

## 10.9. Valid Rejection vs Malformed Input

Malformed lifecycle/status/policy:

```text
TypeError
```

Valid active restriction:

```text
blocked / active_restriction
```

Do not throw simply because an action is restricted.

# 11. EF29 — Effect Application Restrictions

## 11.1. Objective

Allow Effect Application to be denied by existing active restriction contributions.

**Reuse existing EF08 admission.**

Do not create another application validator.

## 11.2. Approved Integration Flow

```text
Target Active Effects
         ↓
Active Restriction Projection
         ↓
L3 Effect Application Policy
         ↓
Restriction Assessment
         ↓
L4 Combines Eligibility
         ↓
EF08 Effect Apply Admission
```

Effect must not import a second application engine.

## 11.3. Poison Immunity Example

Target has:

```text
Effect:
  poison-immunity

Status:
  poison-immune

Restriction:
  immune-poison
```

L3 Poison Application policy:

```ts
{
  blockedByRestrictionIds: [
    "immune-poison"
  ]
}
```

Restriction assessment:

```text
blocked
```

L4 supplies to existing EF08:

```text
targetEligible = false
```

Expected EF08 result:

```text
rejected / target_ineligible
```

No new `immune_to_poison` reason is required in EF08.

The restriction assessment supplies provenance explaining why targetEligible was false.

## 11.4. Different Effect Allowed

Same target:

```text
Active restriction:
  immune-poison
```

Burning application policy:

```ts
{
  blockedByRestrictionIds: [
    "immune-burning"
  ]
}
```

Expected:

```text
allowed
```

EF08 may accept Burning if all other existing admission conditions pass.

## 11.5. Multiple Immunities

Target:

```text
immune-poison
immune-burning
```

Poison and Burning application policies independently identify their relevant blocking restrictions.

No automatic matching by Effect ID.

No `effectId.includes("poison")` logic.

## 11.6. No Immunity Bypass of Existing Checks

Even if restriction assessment returns allowed, EF08 must still evaluate:

- Source existence.
- Target existence.
- Target life.
- Source eligibility.
- Target eligibility.
- Duplicate Effect Instance ID.

An allowed restriction assessment is not full Effect admission.

## 11.7. Eligibility Composition

L4 must combine independent conditions.

Conceptually:


**L1 Core:** Sole numerical owner; no new numerical capability required.

**L2 Entity:** Owns Entity identity, resources and life.

**L2 Effect:** Owns active Effect status/restriction contributions and generic matching assessment.

**L2 Skill:** Continues to own Skill admission.

**L2 Combat:** Continues to own Combat admission and targeting.

**L3:** Owns the meaning of Stun/Silence/Immunity and which gameplay actions each restriction blocks.

**L4:** Owns current authoritative state, eligibility composition, sequencing, commit and persistence.
