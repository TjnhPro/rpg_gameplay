# 4. GF14 — Injectable Clock Abstraction

## 4.1. Objective

Loại bỏ nhu cầu sử dụng thời gian hệ thống trực tiếp trong các gameplay operations.

Clock phải do caller cung cấp.

Ví dụ:

```ts
const clock = {
  now: () => 1500
};
```

Foundation không tự quyết định clock tương ứng với:

- Wall-clock.
- Simulation time.
- Server time.
- Turn-based time.
- In-game world time.

Consumer chọn time source phù hợp.

## 4.2. Required Clock Contract

Cung cấp public type tương đương:

```ts
interface GameplayClock {
  now(): number;
}
```

Quy ước tối thiểu:

- Giá trị thời gian là number.
- Đơn vị mặc định: milliseconds.
- Time origin do caller xác định; không mặc định coi là Unix epoch.
- Giá trị phải finite.
- Không chấp nhận `NaN`, `Infinity`, `-Infinity`.
- Với Foundation v0.1.5, time value phải không âm.

Không tự động thay đổi giá trị thời gian.

Không tự tạo system clock fallback.

Không tự gọi `Date.now()` khi caller không inject clock.

## 4.3. Clock Read Behavior

Cần có public function hoặc execution-context function tương đương:

```ts
readExecutionTime(execution);
```

Bắt buộc:

1. Gọi đúng clock provider đã inject.
2. Trả giá trị quan sát được từ provider.
3. Không cache thời gian ngầm.
4. Không tự tăng timestamp.
5. Không sửa caller-owned clock.
6. Không phụ thuộc clock toàn cục.
7. Invalid clock output bị reject rõ ràng.

Clock chỉ được đọc khi một operation chủ động yêu cầu thời gian.

Không tự đọc clock khi:

- Đăng ký Module.
- Resolve dependencies.
- Compose modules.
- Tạo Messaging Context.
- Tạo Execution Context, trừ validation không gây gọi `now`.
- Inspect Runtime.

## 4.4. Controllable Time

Test phải chứng minh caller có thể kiểm soát thời gian:

```ts
let time = 1000;

const clock = {
  now: () => time
};
```

Expected:

```text
read → 1000
caller changes time → 1500
read → 1500
```

Foundation không được tự làm thay đổi `time`.

Không cần API `advanceTime()` trong production library. Virtual clock fixtures thuộc tests hoặc consumer.

## 4.5. Clock Non-Goals

Không triển khai:

- Timers.
- Scheduler.
- Tick engine.
- Game loop.
- Cooldown system.
- Timezone conversion.
- Calendar.
- Frame delta integration.
- Time synchronization.
- Pause/resume simulation clock.
- Automatic timestamps cho mọi command/event.

Các capabilities thực tế sẽ quyết định sau này khi nào cần đọc thời gian.

# 5. GF15 — Execution Dependencies

## 5.1. Objective

Tạo một explicit execution dependency boundary để gameplay functions sau này có thể sử dụng clock, randomness hoặc ID providers mà không phụ thuộc hidden globals.

Tập trung vào những dependencies thực sự cần cho deterministic gameplay:

- Clock.
- Random number provider, khi cần.
- ID provider, khi cần.

Không phát triển một generic Dependency Injection framework.

## 5.2. Proposed Contract

Public types định hướng:

```ts
interface GameplayRandom {
  next(): number;
}

interface GameplayIdProvider {
  next(): string;
}

interface GameplayExecutionDependencies {
  readonly clock: GameplayClock;
  readonly random?: GameplayRandom;
  readonly ids?: GameplayIdProvider;
}
```

Đây là contract định hướng. Agent có thể điều chỉnh names/internal representation phù hợp với existing conventions.

Semantics bắt buộc phải giữ nguyên.

**Clock là dependency bắt buộc cho một execution context; RNG và ID providers là optional.**

Không ép những gameplay modules không cần RNG hoặc ID phải inject providers không sử dụng.

## 5.3. Execution Context

Triển khai function tương đương:

```ts
const execution = createExecutionContext({
  clock,
  random,
  ids
});
```

Yêu cầu:

- Explicit constructor/function.
- Không tự tạo default providers.
- Không gọi provider tại thời điểm tạo context.
- Không tạo global singleton.
- Không tự tạo Gameplay Runtime.
- Không tự tạo Messaging Context.
- Không tự start module.
- Không chứa arbitrary service locator.
- Không chứa application/game state.

Context phải có ownership riêng.

Multiple contexts phải độc lập về framework-owned execution state.

## 5.4. Random Provider

Nếu RNG được inject, cung cấp một cách truy cập rõ ràng tương đương:

```ts
nextExecutionRandom(execution);
```

Random contract:

- Mỗi lần gọi tiêu thụ đúng một sample do provider trả về.
- Sample phải là finite number trong `[0, 1)`.
- Không dùng `Math.random()` làm fallback.
- Không tự thay đổi RNG algorithm.
- Không tự seed RNG.
- Không tự generate loot/damage/critical từ random sample.
- Không tự áp đặt game balance.

Invalid provider output phải fail rõ ràng.

Nếu caller không inject RNG mà yêu cầu random sample, phải reject thay vì âm thầm tạo random value.

Không tự triển khai PRNG algorithm trong Foundation.

RNG implementation/seed ownership thuộc caller hoặc capability chuyên biệt trong tương lai.

## 5.5. ID Provider

Nếu ID provider được inject, cung cấp cách lấy ID tương đương:

```ts
nextExecutionId(execution);
```

Yêu cầu:

- Dùng đúng provider.
- Không tự dùng `crypto.randomUUID()` hoặc global counter.
- Output phải là non-empty string.
- Không tự generate ID khi provider không tồn tại.
- Invalid output phải fail.
- Không bắt buộc mọi ID theo format Module ID.
- Không tự bảo đảm uniqueness toàn cục.

Uniqueness và collision policy do consumer hoặc gameplay capability có trách nhiệm tương ứng quyết định.

Không tạo một distributed ID service.

## 5.6. Provider Ownership & Validation

Execution Context phải:

1. Validate presence/type của required providers.
2. Snapshot các callback bindings cần thiết để caller thay thế method sau đó không âm thầm thay đổi provider binding.
3. Không mutate hoặc deep-freeze caller-owned providers.
4. Không expose mutable internal execution records.
5. Không giữ global mutable registry.
6. Không call providers ngoài explicit request.
7. Không silently convert invalid results thành default values.

Nếu provider được thiết kế stateful, nội bộ provider tiếp tục thuộc caller.

Snapshot callback binding không đồng nghĩa với clone trạng thái bên trong provider.

## 5.7. Error Semantics

Các trường hợp malformed input hoặc invalid provider outputs phải có lỗi rõ ràng.

Ví dụ:

- Missing clock.
- `clock.now` không callable.
- RNG không được inject.
- RNG trả `NaN` hoặc giá trị ngoài `[0,1)`.
- ID provider trả chuỗi rỗng.
- Provider callback throw.

Không swallow errors.

Không retry provider ngầm.

Không tăng hoặc phục hồi RNG/ID sequence sau failure trừ khi caller quyết định.

Nếu lỗi xuất hiện bên trong GF07 lifecycle hook hoặc GF10 command handler, phải để existing lifecycle/command failure semantics xử lý; không tạo một error pipeline thứ hai.

# 6. GF16 — Deterministic Execution Contract

## 6.1. Objective

Chứng minh rằng Foundation cho kết quả có thể tái tạo khi:

- Input giống nhau.
- Registry/composition giống nhau.
- Command/event registrations giống nhau.
- Lifecycle bindings có cùng behavior.
- Clock provider cho cùng chuỗi values.
- RNG provider cho cùng chuỗi values.
- ID provider cho cùng chuỗi values.
- Thứ tự các explicit calls giống nhau.
- Starting provider/context state tương đương.

**Determinism không có nghĩa mọi execution đều trả kết quả giống nhau bất kể input hoặc lịch sử provider.**

## 6.2. Deterministic Execution Principles

Foundation phải bảo đảm:

1. Module resolution order là deterministic.
2. Module lifecycle ordering là deterministic.
3. Command routing là deterministic.
4. Event subscriber ordering là deterministic.
5. Event fan-out semantics được xác định.
6. Error/failure ordering được xác định.
7. Clock/RNG/IDs không được truy cập từ hidden global sources.
8. Execution dependency reads diễn ra theo explicit call order.
9. Hai executions độc lập không chia sẻ framework-owned state.
10. Output metadata/inspection không chứa implicit timestamps hoặc random IDs.

Các behaviors được GF01–GF13 nghiệm thu phải được **kiểm chứng lại**, không viết lại.

## 6.3. Reproducibility Test

Xây dựng hai execution sessions độc lập:

```text
Session A:
  Inputs: X
  Clock sequence: T
  RNG sequence: R
  ID sequence: I

Session B:
  Inputs: X
  Clock sequence: T
  RNG sequence: R
  ID sequence: I
```

Expected:

```text
Observable trace A == Observable trace B
```

Observable trace phải bao gồm những giá trị có ý nghĩa:

- Module resolution order.
- Lifecycle hook invocation order.
- Explicit clock reads.
- RNG samples.
- Generated IDs.
- Command results.
- Event delivery order.
- Cleanup results.
- Final Runtime Inspection.

Không bắt buộc object identity hoặc function references giống nhau giữa hai sessions.

Không kiểm tra equality bằng cách stringify các capability objects có private identity.

So sánh semantic outputs được mô tả trong public contracts.

## 6.4. Changed Dependency Sequence

Bắt buộc chứng minh ít nhất một trường hợp thay đổi dependency outputs sẽ thay đổi observable results theo đúng expected.

Ví dụ:

```text
Same input
Same composition
Different injected clock sequence
```

Expected:

- Clock-dependent output thay đổi đúng theo injected values.
- Dependency order không thay đổi.
- Command/Event framework không tự tạo timestamps khác.

Tương tự, RNG sequence khác phải tạo kết quả sample khác tại đúng explicit call site.

Không cần tự viết damage/loot algorithm để chứng minh điều này.

## 6.5. No Hidden Nondeterminism

Không được sử dụng trong các execution functions mới:

```ts
Date.now();
Math.random();
crypto.randomUUID();
```

Ngoại trừ việc những API này được dùng bên trong **caller-owned providers**, nằm ngoài trách nhiệm Foundation.

Không có global execution counter hoặc singleton execution state.

Không phụ thuộc network timing.

Không phụ thuộc rendering frame time.

Không phụ thuộc event-loop scheduling để đạt kết quả.

## 6.6. Execution Order & Side Effects

Foundation chịu trách nhiệm thứ tự thực thi các callbacks do nó điều phối.

Foundation **không cam kết** kết quả từ một callback có hidden nondeterminism riêng.

Ví dụ, nếu caller-owned handler tự gọi `Math.random()`, Foundation không thể bảo đảm replay sẽ giống nhau.

Documentation phải nêu rõ phạm vi bảo đảm này.

Không claim deterministic gameplay behavior tổng quát khi chưa có gameplay modules thực tế.

## 6.7. Failure Determinism

Với cùng scripted callbacks và failure ở cùng vị trí:

- Module/stage thất bại phải giống nhau.
- Completed lifecycle stages phải giống nhau.
- Command failure status phải giống nhau.
- Event completed-delivery count phải giống nhau.
- Listeners sau lỗi không được thực thi.
- Cleanup trace phải giống nhau.

Không tự retry/rollback để làm kết quả hai lần chạy trông giống nhau.

## 6.8. Reentrancy Preservation

Giữ semantics hiện có:

- GF07 không cho replay/reentrant lifecycle execution.
- GF10/GF13 không cho unsupported nested dispatch/publish trên cùng Messaging Context.
- Failed operation không poison context nếu existing contract yêu cầu có thể tiếp tục.
- Các contexts độc lập không ảnh hưởng lẫn nhau.

Không thêm async queue hoặc event scheduler.

# 7. Integration Với Foundation Hiện Có

## 7.1. Integration Strategy

Execution dependencies phải được sử dụng bằng explicit caller wiring.

Không sửa existing GF07/GF10/GF12 callback signatures để inject thêm execution context một cách breaking.

Ví dụ:

```ts
const execution = createExecutionContext({
  clock: {
    now: () => 1000
  },
  random: {
    next: () => 0.25
  },
  ids: {
    next: () => "execution-1"
  }
});

const messaging = createGameplayMessaging(composition);

registerCommandHandler(messaging, {
  moduleId: "module-a",
  commandType: "perform-action",
  handler() {
    const time = readExecutionTime(execution);
    const sample = nextExecutionRandom(execution);
    const id = nextExecutionId(execution);

    return {
      status: "success",
      value: {time, sample, id}
    };
  }
});
```

Đây là conceptual usage.

Không yêu cầu thay đổi GF10 public handler contract.

Không tự gắn execution context vào tất cả modules.

Không thiết kế một universal context bắt buộc mọi module phải sử dụng.

## 7.2. Ownership

Cấu trúc tham khảo:

```text
src/
  foundation/
    modules/      GF01–GF05
    runtime/      GF06–GF09
    messaging/    GF10–GF13
    execution/    GF14–GF16
  index.ts
```

`execution/` là một Foundation owner riêng, không phải một gameplay module trong static `harness/modules.json`.

Không đăng ký `clock`, `random`, `execution` thành các gameplay modules giả.

Không tạo nhiều implementations cho cùng execution dependency boundary.

## 7.3. Public API

Bổ sung tối thiểu những public types/functions thực sự cần dùng.

Ví dụ public surface định hướng:

- `GameplayClock`
- `GameplayRandom`
- `GameplayIdProvider`
- `GameplayExecutionDependencies`
- `GameplayExecutionContext`
- `createExecutionContext`
- `readExecutionTime`
- `nextExecutionRandom`
- `nextExecutionId`

Tên có thể điều chỉnh, nhưng semantics phải rõ ràng.

Không export internal mutable records, provider stores hoặc debug-only state.

Không mở deep package exports nếu root entrypoint đáp ứng yêu cầu.

# 11. Test Design Requirements

## 11.1. Deterministic Providers

Tests sử dụng scripted providers với expected values cố định.

Ví dụ:

```ts
const clockSequence = [1000, 1500, 2000];
const randomSequence = [0.1, 0.75, 0.25];
const idSequence = ["id-1", "id-2", "id-3"];
```

Provider state của Session A và Session B phải độc lập.

Không dùng cùng một mutable provider instance giữa hai executions rồi tuyên bố isolation.

Không tự reset hidden state trong Foundation để hai traces bằng nhau.

## 11.2. Independent Expected Values

Expected traces phải được viết từ approved contracts, không tạo bằng chính function đang test.

Ví dụ:

```text
Expected:
  initialize: actor
  initialize: action
  start: actor
  start: action
  clock: 1000
  random: 0.1
  command: success
  event: observer-1
  stop: action
  stop: actor
  dispose: action
  dispose: actor
```

Actual được thu thập độc lập.

Test phải fail khi:

- Sai thứ tự.
- Thừa hoặc thiếu callback.
- Clock/RNG không dùng injected provider.
- Event delivery sai.
- Cleanup không hiệu lực.
- Runtime inspection sai.

## 11.3. Failure Tests

Ưu tiên một vài meaningful negative scenarios:

- Invalid clock result.
- Invalid RNG sample.
- Missing ID provider.
- Provider throw trong command handler.
- Deterministic event listener failure.
- Cross-context leakage.

Không tạo Cartesian product giữa mọi dependency, operation và failure stage nếu không bổ sung invariant mới.

## 11.4. Existing Regression Preservation

Giữ nguyên expected behaviors của GF01–GF13.

Không rewrite các fixtures cũ để thích nghi với một implementation sai.

Không bỏ tests chỉ vì full verification mất thời gian.

Không thay đổi existing public result statuses.

Không làm yếu runtime encapsulation regression.

Không thay đổi Event/Command failure semantics.
