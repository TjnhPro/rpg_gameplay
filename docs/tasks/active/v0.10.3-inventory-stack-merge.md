## Existing contract freeze / ownership

Use unchanged `InventoryState {inventoryId,owner,entries}`, `InventoryEntry {item,quantity}`, `InventoryValidationContext`, `InventoryTransitionResult` and Item public `assessItemStackCompatibility`. The **destination entry** keeps its exact Item Instance snapshot and identity; the **source entry** disappears from the candidate Inventory membership after a successful merge. This does **not** establish global destruction of the source Item or allow the same ID to appear in another storage; L4 must enforce global current-state invariants.

### Proposed new operation

```ts
export type InventoryMergeReason =
  | 'ineligible'
  | 'missing_entry'
  | 'same_instance'
  | 'item_incompatible'
  | 'stack_limit_exceeded';

export function mergeInventoryEntries(
  state: InventoryState,
  context: InventoryValidationContext,
  sourceInstanceId: string,
  destinationInstanceId: string,
  admission: InventoryOperationAdmission,
): InventoryTransitionResult<InventoryMergeReason>;
```

**One runtime function + one reason type.** Reuse shared accepted outcome contract, no new Item API or Manager.

### Exact merge behavior

1. Structurally validate full incoming state/context, two exact string IDs and closed admission without calling accessors; malformed input => TypeError.
2. Legitimate `eligible:false` => `rejected/ineligible`, no candidate. Missing source/destination => `missing_entry`. Same valid source/destination instance ID => `same_instance`, no candidate.
3. Resolve both entries' **complete** definitions from explicit context; call **accepted** Item public `assessItemStackCompatibility` with approved `stackPolicy`; never compare only definitionId or create an Inventory-only duplicate item equality rule.
4. If Item says incompatible for any reason (`different_properties`, `not_stackable`, `definition_conflict`, ...), return `rejected/item_incompatible` with no candidate; optionally document actual Item result in test evidence, not additional required fields. No silent merge for loss of an affix or durability.
5. Compute total with **safe integer guard**, no rounding; reject `stack_limit_exceeded` for `Number.MAX_SAFE_INTEGER` overflow or explicit maxStackQuantity overflow. No auto-create a remainder stack.
6. Accept: destination entry keeps same `item` identity/data and earlier position; its `quantity = old destination quantity + source quantity`; remove source entry; other entries retain deterministic relative order. Revalidate complete candidate via canonical Inventory and Item validators.
7. Candidate is deeply detached/frozen, original input unchanged; **no events, DB commit, source ID retirement registry, wallet changes, item generation, split or Equipment state**.
8. This function works only **inside one InventoryState**. Cross-inventory transfer is deferred to game-driven expansion using future paired state candidates (C2), not scaffolded here.

#### Cases

S01 compatible equal properties and stackable true → expected qty 11.
S02 source/destination IDs identical → `same_instance`, no output.
S03 destination/source missing → `missing_entry`.
S04 different definition IDs → `item_incompatible`.
S05 same definition ID but different full definition contents → Item `definition_conflict` causes Inventory `item_incompatible`.
S06 same definition, different instance properties (`durability`) → `item_incompatible`.
S07 stackable false even with equal payload → `item_incompatible`.
S08 sum > maxStackQuantity → `stack_limit_exceeded`.
S09 sum unsafe > MAX_SAFE_INTEGER → `stack_limit_exceeded`.
S10 `eligible:false` with valid input → `ineligible`; malformed input still TypeError.
S11 successful merge removes exactly one entry; capacity is freed, entry order stable.
S12 nested callers and outputs detached/frozen, replay deterministic; no Item snapshot modifications.
S13 packed ESM strict NodeNext Item+Inventory consumer; prior regressions.
S14 future split/transfer **design-only** inspection: foundation state doesn't require new fields, but operations remain absent.
