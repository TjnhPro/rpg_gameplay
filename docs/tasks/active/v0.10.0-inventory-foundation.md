| --- | --- | --- |

## Foundation API, invariants and decisions

### Proposed stable foundational model (final signature subject to accepted Item preflight)

```ts
// Only fields with stable, long-lived Inventory semantics are in state.
export interface InventoryOwnerReference {
  readonly ownerKind: string;
  readonly ownerId: string;
}
export interface InventoryEntry {
  readonly item: ItemInstanceState; // canonical Item snapshot, not a new Item subtype
  readonly quantity: number;        // integer >= 1, safe integer
}
export interface InventoryState {
  readonly inventoryId: string;
  readonly owner: InventoryOwnerReference | null;
  readonly entries: readonly InventoryEntry[];
}
// Explicit L3 facts; never stored in InventoryState.
export interface InventoryItemContext {
  readonly definition: ItemDefinition;
  readonly stackPolicy: ItemStackPolicy;
  readonly maxStackQuantity: number | null; // positive safe integer or explicit no cap
}
export interface InventoryValidationContext {
  readonly items: readonly InventoryItemContext[];
}
// Stable extension mechanism: each future operation owns its own typed reason union.
export type InventoryTransitionResult<TReason extends string> =
  | { readonly status: 'accepted'; readonly reason: 'none'; readonly candidate: InventoryState }
  | { readonly status: 'rejected'; readonly reason: TReason; readonly candidate: null };

export function createInventoryState(
  input: InventoryState,
  context: InventoryValidationContext,
): InventoryState;
export function validateInventoryState(
  state: InventoryState,
  context: InventoryValidationContext,
): InventoryState;
```

**Contract design rationale:** `item.instanceId` is the unique membership key within one inventory. No redundant `entryId` until a real use case proves independent entry identity is necessary. Entries have **no slot index**; array order is stable membership order, not a promise of display/grid position. No max slots/weight policy, transaction ID, revision, item catalog or database record inside the canonical state. Owner is a neutral **reference/fact**, not proof of authorization. `ItemInstanceState` is supplied by Item; Inventory must never mint or mutate Item identity by itself.

**Definition integrity:** canonical `validateItemInstance(definition,item)` needs real complete ItemDefinition from caller. `context.items` supplies each referenced definition and the explicit Item stack policy/maximum. Reject duplicate/conflicting context definitions, unresolved definition IDs, invalid policy, instance mismatch. Reuse accepted public Item validators. Validate the whole snapshot, deep-detach/freeze all results and never modify/freeze caller-owned objects. Definition/catalog lookup remains an external L3/L4 concern; no automatic resolver/global store.

**Core invariants:** exact nonblank opaque inventoryId and owner IDs/kinds; distinct `item.instanceId`s across entries; positive safe-integer quantity; nonstackable `quantity===1`; stackable quantity at most the supplied `maxStackQuantity` when not null; no implicit normalization, auto-stack, auto-ID, property override or ItemDefinition inheritance. Empty inventory valid; entries ordered deterministically, data-only, closed shape, frozen detached. Malformed input TypeError; valid but denied operation uses a typed rejection outcome. `maxStackQuantity:null` means policy supplies **no additional per-stack maximum**, still bounded by JS safe integers.

**Important future boundary:** v0.9.2 compatibility demands different valid instance IDs and identical relevant Item data before merging. Merge keeps destination ID and retires source **membership reference only**; global Item identity retirement/uniqueness is an L4 obligation. A future split needs caller-provided new instance ID via canonical Item creation. Future transfer requires paired source/destination candidates and L4 atomic commit; neither needs a new field in this InventoryState.

### Input/validation behavior

- `createInventoryState` accepts a complete explicit snapshot (empty or prefilled) plus complete context. `validateInventoryState` performs same checks on existing snapshot and returns a **fresh** detached/frozen snapshot. A complete snapshot permits future L4 hydration **without** implementing persistence.
- Closed own-data records only (no prototypes/getters/symbols/unknown keys); recursively validate Item through canonical v0.9 public functions, not a parallel Item serializer. Negative hostile inputs must not trigger getters.
- `context.items` may include definitions **not yet present** to support explicit later add. Same `definitionId` may occur **once**, and Item `validateItemDefinition` must capture it before binding. Caller context order does not affect lookup semantics.
- `maxStackQuantity` positive safe integer or `null`; `stackPolicy` must be accepted Item policy with `stackable:boolean`. For nonstackable, inventory quantity must be **exactly 1**, even if max allows more; stackable may be quantity 1. Safe integer arithmetic is enforced at all boundaries.
- Identical `item.instanceId` twice in one inventory is invalid regardless of different definition or entry ordering. Cross-storage uniqueness **cannot** be claimed by a single snapshot validator.
- Empty ownerless inventory is valid. No default owner, `playerId`, bag type, max slots, item catalog or global Item Store.
