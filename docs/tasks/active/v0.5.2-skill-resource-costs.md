# 2. Mandatory Architecture Decisions

## 2.1. Strict Layer Ownership

| Responsibility | Canonical Owner | Rule |
|---|---|---|
| Numerical Resource Calculation | L1 — RPG Core | Calculate resource transitions, clamping và applied values |
| Entity Resource State | L2 — Entity | Current resource values và immutable transitions |
| Entity Life State | L2 — Entity | Alive/dead và defeat/revival |
| Skill Definition / Instance | L2 — Skill | Identity và instance contract |
| Skill Admission | L2 — Skill | SK06–SK10 availability evaluation |
| Skill Resource Costs | L2 — Skill | Cost contracts, sufficiency và cost outcomes |
| Concrete Cost Configuration | L3 | Resource IDs, amounts, cost tuning |
| Dynamic Cost Policies | L3 | Rank scaling, discounts, requirements và resource rules |
| Resource Bounds Source | L3 / caller | Live bounds được resolve từ authoritative state và canonical numerical contracts |
| Runtime Commit | L4 / caller | Áp dụng candidate snapshots vào authoritative gameplay state |
| Persistence / Concurrency | L4 | Storage, synchronization, locking và transaction authority |

**Không được chuyển numerical calculation từ Core sang Skill.**

**Không được chuyển Resource State ownership từ Entity sang Skill.**

## 2.4. Cost Configuration Belongs to L3

L3 sở hữu concrete values như:

```text

  manaCost = 25

  manaCost = 20

```

```text

```

Resource identifiers là opaque strings.

L2 contract phải hỗ trợ resource identifiers bất kỳ được Entity quản lý.

Không tự áp đặt mana là resource mặc định.

## 2.5. No Premature Cost Formula

v0.5.2 nhận **resolved, nonnegative, finite scalar costs**.

Không triển khai:

- Percentage of maximum resource cost.
- Rank-dependent cost formula.
- Attribute scaling.
- Cost reductions.
- Cost multipliers.
- Cost rounding engine.
- Randomized resource cost.
- Cost over time.
- Dynamic cost callbacks.

Nếu L3 cần numerical transformation, caller phải sử dụng canonical Core capability phù hợp trước khi truyền resolved cost.

Nếu Core thiếu capability bắt buộc, báo `BLOCKED_WITH_EVIDENCE`.

Không tự xây formula trong Skill.

## 2.6. Skill Is Not the Activation Transaction Owner

Cost evaluation và application là reusable operations riêng biệt.

Chúng không quyết định:

- Target có hợp lệ không.
- Cooldown đã ready chưa.
- Combat sẽ thành công không.
- Activation đã commit chưa.
- Có cần rollback gameplay transaction không.

L4/caller điều phối toàn bộ workflow.

v0.5.4 mới tích hợp resource costs vào Skill Activation sequence theo approved semantics.

# 5. SK11 — Resource Cost Contracts

## 5.1. Objective

Thiết kế reusable Resource Cost Contract cho Skill mà không lưu cost configuration trong Skill Instance.

## 5.2. Resource Cost Definition

Conceptual public contract:

```ts
export interface SkillResourceCost {
  readonly resourceId: string;
  readonly amount: number;
}
```

Ví dụ:

```ts
{
  resourceId: "mana",
  amount: 25
}
```

Đây là resolved cost của một attempt, không phải authoritative resource state.

Không thêm vào `SkillDefinition` identity-only contract của SK02.

Không thêm cost vào `SkillInstanceState`.

L3 có thể lưu skill content/configuration riêng, sau đó chuyển thành cost request khi cần.

## 5.3. Resource Identity

`resourceId` phải:

- Nonblank string.
- Exact caller value.
- Case-sensitive.
- No trimming.
- No normalization.
- No implicit mapping.

Ví dụ:

```text
mana
health
stamina
energy
custom-resource
```

L2 không tự quyết định resource nào có thể được dùng làm skill cost.

## 5.4. Cost Amount Validation

`amount` phải:

- Number.
- Finite.
- Nonnegative.

Accept:

```text
0
1
20
12.5
```

Reject:

```text
-1
NaN
Infinity
-Infinity
"20"
null
```

Không ép integer.

Không tự round.

Không tạo epsilon hoặc tolerance rule riêng.

`amount = 0` là valid zero-cost entry.

Free skill có thể sử dụng empty cost list.

## 5.5. Resource Bounds Contract

Current Entity Resource State chỉ chứa current values.

Minimum, maximum và above-maximum policy phải được caller cung cấp explicitly.

Conceptual:

```ts
export interface SkillResourceCostBounds {
  readonly resourceId: string;
  readonly minimum: number;
  readonly maximum: number;
  readonly currentAboveMaximum: "allow" | "reject";
}
```

Rules:

- `minimum` và `maximum` là finite numbers.
- `minimum <= maximum`.
- Không hardcode minimum = 0.
- Không tự lấy maximum từ Skill Definition.
- Không tự giả định maximum cố định.
- Không tạo stat recalculation trong Skill.

`currentAboveMaximum` là explicit caller-selected policy, không có default ngầm.

## 5.6. Cost Request Contract

Conceptual:

```ts
export interface SkillResourceCostRequest {
  readonly costs: readonly SkillResourceCost[];
  readonly bounds: readonly SkillResourceCostBounds[];
}
```

Requirements:

- Closed own-data records.
- Dense arrays.
- No inherited entries.
- No accessor-based entries.
- No symbol/unknown fields.
- Unique resource IDs trong `costs`.
- Unique resource IDs trong `bounds`.
- Mỗi cost phải có đúng một matching bounds entry.
- Không có missing hoặc extra bounds entries.
- Exact matching, không normalize resource names.

Cost order là caller-supplied order.

Không tự sort.

Không tự aggregate duplicate costs.

Duplicate resource IDs là malformed input:

```text
TypeError
```

Không silently sum duplicate amounts.

## 5.7. No Persistent Cost State

Không tạo:

```text
SkillCostState
SkillCostRegistry
SkillCostCache
SkillCostStore
```

Cost request chỉ là explicit input của evaluation/application.

## 5.8. Validation & Immutability

Mọi inputs phải được validate và capture trước khi tính outcome.

Không invoke getters.

Không mutate caller data.

Nếu cần return captured cost data, phải detached/frozen.

Không freeze original caller-owned objects.

# 6. SK12 — Resource Sufficiency

## 6.1. Objective

Đánh giá actor có đủ tài nguyên thanh toán **toàn bộ yêu cầu** hay không.

Không chấp nhận partial payment.

## 6.2. Canonical Resource Source

Reuse:

```ts
getEntityResourceCurrent()
transitionEntityResource()
```

Không tự đọc trực tiếp `resources.current[resourceId]` để thay thế canonical Entity validation.

Entity sở hữu Resource State.

Không viết second Resource State validator hoặc second Resource Transition Calculator trong Skill.

## 6.3. Admission Precondition

Cost evaluation chỉ được chạy sau successful Skill-stage admission.

Existing approved contract từ v0.5.1:

```ts
SkillAdmissionResult
```

Required:

```text
status = admitted
reason = none
```

Nếu supplied admission là rejected:

```text
TypeError
```

vì operation được gọi sai thứ tự stage.

Không tự gọi lại Skill Admission.

Không tự kiểm tra lại rank/ownership/actor life.

Không xem một structurally valid admission receipt là trusted authorization token.

## 6.4. Entity Identity Consistency

Required:

```text
admission.actorEntityId
  ==
resources.entityId
```

Nếu mismatch:

```text
TypeError
```

Không cho phép tiêu hao tài nguyên của actor khác.

Không silently rebind Resource State.

## 6.5. Sufficiency Through Canonical Transition

Entity transition:

```ts
transitionEntityResource(
  resources,
  resourceId,
  {
    maximum,
    amount,
    operation: "decrease",
    rule: {
      minimum,
      currentAboveMaximum,
      allowIncreaseFromMinimum: false
    }
  }
)
```

`allowIncreaseFromMinimum` không tham gia decrease semantics trong pinned Core; không đưa nó thành một Skill-specific policy mới.

**Core/Entity phải thực hiện toàn bộ resource arithmetic.**

Skill chỉ được đánh giá canonical transition result.

Full payment khi:

```text
transition.applied === requested amount
```

`transition.applied` là authoritative magnitude do Core trả về.

Nếu Core chỉ applied nhỏ hơn requested:

```text
insufficient_resource
```

Không chấp nhận một phần.

Không tự tính `current - minimum` để thay thế Core transition.

Không tự clamp amount.

## 6.6. Important Core Semantics

Actual pinned Core sử dụng bounded resource transitions.

Ví dụ:

```text
Current = 30
Minimum = 10
Maximum = 100
Requested cost = 25
```

Canonical Core result:

```text
After = 10
Applied = 20
```

Cost yêu cầu 25 nhưng chỉ applied 20.

Expected Skill outcome:

```text
rejected
insufficient_resource
```

Original Resource State giữ nguyên.

Không trả candidate state đã bị trừ 20.

## 6.7. Exact Numerical Semantics

Không sử dụng:

- Epsilon tự chọn.
- Approximate equality.
- Automatic rounding.
- Implicit decimal precision.
- Floating-point workaround.

Full-payment decision dựa trên actual canonical `applied` và requested value.

Nếu game yêu cầu fixed precision hoặc numeric normalization, phải dùng contract phù hợp được approved ở Core/L3.

Không tự điều chỉnh số liệu để biến insufficient thành sufficient.

## 6.8. Missing Resource

Nếu resource ID hợp lệ nhưng không tồn tại trong Entity Resource State:

```text
resource_not_found
```

Đây là valid cost rejection.

Phải phân biệt:

```text
Unknown resource
```

và:

```text
Known resource with insufficient current value
```

Malformed Entity Resource State vẫn phải throw `TypeError` theo canonical Entity validation.

Không tự initialize missing resource.

## 6.9. Zero Cost

`amount = 0`:

- Không thực hiện numerical decrease transition.
- Không làm thay đổi resource current.
- Không normalize over-maximum resource ngầm.
- Vẫn yêu cầu resource ID tồn tại nếu cost entry đã khai báo resource đó.

Empty `costs` và empty `bounds`:

- Valid free cost request.
- Sufficiency PASS.
- No resource operations.
- No side effects.

Không tự thêm mana resource mặc định cho free skills.

# 7. SK13 — Resource Cost Application

## 7.1. Objective

Tạo immutable candidate Resource State thông qua canonical Entity transitions.

Không trực tiếp mutate caller-owned resource state.

## 7.2. Proposed Public Operations

```ts
evaluateSkillResourceCosts(
  admission: SkillAdmissionResult,
  resources: EntityResourceState,
  request: SkillResourceCostRequest
): SkillResourceCostAssessment
```

```ts
applySkillResourceCosts(
  admission: SkillAdmissionResult,
  resources: EntityResourceState,
  request: SkillResourceCostRequest
): SkillResourceCostApplicationResult
```

Hai operations dùng chung một private resolver khi cần.

Không viết hai thuật toán đánh giá costs khác nhau.

### Evaluation

- Validate inputs.
- Kiểm tra stage/identity.
- Thử canonical transitions trên local immutable snapshots.
- Đánh giá sufficiency.
- Trả assessment.
- Không xuất updated state.

### Application

- Validate inputs.
- Kiểm tra stage/identity.
- Resolve lại costs trên input Resource State được cung cấp ở invocation hiện tại.
- Trả final candidate state chỉ khi toàn bộ costs thành công.
- Không mutate original state.

Không dựa vào một assessment cũ như trusted payment approval.

## 7.3. Single Resource Application

Input:

```text
Actor = player-1
Admission = admitted

Resources:
  mana = 100

Cost:
  mana = 25

Bounds:
  minimum = 0
  maximum = 100
  currentAboveMaximum = reject
```

Expected:

```text
status = applied

Before Mana = 100
Requested = 25
Applied = 25
After Mana = 75
```

Returned Resource State:

```ts
{
  entityId: "player-1",
  current: {
    mana: 75
  }
}
```

Original Resource State:

```text
mana = 100
```

Không bị mutate.

## 7.4. Resource Bounds

Phải truyền exact caller-supplied bounds tới canonical Entity API.

Không tự:

- Clamp current trước.
- Normalize bounds.
- Adjust maximum.
- Change above-maximum policy.
- Use default minimum 0.

Nếu Entity/Core reject inconsistent resource conditions, không che failure bằng fallback.

## 7.5. Above-Maximum Behavior

Pinned Core có thể tạo transition mà:

```text
before - after != applied
```

Ví dụ với policy `allow`:

```text
Current = 140
Maximum = 100
Minimum = 0
Cost = 20
```

Canonical decrease result có thể là:

```text
After = 100
Applied = 20
```

Không được tự suy ra `applied = 40` từ before/after.

Skill phải preserve Core diagnostics.

L3/caller chịu trách nhiệm chọn policy:

```text
allow
```

hoặc:

```text
reject
```

Không tự âm thầm đổi policy.

Nếu application sử dụng `allow`, output phải phản ánh cả canonical resulting state và authoritative applied amount.

Nếu `reject` và Core từ chối above-maximum current, giữ nguyên failure semantics.

## 7.6. No Direct Resource Math

Không viết:

```ts
const nextMana = currentMana - manaCost;
```

Không tự thực hiện:

```ts
const after = Math.max(minimum, current - amount);
```

Không duplicate:

```text
normalizeResource()
calculateResourceTransition()
calculateResourceRegeneration()
```

Chỉ sử dụng canonical Entity operations.

## 7.7. No Life-State Mutation

Skill costs có thể sử dụng resource ID như `health` nếu L3 cung cấp.

Tuy nhiên v0.5.2 không được tự:

- Resolve death.
- Revive Entity.
- Modify Life State.
- Emit death event.
- Treat resource minimum as automatic defeat.

Nếu cost làm HP chạm minimum:

- Preserve canonical resource result.
- Preserve `reachedMinimum` diagnostic nếu có.
- Không tuyên bố Life State đã cập nhật.
- Caller/L4 phải điều phối canonical Entity Life transition nếu gameplay yêu cầu.

Cost application chỉ tạo resource candidate state; chưa phải authoritative activation commit.

# 8. SK14 — Multi-Resource Costs & Outcomes

## 8.1. Objective

Hỗ trợ thanh toán nhiều loại tài nguyên trong một Skill Cost Request, nhưng không tạo partial payment.

Ví dụ:

```text
Skill:
  Special Attack

Costs:
  mana = 30
  stamina = 20
```

Không giới hạn chỉ một resource.

## 8.2. Multi-Resource Success

Initial state:

```text
mana = 80
stamina = 40
```

Costs:

```text
mana = 30
stamina = 20
```

Bounds:

```text
minimum = 0
maximum mana = 100
maximum stamina = 50
currentAboveMaximum = reject
```

Expected:

```text
status = applied

mana:
  before = 80
  applied = 30
  after = 50

stamina:
  before = 40
  applied = 20
  after = 20
```

Final candidate state:

```ts
{
  entityId: "player-1",
  current: {
    mana: 50,
    stamina: 20
  }
}
```

Original state vẫn:

```text
mana = 80
stamina = 40
```

## 8.3. Multi-Resource Failure

Initial state:

```text
mana = 80
stamina = 10
```

Costs:

```text
mana = 30
stamina = 20
```

Expected:

```text
status = rejected
reason = insufficient_resource
rejectedResourceId = stamina
```

**Không trả partial candidate state với mana = 50.**

Original state vẫn:

```text
mana = 80
stamina = 10
```

Không gọi refund để hoàn tác mana.

Không tạo rollback engine.

Không commit kết quả của resource đầu tiên trước khi các resource còn lại được kiểm tra.

## 8.4. All-or-Nothing Candidate Semantics

Implementation được phép tạo private provisional snapshots trong quá trình resolve.

Những snapshots này:

- Chỉ tồn tại cục bộ trong operation.
- Không được publish.
- Không được lưu global.
- Không được expose khi rejected.
- Không mutate original state.

Chỉ khi mọi resource đều đủ cost:

```text
Return final candidate state.
```

Nếu một resource không đủ:

```text
Return rejected outcome.
No updated state.
```

Đây là all-or-nothing của **pure candidate result**, không phải distributed transaction guarantee.

Caller vẫn là owner của authoritative commit.

## 8.5. Deterministic Cost Ordering

Cost items được xử lý theo original caller-supplied order.

Nếu nhiều resource không đủ, báo resource thất bại đầu tiên theo cost order.

Ví dụ:

```text
costs:
  mana
  stamina
  energy
```

Cả stamina và energy đều insufficient.

Expected:

```text
rejectedResourceId = stamina
```

Không phụ thuộc vào object key enumeration, hash order hoặc runtime scheduler.

Phải validate toàn bộ request trước khi kết luận gameplay rejection.

Không dừng validation để che malformed entries nằm sau một insufficient cost.

## 8.6. Proposed Assessment Contract

Conceptual:

```ts
export type SkillResourceCostStatus =
  | "payable"
  | "rejected";

export type SkillResourceCostRejectionReason =
  | "none"
  | "resource_not_found"
  | "insufficient_resource";

export interface SkillResourceCostAssessment {
  readonly instanceId: string;
  readonly skillId: string;
  readonly entityId: string;

  readonly status: SkillResourceCostStatus;
  readonly reason: SkillResourceCostRejectionReason;

  readonly rejectedResourceId: string | null;
}
```

Semantics:

- `payable/none` — toàn bộ costs đủ.
- `rejected/resource_not_found` — required resource không tồn tại.
- `rejected/insufficient_resource` — canonical applied amount không đáp ứng cost.

Không thêm reasons speculative:

```text
cooldown_active
target_invalid
actor_dead
cast_interrupted
combat_failed
```

Những điều kiện này không thuộc Resource Cost stage.

## 8.7. Application Result Contract

Conceptual discriminated union:

```ts
export type SkillResourceCostApplicationResult =
  | {
      readonly status: "applied";
      readonly reason: "none";
      readonly assessment: SkillResourceCostAssessment;
      readonly state: EntityResourceState;
      readonly transitions: readonly EntityResourceTransitionResult[];
    }
  | {
      readonly status: "rejected";
      readonly reason:
        | "resource_not_found"
        | "insufficient_resource";
      readonly assessment: SkillResourceCostAssessment;
      readonly state: null;
      readonly transitions: readonly [];
    };
```

Agent có thể dùng canonical transition diagnostics trong success result nhưng không được tái tạo numerical values bằng công thức riêng.

Nếu dùng `EntityResourceTransitionResult`, không được để từng nested interim state trở thành authoritative application result. Nên ưu tiên một minimal immutable per-resource receipt chứa canonical `transition` diagnostics, chỉ trả final `state` một lần.

Không tạo redundant state authorities.

Ở rejected result:

```text
state = null
transitions = []
```

Không expose provisional successful transitions.

Ở successful result:

- Final Entity Resource State immutable.
- Transition diagnostics frozen/detached.
- Cost order được giữ nguyên.
- Original input không bị mutate.
- Unaffected resource keys vẫn giữ nguyên.

Nếu cost list empty hoặc toàn zero cost, returned state phải có equivalent semantic values, không được thay đổi bất kỳ resource nào.

## 8.8. Assessment Is Not a Payment Reservation

`evaluateSkillResourceCosts()` không tạo reservation.

Sau evaluation, resource có thể đã thay đổi ở runtime.

Ví dụ:

```text
Assessment:
  payable

Another action:
  consumes mana

Later application:
  insufficient_resource
```

Expected:

- Application đánh giá lại current snapshot.
- Return rejected nếu không còn đủ.
- Không tin assessment cũ.

Không tạo:

```text
ResourceReservation
PaymentLock
TransactionToken
CostCommitQueue
```

Các concurrency guarantees thuộc L4/caller.

## 8.9. No Activation Commit

Một successful cost application chỉ có nghĩa:

```text
Resource candidate transition successfully resolved.
```

Không có nghĩa:

```text
Skill activated.
Skill executed.
Cooldown started.
Combat resolved.
```

v0.5.4 mới xác định cách phối hợp các stages.

# 9. Validation & Failure Contract

## 9.1. Malformed Input

Throw `TypeError` cho:

- Missing fields.
- Unknown fields.
- Symbol keys.
- Accessor/getter fields.
- Inherited required properties.
- Sparse arrays.
- Arrays with extra properties.
- Duplicate cost resource IDs.
- Duplicate bounds resource IDs.
- Missing matching bounds.
- Extra unmatched bounds.
- Invalid resource IDs.
- Negative amounts.
- Nonfinite amounts.
- Invalid minimum/maximum.
- Inverted bounds.
- Unsupported above-maximum policy.
- Admission/Resource Entity ID mismatch.
- Rejected admission supplied to payment operation.
- Malformed canonical Resource State.

Không tự coerce.

Không silently normalize.

## 9.2. Legitimate Gameplay Rejection

Trả structured rejection cho:

```text
resource_not_found
insufficient_resource
```

Không throw exception cho normal insufficient-resource case.

## 9.3. Core/Entity Failure Propagation

Nếu canonical Entity/Core reject hoặc throw do invalid state/policy ngoài ordinary insufficiency:

- Propagate failure.
- Không fallback sang custom calculation.
- Không biến tất cả exceptions thành `insufficient_resource`.
- Không tạo partial result.
- Không commit candidate state.

## 9.4. Full Validation Before Outcome

Phải validate tất cả cost entries/bounds trước khi kết luận gameplay rejection.

Ví dụ:

```text
First resource:
  insufficient

Second cost:
  amount = NaN
```

Expected:

```text
TypeError
```

Không được trả `insufficient_resource` và bỏ qua malformed cost phía sau.

## 9.5. Immutable Output

Assessment/application results phải:

- Detached.
- Frozen.
- No mutable aliases.
- No internal mutable references.
- Deterministic.
- No caller input mutation.

Không freeze original caller-owned input records như side effect.
