## 1. Objective

Implement **Encounter Creation & Activation**, the controlled handoff from a **structurally prepared** Encounter to an **active** engagement. Use only the Encounter Foundation approved in v0.8.0. Do **not** spawn entities, select or execute Combat/Skill/AI actions, create a World runtime, or decide victory.

| Feature | Capability | Required result |
|---|---|---|
| **EN06** | Encounter Initialization | Compose an existing prepared Encounter with L3 activation policy and explicit L4 facts; **reuse v0.8.0 creation** |
| **EN07** | Initial Roster Validation | Revalidate the complete structural roster and caller-supplied per-participant readiness/Life facts |
| **EN08** | Activation Admission | Deterministically determine whether the prepared Encounter is ready under L3 rules |
| **EN09** | Lifecycle Start Transition | Return an immutable `prepared → active` candidate **only if admission passes** |
| **EN10** | Activation Outcomes | Distinguish admitted/rejected/activated with exact, stable reasons, no side effects |

### Expected consumer flow

```text
L4: Create canonical Player/Monster Entities (and physically spawn if applicable)
                 ↓
L2 Encounter v0.8.0: createEncounterState(...) → prepared
                 ↓
L3: Supply activation policy (counts, required sides, permitted Life statuses)
                 ↓
L4: Supply current roster-aligned Entity Life and World-ready observations
                 ↓
L2: evaluateEncounterActivationAdmission(...) → admitted | rejected
                 ↓
L2: activateEncounter(...) → active state candidate | rejected
                 ↓
L4: Compare against current authoritative state/World, then commit or reject
```

**An admitted assessment is not an execution permit, a spawn receipt or a durable transaction.** The transition function must independently validate the original state, policy and observations, rather than trust a caller-created admission object.

**EN06 does not add a second encounter creation API:** `createEncounterState(...)` already belongs to EN03 and owns the initial roster. EN06 verifies its correct composition with activation. A redundant `EncounterBuilder`, `EncounterManager` or second roster storage is forbidden.

## 4. L1 / L2 / L3 / L4 ownership and dependency boundary

### L1 — RPG Core Kernel

Only canonical numerical calculations. v0.8.1 does not invoke Core and adds no numerical formula. No Core or Legacy API edits.

### L2 — Encounter (this task)

Owns **activation policy input contracts**, roster/readiness validation, pure deterministic activation admission, and frozen `active` state candidate. This does **not** grant Combat or World authority.

### L2 — Entity (canonical owner)

Owns `Entity.id`, collection membership, `EntityLifeState` (`alive`/`dead`), resource and Life transitions. Encounter reads only snapshots/facts; no HP or Life mutation. Do not create a parallel life owner.

### Other L2 modules

Combat, Skill, Effect and Actor AI remain canonical owners of their own actions, effects, decisions and lifecycle. None are directly imported by Encounter. There is no Encounter-specific CombatSession and no reverse dependency.

### L3 — Game-specific rules

Supplies `requiredOccupiedSideIds`, minimum roster size, minimum occupied sides, permitted Life statuses and whether actual World readiness is required. **No fixed mandatory two-side rule**: one-side objective/survival engagements and two-side PvE/PvP are configured differently.

### L4 — Application / World

Owns physical spawn, current Entity Life, truth/freshness of readiness facts, availability of World participants, current Encounter registry, authoritative controller/mode, transaction/commit and error recovery. L4 must verify no intervening state/World changes before committing an `active` candidate. A caller-provided `worldReady: true` is an observation, **not** a cryptographic or canonical spawn certificate.

### Exact module graph

```text
entity      → []
progression → [entity]
combat      → [entity]
skill       → [entity]
effect      → [entity]
actor-ai    → [entity]
encounter   → [entity]
```

**Forbidden** `encounter → combat/skill/effect/actor-ai`, `combat → encounter`, `actor-ai → encounter`, `encounter → world`, global EncounterManager/WorldEngine/transaction layer, framework storage or event dispatcher.

## 5. EN06 — Encounter Initialization (reuse prepared state)

**Objective:** Establish the lawful inputs to activation without creating an alternate encounter initialization function.

- Use v0.8.0 `createEncounterDefinitionReference` and `createEncounterState` to construct one structural `prepared` Encounter.
- Reuse the caller-supplied `sides` and `participants` *as validated by the Foundation*. Never produce duplicate side or participant lists.
- L4 must supply EntityCollection containing each referenced Entity. The Foundation `validateEncounterState` revalidates this membership at evaluation time.
- `prepared` can legitimately contain **zero** sides/participants or dead participants. EN08 determines readiness; **never** treat structural validity as activation admission.
- L4 World spawn/setup is performed outside L2 when the game needs it. EN06 must not spawn or add Entities to a collection.
- A prepared Encounter can reuse an L3 `definitionId` with a new `encounterId`; L4 enforces global encounter identity uniqueness and one-current-encounter rules when relevant.
- Caller is free to configure PvE, multi-side PvP, NPC, Pet, Summon, custom entities, or a one-sided objective-based Encounter using the **same** core contracts.

**Example**:

```text
Encounter: forest-fight-001 / definition forest-wolves
Sides: party, enemies
Participants: player-001→party, monster-001→enemies
Status: prepared
World: two referenced entities already spawned by L4 (not L2)
```

This feature is **composition evidence and initialization validation**; no new `createEncounterInstance`/`initializeEncounterEngine`/`EncounterBuilder` is authorized.

## 6. EN07 — Initial Roster Validation & Readiness Observation

### 6.1. Canonical Life input

Reuse existing `EntityLifeState`, not a new Encounter Life state. Caller supplies a **current** Life snapshot for each participant it can observe.

Proposed:

```ts
export interface EncounterParticipantActivationFact {
  readonly entityId: string;
  readonly life: EntityLifeState;
  readonly worldReady: boolean;
}

export interface EncounterActivationObservation {
  readonly encounterId: string;
  readonly participants: readonly EncounterParticipantActivationFact[];
}
```

`worldReady` is a caller-provided boolean (e.g., physically spawned and available in a game that needs that). **L2 does not look up, spawn, position, pathfind or query World.** If World readiness is irrelevant to a headless/turn-based Encounter, L3 sets the corresponding policy flag to false; facts still explicitly carry the boolean.

### 6.2. Fact validation

- `entityId` must be an exact nonblank Entity ID.
- `life` must follow the accepted closed canonical `EntityLifeState` shape and valid `EntityLifeStatus` values; `life.entityId === fact.entityId` exactly.
- `worldReady` must be boolean, never truthy/falsy coercion.
- No duplicate `entityId` facts.
- `observation.encounterId` binds to the assessed Encounter.
- Unrelated/foreign facts referring to no participant are malformed (`TypeError`), not covert new Join requests.
- **Missing facts are valid as an incomplete observation** but **must reject admission** with `participant_fact_missing` for the **first missing participant in `state.participants` order**; no optimistic readiness.
- Source array iteration/order must not affect the verdict: facts map by exact ID; missing/eligibility checks traverse the accepted Encounter's participant order.
- Do not read `Date.now()` or cache caller facts; freshness and trust are L4 responsibilities.
- A structurally valid `dead` Life fact may be provided. Policy decides if that Life status is activation-eligible. Life is not changed by evaluation.

Proposed factory:

```ts
export function createEncounterActivationObservation(
  input: EncounterActivationObservation,
): EncounterActivationObservation;
```

Return deeply frozen and detached arrays, nested fact records and captured Life snapshots; source arrays and objects remain untouched and unfrozen.

### 6.3. Roster validation

Admission must **first** call or reuse canonical `validateEncounterState(state, entities)`; this rejects:

- Duplicate participant IDs, duplicate side IDs, participant→undeclared side.
- Missing Entity reference in current canonical EntityCollection.
- Malformed/forged state fields, array shape or enum value.

EN07 does not implement live Join/Leave, switch side, Entity creation or global cross-Encounter exclusivity. A roster can be changed later only by separately accepted EN11–EN15 and authoritative L4 commit.

### 6.4. Structural vs domain invalidity

Use **`TypeError`** for malformed schemas/identity binding/extra facts/prototype/getters/invalid Life fields. Return an **admission rejection result** for well-formed but not-ready situations: insufficient roster size, required side empty, missing readiness fact, Life disallowed or World not ready.

Do not conflate absent Entity membership with a `worldReady:false` fact: canonical membership failure remains a Foundation structural error; physical World availability is a separate L4-supplied observation.

## 7. EN08 — Activation Policy & Admission

### 7.1. Proposed public policy

```ts
export interface EncounterActivationPolicy {
  readonly requiredOccupiedSideIds: readonly string[];
  readonly minimumParticipants: number;
  readonly minimumOccupiedSides: number;
  readonly allowedLifeStatuses: readonly EntityLifeStatus[];
  readonly requireWorldReady: boolean;
}
```

Policy properties are **all required**. There are no implicit defaults, hidden presets or global rule registry.

- `requiredOccupiedSideIds` — ordered distinct opaque Side IDs that must **each** have at least one member. Empty list is permitted.
- `minimumParticipants` — a **positive safe integer** (`>=1`), evaluated against actual participant count.
- `minimumOccupiedSides` — a **positive safe integer** (`>=1`), evaluated against **distinct sides with at least one participant**, not number of declared sides.
- `allowedLifeStatuses` — nonempty, unique array of canonical `EntityLifeStatus` values (`alive`, `dead`). L3 normally supplies `['alive']` for real combat. No hardcoded Monster/Player case.
- `requireWorldReady` — explicit boolean. If true, any participant with `worldReady:false` blocks activation. If false, L2 does not interpret `worldReady` as a gate.

Counts are policy-driven; L2 does **not** mandate `2` occupied sides. A one-sided survival/training/escort objective may validly configure `minimumOccupiedSides:1` and `minimumParticipants:1`.

Proposed factory:

```ts
export function createEncounterActivationPolicy(
  input: EncounterActivationPolicy,
): EncounterActivationPolicy;
```

Return detached, fully frozen policy. Reject duplicate/invalid required sides or allowed life statuses, NaN, infinity, fractional/negative/zero/unsafe counts, unknown properties, accessors and sparse arrays.

A policy asking for more occupied sides/participants than currently exist is **valid policy** and produces **rejection**, not a hidden policy rewrite. An `requiredOccupiedSideId` absent from the current roster's `state.sides` is a **readiness failure** (`required_side_unoccupied`), not evidence of a new side being created. Policy ID typo does not silently get corrected.

### 7.2. Admission result

Proposed:

```ts
export type EncounterActivationRejectionReason =
  | 'not_prepared'
  | 'insufficient_participants'
  | 'insufficient_occupied_sides'
  | 'required_side_unoccupied'
  | 'participant_fact_missing'
  | 'participant_life_not_allowed'
  | 'participant_world_not_ready';

export type EncounterActivationAdmissionResult =
  | {
      readonly status: 'admitted';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly sideId: null;
      readonly entityId: null;
    }
  | {
      readonly status: 'rejected';
      readonly reason: EncounterActivationRejectionReason;
      readonly encounterId: string;
      readonly sideId: string | null;
      readonly entityId: string | null;
    };
```

Diagnostics must have **exactly** the fields above. For non-participant reasons set both IDs to null, except `required_side_unoccupied` sets `sideId` to the first unmet ID in policy order. For participant-specific reasons `entityId` is the first offending participant in canonical roster order and `sideId` is that participant's canonical assigned side ID.

### 7.3. Proposed evaluator

```ts
export function evaluateEncounterActivationAdmission(
  state: EncounterState,
  entities: EntityCollection,
  policy: EncounterActivationPolicy,
  observation: EncounterActivationObservation,
): EncounterActivationAdmissionResult;
```

Pure, synchronous and deterministic. It does **not** modify status, call Combat or return a committed encounter.

### 7.4. Exact validation and rejection precedence

**Phase A — validate all structural inputs first, regardless of current state**:

1. `validateEncounterState(state, entities)` — canonical Entity membership and v0.8.0 foundation invariants.
2. Capture/validate policy fully.
3. Capture/validate observation fully.
4. Require matching `observation.encounterId === state.encounterId`.
5. Reject foreign participant facts not listed in `state.participants`, plus duplicate facts or mismatched Life identity, via `TypeError`.
6. Only after structural validation: execute domain admission checks.

**Phase B — first matching rejection wins**:

1. State not `prepared` → `not_prepared`.
2. Participant count below policy minimum → `insufficient_participants`.
3. Distinct occupied side count below minimum → `insufficient_occupied_sides`.
4. First required side with zero participants → `required_side_unoccupied`.
5. First canonical roster participant without observation fact → `participant_fact_missing`.
6. First roster participant whose Life status is not permitted → `participant_life_not_allowed`.
7. First roster participant `worldReady:false` **when** policy requires it → `participant_world_not_ready`.
8. Otherwise `admitted` with `reason:'none'`.

All participant-specific stages use the existing `state.participants` ordering; **never** sort participants or derive order from observation array/Map iteration. A valid dead Entity structurally present in v0.8.0 can produce `participant_life_not_allowed` if policy is `['alive']`.

The evaluator is **not an execution authorization**: L4 must re-sample current Life/World and verify current Encounter/Entity revision before actual commit/dispatch. No implicit time/revision is introduced at L2.

## 8. EN09 — Explicit lifecycle start transition

### 8.1. Proposed transition result

```ts
export type EncounterActivationTransitionResult =
  | {
      readonly status: 'activated';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly state: EncounterState;
    }
  | {
      readonly status: 'rejected';
      readonly reason: EncounterActivationRejectionReason;
      readonly encounterId: string;
      readonly state: null;
    };
```

### 8.2. Proposed transition API

```ts
export function activateEncounter(
  state: EncounterState,
  entities: EntityCollection,
  policy: EncounterActivationPolicy,
  observation: EncounterActivationObservation,
): EncounterActivationTransitionResult;
```

Requirements:

1. Must internally apply the **same structural and admission checks** as EN08, not trust a possibly forged/stale caller-created `EncounterActivationAdmissionResult`.
2. If admission rejects, return `status:'rejected'`, the **exact same** reason and encounter ID, and `state:null`. Do not emit partial/optimistic active state.
3. If admitted, return a **new detached/frozen** `EncounterState` candidate with `status:'active'` and the *exact* same `encounterId`, `definitionId`, `sides`, `participants` semantics.
4. Only `status` may differ from validated input state; do not add `startedAt`, outcome, spawn IDs, revisions or execution receipts.
5. Never mutate `state`, EntityCollection, canonical Life facts or caller policy/observation.
6. Transition on `active`, `resolved`, `closed`, `cancelled` → rejected `not_prepared`, with `state:null`; **no reopen**.
7. Replaying an already active state is rejected, not silently accepted as idempotent success. L4 alone may define replay/idempotency around its authoritative store.
8. Invoking two evaluations from the *same prepared snapshot* may yield identical **candidates**. This is not permission to commit twice; L4 uses current-state/version compare-and-swap or equivalent atomic check.
9. Do not auto-dispatch Combat/Skill/Actor AI, start timers, publish messages, spawn, enter a World scene, initialize a turn order or emit rewards.

### 8.3. Canonical sample

```ts
const policy = createEncounterActivationPolicy({
  requiredOccupiedSideIds: ['party', 'enemies'],
  minimumParticipants: 2,
  minimumOccupiedSides: 2,
  allowedLifeStatuses: ['alive'],
  requireWorldReady: true,
});

const observation = createEncounterActivationObservation({
  encounterId: 'forest-fight-001',
  participants: [
    {entityId:'player-001', life:{entityId:'player-001', status:'alive'}, worldReady:true},
    {entityId:'monster-001', life:{entityId:'monster-001', status:'alive'}, worldReady:true},
  ],
});

const admission = evaluateEncounterActivationAdmission(prepared, entities, policy, observation);
// {status:'admitted', reason:'none', encounterId:'forest-fight-001', sideId:null, entityId:null}

const transition = activateEncounter(prepared, entities, policy, observation);
// {status:'activated', reason:'none', encounterId:'forest-fight-001', state:{...prepared,status:'active'}}
```

Sample is **illustrative until the accepted foundation type signatures are rechecked**. Use the actual accepted Entity Life data shape. No World-ready fact constitutes proof of spawning.

## 9. EN10 — Outcomes and failure semantics

| Input condition | API result | Required effect |
|---|---|---|
| Proper prepared roster and eligible facts/policy | `admitted` / `activated` | New immutable `active` **candidate** only |
| Status `active`, `resolved`, `closed`, `cancelled` | `rejected / not_prepared` | No next state |
| Empty prepared roster, minimumParticipants `>=1` | `rejected / insufficient_participants` | No auto-population |
| Declared two sides, occupants only on one, minimumOccupiedSides `2` | `rejected / insufficient_occupied_sides` | No fake opponent |
| Required occupied side missing occupants | `rejected / required_side_unoccupied` | No auto-spawn |
| Missing participant Life/readiness fact | `rejected / participant_fact_missing` | No optimistic defaults |
| Dead status with policy `['alive']` | `rejected / participant_life_not_allowed` | No revive/reset |
| World not ready when required | `rejected / participant_world_not_ready` | No spawn/movement |
| Wrong Encounter identity, malformed policy, invalid fact identity | `TypeError` | No mutation or result |
| Unknown canonical Entity in state | `TypeError` via foundation validation | No invented Entity |

### Explicit non-guarantees

A successful activation candidate does **not** mean:

- every Entity is still alive after the observation was captured;
- all Entities are physically spawned or even share a World shard;
- Combat admission, target relation, Skill resource/cooldown or AI controller checks have passed;
- a turn/realtime scheduler has begun;
- the candidate has been committed or is globally unique;
- victory conditions, wave objectives or rewards are satisfied.

L4 must separately enforce those constraints at its own boundaries.

## 11. Closed schemas, snapshot isolation and deterministic behavior

Follow the accepted Foundation's closed-record and array rules:

- Exactly expected own, string-named data keys; reject extra/missing/unknown/symbol/inherited/accessor properties, unexpected prototypes, arrays masquerading as records.
- Never invoke user getters/proxies to “repair” invalid records; avoid side-effectful enumeration beyond existing validated conventions.
- Dense proper arrays only; reject holes, inherited entries, extra props, symbol keys and malformed nested data.
- Exact nonblank identifiers; no normalization or implicit ID generation.
- Safe-integer counts; no rounding, NaN, infinity or unsafe precision.
- Reject duplicate required side IDs, duplicate allowed Life statuses and duplicate observation Entity IDs.
- Nested `EntityLifeState` must be safely captured/validated and entity IDs correlated with its containing fact.
- Validation must occur **before** status-specific early returns, including for `active`/`closed` inputs.
- Return newly detached/frozen policies, observations, admissions, transitions and nested `active` state candidates; inputs remain unchanged/unfrozen.
- Same state/EntityCollection/policy/observation → identical literal semantics across independent sessions.
- No `Date.now()`, `Math.random()`, timers, hidden global state, external I/O, auto-ID generation or implicit Foundational Clock/ID calls.

**No global one-time admission ledger.** v0.8.1 offers pure state candidates. Current-staleness and duplicate commit protection are authoritative L4 concerns; do not claim L2 exactly-once behavior.
