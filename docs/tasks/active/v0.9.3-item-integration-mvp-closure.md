## 4. IT12 — installed end-to-end acceptance flow

Run a **single readable, independently asserted fixture** with actual installed root ESM APIs:

```text
L3 test fixture: complete opaque Item Definition input
      ↓
createItemDefinitionReference → createItemDefinition
      ↓
createItemInstance (explicit caller instanceId + own properties)
      ↓
validateItemInstance and inspect present/missing/null keys
      ↓
setItemInstanceProperty(..., {eligible:true})
      ↓
accepted immutable full instance candidate → validateItemInstance
      ↓
replaceItemInstanceProperties(..., {eligible:true})
      ↓
new complete immutable candidate, omitted old properties absent
      ↓
validateItemStackPolicy → assessItemStackCompatibility
      ↓
read-only Inventory-like / Equipment-like consumer fixture
      ↓
record literal output: NO authoritative commit, NO quantity/slot/loot/reward state
```

Minimum additional assertions:

- Two different valid instance IDs with same definition and exactly equal instance properties can be compatible under `{stackable:true}`.
- Changing instance property in one operand refuses compatibility (`different_properties`); same ID refuses `same_instance`; definition metadata conflict refuses `definition_conflict` with correct priority; `stackable:false` refuses `not_stackable`.
- `getItemInstanceProperty` returns exact `{found:false}` for missing key even when definition has that key; explicit `null` is **present**.
- Property set/replacement preserve identity, never merge definition properties, never mutate/freeze caller input; rejected admission yields `candidate:null`.
- The consumer's *local* memory of whether it later accepts a candidate **is not** Item state. Do not mislabel a fixture variable assignment as a persisted, atomic L4 transaction.
- An Item Instance reference is not proof of global uniqueness, entitlement, ownership, currentness or capacity.

Write expected **literal structures by hand**. No source import, deep internal package import, duplicate Item implementation or using an Item function as the expected oracle.

## 5. IT13 — cross-system contract stress proof, no premature modules

### 5.1. Four explicit source/reader profiles

| Consumer | Test-local operation | Exact intended claim | NOT IMPLEMENTED |
| --- | --- | --- | --- |
| **Inventory-facing** | Accept typed `ItemDefinition`/`ItemInstanceState` and read `instanceId`,`definitionId`/properties; test-local entry may hold snapshot | Public Item shapes can be embedded/read without modifying them | No inventory add/remove/quantity/stack store/merge/transfer |
| **Equipment-facing** | Independently read category/rarity/properties through public types | Item has enough data to pass to future Equipment rules | No equip slots/stat projection/equip/unequip |
| **Loot-facing** | Call existing Item creation APIs from explicit fixture chosen as a loot-like source | Item creation is source-neutral and does not roll loot | No loot table/drop selection/world spawn |
| **Reward-facing** | Call the same Item creation APIs from a differently labeled fixture | No Reward-specific Item factory/field necessary | No reward eligibility/claim/grant/receipt |

The source label is **outside** the Item payload, never an Item field, catalog authority or gameplay permission. Don't add `sourceType`, `rewardId`, `lootContext`, `ownerId`, `equipped`, `location` to Item to satisfy these fixtures.

### 5.2. Three distinct L3 fixtures using one public API

- **Text RPG:** ordinary consumable and quest-like opaque definitions, simple instance properties.
- **RPG 2D:** weapon/armor-like opaque metadata, unique instance data, nested L3 values.
- **RPG 2.5D:** material/equipment-like opaque metadata, nested attributes/tags, explicit compatibility policy.

Each profile demonstrates definition creation, independent instance identity, property inspection/candidate, stack assessment where relevant and a read handoff; at least one invalid input with expected exact failure. **No conditional engine-specific production branch**, no UI/game scenes. Profiles may share one test-local driver; test expectations remain profile-specific and independently literal.

### 5.3. Follow-through semantics (no accidental completion claims)

| Claimed fact | Can Item prove? | Who must prove it later? |
| --- | --- | --- |
| Exact input/instance structural shape | **Yes** | Item validators |
| Changed property proposal is structurally valid | **Yes** | Item candidate operation |
| Two item payloads are structurally compatible | **Yes**, under explicit policy | Item assessment |
| Instance ID is globally unique or current | **No** | L4 / canonical storage state |
| Item can fit capacity or merge quantity | **No** | Inventory + L3/L4 |
| Item is equipped or applies modifier | **No** | Equipment + canonical Entity/Core owner |
| Item is dropped/earned/claimed | **No** | Loot/Reward + L4 |
| Candidate has been atomically committed | **No** | L4 transaction/application |
