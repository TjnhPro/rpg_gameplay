# 1. Objective

Mở rộng Combat System để kiểm tra **target của một Combat Action có hợp lệ theo caller-defined targeting policy hay không**.

Target Validation phải tách biệt với:

- Actor Admission.
- Attack Resolution.
- Damage Application.
- Skill Targeting.
- Effect Execution.

Triển khai:

| ID | Feature | Responsibility |
|---|---|---|
| CB11 | Target Existence & Identity | Xác nhận target tồn tại trong Entity Collection và state gắn đúng Entity ID |
| CB12 | Target Relation | Phân biệt self, ally, enemy và neutral |
| CB13 | Target Policy | Cấu hình explicit allowed relations và allowed life statuses |
| CB14 | Target Life Validation | Dùng canonical Entity Life State, không tạo Target Life Store |
| CB15 | Target Result & Verification | Immutable result, rejection reasons, deterministic evaluation, installed package |

## 1.1. Expected Outcome

Consumer có thể:

1. Tạo Combat Action Context bằng CB03.
2. Thực hiện Actor Admission bằng CB06–CB10.
3. Chỉ tiếp tục target validation sau khi actor đã được admitted.
4. Kiểm tra target existence.
5. Xác định self-target bằng Entity IDs.
6. Nhận caller-resolved ally/enemy/neutral relation.
7. Kiểm tra target relation theo explicit policy.
8. Kiểm tra target life status.
9. Nhận structured validation result.
10. Không thay đổi Entity, Combat hoặc Resource State.

## 1.2. Critical Boundary

**Target Validation là phép đánh giá, không phải Attack Execution.**

Một target được chấp nhận chưa có nghĩa:

- Actor vẫn eligible ở thời điểm commit.
- Target đang trong attack range.
- Skill có đủ mana.
- Skill cooldown đã hoàn tất.
- Attack hit.
- Damage được áp dụng.
- Target bị tiêu diệt.

Không tạo execution authorization token.

# 6. CB12 — Target Relation

## 6.1. Objective

Phân biệt các loại quan hệ giữa source và target để hỗ trợ:

- Basic Attack.
- Healing.
- Buff.
- Debuff.
- Friendly fire.
- PvP.
- PvE.
- Neutral entities.

Tuy nhiên, v0.4.2 chỉ thực hiện **relation evaluation**, không thực hiện những gameplay actions nói trên.

## 6.2. Relation Contract

Conceptual:

```ts id="8szoak"
export type CombatTargetRelation =
  | "self"
  | "ally"
  | "enemy"
  | "neutral";
```

`neutral` là quan hệ hợp lệ, không phải fallback của unknown relation.

Unknown relation phải reject.

## 6.3. Self Relation

Self xác định bằng:

```text id="p37e2y"
sourceEntityId === targetEntityId
```

Ví dụ:

```text id="4uv39d"
Source = player-1
Target = player-1
```

Actual relation:

`self`

Không cần faction/team lookup.

Nếu caller khai báo:

```text id="skj5di"
relation = enemy
```

trong khi source và target IDs bằng nhau:

Reject inconsistent relation bằng `TypeError`.

Không silently đổi enemy thành self.

## 6.4. Ally Relation

Ví dụ:

```text id="i151r6"
Source = player-1
Target = player-2

Caller relation = ally
```

Combat chấp nhận relation do caller cung cấp nếu structural identity hợp lệ.

Không suy luận ally từ:

- Cùng `Entity.kind`.
- Cùng Character Class.
- Cùng Entity Collection.
- Có cùng naming prefix.

Không tạo Team/Faction System.

## 6.5. Enemy Relation

Ví dụ:

```text id="hfhe9w"
Source = player-1
Target = monster-1

Caller relation = enemy
```

Relation hợp lệ.

Nhưng chưa đồng nghĩa target được phép attack.

Điều đó phụ thuộc Target Policy.

## 6.6. Neutral Relation

Ví dụ:

```text id="1uq1bs"
Source = player-1
Target = npc-1

Caller relation = neutral
```

Không tự coi neutral là enemy.

Không tự coi neutral là ally.

Nếu policy cho phép neutral target:

Validation có thể PASS.

Nếu không:

Return relation rejection.

## 6.7. Relation Consistency

Bắt buộc:

```text id="uf6q26"
same IDs
  → relation must be self

different IDs
  → relation cannot be self
```

Không cho caller khai báo:

```text id="k9c6ic"
player-1 vs monster-1 = self
```

Không cho caller khai báo:

```text id="1bmgya"
player-1 vs player-1 = enemy
```

Trong khi đó, ally/enemy/neutral của hai IDs khác nhau là caller-authoritative input.

Combat không thể xác minh sự thật về faction nếu không có Faction State; không được claim đã xác minh.

# 7. CB13 — Target Policy

## 7.1. Objective

Caller quyết định relation nào và life status nào được chấp nhận.

Không hardcode:

```text id="fai06s"
basic_attack -> enemy only
```

hoặc:

```text id="k9w2vh"
heal -> ally only
```

Những quyết định này thuộc caller/game rules.

## 7.2. Policy Contract

Conceptual:

```ts id="8vde1x"
export interface CombatTargetPolicy {
  readonly relation: CombatTargetRelation;

  readonly allowedRelations:
    readonly CombatTargetRelation[];

  readonly allowedLifeStatuses:
    readonly EntityLifeStatus[];
}
```

Trong đó:

- `relation`: resolved relation do caller cung cấp; Combat kiểm tra self consistency.
- `allowedRelations`: danh sách quan hệ được phép.
- `allowedLifeStatuses`: danh sách life statuses được phép.

Không có defaults.

Không callback.

Không implicit policy provider.

## 7.3. Basic Attack Policy Example

```ts id="gmlv6g"
{
  relation: "enemy",
  allowedRelations: ["enemy"],
  allowedLifeStatuses: ["alive"]
}
```

Ví dụ:

```text id="gspq8a"
player-1 → monster-1
```

Nếu monster tồn tại và alive:

Target Validation PASS.

Không tính hit/damage.

## 7.4. Friendly Target Example

```ts id="oyir25"
{
  relation: "ally",
  allowedRelations: ["self", "ally"],
  allowedLifeStatuses: ["alive"]
}
```

Có thể dùng cho healing/buff targeting sau này.

Không tự hồi HP.

Không tạo Effect instance.

## 7.5. Dead Target Example

Một game có thể cho phép nhắm vào target đã chết để thực hiện hành động đặc biệt.

```ts id="dsjxm7"
{
  relation: "ally",
  allowedRelations: ["ally"],
  allowedLifeStatuses: ["dead"]
}
```

Expected:

- Dead target được phép nếu policy explicit cho phép.
- Không revive tự động.
- Không thay đổi Life State.

**Không hardcode dead target luôn invalid.**

Đây là điểm quan trọng để Combat generic.

## 7.6. Relation Restrictions

Ví dụ:

```text id="su42ur"
Actual relation = ally
Allowed relations = [enemy]
```

Expected:

```text id="yf40zs"
status = rejected
reason = relation_not_allowed
```

Không gọi Skill restrictions.

Không xem đây là malformed policy.

## 7.7. Policy Validation

Bắt buộc:

- Exact supported relation literals.
- Arrays dense, own-data entries.
- No duplicate relations.
- No duplicate life statuses.
- No unknown array properties.
- No accessors/getters.
- No inherited fields.
- No unknown policy fields.
- Valid life status values.
- No implicit coercion.
- Immutable captured policy values.

Đề xuất `allowedRelations` và `allowedLifeStatuses` phải là nonempty arrays để tránh vô tình tạo deny-all policy.

Nếu caller cần deny-all, họ có thể từ chối ở Actor Admission bằng external eligibility hoặc không thực hiện target validation.

Không tạo new generic Condition Engine.

## 7.8. No Faction Authority

Combat Target Policy là dữ liệu đánh giá tại một operation.

Nó không phải:

- Faction Relationship Database.
- Team Membership Table.
- PvP Rule Engine.
- Aggro System.
- Reputation System.

Nếu tương lai nhiều modules cùng cần authoritative relation resolution, thiết kế optional Faction/Relationship extension riêng.

Không tạo extension ngay tại v0.4.2.

# 9. CB15 — Target Validation Result

## 9.1. Objective

Trả structured result để consumer biết:

- Target được chấp nhận hay bị từ chối.
- Lý do.
- Target identity.
- Actual relation.
- Actual life status.

Không chỉ trả boolean.

## 9.2. Result Types

Conceptual:

```ts id="99i7nv"
export type CombatTargetValidationStatus =
  | "accepted"
  | "rejected";

export type CombatTargetRejectionReason =
  | "none"
  | "target_not_found"
  | "relation_not_allowed"
  | "target_life_not_allowed";

export interface CombatTargetValidationResult {
  readonly context: CombatActionContext;
  readonly targetEntityId: string;

  readonly relation: CombatTargetRelation;
  readonly targetLifeStatus: EntityLifeStatus;

  readonly status: CombatTargetValidationStatus;
  readonly reason: CombatTargetRejectionReason;
}
```

Nếu actual public API conventions dùng `validated` thay vì `accepted`, chỉ được chọn một tên nhất quán cho target stage. Không dùng `admitted` để tránh nhầm với CB09 actor admission.

Không tạo generic union của Actor Admission Result và Target Validation Result.

## 9.3. Public Function

Đề xuất:

```ts id="p2l5wd"
evaluateCombatTargetValidation(
  admission: CombatAdmissionResult,
  entities: EntityCollection,
  targetLife: EntityLifeState,
  policy: CombatTargetPolicy
): CombatTargetValidationResult
```

Function phải:

- Validate supplied admission snapshot.
- Chỉ xử lý nếu admission status là `admitted`.
- Sử dụng canonical Combat Action Context.
- Không evaluate lại source life/eligibility.
- Kiểm tra target existence.
- Kiểm tra relation.
- Kiểm tra target life policy.
- Trả immutable result.

## 9.4. Actor Admission Precondition

Target Validation được gọi sau accepted CB09 admission.

Nếu:

```text id="r6ad3m"
admission.status = rejected
```

thì không thực hiện target evaluation.

Đối với direct API invocation với rejected admission, trả `TypeError` cho invalid stage precondition; caller phải xử lý actor rejection tại CB09.

Không tự đổi:

```text id="1i13ra"
source_dead
```

thành target rejection.

Không tự re-run Actor Admission.

## 9.5. Admission Receipt Boundary

`CombatAdmissionResult` không phải security credential hoặc durable execution permission.

Structural validation không chứng minh receipt xuất phát từ một trusted executor.

Caller chịu trách nhiệm:

- Sử dụng actual latest admission result.
- Không dùng stale Entity snapshots.
- Áp dụng action processing theo đúng thứ tự.

Không tạo:

- Admission Token Store.
- Cryptographic Receipt.
- Persistent transaction ledger.
- Global Action Authorization Manager.

Nếu strict structural validation không đủ bảo vệ current operation, báo limitation; không tự thêm trusted runtime infrastructure.

## 9.6. Successful Result

Ví dụ:

```text id="r8kx4z"
Action:
  player-1 → monster-1

Admission:
  admitted

Target:
  monster-1 exists
  relation = enemy
  status = alive

Policy:
  allowedRelations = [enemy]
  allowedLifeStatuses = [alive]
```

Expected:

```text id="pr7mdy"
status = accepted
reason = none

targetEntityId = monster-1
relation = enemy
targetLifeStatus = alive
```

Không damage.

Không HP changes.

## 9.7. Rejected Result

Wrong relation:

```text id="ueke9j"
status = rejected
reason = relation_not_allowed
```

Dead target not allowed:

```text id="8ozm28"
status = rejected
reason = target_life_not_allowed
```

Target missing:

```text id="nl1lj7"
status = rejected
reason = target_not_found
```

Không tự retry hoặc chọn target khác.

## 9.8. Deterministic Rejection Priority

Sau khi validate toàn bộ input contracts và identity consistency:

1. Target not found.
2. Relation not allowed.
3. Target life status not allowed.
4. Accepted.

Priority:

```text id="9rfs3m"
target_not_found
relation_not_allowed
target_life_not_allowed
none
```

Ví dụ:

```text id="tkqy44"
Target exists.
Relation = ally, not allowed.
Target dead, not allowed.
```

Expected:

`relation_not_allowed`

Malformed input phải reject trước gameplay result.

Không giấu invalid policy bằng `target_not_found`.

## 9.9. Immutable Results

Bắt buộc:

- Result frozen.
- Nested context frozen/detached.
- No mutable policy reference retained.
- Caller inputs unchanged.
- No global state changes.
- No event publication.

Nếu result chứa copied target/life information, chỉ chứa validated scalars.

Không tạo second authoritative Target State.

- Missing arrays.
- Empty allowed lists.
- Duplicate relations.
- Duplicate life statuses.
- Sparse arrays.
- Getter-based policy fields.
- Extra fields.
- Inherited fields.
- Wrong array element types.
- Invalid self-relation configuration.
