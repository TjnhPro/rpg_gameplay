## 1. Objective and exact EN26–EN30 inventory

Implement the **explicit, immutable and side-based terminal lifecycle** of one Encounter, from a **freshly justified** completion assessment to `resolved`, from `resolved` to `closed`, and by an independently authorized cancellation path to `cancelled`. Deliver **structural cleanup handoff data**, not World cleanup execution. This work must **preserve** v0.8.0's public five-field `EncounterState` shape and v0.8.4's separation between an advisory completion assessment and an authoritative terminal transition.

| ID | Capability | Acceptance boundary |
| --- | --- | --- |
| **EN26** | **Resolution Transition** | Freshly assess current `active` Encounter via accepted EN21–EN25 API; propose `active → resolved` only for `resolvable`, never on a stale/forged assessment. |
| **EN27** | **Outcome Recording** | Return a detached, immutable **side-based disposition record** correlated to the Encounter and selected rule. No new fields in `EncounterState`, no individual rewards. |
| **EN28** | **Encounter Close** | Explicit `resolved → closed`; validate correlated outcome record; no implicit close during resolution. |
| **EN29** | **Encounter Cancellation** | Explicit L3-permitted `prepared|active → cancelled` with opaque cancellation reason; cannot overwrite a resolved outcome. |
| **EN30** | **Cleanup Contract** | Post-terminal, pure snapshot/handoff for L4; never despawn an Entity, clear Effects, grant rewards or call external providers. |

**Representative normal success:**

```text
Encounter: forest-fight-001
State: active
Sides: party, enemies
Participants: player-001→party; monster-001→enemies
Fresh Entity Life: player alive, monster dead
Continuation: clear
L3 completion rule: kill-all-enemies (side_elimination)

resolveEncounter(...) → resolved candidate (same roster) +
  {kind:resolution, encounterId, definitionId, ruleId,
   outcome:{kind:victory,winnerSideIds:[party],defeatedSideIds:[enemies]}}
L4 checks original snapshot/current World + accepts state AND record together
closeEncounter(accepted resolved state, accepted record) → closed candidate
L4 commits closed state
createEncounterCleanupHandoff(accepted closed state, accepted record) →
  structural participant IDs only; L4 alone decides and performs any cleanup
```

A `resolvable` EN25 assessment is **not** a victory receipt. Producing an immutable candidate is **not** a commit. A `resolved` Encounter is **not yet** `closed`; `closed` and `cancelled` are terminal. Never conflate those distinctions.

## 4. Layer ownership and optional graph

**L1 RPG Core:** Stats, damage, mitigation, numerical/resource operations through canonical modules. Encounter performs none.

**L2 Entity:** The canonical identities, collections, resources and `EntityLifeState`. A resolved or cancelled Encounter does not set Life to dead/alive, clear HP, create/remove an Entity, or cause defeat/revival.

**L2 Encounter:** Pure validation, encounter membership references, explicit lifecycle transition candidates, side-based disposition record, cancellation metadata and structural cleanup handoff. One owner for Encounter.status, no second Encounter runtime/state store.

**L2 Combat/Skill/Effect/Actor AI:** Existing independent canonical gameplay owners. No direct dependency on Encounter (or Encounter on them); no change to their accepted input/output contracts.

**L3 Game Rules:** Completion policy, configured objectives and winner side IDs, cancellation-allowed statuses, cancellation reason meanings, dungeon/wave continuation and any downstream reward or respawn content. L3 policy has no runtime authority.

**L4 Application:** Current World, spawn/despawn, authoritative Encounter snapshot and revision, current Entity Life/objective/wave readiness, revalidation of source facts, atomic or transactional commitment of Encounter status + disposition, durable dedupe/event-outbox if an application needs it, cleanup execution, rewards through the proper future owner, persistence and turn/scheduler. This library provides **no durability/exactly-once guarantee**.

Preserve the graph:

```text
entity       → []
progression  → [entity]
combat       → [entity]
skill        → [entity]
effect       → [entity]
actor-ai     → [entity]
encounter    → [entity]
```

**Forbidden:** `encounter→combat/skill/effect/actor-ai/progression/world`, sibling reverse imports or cycles; Encounter numerical calculator, CombatSession clone, EncounterManager singleton, World cleanup service, background timer, unapproved runtime library. Test-local L4 composition can import the package root for all approved modules.

## 6. EN26 — Explicit active → resolved transition

### 6.1. Public API proposal

```ts
export type EncounterResolutionTransitionResult =
  | {
      readonly status: 'resolved';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly state: EncounterState;
      readonly disposition: EncounterDispositionRecord;
    }
  | {
      readonly status: 'rejected';
      readonly reason: EncounterCompletionPendingReason;
      readonly encounterId: string;
      readonly state: null;
      readonly disposition: null;
    };

export function resolveEncounter(
  state: EncounterState,
  entities: EntityCollection,
  policy: EncounterCompletionPolicy,
  observation: EncounterCompletionObservation,
): EncounterResolutionTransitionResult;
```

`EncounterCompletionPendingReason` is reused **unchanged** from v0.8.4; new rejection reasons are not manufactured just to make this milestone green. If the accepted v0.8.4 type differs, explicitly audit/match the actual public type and report a genuine contract conflict rather than guessing new fields.

### 6.2. Preconditions and evaluation procedure

1. Validate/detach the entire canonical `EncounterState` against `EntityCollection` (using accepted validator) and the entire completion policy and observation **before status short circuits**.
2. Verify policy's exact `definitionId` and observation's exact `encounterId` match state, and all referenced side/participant Life/objective facts are valid, using accepted EN25 evaluator.
3. **Invoke `evaluateEncounterCompletion` anew**; do not accept a pre-generated `EncounterCompletionAssessment` parameter or read cached “victory” from UI/World.
4. For `assessment.status:'pending'`, return rejected with precisely the EN25 reason and null candidates. Preserve current Encounter/Entity/AI/Combat/Skill/Effect values.
5. For `assessment.status:'resolvable'`, create a **new** five-field state snapshot with **only** `status:'resolved'` changed. Return a matching immutable disposition record containing the exact selected rule and outcome.
6. `resolveEncounter` never changes membership, actor Life, current combat state, timing, objectives, wave staging or L4 storage. It never calls a Clock or RNG.

Because v0.8.4 returns `pending / encounter_not_active` whenever state is not `active`, resolution is naturally active-only. This function **does not bypass** v0.8.4's precedence of `continuation_pending` and `participant_fact_missing` before evaluating rules.

### 6.3. Freshness, replay and authoritative commit

The *library* consumes explicit inputs deterministically and returns candidates. It cannot know if L4's observation is stale. L4 must re-read current Encounter membership/revision and Entity Life/objectives/continuation immediately prior to a **single authoritative commit**, then compare to the baseline used to prepare the candidate. Accept **state + disposition together** or accept neither. A concurrent leave/join/change-side, revival/death, next wave announcement, controller action or cancellation makes stale candidates invalid under L4 authority.

A second call with an unchanged `active` input can **reproduce** the same semantic candidate (pure function)—this is not a second accepted commit. A second call on an accepted `resolved` state returns `rejected / encounter_not_active`. L4 must prevent duplicated rewards or commit with its own revision/ledger; L2 does not generate transaction IDs or exactly-once receipts.

### 6.4. Examples

```text
ACTIVE + continuation clear + all Life facts + winning rule
 → resolved, reason none, state.status resolved, disposition.kind resolution
ACTIVE + continuation pending
 → rejected, reason continuation_pending, state/disposition null
ACTIVE + Life fact missing
 → rejected, reason participant_fact_missing, state/disposition null
ACTIVE + no matched rule
 → rejected, reason no_completion_condition_met
PREPARED / RESOLVED / CLOSED / CANCELLED
 → rejected, reason encounter_not_active (after full input validation)
```

## 7. EN27 — Side-based outcome/disposition recording

### 7.1. Why a separate record is mandatory

v0.8.0 freezes the shape of EncounterState to five public fields. v0.8.4 intentionally returns outcome *only in the assessment*. v0.8.5 must **not** break that accepted contract by inserting `outcome` into EncounterState. Instead return **one immutable companion** that L4 commits alongside the status transition.

```ts
export type EncounterDispositionRecord =
  | {
      readonly kind: 'resolution';
      readonly encounterId: string;
      readonly definitionId: string;
      readonly ruleId: string;
      readonly outcome: EncounterResolutionOutcome;
    }
  | {
      readonly kind: 'cancellation';
      readonly encounterId: string;
      readonly definitionId: string;
      readonly reasonId: string;
      readonly outcome: null;
    };
```

This is the **single companion type** for terminal result metadata. `EncounterState.status` remains the **sole** state/lifecycle authority; the record is not a second status store. `kind:'resolution'` records the same `EncounterResolutionOutcome` and EN25 selected rule; `kind:'cancellation'` records only explicit caller reason, never an invented draw/defeat. There is **no** new global record repository or record ID registry.

### 7.2. Invariants

- `encounterId` and `definitionId` preserve exact spelling/case/whitespace, and must match the relevant Encounter.
- A resolution's `ruleId` is exactly the accepted EN25 `ruleId`, not a generic “win” string.
- Resolution `outcome` is one of the already-approved side-based unions, with unique/disjoint ID lists, declared side references and frozen detached arrays. A draw has **exactly** empty winners/defeated lists.
- A cancellation record has `reasonId` supplied by L4 according to L3 policy, required nonblank and opaque; **no outcome** (`null`) and no fabricated winner or defeated sides.
- A record has exactly its discriminant-specific fields: never both `ruleId` and `reasonId`, never an optional mystery timestamp, never an embedded `EncounterState`/Entity/Reward/World object.
- Records are metadata/commit candidates. A caller could fabricate a structurally valid record. **L2 structural correlation does not authenticate provenance**. Only L4 can assert it retained the exact disposition from the accepted transition.
- A state transitioned to `resolved` **must be stored by L4 with the matching disposition in the same commit**. The output of `resolveEncounter` is not evidence this storage occurred.
- L4 likewise stores a `cancelled` state and its cancellation disposition together or neither.
- No record is silently altered when `resolved → closed`; the accepted same record travels with the Encounter through that transition.

### 7.3. No redundant per-actor or numerical owners

Never store member HP/Life/status snapshots, accumulated damage, Skill/Effect outcomes, individual winner flags, XP/loot/coins, reward-claimed status or permanent World state in this record. Future Reward and Persistence contracts consume **L4-accepted** Encounter records under their own gates, not any caller-supplied structure.

## 8. EN28 — Explicit resolved → closed

### 8.1. Public API proposal

```ts
export type EncounterCloseTransitionResult =
  | {
      readonly status: 'closed';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly state: EncounterState;
      readonly disposition: EncounterDispositionRecord;
    }
  | {
      readonly status: 'rejected';
      readonly reason: 'encounter_not_resolved' | 'already_terminal';
      readonly encounterId: string;
      readonly state: null;
      readonly disposition: null;
    };

export function closeEncounter(
  state: EncounterState,
  entities: EntityCollection,
  disposition: EncounterDispositionRecord,
): EncounterCloseTransitionResult;
```

### 8.2. Procedure

1. Validate/detach **all** state fields, entity collection and disposition record, including nested outcome and side references, before normal rejection.
2. Correlate record `encounterId`/`definitionId` exactly to state. Mismatches are **TypeError**, even for terminal statuses.
3. For current `status:'resolved'`, accept only `disposition.kind:'resolution'`; mismatched record kind is TypeError, never rewritten as a cancellation.
4. For `status:'prepared'|'active'`, return `rejected / encounter_not_resolved` if input record is otherwise well-formed/correlated; cannot fabricate missing transition.
5. For `status:'closed'|'cancelled'`, return `rejected / already_terminal` after complete input validation. Never re-open or emit second candidate.
6. For valid `resolved`, return a new detached state with **only** status changed to `'closed'`, plus a fully captured immutable copy of the **same resolution disposition**. No membership change or outcome recomputation.

`closeEncounter` does **not** re-evaluate battle completion; accepted `resolved` state and accepted disposition are a package L4 commits and later supplies. L4 verifies both came from its authoritative store. An arbitrary forged `resolved` state or a fabricated record can pass structural validation but **does not convey authority**.

### 8.3. Closure and disposal are different

`closed` means the Encounter lifecycle has terminated. It does **not** mean Monster entities are despawned, AI disabled, Effects removed, rewards granted, players teleported, or a World scene unloaded. These side effects require separate L4/owner operations after successful authoritative commit. If World cleanup fails, the accepted closed Encounter stays closed and L4 handles retry/idempotency externally; no reopen.

## 9. EN29 — Policy-controlled cancellation

### 9.1. Proposed input contracts

```ts
export interface EncounterClosurePolicy {
  readonly definitionId: string;
  readonly cancelAllowedStatuses: readonly ('prepared' | 'active')[];
}

export interface EncounterCancellationRequest {
  readonly encounterId: string;
  readonly reasonId: string;
}

export function createEncounterClosurePolicy(
  input: EncounterClosurePolicy,
): EncounterClosurePolicy;

export type EncounterCancellationTransitionResult =
  | {
      readonly status: 'cancelled';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly state: EncounterState;
      readonly disposition: EncounterDispositionRecord;
    }
  | {
      readonly status: 'rejected';
      readonly reason: 'cancellation_not_allowed' | 'already_finalized';
      readonly encounterId: string;
      readonly state: null;
      readonly disposition: null;
    };

export function cancelEncounter(
  state: EncounterState,
  entities: EntityCollection,
  policy: EncounterClosurePolicy,
  request: EncounterCancellationRequest,
): EncounterCancellationTransitionResult;
```

### 9.2. Policy and request semantics

- `definitionId` must match state exactly. `cancelAllowedStatuses` is a **dense** ordered subset of `['prepared','active']`, no duplicates. Empty list is valid and means **no cancellation allowed**.
- The request must exactly contain `encounterId` and opaque, nonblank `reasonId`. No manual/force bypass, credentials, userID, arbitrary request metadata, caller supplied winners or injected outcome.
- Validate both policy and request as closed own-data records **before** checking status, including when cancellation is disabled. Wrong definition/encounter IDs: **TypeError**, never a soft rejection to conceal identity mismatch.
- `resolved`, `closed`, `cancelled` cannot be cancelled and return `rejected / already_finalized` (after validation). For `prepared` or `active` statuses absent from policy list, return `rejected / cancellation_not_allowed`.
- On permitted `prepared/active`, return **only** `status:'cancelled'` state candidate and `disposition.kind:'cancellation'` with exact `reasonId`, `outcome:null`. All state IDs, sides, members, ordering preserved.
- Cancel does **not** erase Combat/AI/Effect/Entity changes, roll back Skill payment, mark all participants defeated, declare draw, or pay consolation rewards.
- Policy is L3 input, not an authorization receipt. L4 checks authoritative controller/user permission, current state baseline/revision and transactional commit; an admin/user “cancel” string alone is not authoritative.

### 9.3. Cancellation path

```text
PREPARED — L3 allowed → CANCELLED
ACTIVE   — L3 allowed → CANCELLED
PREPARED / ACTIVE — L3 denied → rejected/cancellation_not_allowed
RESOLVED / CLOSED / CANCELLED → rejected/already_finalized
```

This phase does not implement a `cancelled → closed` second transition. Cancellation itself is terminal under approved ENC-D06.

## 10. EN30 — Pure cleanup handoff, never World cleanup

### 10.1. Public handoff contract

```ts
export interface EncounterCleanupHandoff {
  readonly encounterId: string;
  readonly terminalStatus: 'closed' | 'cancelled';
  readonly dispositionKind: 'resolution' | 'cancellation';
  readonly participantEntityIds: readonly string[];
}

export function createEncounterCleanupHandoff(
  state: EncounterState,
  entities: EntityCollection,
  disposition: EncounterDispositionRecord,
): EncounterCleanupHandoff;
```

### 10.2. Exact semantics

- Validate the complete existing state against canonical `EntityCollection`, the disposition closed record and ID/definition/side binding **before** any terminal-status shortcut.
- Require matching pair: `closed ↔ resolution`, `cancelled ↔ cancellation`. A wrong pair is TypeError. For `prepared`/`active`/`resolved`, throw `TypeError('Encounter is not terminal')`; do **not** build an early cleanup plan.
- Return only the exact `encounterId`, terminal status, disposition kind and **current canonical `state.participants` Entity IDs in their encounter ordering**. Do not sort or discover new World entities.
- Return a completely detached, frozen handoff. No callbacks. No `cleanup()` implementation. No event publisher. No direct Entity removal.
- All IDs are references, **not instructions to despawn every member**. Example: Player participants may stay in World while Monster actors are eligible for despawn under the game's World rules. L4 decides which side effects are appropriate; empty list is allowed.
- The factory checks only structural integrity and terminal coherence; it **cannot prove L4 committed the candidate**. L4 must call it **only after accepting a terminal Encounter state and disposition together**.
- Handoff creation is pure, so repeated calls can reproduce equivalent outputs. L4 owns deduplicating downstream cleanup, retries and receipts. No at-most-once promise is made in L2.
- The closed/cancelled Encounter remains terminal even if a downstream cleanup action fails or retries. L4 never changes status back to `active` to recover.

### 10.3. Illustrative post-commit sequence

```text
1. L4 reads current Encounter State/Disposition and World facts.
2. L4 invokes resolveEncounter() or cancelEncounter() to obtain candidates.
3. L4 compares original revision/current facts and atomically accepts/rejects candidates.
4. If resolved was accepted, L4 invokes closeEncounter(accepted resolved State, accepted record).
5. L4 accepts closed State under revision/record integrity check.
6. Only after terminal commit, L4 invokes createEncounterCleanupHandoff().
7. L4 interprets participant refs and dispatches its own cleanup/Effect/AI/World operations.
8. L4 records/retries/deduplicates side effects in its own authoritative ledger, if required.
```

No cleanup is triggered automatically by calling an L2 function; step 7 is test-local L4 composition at this milestone.

## 11. Lifecycle transition matrix and invariants

| Current state | Operation | New state | Rejection | Outcome handling |
| --- | --- | --- | --- | --- |
| `prepared` | `resolve` | — | `encounter_not_active` | No outcome |
| `active` | `resolve`, EN25 resolvable | `resolved` candidate | — | Resolution companion created |
| `active` | `resolve`, EN25 pending | — | Existing EN25 pending reason | No companion |
| `resolved` | `resolve` | — | `encounter_not_active` | No replacement |
| `closed` / `cancelled` | `resolve` | — | `encounter_not_active` | No replacement |
| `prepared` / `active` | `close` | — | `encounter_not_resolved` | No new record |
| `resolved` | `close` + matching resolution record | `closed` candidate | — | Same resolution record preserved |
| `closed` / `cancelled` | `close` | — | `already_terminal` | No new record |
| `prepared` / `active` | `cancel`, allowed by policy | `cancelled` candidate | — | Cancellation-only companion |
| `prepared` / `active` | `cancel`, denied by policy | — | `cancellation_not_allowed` | No companion |
| `resolved` / `closed` / `cancelled` | `cancel` | — | `already_finalized` | Do not overwrite win/draw |
| `closed` / `cancelled` | create cleanup handoff | unchanged | — | Read-only references |
| Any other state | create cleanup handoff | — | TypeError | No early cleanup |

There is **no** implicit `active→closed`, `prepared→resolved`, `resolved→cancelled`, `closed→active`, `cancelled→prepared` or `cancelled→closed` operation. The incoming structural `EncounterStatus` vocabulary remains unchanged.

### 11.1. Mutually exclusive terminal outcomes

- A resolved Encounter records `kind:'resolution'` (victory or draw). A cancelled Encounter records only `kind:'cancellation'`, never a synthetic victory/draw.
- Resolution and cancellation compete only at the **L4 authoritative commit** boundary: exactly one accepted state+record pair may win. L2 cannot claim global serialization.
- If a caller passes an arbitrary `resolved` structural state, the validation path cannot certify whether a real L4 commit happened. Consumer tests must explicitly demonstrate that production L2 does **not** claim such evidence.

### 11.2. Side/roster immutability

- Transitions change only `status` in the same five-field Encounter State and create separate metadata; never alter side or participant order.
- Death does not auto-remove participants. Leaving/side changes must have completed through canonical EN11–EN15 before evaluation; if they race with resolution, L4 rejects the stale proposal.
- Do not change prepared/active activation and membership APIs to call closure implicitly.

## 12. Input validation, rejection precedence, identity consistency

### 12.1. Strict schema rules

- All public inputs are exact **closed own-data records**, with ordinary/null prototype per accepted Encounter validation convention. Reject inherited or accessor fields (getter invocation must remain zero), symbols, unknown fields, arrays-as-records, sparse arrays, nonboolean flags and malformed discriminants.
- IDs: exact nonblank strings with original case/spaces preserved. No ID generation, lowercase, trim-as-normalization or implicit “World actor” lookup.
- Arrays: dense; preserve relevant order, no duplicates; return detached/frozen arrays and nested record copies. Do not freeze caller originals.
- All outputs include **only** the declared union branch fields. `state:null` and `disposition:null` together on rejected outcomes; no half-transition.
- Validate all structural inputs **before** an early status rejection, whether state is `active`, `closed`, or the cancellation policy is empty. `EncounterCompletionPolicy/Observation` validation must continue to use accepted EN25 full-precedence checks.

### 12.2. Resolution precedence (after input validation)

Follow EN25 unmodified: `encounter_not_active` → `continuation_pending` → first missing Life fact (canonical roster order) → first matching configured rule → `no_completion_condition_met`. Return exact existing pending reason and no candidate. A conflicting objective or foreign participant fact is TypeError before status checks.

### 12.3. Close precedence

1. Validate `EncounterState` and canonical EntityCollection.
2. Validate complete disposition kind/shape, nested outcome, side reference integrity, exact encounter/definition binding.
3. `closed|cancelled` → `already_terminal`.
4. `prepared|active` → `encounter_not_resolved`.
5. `resolved` and `kind:'resolution'` → closed candidate; `resolved` and `kind:'cancellation'` → TypeError (mismatch).

### 12.4. Cancellation precedence

1. Validate/detach State, L3 ClosurePolicy and CancellationRequest, exact identities.
2. `resolved|closed|cancelled` → `already_finalized`.
3. `prepared|active` but policy excludes status → `cancellation_not_allowed`.
4. Otherwise `cancelled` candidate + cancellation disposition.

### 12.5. Cleanup validation precedence

1. Full structural validation and exact correlation.
2. Coherent terminal-state/record kind pairing.
3. Require terminal status, or TypeError (no handoff).
4. Build immutable ordered participant reference handoff.

**Important:** `closeEncounter` should not validate the *status↔disposition kind* pairing until the `resolved` eligibility stage, so a well-formed cancellation record on `prepared` can still produce deterministic `encounter_not_resolved`; cleanup requires strict final pairing. No mutable “last result” cache, hidden pre-validation shortcut or reflection-based public state.

## 13. Independent L4 composition requirements (test-only)

### 13.1. Forest fight — resolution and closure

Test-local caller constructs canonical Entities, Life facts, Encounter active through the accepted activation API, explicit completion policy/observation, then resolves + accepts candidate + closes + accepts terminal state + creates cleanup handoff. Independent literal oracle:

```text
Encounter ID forest-001 / definition forest-wolves
party: player-001 alive
monsters: monster-001 dead
continuation clear
L3 rule kill-enemies

resolution record winnerSideIds [party], defeatedSideIds [monsters]
prepared/active source state never mutated
resolved accepted status resolved, same roster
closed accepted status closed, same record, no re-evaluation
handoff participantEntityIds [player-001, monster-001]
World despawn calls = 0, XP grants = 0, Effect clears = 0
```

### 13.2. Dungeon wave barrier

At time T the same Life snapshot with continuation `pending` cannot resolve. Only after L4 explicitly clears continuation and supplies a fresh observation can `resolveEncounter` emit a candidate. If a second wave appears after staging but before authoritative commit, L4 rejects stale candidate. L2 never advances wave or spawns Monsters.

### 13.3. PvP multi-side

Objective rule names winner sides `alpha`,`beta`, defeated side `gamma`. Disposition and later close preserve winner array order exactly; no automatic Combat relation interpretation. Mutual elimination and explicit `draw` preserve empty winner/defeated arrays and the selected `ruleId`.

### 13.4. Cancellation from prepared/active

An explicit L3 policy permits prepared cancellation but forbids active cancellation; a distinct policy reverses that. Legal cancellation creates a cancellation companion; illegal cancellation leaves everything unchanged. Neither path marks a Player/Monster defeated or awards refund/reward.

### 13.5. Round/turn-based compatibility

A turn controller at L4 supplies explicit current objective/Life facts after a turn. Encounter resolution is caller-invoked, not scheduled by turn events; no `turnId`, initiative, queue, battle loop or scheduler added to L2.

### 13.6. Full cross-module noninterference

In a test-only installed consumer, snapshot canonical Entity Life/Resources, Combat traces, Skill cooldown/resource states, Effect lifecycle/restrictions, Actor AI state/timing, and World fixtures before/after Encounter transitions. Only accepted Encounter status and disposition candidate change. Downstream side effects occur **only** when the caller explicitly invokes their canonical APIs; cancellation doesn't rollback previously accepted Skill/Combat payments.

### 13.7. Current-baseline commit race

Demonstrate two L4 proposals from the same active Encounter revision: resolve vs cancel. A caller-owned compare-and-swap/revision check accepts one and rejects the other, no double disposition. Also test accepted `resolved→closed` baseline race and stale join/leave/side change. **L4 fixture only**; no production revision fields or transaction layer introduced.
