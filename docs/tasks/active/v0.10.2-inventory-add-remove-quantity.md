### Proposed additive API

```ts
export interface InventoryOperationAdmission { readonly eligible: boolean; }
export type InventoryMutationReason =
  | 'ineligible'
  | 'already_present'
  | 'missing_entry'
  | 'capacity_exceeded'
  | 'quantity_underflow'
  | 'stack_limit_exceeded'
  | 'quantity_not_allowed';

export function addInventoryEntry(
  state: InventoryState, context: InventoryValidationContext,
  entry: InventoryEntry, capacity: InventoryCapacityPolicy,
  admission: InventoryOperationAdmission,
): InventoryTransitionResult<InventoryMutationReason>;

export function removeInventoryEntry(
  state: InventoryState, context: InventoryValidationContext,
  instanceId: string, admission: InventoryOperationAdmission,
): InventoryTransitionResult<InventoryMutationReason>;

export function adjustInventoryQuantity(
  state: InventoryState, context: InventoryValidationContext,
  instanceId: string, delta: number, admission: InventoryOperationAdmission,
): InventoryTransitionResult<InventoryMutationReason>;
```

Three runtime functions + two types only. `InventoryTransitionResult<Reason>` is the **existing generic Foundation union**; do not create another outcome engine. An accepted result has exactly `status:'accepted',reason:'none',candidate:<full state>`; rejection has `status:'rejected',reason:<reason>,candidate:null`. Returned result/candidate are frozen/detached; no partial mutation.

### Structural vs business outcome boundary

- Invalid **state**, invalid Item/binding/definition, malformed new entry, missing context, fractional/zero/unsafe input quantity, invalid ID/type, malformed closed admission/policy => `TypeError` even when admission is false. Validate structural facts first; no getter invocation.
- For `addInventoryEntry`, first validate the **incoming entry's structural data and canonical Item binding** without classifying its would-be quantity against the target Inventory policy. Then return an ordinary rejection for a structurally positive/safe quantity that exceeds nonstackable/max limits. Do **not** call `validateInventoryState` on the invalid proposed candidate and accidentally turn an expected policy rejection into `TypeError`. The final accepted candidate MUST pass the full canonical validator. Likewise apply candidate limits after validating the original state in `adjustInventoryQuantity`.
- A structurally well-formed proposed operation may be **rejected**: `eligible:false`, duplicate instance ID, missing source ID, finite capacity exceeded, nonstackable quantity >1, per-stack max exceeded, would become negative.
- `removeInventoryEntry` removes the complete *membership entry*, not the Item's existence. Future L4 may place the Item elsewhere; no hidden delete from global Item authority.
- `adjustInventoryQuantity` takes a **nonzero safe integer delta**. Positive means caller explicitly proposes a grant/replenishment; it does not prove Loot/Reward entitlement. Negative reduces quantity; when it becomes zero remove the entry completely; negative result rejects (no zero-quantity entry).
- Preserve original entry order on ordinary updates/removals; add appends one entry. Never silently auto-stack matching definitions or reassign IDs.
- Check `Number.isSafeInteger(current+delta)` with overflow-safe arithmetic. Avoid importing or reimplementing Kernel gameplay numerical calculations for integer bookkeeping.
