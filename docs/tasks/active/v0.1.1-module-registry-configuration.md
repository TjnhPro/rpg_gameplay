# 4. GF01 — Module Contract

## 4.1. Required Contract

Tạo public TypeScript contract cho một gameplay module.

Tối thiểu phải biểu diễn được:

- `id`: định danh duy nhất.
- `optional`: module có thể không được sử dụng hay không.
- `dependencies`: danh sách module IDs mà module khai báo cần.
- Metadata mô tả cơ bản nếu thực sự cần cho việc nhận diện, không chứa game-specific configuration.

Ví dụ contract định hướng:

```ts
interface GameplayModuleDefinition {
  readonly id: string;
  readonly optional: boolean;
  readonly dependencies: readonly string[];
}
```

Tên type và cách tổ chức file có thể điều chỉnh cho phù hợp conventions, nhưng không được thay đổi ý nghĩa đã mô tả.

Không đưa Character, Combat, Item, Skill hoặc bất kỳ game-specific property nào vào contract.

## 4.2. Validation

Contract phải có khả năng kiểm tra:

1. Module ID hợp lệ, không rỗng.
2. Metadata bắt buộc đúng kiểu dữ liệu.
3. Dependencies là danh sách module IDs hợp lệ.
4. Không có duplicate dependencies trong cùng một definition.
5. Không chấp nhận self-dependency.
6. Input không hợp lệ bị từ chối với kết quả/lỗi rõ ràng.

Có thể kế thừa convention module ID hiện có trong Harness để tránh xuất hiện hai quy chuẩn identity khác nhau.

**Không kiểm tra module phụ thuộc đã được đăng ký hay chưa, không tự resolve dependency graph ở version này.**

Những hành vi đó thuộc GF04 — v0.1.2.

## 4.3. Contract Stability

- Public definitions không được phụ thuộc classes hoặc framework runtime.
- Không giữ reference có thể bị caller mutate làm thay đổi registry ngoài ý muốn.
- Types và validation có trách nhiệm rõ ràng.
- Không bắt buộc tạo lifecycle hooks trước khi GF07 được thiết kế.
- Không tạo generic extension framework phức tạp chỉ để dự phòng tương lai.

# 5. GF02 — Module Registry

## 5.1. Required Functional APIs

Triển khai một tập public functions tối thiểu hỗ trợ:

- Tạo module registry độc lập.
- Đăng ký module definition.
- Lấy module theo ID.
- Liệt kê các module đã đăng ký.
- Phát hiện và từ chối duplicate registration.

Ví dụ public API định hướng:

```ts
const registry = createModuleRegistry();

const nextRegistry = registerModule(registry, {
  id: "inventory",
  optional: true,
  dependencies: []
});

const module = getModule(nextRegistry, "inventory");

const modules = listModules(nextRegistry);
```

Đây là ví dụ semantics mong muốn. Agent được chọn cách thể hiện types, readonly structures và failure results phù hợp, nhưng phải giữ public functions nhất quán và đơn giản.

## 5.2. Required Behavior

### Registration

- Module definition hợp lệ được đăng ký thành công.
- Duplicate ID bị từ chối, kể cả khi definitions giống nhau.
- Invalid definition không làm thay đổi registry.
- Không ghi đè một module đã đăng ký.
- Registry phải có thể được tạo độc lập nhiều lần.

### Lookup

- Tra cứu chính xác theo module ID.
- Không tìm thấy module phải có kết quả rõ ràng.
- Không tạo module mới trong quá trình lookup.
- Không tự tải module bằng dynamic import.

### Enumeration

- Danh sách module có thứ tự xác định.
- Cùng chuỗi registrations phải trả cùng kết quả.
- Caller không thể mutate dữ liệu trả về để sửa registry ngoài ý muốn.

### State Ownership

Không dùng global singleton hoặc module-level mutable registry.

Ưu tiên explicit state được truyền qua functions và trả về trạng thái mới. Nếu lựa chọn implementation khác, phải chứng minh rằng nhiều registries hoàn toàn độc lập và không có hidden shared state.

Không sử dụng database hoặc persistence.

## 5.3. Không thuộc GF02

- Không chạy lifecycle hooks.
- Không tự tạo module instances.
- Không resolve dependencies.
- Không tự đăng ký tất cả gameplay modules.
- Không module auto-discovery.
- Không dynamic plugin loading.
- Không tạo Gameplay Runtime.

# 6. GF03 — Module Enable / Disable

## 6.1. Objective

Cho phép consumer lựa chọn gameplay modules cần sử dụng mà không phải thay đổi implementation của framework.

Ví dụ:

```ts
const configuration = configureModules(registry, {
  enable: ["inventory"],
  disable: ["some-optional-module"]
});

isModuleEnabled(configuration, "inventory");
```

Đây là cấu hình lựa chọn module, không phải yêu cầu thực thi module.

## 6.2. Configuration Semantics

Phiên bản đầu áp dụng:

| Module | Default | Configuration |
|---|---|---|
| `optional: true` | Disabled | Có thể enable hoặc disable |
| `optional: false` | Enabled | Không được disable |
| Unknown module ID | Không hợp lệ | Phải reject |

Một configuration phải có kết quả xác định và có thể kiểm tra qua public functions.

Không được silently ignore:

- Unknown module IDs trong enable/disable.
- Một ID vừa được enable vừa được disable.
- Cố gắng disable required module.
- Duplicate IDs trong cùng danh sách cấu hình.

Hành vi reject cần nhất quán với contracts của Foundation.

## 6.3. Selection Isolation

- Không sửa registry definitions khi cấu hình enable/disable.
- Không thay đổi global configuration.
- Hai configurations có thể được tạo độc lập từ cùng registry.
- Thay đổi input configuration bên ngoài không được ảnh hưởng đến kết quả đã tạo.
- Danh sách module được lựa chọn phải có thứ tự ổn định.

## 6.4. Dependency Boundary

Ở v0.1.1, enable/disable chỉ biểu diễn **configuration intent**.

Không được:

- Tự enable required dependencies.
- Tự kiểm tra missing dependencies.
- Tự sắp xếp module theo dependency graph.
- Tự khởi tạo các modules được enable.
- Tự gọi lifecycle hooks.

GF04 sẽ chịu trách nhiệm dependency resolution ở v0.1.2.

Ví dụ: nếu `equipment` khai báo dependency `inventory`, v0.1.1 chỉ lưu khai báo và cấu hình lựa chọn. Tính hợp lệ của tổ hợp module sẽ được xử lý tại GF04.

Không báo cáo rằng module đã được khởi chạy chỉ vì module được đánh dấu enabled.

```ts
const original = createModuleRegistry();

  id: "inventory",
  optional: true,
  dependencies: []
```
