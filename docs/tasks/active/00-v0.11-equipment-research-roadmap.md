## 1. Research & existing-system audit

**Primary verified sources:**

1. Epic Games, [Lyra Inventory and Equipment](https://dev.epicgames.com/documentation/en-us/unreal-engine/lyra-inventory-and-equipment-in-unreal-engine). Lyra separates inventory and equipment lifetime/ownership and uses equipment bookkeeping entries. **Not copied:** Gameplay Ability System grants, Actor lifecycle, manager components, replicated inventory/equipment actors. In our design the **same canonical ItemInstanceState** moves between separate storage snapshots; do not copy Lyra's ephemeral EquipmentInstance/InventoryItemInstance double-model.
2. Unity, [ScriptableObject](https://docs.unity3d.com/cn/6000.0/ScriptReference/ScriptableObject.html); Unity Economy [resource/instance data](https://docs.unity.com/en-us/economy/custom-data) and [player inventory](https://docs.unity.com/economy/player-data). Separate reusable definitions from instance-specific values. **Not copied:** Unity runtime objects, multiplayer services, economy transactions, central managers or Unity-specific editor serialization. Unity Economy is a distinct service, not a reference implementation of this L2 equipment contract.
3. Godot, [Resources](https://docs.godotengine.org/en/3.6/tutorials/scripting/resources.html). Separate data containers from Node scene/behavior. **Not copied:** Resource class inheritance, Godot Nodes/Signals/Autoload or an engine-coupled equipment plugin. Godot's core Resource documentation does **not** prescribe a universal Equipment API; slot ownership and schema below are **our design decisions**.

**Repository context and task sources audited:**

- `docs/DECISIONS.md`: D01–D14, pure headless systems, canonical owners, Developer approval; `ARCHITECTURE.md`, `docs/GAMEPLAY_CAPABILITIES.md` (Group 11 Equipment: equip/unequip/slots/requirements/modifier source wiring), `docs/MODULE_BOUNDARIES.md`, `harness/modules.json` and pinned Core boundary.
- `/mnt/data/item-v0.9-mvp-revised/01..04`: *proposed revised* Item Foundation/Property/Stack/Closure. Item Definition/Instance and structural validation live in Item; stack/quantity do not.
- `/mnt/data/inventory-v0.10-mvp-proposed/00..06`: *proposed* Inventory Foundation/Query/Add/Stack/Closure. `InventoryEntry` holds Item Snapshot + quantity; L4 owns transfers/commits; **no shipped Inventory→Equipment transfer API**.
- Read-only GitHub check 2026-10-21: `main @rpg/gameplay` version `0.8.7`, Item `feat/v0.9-item` and Draft PR #14 existed; `feat/v0.10-inventory` and `feat/v0.11-equipment` were not found. State may change; verify on execution.

### What to learn, what not to copy

| Question | Design learning | Equipment L2 decision |
| --- | --- | --- |
| Canonical ownership | Inventory keeps unequipped possession; Equipment owns occupied equipment locations | Two independent storages, no combined manager |
| Identity | Distinguish Item definition, Item instance, storage and slot | `equipmentId`, `owner`, opaque `slotIds`, canonical Item `instanceId` |
| Relationships | Equipment may affect abilities/appearance/stats | L3 interprets Item, L4 orchestrates; Entity/Core calculate stats |
| Extension points | Slot layouts and eligibility are game-specific | Opaque slot IDs, caller-supplied admission; no enum/class engine |
| Lifecycle | Equip/unequip may have gameplay side effects | L2 returns immutable candidates only; no side-effect hooks |
| Common refactor trap | Put player-specific slot set or stat bonuses inside shared model | Keep slot allocation policy and numerical properties out of Equipment State |

## 2. Approved decisions and new proposed Equipment choices

**Retain Group C C-D01–C-D07**: Inventory owns stack `quantity`; Equipment owns separate storage; L2 proposals/L4 commit; Item Instance holds definition reference; Inventory and Equipment independent; Loot/Reward don't grant via Equipment.

| Equipment decision | Choice for this phase | Why / tradeoff |
| --- | --- | --- |
| **EQ-D01** | Equipment entry contains **ItemInstanceState snapshot** (same A2 as Inventory), never a separate EquipmentItem definition | No global ItemStore, no aliasing or double creator. L4 must enforce cross-storage uniqueness |
| **EQ-D02** | Entry contains **nonempty unique `slotIds: readonly string[]`**, not single slot | Supports future two-handed occupancy/multi-slot equipment without changing Foundation; MVP uses one slot. Slightly more structural validation |
| **EQ-D03** | State is **`equipmentId`, neutral `owner`, ordered `entries`**; no slot layout or item stats stored there | Stable membership snapshot; layout/requirements L3 policy, optional future companion for grid/presentation |
| **EQ-D04** | Equipment optional `dependencies:['item']` only | Item is canonical data/validator; no direct Inventory/Entity/Skill/Effect dependency |
| **EQ-D05** | Explicit `EquipmentValidationContext` supplies complete ItemDefinitions, no implicit catalog | Pure and safely validated, but caller must provide contexts; v0.11.0 preflight reconciles accepted Item types |
| **EQ-D06** | Explicit **closed** `{eligible:boolean}` admission for equip, unequip, replace | MVP avoids game-rule DSL; L3/L4 must check class/level/cursed restrictions and freshness before authoritative commit |
| **EQ-D07** | `equip`, `unequip`, `replace` create full immutable candidates; unequip/replace additionally return released Item snapshot | Safe L4 handoff; no automatic Inventory updates or destructive replacement |
| **EQ-D08** | Cross-storage movement and stat composition are **test-local L4 orchestrations** only | Demonstrates real consumer integration without producing transaction/Stats engines |

All EQ-D choices above are proposed contracts for **Developer approval as part of v0.11.0 Foundation**, not evidence they already exist. If accepted predecessor APIs make any choice incompatible, stop and ask for a narrow contract decision before implementation.

## 3. L1–L4 boundary and dependency graph

```text
L3 game equipment layout, classes, level requirements,
   mapping equipped Item property → Core modifier
             | supplies explicit facts/policies
             v
L4 current Item/Inventory/Equipment/Entity state,
   eligibility, ownership, cross-storage atomic commit, UI, persistence
             | calls (no inverse imports)
             v
L2 Equipment --------> L2 Item ----> []
    | immutable slot occupancy        definition/instance/properties validation
    | equip/unequip candidates
    | NO direct Inventory/Entity dependency

L2 Inventory --------> L2 Item (holds snapshots and quantity)
L2 Entity -----------> L1 Core Kernel (canonical stat computation)
```

- **L1:** stats/modifiers/resource calculations. Equipment does no damage or numeric modifiers calculation. Counting slots/array membership is generic L2 structural bookkeeping, not gameplay numeric engine.
- **L2 Item:** creates/validates item definitions/instances and their data. Equipment never recreates its data model.
- **L2 Inventory:** owns inventory entries, quantity and bag capacity; no slots for Equipment.
- **L2 Equipment:** owns equipment storage and slot occupancy; no bag quantity or game classes.
- **L2 Entity:** owns canonical character stat/resource snapshots; accepted Kernel delegates calculations.
- **L3:** equipment slot names/sets, class/level/item restrictions, multi-slot policies, mapping Item attributes to modifiers, appearance hints.
- **L4:** current-state freshness/permission, uniqueness across storages, commit both Inventory + Equipment, persistence/DB transactions, renderer, Effect/Skill actual execution.

## 4. Foundation contracts (proposal — reconcile against actual accepted Item/Inventory)

```ts
export interface EquipmentOwnerReference {
  readonly ownerKind: string;
  readonly ownerId: string;
}
export interface EquippedEntry {
  readonly item: ItemInstanceState;
  readonly slotIds: readonly string[]; // nonempty, exact unique IDs
}
export interface EquipmentState {
  readonly equipmentId: string;
  readonly owner: EquipmentOwnerReference | null;
  readonly entries: readonly EquippedEntry[];
}
export interface EquipmentItemContext {
  readonly definition: ItemDefinition;
}
export interface EquipmentValidationContext {
  readonly items: readonly EquipmentItemContext[];
}
export function createEquipmentState(
  input: EquipmentState, context: EquipmentValidationContext,
): EquipmentState;
export function validateEquipmentState(
  state: EquipmentState, context: EquipmentValidationContext,
): EquipmentState;
```

**Normative meanings:** State entries retain insertion order and are detached/frozen. One exact `item.instanceId` may occur at most once per Equipment State. One exact slot ID may occur in **at most one entry**. Within one entry slot IDs are nonempty, ordered, nonduplicate, exact nonblank strings. An empty `entries` array is valid. No unknown fields, accessors, unsafe structures or implicit identifier generation. `context.items` contains **unique** valid full ItemDefinitions identified by `definitionId`; unused definitions are permitted. Every equipped Item must have exactly one matching definition; invoke canonical public Item `validateItemInstance`. Context is supplied, not stored in State. Create/validate may accept a nonempty initial snapshot but never authorizes equip from Inventory.

**No extra `equipmentEntryId`:** `item.instanceId` already gives identity inside one Equipment State. **No `quantity`:** always one unique Item Instance per equipped entry; L4 must not equip Inventory quantity greater than one. **No fixed slot catalog:** `weapon_main`, `ring_left` etc are sample fixture strings, not public enumerations. **No stat field / EquipmentItem:** Item properties remain in Item; Entity/Core owns calculated stats. **No `revision`, event log, global ID registry, database record** until a real consumer needs them.

Future-safe multi-slot **representation** is in Foundation, but slot availability assessment and equip/unequip are later operations. The model need not encode a future game's semantic rule requiring both hands; explicit L3 admission supplies the required slot set, and the L2 operation checks collisions of exactly those IDs. This is **not** an implementation of two-hand combat.

## 5. Future Contract Stress Test — DESIGN ONLY

| Possible future need | Foundation effect | MVP implementation |
| --- | --- | --- |
| Two ring slots / player armor / monster gear | Opaque owner/slot IDs, one state | Single-slot fixtures only |
| One two-handed item | One entry can occupy 2 slots, collision detectable | Foundation validation; no L3 two-hand rule |
| Dual wield / set bonuses | Multiple entries may be inspected | No effects/bonuses/ability grants |
| Costume or companion equipment | Neutral owner, opaque slot namespace | Data fixtures only |
| Level/class requirement / cursed unequip | Explicit eligibility fact | L3 policy eval not built |
| Item refinement/durability | Item Instance properties can evolve | No Item mutation manager; later additive Equipment snapshot refresh may be needed |
| Inventory → Equipment / back | Same Item snapshot shape, separate candidates | L4 fixture only, no transaction manager |
| Inventory stack quantity >1 | L4 checks quantity; requires split before moving | MVP rejects this handoff, split deferred |
| Rendering, animation, sockets | L4 attaches model based on content | No 2D/3D/UI/World code |
| Persistent multiplayer concurrency | L4 verifies fresh state + atomic commit | Not claimed by pure functions |

**Admitted design limitation:** Equipped Item property updates while remaining equipped would need an approved additive operation that replaces an Item snapshot without changing equipment membership. It is deliberately **not** in this MVP; absence is not a reason to insert a hidden mutator or change Foundation. If game needs it later, audit Item/Equipment and add bounded API. No framework can promise future 100% schema stability.

## 6. Minimal roadmap — FOUR milestones; EQ01–EQ20

| Milestone | IDs | Real MVP result | New production scope |
| --- | --- | --- | --- |
| **v0.11.0 Equipment Foundation** | EQ01–EQ05 | Define validated, immutable equipment with exact slot occupancy structure | Identity/owner/entry/state/context + create/validate; module owner |
| **v0.11.1 Slot Queries & Admission** | EQ06–EQ10 | List/query/has and assess eligibility with L3 fact + occupied-slot checks | Read/admission functions; no state transitions |
| **v0.11.2 Equip & Unequip Operations** | EQ11–EQ15 | Equip, unequip, safe replace + released item, immutable candidates | Real state transitions; no Inventory commit |
| **v0.11.3 Integration & MVP Closure** | EQ16–EQ20 | Installed Item/Inventory + Equipment handoff and Entity/Core stat consumer, regression, CI, final review | **No new production API** |

**Deliberately deferred:** split-stack, multi-storage transfer production APIs, automatic item-return on unequip, multi-slot gameplay rules, effect/skill grants, durability/refine, set bonuses, quick swap/loadouts, costume/VFX, replication, database transaction coordinator, global Item store/manager, UI.

## 7. Task writing & execution rules

1. **Research/Audit:** Read accepted code & public types, compare framework learnings; never implement from draft schemas when the predecessor differs.
2. **Boundary:** Item/Inventory/Equipment/Entity/Core separate owners. No copying calculators or introducing `EquipmentEngine`.
3. **Foundation:** Approve exact identity/state/invariants/extension boundary in v0.11.0; installed tests prove structural behavior.
4. **Stress test:** Design-only future scenarios establish no obvious early breaking changes; not production APIs.
5. **MVP:** EQ06–EQ15 build only observed operations on frozen Foundation.
6. **Milestones:** One branch/Draft PR; each milestone exactly one bounded checkpoint, report, real packed ESM + strict NodeNext, targeted meaningful tests/negative injection/full regressions and exact-SHA CI per accepted harness.
7. **Game evolution:** Audit canonical owner before adding functionality; only actual game need may motivate an additive feature. Breaking Foundation requires Developer-approved evidence and impact review.

**Stop/authorization:** This roadmap and four files are task proposals; they are **not permission to start v0.11.0** without explicit approval and accepted/merged Item/Inventory prerequisites. Each successor requires explicit Developer checkpoint acceptance. Never auto-ready/merge/tag/publish or start v0.12.x.
