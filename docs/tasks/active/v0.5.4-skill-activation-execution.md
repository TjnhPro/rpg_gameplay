Triển khai reusable **Skill Activation & Execution Contracts** tại RPG Gameplay L2.

Sau v0.5.3, hệ thống đã có các capabilities được thiết kế:

- Skill Definition và Skill Instance.
- Skill Availability & Admission.
- Resource Cost Sufficiency và Application.
- Cooldown State và Ready/Reuse Validation.

v0.5.4 kết hợp những capabilities đó thành một **Skill Activation Attempt** có kết quả xác định, đồng thời thiết kế cách chuyển accepted execution request tới canonical Combat hoặc caller-owned executor.

| ID | Feature | Responsibility |
|---|---|---|
| SK21 | Skill Activation Contracts | Activation attempt identity, execution intent, input/output contracts |
| SK22 | Activation Sequence & Gates | Admission, execution preflight, costs, cooldown và rejection ordering |
| SK23 | Accepted Execution Request | Immutable handoff request, identity consistency, candidate states |
| SK24 | Combat Handoff & Execution Outcomes | Caller-mediated Combat integration, completion/failure reporting |
| SK25 | Integration & Verification | End-to-end function-level scenarios, installed package, regressions và CI |

**Expected outcome:** Consumer có thể thực hiện một activation attempt, nhận accepted execution request khi mọi điều kiện hợp lệ, hoặc nhận structured rejection mà không làm thay đổi gameplay state.

Nếu accepted:

- Resource cost candidate state được tạo.
- Cooldown candidate state được tạo.
- Execution request được tạo.
- Caller quyết định authoritative commit và dispatch.

Nếu rejected:

- Không có execution request.
- Không expose resource candidate state.
- Không expose cooldown candidate state.
- Không có gameplay side effects.

**v0.5.4 không tạo một Skill Execution Engine mới.**

# 2. Mandatory Architecture Decisions

## Decision A — Strict Layer Ownership

| Responsibility | Canonical Owner | Rule |
|---|---|---|
| Numerical calculations | L1 — RPG Core | Damage, resources, cooldown duration |
| Skill Identity | L2 — Skill | Definition, Instance, attempt identity |
| Skill Admission | L2 — Skill | Ownership, rank eligibility, actor eligibility |
| Resource Cost Orchestration | L2 — Skill | Cost request, sufficiency và candidate result |
| Resource State / Transition | L2 — Entity | Canonical resource authority |
| Cooldown State / Lifecycle | L2 — Skill | Ready/reuse/start candidate |
| Cooldown Numerical Duration | L1 — RPG Core | Canonical `calculateCooldownDurationMs()` |
| Clock | L2 — Foundation | `readExecutionTime()` |
| Combat Admission / Targeting | L2 — Combat | Canonical Combat validation |
| Attack / Damage / Death | L2 Combat + Entity + L1 Core | Canonical Combat/Entity execution |
| Skill Execution Request | L2 — Skill | Accepted dispatch intent |
| Skill Content / Policies | L3 | Skill configuration, target requirements, dispatch rules |
| Runtime Orchestration | L4 — Application | Cross-module sequencing, authority, commit và dispatch |
| Persistence / Concurrency | L4 — Application | Storage, synchronization, idempotency |

**Skill không được copy Combat Admission, Target Validation hoặc numerical calculations.**

## Decision B — Skill Owns Activation Decision, Not Combat Resolution

Skill chịu trách nhiệm:

```text
Skill Admission
Execution Preflight Gate
Resource Cost Gate
Cooldown Gate
Accepted Execution Request
```

Combat chịu trách nhiệm:

```text
Combat Action Admission
Combat Target Validation
Attack Resolution
Damage Application
Death Resolution
```

Không chuyển các operations này vào Skill.

## Decision C — Execution Handoff Through L4

Để bảo toàn optional-module independence:

```text
skill → [entity]
combat → [entity]
```

Skill production module **không có dependency bắt buộc vào Combat**.

Combat handoff được thực hiện bởi L4/caller thông qua public contracts.

Không import Combat production module từ Skill để gọi:

```ts
createCombatActionContext()
evaluateCombatActionAdmission()
evaluateCombatTargetValidation()
resolveCombatAttack()
applyCombatAttackDamage()
```

Những functions đó chỉ được gọi ở caller/integration consumer.

Không tạo shared Skill/Combat execution engine.

## Decision D — Preflight Before Candidate Commit

Activation sequence phải kiểm tra tất cả điều kiện cần thiết trước khi L4 commit resource và cooldown states.

Nếu execution cần Combat targeting, L4 phải hoàn thành canonical Combat preflight trước khi chấp nhận activation.

Một accepted Skill Admission không được xem là đủ điều kiện để tiêu hao tài nguyên.

## Decision E — No Rollback Engine

Resource Costs v0.5.2 và Cooldown v0.5.3 đều trả immutable candidate states.

v0.5.4 phối hợp các candidate states nhưng:

- Không mutate authoritative state.
- Không commit từng phần.
- Không tạo rollback transaction.
- Không tự refund resource.
- Không tự reset cooldown.
- Không tạo locking manager.

Authoritative commit thuộc L4.

## Decision F — Accepted Does Not Mean Executed

Phân biệt ba khái niệm:

**Activation Accepted**

Các preconditions đã pass và candidate states/execution request đã được tạo.

**Execution Dispatched**

Caller đã chuyển request đến actual execution owner.

**Execution Completed**

Actual executor đã xử lý request và caller báo kết quả.

Không đồng nhất ba trạng thái này.

Không tạo execution success giả khi mới chỉ tạo accepted request.

# 5. SK21 — Skill Activation Contracts

## 5.1. Objective

Chuẩn hóa một independent Skill Activation Attempt.

Không tạo persistent Activation Session.

Không tạo actor-global action state.

## 5.2. Activation Attempt Identity

Mỗi attempt có:

```text
attemptId
instanceId
skillId
actorEntityId
```

`attemptId`:

- Opaque nonblank string.
- Caller-supplied.
- Exact/case-sensitive.
- Không tự generate.
- Không ép UUID.
- Không yêu cầu global uniqueness ở L2.
- Không tạo global attempt registry.

Caller/L4 chịu trách nhiệm idempotency và uniqueness nếu gameplay cần.

Không dùng `instanceId` thay thế `attemptId`.

Một Skill Instance có thể được attempted nhiều lần.

## 5.3. Execution Intent

Định nghĩa explicit dispatch intent cho một attempt.

Proposed contract:

```ts
export interface SkillExecutionIntent {
  readonly attemptId: string;

  readonly dispatch:
    | {
        readonly kind: "combat";
        readonly actionId: string;
        readonly actionType: string;
        readonly targetEntityId: string;
      }
    | {
        readonly kind: "caller";
      };
}
```

Hai modes:

**`combat`**

Caller muốn chuyển accepted request đến Combat.

**`caller`**

Caller chịu trách nhiệm execution ngoài Combat, ví dụ skill không gây tấn công.

`caller` không đồng nghĩa với Effect System đã được triển khai.

Không tự tạo executor cho mode này.

## 5.4. Combat Intent Boundary

Các fields:

```text
actionId
actionType
targetEntityId
```

chỉ là handoff references.

Skill không:

- Xác định target relation.
- Kiểm tra target life.
- Tính range.
- Tính hit/dodge.
- Tính damage.
- Validate Combat Action Context thay Combat.
- Quyết định `actionType` nào được Combat executor hỗ trợ.

L3/L4 cung cấp action configuration.

L4 sử dụng canonical Combat public factory để tạo `CombatActionContext`.

Không tự copy Combat Action validator vào Skill.

## 5.5. Execution Preflight

Proposed contract:

```ts
export type SkillExecutionPreflight =
  | {
      readonly kind: "combat";
      readonly status: "accepted" | "rejected";
    }
  | {
      readonly kind: "caller";
      readonly status: "accepted" | "rejected";
    };
```

Đây là **caller-supplied preflight assessment**, không phải một authoritative Combat receipt.

Required:

```text
intent.dispatch.kind == preflight.kind
```

Nếu mismatch:

```text
TypeError
```

Nếu preflight rejected:

```text
Skill activation rejected.
No candidate states.
No execution request.
```

Không duplicate Combat rejection reason taxonomy.

L4 giữ canonical Combat result để cung cấp detailed rejection reason cho application.

## 5.6. No Forged Authorization Guarantee

`SkillExecutionPreflight` là explicit assertion từ caller.

Nó không chứng minh:

- Combat target thực sự hợp lệ.
- Caller đã chạy Combat API.
- Actor vẫn còn sống.
- Request chưa được dùng trước đó.
- Concurrent state không thay đổi.

Skill không được mô tả nó là security token hoặc transaction receipt.

L4 phải thực hiện canonical preflight thật trước khi truyền `status: "accepted"`.

Installed integration phải chứng minh workflow đó.

## 5.7. Activation Input

Conceptual public contract:

```ts
export interface SkillActivationInput {
  readonly instance: SkillInstanceState;

  readonly admission: SkillAdmissionResult;

  readonly resourceState: EntityResourceState;
  readonly resourceCosts: SkillResourceCostRequest;

  readonly cooldownState: SkillCooldownState;
  readonly cooldownConfig: SkillCooldownConfiguration;

  readonly executionContext: GameplayExecutionContext;

  readonly intent: SkillExecutionIntent;
  readonly executionPreflight: SkillExecutionPreflight;
}
```

Các nested types phải reuse actual accepted public contracts.

Không tạo second copies của Resource/Cooldown/Admission types.

Execution Context là opaque Foundation capability, không phải JSON object cần clone.

## 5.8. Identity Consistency

Bắt buộc:

```text
instance.instanceId
  == admission.instanceId
  == cooldownState.instanceId

instance.skillId
  == admission.skillId
  == cooldownState.skillId

instance.entityId
  == admission.actorEntityId
  == resourceState.entityId
  == cooldownState.entityId
```

Nếu inconsistent:

```text
TypeError
```

Không tự rebind.

Không tạo fake Entity để sửa mismatch.

## 5.9. Closed Contract Validation

Reject:

- Missing required fields.
- Unknown fields.
- Symbol keys.
- Accessor/getter fields.
- Inherited required fields.
- Invalid attempt ID.
- Invalid dispatch kind.
- Missing Combat fields.
- Extra Combat fields in caller mode.
- Invalid preflight status.
- Dispatch/preflight kind mismatch.
- Identity mismatch.

Không invoke getters.

Không silently normalize.

# 6. SK22 — Activation Sequence & Gates

## 6.1. Objective

Xác định một deterministic activation sequence dùng existing canonical operations.

## 6.2. Activation Sequence

Mandatory logical stages:

```text
1. Structural validation
          ↓
2. Skill Admission Gate
          ↓
3. Execution Preflight Gate
          ↓
4. Resource Cost Gate
          ↓
5. Cooldown Gate
          ↓
6. Accepted Execution Request
          ↓
7. Immutable Candidate States
          ↓
8. Caller/L4 Commit & Dispatch
```

Đây là logical activation sequence, không phải một global execution pipeline.

## 6.3. Structural Validation

Trước gameplay outcome:

- Validate complete activation input shape.
- Validate all Skill identity associations.
- Validate execution intent.
- Validate preflight kind/status.
- Validate all supplied closed records theo existing module conventions.

Phải reuse accepted validation/resolver logic trong cùng Skill owner.

Không tạo validator thứ hai cho:

```text
Entity Resource State
Entity Life State
Combat Action Context
Core numerical contracts
```

Malformed contracts phải fail-closed.

Không che malformed configuration bằng gameplay rejection nếu configuration đó đã được cung cấp và thuộc approved activation input.

Nếu prior milestone không expose reusable validation helper, được phép refactor **private helpers bên trong Skill** mà không đổi public semantics; không viết parallel business logic.

## 6.4. Skill Admission Gate

Input:

```text
admission.status = admitted
admission.reason = none
```

Expected:

```text
Continue.
```

Input:

```text
admission.status = rejected
```

Expected:

```text
activation rejected

```

Không tự gọi lại `evaluateSkillActivationAdmission()`.

Không tự:

- Resolve rank.
- Check class.
- Check Entity Life.
- Check Skill Ownership.

Existing SK06–SK10 stage vẫn là canonical owner.

## 6.5. Execution Preflight Gate

Input:

```text
executionPreflight.status = accepted
```

Expected:

```text
Continue.
```

Input:

```text
executionPreflight.status = rejected
```

Expected:

```text
activation rejected
reason = execution_preflight_rejected
```

Không tạo candidate states khi preflight rejected.

Với combat mode, caller phải chạy Combat Action Admission và Target Validation trước stage này.

Không tin target ID đơn thuần là bằng chứng target hợp lệ.

```text
status = rejected
```

Expected:


Capture candidate resource state.

Chưa commit.

## 6.7. Cooldown Gate

Reuse:

```ts
startSkillCooldown(
  instance,
  cooldownState,
  executionContext,
  cooldownConfig

```

Nếu:

```text
status = rejected
reason = cooldown_active
```

Expected:

```text
activation rejected
reason = cooldown_active
```

Không expose provisional resource state đã tính ở stage trước.

Nếu:

```text
status = started
```

Capture candidate cooldown state.

Chưa commit.

Không gọi Core cooldown formula riêng từ Activation.

## 6.8. Clock Read Semantics

Cooldown start sử dụng Foundation clock.

Không gọi thêm:

```ts
readExecutionTime()
```

trong Activation chỉ để tạo metadata.

Không tạo second clock read.

Một successful activation attempt phải sử dụng time từ canonical Cooldown Start operation.

Không gọi readiness rồi start bằng hai clock observations nếu điều đó làm thay đổi admission semantics.

Không tự generate timestamps.

## 6.9. Gate Rejection Priority

Deterministic priority:

```text
1. skill_admission_rejected
2. execution_preflight_rejected
3. resource_cost_rejected
4. cooldown_active
5. none
```

Đây là **activation-stage priority**, không thay đổi rejection priority nội bộ của SK10 hoặc SK14.

Examples:

```text
Admission rejected
Resource insufficient
Cooldown active
```

Expected:

```text
skill_admission_rejected
```

```text
Admission accepted
Combat preflight rejected
Resource sufficient
```

Expected:

```text
execution_preflight_rejected
```

```text
Admission accepted
Preflight accepted
Resource insufficient
Cooldown active
```

Expected:

```text
resource_cost_rejected
```

Không tạo generic error-priority framework.

## 6.10. No Partial Candidate Exposure

Nếu Resource stage success nhưng Cooldown stage reject:

```text
activation rejected
resourceState = null
cooldownState = null
executionRequest = null
```

Không trả resource candidate thông qua hidden diagnostic field.

Không tự refund.

Không tạo rollback manager.

Local immutable provisional values có thể tồn tại trong resolver, nhưng không được publish khi rejected.

## 6.11. No Unnecessary Execution

Nếu rejection xảy ra tại:

- Skill Admission: không gọi Resource/Clock/Combat.
- Execution Preflight: không gọi Resource/Clock/Combat.
- Resource Cost: không start Cooldown.
- Cooldown: không tạo accepted execution request.

Full structural input validation vẫn bắt buộc; không được dùng short-circuit để che malformed records.

Không gọi actual Combat từ Skill trong bất kỳ stage nào.

# 7. SK23 — Accepted Execution Request

## 7.1. Objective

Tạo immutable request sau khi toàn bộ Skill activation gates đã thành công.

## 7.2. Proposed Public API

```ts
activateSkill(
  input: SkillActivationInput
): SkillActivationResult
```

Operation phải:

- Synchronous.
- Deterministic với supplied inputs/clock.
- Side-effect free.
- No mutable global state.
- No implicit event publication.
- No actual Combat execution.

## 7.3. Accepted Request Contract

Conceptual type:

```ts
export interface SkillExecutionRequest {
  readonly attemptId: string;
  readonly instanceId: string;
  readonly skillId: string;
  readonly actorEntityId: string;

  readonly dispatch: SkillExecutionIntent["dispatch"];
}
```

Đây là **accepted Skill execution intent**.

Không bao gồm:

```text
damage
hitChance
criticalChance
targetRelation
targetLife
combatResult
resourceBalance
cooldownManager
animation
VFX
```

Các giá trị đó thuộc owner khác.

## 7.4. Accepted Result

Proposed:

```ts
export type SkillActivationResult =
  | {
      readonly status: "accepted";
      readonly reason: "none";

      readonly request: SkillExecutionRequest;

      readonly resources: EntityResourceState;
      readonly cooldown: SkillCooldownState;
    }
  | {
      readonly status: "rejected";
      readonly reason: SkillActivationRejectionReason;

      readonly request: null;
      readonly resources: null;
      readonly cooldown: null;
    };
```

Public rejection reason:

```ts
export type SkillActivationRejectionReason =
  | "skill_admission_rejected"
  | "execution_preflight_rejected"
  | "resource_cost_rejected"
  | "cooldown_active";
```

Accepted status sử dụng exact `"none"`.

Không cho phép:

```text
status = accepted
reason != none
```

Không cho phép rejected result chứa candidate states.

## 7.6. Request Identity

Request identities phải lấy từ validated canonical input.

Không:

- Override dispatch target.
- Infer target from Entity kind.

## 7.7. Candidate State Invariants

Accepted result phải chứa:

```text
One final Resource State
One final Cooldown State
```

# 8. SK24 — Combat Handoff & Execution Outcomes

## 8.1. Objective

Thiết kế actual integration boundary với Combat, đồng thời phân biệt accepted activation và completed execution.

## 8.2. Caller-Owned Combat Preflight

Với Combat execution intent:

```text
dispatch.kind = combat
```

L4/caller phải thực hiện:

```text
1. Build canonical Combat Action Context.
2. Evaluate Combat Action Admission.
3. Evaluate Combat Target Validation.
4. Map canonical result to explicit execution preflight.
5. Call Skill Activation only after required preflight.
```

Concrete public APIs:

```ts
createCombatActionContext()
evaluateCombatActionAdmission()
evaluateCombatTargetValidation()
```

Skill không implement các bước này.

## 8.3. Canonical Combat Context

Caller sử dụng intent để tạo actual Combat Action Context.

Conceptual example:

```ts
const context = createCombatActionContext({
  actionId: intent.dispatch.actionId,
  actionType: intent.dispatch.actionType,
  sourceEntityId: instance.entityId,
  target: {
    kind: "entity",
    entityId: intent.dispatch.targetEntityId
  }
});
```

Chỉ áp dụng sau khi đã narrow `dispatch.kind === "combat"`.

Không tạo fake Combat context.

Không hardcode `actionType = "basic_attack"` trong Skill.

L3/L4 quyết định action type phù hợp.

## 8.4. Actual Combat Validation

Caller sử dụng:

```ts
evaluateCombatActionAdmission()
evaluateCombatTargetValidation()
```

Expected canonical behavior:

- Combat actor admission từ Combat.
- Combat target relation từ Combat.
- Combat target life policy từ Combat.
- Invalid target được Combat reject.
- Skill không duplicate target checking.

Nếu Combat admission rejected:

```text
executionPreflight.status = rejected
```

Nếu Combat target validation rejected:

```text
executionPreflight.status = rejected
```

Không tạo resource/cooldown candidate.

Nếu cả hai accepted:

```text
executionPreflight.status = accepted
```

Caller phải kiểm tra identity consistency giữa canonical Combat results và intended action.

Không dùng status boolean thay cho xác thực toàn bộ data trong L4.

## 8.5. Combat Handoff Identity

Phải giữ exact:

```text
Skill attemptId
Skill instanceId
Skill skillId
Actor entityId

Combat actionId
Combat actionType
Combat sourceEntityId
Combat targetEntityId
```

Required:

```text
Skill actorEntityId
  == Combat sourceEntityId

Skill dispatch.actionId
  == Combat context.actionId

Skill dispatch.actionType
  == Combat context.actionType

Skill dispatch.targetEntityId
  == Combat context.target.entityId
```

Identity mismatch không được silently repaired.

Không tạo cross-module registry.

## 8.6. Accepted Request Dispatch

Sau accepted activation:

```text
SkillExecutionRequest
         ↓
L4 Caller
         ↓
Canonical Combat APIs
```

Actual Combat resolution:

```ts
resolveCombatAttack()
```

Damage application:

```ts
applyCombatAttackDamage()
```

Vẫn thuộc Combat/Entity/Core.

Skill không:

- Calculate hit.
- Roll dodge.
- Calculate critical.
- Calculate mitigation.
- Calculate damage.
- Update HP.
- Resolve death.

## 8.7. Combat Outcomes

Actual Combat có thể trả:

```text
dodged
landed
```

Đây là Combat-specific outcomes.

Không copy chúng thành một second Skill damage/outcome engine.

Một `dodged` attack vẫn là một execution attempt đã được Combat xử lý thành công.

Nếu activation cost/cooldown policy đã được commit khi accepted:

- Dodged không tự refund.
- Landed không tự thay cooldown.
- Skill không re-run resource spending.

Refund/retry mechanics, nếu cần, phải được thiết kế riêng với L3 policy và approved canonical ownership.

## 8.8. Execution Completion Reporting

Cung cấp một minimal immutable execution outcome contract để caller ghi nhận kết quả execution.

Proposed:

```ts
export type SkillExecutionStatus =
  | "completed"
  | "failed";

export interface SkillExecutionReport {
  readonly status: SkillExecutionStatus;
}

export interface SkillExecutionOutcome {
  readonly attemptId: string;
  readonly instanceId: string;
  readonly skillId: string;
  readonly actorEntityId: string;

  readonly dispatchKind: "combat" | "caller";
  readonly status: SkillExecutionStatus;
}
```

Proposed function:

```ts
reportSkillExecutionOutcome(
  request: SkillExecutionRequest,
  report: SkillExecutionReport
): SkillExecutionOutcome
```

Function chỉ:

1. Validate accepted request shape.
2. Validate caller-supplied report.
3. Capture exact identities.
4. Return detached immutable outcome.

Không tự execute.

Không tự xác thực actual executor đã chạy.

Không tạo persistent execution state.

## 8.9. Completion Semantics

`completed` nghĩa là caller báo actual execution path đã hoàn tất.

Với Combat:

```text
dodged → completed
landed → completed
```

vì Combat đã xử lý attack attempt.

Không map:

```text
dodged → failed
```

chỉ vì không gây damage.

`failed` nghĩa là caller báo execution/dispatch không hoàn thành theo application-level expectation.

Không tự tạo exception taxonomy hoặc arbitrary diagnostics engine.

Detailed Combat diagnostics tiếp tục nằm trong canonical Combat results.

## 8.10. Failure After Accepted Activation

Nếu Skill Activation accepted và candidate states đã được caller commit, nhưng actual executor sau đó failed:

- Không tự refund costs.
- Không tự rollback cooldown.
- Không mutate Skill Instance.
- Không tự retry execution.
- Không tạo compensating transaction.

Caller/L4 quyết định recovery policy.

Nếu game yêu cầu refund on execution failure, phải có future approved task và canonical owner.

Không tự sửa SK13/SK19 để thêm refund.

## 8.11. Non-Combat Execution

Với:

```text
dispatch.kind = caller
```

Skill vẫn có thể:

- Pass admission.
- Pass resource cost.
- Pass cooldown.
- Create accepted execution request.

Caller quyết định actual effect/action.

Không yêu cầu Combat module.

Không triển khai Effect System hoặc Healing Executor tại v0.5.4.

Không tuyên bố non-combat skill đã tạo gameplay effect chỉ vì activation accepted.

# 20. Completion Criteria

v0.5.4 đạt `CHECKPOINT_COMPLETE` khi:

- SK21–SK25 được triển khai đầy đủ.
- Activation attempt identity được phân biệt với Skill Instance/Combat Action identity.
- Admission, execution preflight, resource cost và cooldown gates có sequence rõ ràng.
- Rejection reason và priority deterministic.
- Malformed contracts fail-closed.
- Accepted activation trả immutable execution request.
- Accepted activation trả đúng một Resource candidate và một Cooldown candidate.
- Rejected activation không expose partial candidate states.
- Skill không gọi hoặc duplicate Combat target/attack/damage APIs.
- Actual installed integration chứng minh L4 có thể thực hiện canonical Combat handoff.
- Combat dodge/landed không gây automatic refund hoặc duplicate Skill execution.
- Execution outcome chỉ phản ánh caller-reported completion/failure.
- Không tạo generic ability engine, transaction manager hoặc global activation store.
- Existing Skill/Entity/Progression/Combat/Core semantics giữ nguyên.
- Installed package PASS.
- Strict NodeNext PASS.
- Full regressions PASS.
- Exact-head CI PASS.
