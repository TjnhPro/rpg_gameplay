## 3. Exactly additive proposed public API

**Four runtime functions and two public types**; no new state field, generic rule evaluator, callback executor or `EquipmentStateV2`.

```ts
export interface EquipmentAdmission {
  readonly eligible: boolean; // caller-derived L3/L4 fact, NOT authority
}
export type EquipmentAdmissionResult =
  | { readonly allowed: true; readonly reason: 'none' }
  | {
      readonly allowed: false;
      readonly reason: 'already_equipped' | 'slot_occupied' | 'ineligible';
    };

export function listEquippedEntries(
  state: EquipmentState,
  context: EquipmentValidationContext,
): readonly EquippedEntry[];

export function getEquippedEntryBySlot(
  state: EquipmentState,
  context: EquipmentValidationContext,
  slotId: string,
): EquippedEntry | null;

export function hasEquippedItem(
  state: EquipmentState,
  context: EquipmentValidationContext,
  instanceId: string,
): boolean;

export function assessEquipmentAdmission(
  state: EquipmentState,
  context: EquipmentValidationContext,
  item: ItemInstanceState,
  slotIds: readonly string[],
  admission: EquipmentAdmission,
): EquipmentAdmissionResult;
```

**Actual accepted predecessor API wins**. If these exact proposed shapes cannot be added without breaking v0.11.0, STOP and request Developer approval for the smallest compatible adjustment.

### 3.1. Validation order and input semantics

1. Validate **complete** `EquipmentState` with existing canonical `validateEquipmentState(state,context)`; canonical Item validation and definition binding must execute even for read requests and admission rejections. Do not create a second Equipment validator.
2. For lookup/has, require exact **nonblank string** slot/instance ID. Preserve exact bytes/case/whitespace; reject wrong type/blank with `TypeError`, never coerce or normalize. `get...` missing valid ID returns `null`, `has...` returns `false`.
3. For assess: validate incoming **full** `ItemInstanceState` using the matching full ItemDefinition from `context.items` via public Item `validateItemInstance`; reject missing definition, duplicate/invalid context, mismatched binding/invalid item data as **TypeError**. Do this even when `eligible:false`.
4. `slotIds` obey **exact Foundation nonempty/dense/unique/opaque-ID constraints**; explicit caller-provided list; do not infer slots from category/rarity. Validate the full array even if eligibility false.
5. `admission` must be an exact closed own-data record `{eligible:boolean}`. Missing/ad hoc default/truthy coercion/getters/symbol fields/unknown keys => `TypeError`. All structural checks happen **before** ordinary denial.
6. No public `slotDefinitions`, class lookup, allowed-slot dictionary, level calculations, GameItem/Entity dependency, hidden RNG/clock/ID/store or callbacks.

### 3.2. EQ06–EQ08: inspection semantics

- `listEquippedEntries`: fresh deeply frozen array of **fresh deeply detached** entries, in canonical EquipmentState order; no UI slot sorting, no dedup that masks invalid state, no `quantity`.
- `getEquippedEntryBySlot`: return the **whole containing EquippedEntry** for an exact slot. If one entry occupies `['hand_left','hand_right']`, both lookups return semantically identical whole entry snapshots. The returned snapshot must not alias the input; absent slot → `null`.
- `hasEquippedItem`: match exact `item.instanceId` against **entries**, not definition, slot name or implicit Item catalog; same definition can have two distinct valid instances in distinct slots.

### 3.3. EQ09–EQ10: deterministic admission decision

After full structural validation, for **valid** input decide in this priority:

| Priority | Condition | Exact result |
| --- | --- | --- |
| 1 | Incoming `item.instanceId` already present anywhere | `{allowed:false,reason:'already_equipped'}` |
| 2 | Any requested slot occupied by any entry | `{allowed:false,reason:'slot_occupied'}` |
| 3 | Explicit `admission.eligible === false` | `{allowed:false,reason:'ineligible'}` |
| 4 | All clear | `{allowed:true,reason:'none'}` |

- Check **all** requested slot IDs for collisions; do not accept partially available multi-slot targets.
- An occupied slot is ordinary valid but denied; duplicate occupied slots **within a supplied state** remain invalid `TypeError` from Foundation.
- A new Item with a different instanceId but same `definitionId` is not automatically denied; same definition may occupy different slots if caller policy allows.
- All result objects are **fresh, closed and frozen**; no candidates, reservations, writes, events, applied stats, game authority or slot claims.
- Assessing `eligible:true` is NOT L4 authorization to equip a player. L4 rechecks current Inventory membership, Item identity, slot policy, class/level and commit freshness.
