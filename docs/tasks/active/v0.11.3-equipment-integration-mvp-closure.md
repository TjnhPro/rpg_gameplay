## 4. EQ16: fully installed Equipment-only MVP flow

Use **physically installed** `@rpg/gameplay@0.11.3` root ESM in a clean independent consumer directory.

```text
L3 fixture: Item Definition + two distinct Item Instances (sword-A, sword-B)
  -> createEquipmentState(empty)
  -> list returns [] and slot lookup returns null
  -> assessEquipmentAdmission(sword-A, ['weapon_main'], eligible:true)
  -> equipEquipmentItem(sword-A)
  -> candidate: one entry, weapon_main→sword-A
  -> lookup weapon_main = sword-A; has sword-A = true
  -> replaceEquipmentItem(sword-A, sword-B, same slot)
  -> candidate slot weapon_main→sword-B, released=sword-A
  -> unequipEquipmentItem(sword-B)
  -> candidate empty; released=sword-B
  -> validate each candidate and compare exact literal immutable outcomes
```

Mandatory rejections: duplicate same instance, occupied slot, missing old instance, ineligible class/level fact, invalid item binding, overlapping supplied multi-slot state and request for two slots with one occupied. One future two-slot data representation should be validated, **not** a new two-hand rule. No `applyEffect`, damage, Item destruction, direct stats, actions/timers/events, Item instance generation or Equipment UI.

## 5. EQ17: real Item ↔ Inventory ↔ Equipment consumer handoff

Prove the actual Inventory MVP's **remove whole entry** and **add entry** public functions can be orchestrated without modifying either production module.

### 5.1. Equip from Inventory (safe quantity=1 case)

1. L3 fixture creates an ItemDefinition and **one canonical sword ItemInstanceState** using accepted Item APIs.
2. Accepted Inventory API creates a bag with **`InventoryEntry{item:sword,quantity:1}`** and accepted explicit Item context/stack policy/capacity/admission. Equipment starts empty.
3. Test-local L4 verifies **current Inventory membership, `quantity===1`, correct Item identity**, Equipment owner relation/slot policy and no simultaneous authoritative Equipment membership.
4. Independently request `removeInventoryEntry` candidate and `equipEquipmentItem` candidate from their **respective original snapshots**; check both accepted. Do not actually mutate either original.
5. Test-local L4 stages and publishes **both full snapshots as one in-memory object update** only if both candidates accepted and current baselines are still the ones validated. If either fails, publish **neither**; no partial moving/duplication.
6. Assert exact before/after: sword ID and properties unchanged; bag entry absent; equipped entry present once, no `quantity` in Equipment. This is a local fixture proof, **not a durable DB or distributed transaction guarantee**.

### 5.2. Unequip back to Inventory

1. Start from the accepted local equip state. Call `unequipEquipmentItem` → `candidate` + exact `released:sword` Item snapshot.
2. Call Inventory `addInventoryEntry` with **quantity 1** on current bag, supplying accepted Item Definition, policy, capacity and admission facts.
3. Publish **both** only if both accepted and the baselines remain current. Assert Equipment empty, Inventory has same sword ID/properties quantity 1.
4. Negative: Inventory full or admission false means **do not publish unequip candidate**; item stays equipped. Negative: an Inventory source stack with **quantity >1 cannot be equipped wholesale** by L4; no silent split/new ID/duplicate across storages.
5. If Inventory APIs cannot supply these exact semantics because of accepted predecessor changes, **STOP with evidence** instead of altering Inventory, Equipment or inventing a transaction helper in production.

### 5.3. Safe replacement crossing storages

Use **test-only** replacement handoff: old sword released by Equipment, candidate new sword equipped; the L4 fixture must stage removal of replacement sword from Inventory and admission of released old sword into Inventory as appropriate, or keep both uncommitted on bag capacity failure. This is a contract stress scenario; don't build full production swap coordinator and don't claim MMO atomicity. If real accepted Inventory add/merge interfaces do not permit the simulated variant, record it as **DEFERRED** rather than weakening tests or fabricating an API.
