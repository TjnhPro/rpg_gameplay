## 1. Objective

Triển khai **integration contracts và end-to-end verification** để Actor AI decisions từ AI01–AI25 được L4 đưa qua các **canonical gameplay gates/execution owners đã có**: Combat, Skill, Effect và Entity/Core.

**Nguyên tắc bắt buộc:** **AI đề xuất hành động; L4 kiểm tra, thực thi, commit và báo kết quả thực tế.** Actor AI không được tính toán damage, tự kích hoạt Skill, diễn giải Effect thành một admission engine khác hoặc viết game runtime mới.

| ID | Feature | Expected outcome |
| --- | --- | --- |

| **AI27** | Skill Integration | Skill intent đi qua existing Skill admission, resource/cooldown/preflight, activation, dispatch và execution outcome |
| **AI28** | Effect Restriction Integration | Active restrictions trở thành **AND gate** với canonical Combat/Skill/Effect eligibility; không tự tạo status rule engine |
| **AI29** | Action Execution Feedback | Terminal feedback có actor/decision/action/attempt correlation, phản ánh **actual** L4 outcome, immutable và fail-closed |
| **AI30** | Safe Fallback & Integration Closure | Rejection/failure không tự retry; caller có thể yêu cầu fresh decision, kiểm chứng scenarios và regression |

**Cụ thể phải chứng minh:**

1. **Monster, Player Auto Combat, Pet, Summon, NPC** cùng dùng một Actor AI decision API.
2. Một action intent chỉ là **proposal**, không phải execution token.
3. Combat/Skill/Effect canonical owners vẫn là nguồn quyết định cuối cùng.
4. Action success/failure được báo **sau** sự kiện thực tế, không suy ra từ `available` hoặc `accepted`.
5. Rejected/failed action không làm hỏng AI/Entity/Skill/Effect state do L2 Actor AI sở hữu; mọi state candidate do L4 quyết định commit.
6. Không tạo `AICombatEngine`, `AISkillEngine`, scheduler, persistence hay L2 orchestration runtime.

**MVP delivery:** nhỏ nhất có thể — ưu tiên **L4-style integration consumers/tests** sử dụng public APIs thật và một **feedback contract/validator thuần** trong `actor-ai` nếu chứng minh cần. Không thêm production orchestration không có owner.

## 3. Approved Architecture — L1 / L2 / L3 / L4

| Layer | Canonical responsibility | v0.7.5 rule |
| --- | --- | --- |
| **L1 Core** | Numerical stats, modifiers, hit/crit/damage/mitigation/resources | No new formulas or Legacy bypass |
| **L2 Entity** | Identity, Resources, Life, death transition | Preserve existing canonical transitions |
| **L2 Combat** | Attack context/admission, target validation, resolution and damage application | Never duplicate in Actor AI |
| **L2 Skill** | Skill identity/ownership/rank, cost/cooldown, activation, dispatch contracts/outcomes | Never bypass accepted public gates |
| **L2 Effect** | Active restrictions, statuses, apply/lifecycle | Only restriction contributions; L3/L4 interpret/apply |
| **L2 Actor AI** | Immutable AI decision and proposed intent, optional generic terminal feedback validation | No canonical combat/skill execution |
| **L3** | AI profiles, actionKey binding, action priorities, restriction-to-action policies | No hardcoded gameplay content in L2 |
| **L4** | World facts, availability, current Controller, admission orchestration, dispatch, outcome, authoritative commit/retry policy | **One execution authority** |

Preserve dependency graph exactly:

```text
entity      → []
progression → [entity]
combat      → [entity]
skill       → [entity]
effect      → [entity]
actor-ai    → [entity]
```

**Prohibited:** `actor-ai → combat/skill/effect/progression/world/movement`, modifications to Core, a new L2 scheduler, or second action execution owner. Integration code using multiple modules belongs to **consumer/L4 test composition**, not a new production `AIIntegrationEngine`.

### D01–D05 preserved

- **D01 A:** L2 Actor AI immutable state; L4 authoritative commit; no state changes merely because an intent was emitted.
- **D02 A:** Existing flat FSM + ordered priority; no Behavior Tree/Utility AI.
- **D03 A:** At most one authoritative controller per actor. Manual takeover must invalidate AI execution if authority changed.
- **D04 A:** Feedback follows **actual** canonical dispatch/execution result; never optimistic success.
- **D05 A:** Explicit deterministic inputs/order, stable replay and no hidden time/RNG.

## 4. Integration Flow & Freshness Rules

Expected caller composition:

```text
L4 supplies Perception / World facts
          ↓
L2 Actor AI: target selection (AI11–15)
          ↓
L2 Actor AI: behavior transition (AI16–20)
          ↓
L4 supplies explicit availability from current gameplay snapshots
          ↓
L2 Actor AI: action selection (AI21–25)
          ↓
Existing ActorAIActionIntent
          ↓
L4 validates actor/controller/target/decision freshness
          ↓
L3 actionKey binding → action kind / Skill instance / movement route
          ↓
Effect restrictions AND canonical Combat/Skill admission
          ↓
Existing canonical execution/candidate APIs
          ↓
L4 authoritative commit / dispatch / outcome
          ↓
L4 builds truthful Actor AI terminal feedback
          ↓
L2 validates correlation (if additive validator needed)
          ↓
L4 may schedule **a fresh decision** explicitly
```

### Hard rules

1. `available` from AI21–AI25 is **advisory**; recheck canonical admission at execution.
2. Current `actorId`, `decisionId`, `actionKey`, target and active controller must match the accepted proposal and authoritative state.
3. `decisionId` is **not** automatically a Combat `actionId` or Skill `attemptId`; mapping is explicit and owned by L4.
4. L4 rejects stale/duplicate attempts; L2 stateless validation cannot enforce durable at-most-once execution.
5. No partial authoritative commit from rejected admission or failed candidate generation; accepted Skill resource/cooldown candidate commit and later execution failure are **different stages**. Do not assume automatic refund/rollback.
6. If the target became dead, vanished, or became ineligible after AI selection, **no attack/Skill execution**; do not trust stale perception or AI selection.
7. No gameplay mutation occurs in AI feedback validation.

## 5. AI26 — Combat Integration

### 5.1. Objective

End-to-end **Basic Attack** from a selected AI intent through **existing Combat public APIs**, invoked by L4 integration consumer.

### 5.2. Required real pipeline

```text
AI action kind = basic_attack
  → L4 maps actionKey to Combat actionType/context
  → createCombatActionContext()
  → evaluateCombatActionAdmission()
  → evaluateCombatTargetValidation()       [only after admitted]
  → L3/L4 supplies canonical numerical attack inputs
  → resolveCombatAttack()
  → applyCombatAttackDamage()
  → Entity Resource/Life candidate
  → L4 commits accepted candidates
  → L4 reports terminal feedback
```

- L4 binds exact source/target IDs, current Life states and relation policy.
- Target validation must not run as if admission succeeded when `source_dead` or otherwise rejected.
- `resolveCombatAttack()` uses **real Core Kernel stages**, seeded/explicit RNG from Foundation as existing Combat contract requires. No invented hit/damage math.
- `applyCombatAttackDamage()` owns canonical resource/death handling. Tests assert the real `.appliedDamage` / `.lifeResult` or documented zero/dodge outcomes; do not recompute `before-after` as a universal damage oracle.
- A landed zero-damage or dodged attack can count as an executed, completed attempt **without damage**, not a fabricated rejection.
- No second HP/life store or hit resolution in Actor AI.

### 5.3. Required rejection paths

- Source missing/dead/ineligible.
- Target missing/dead/relation denied.
- Effect block even when Combat would otherwise admit.
- Manual control takeover after action selection.
- Stale target reference, stale state/decision, duplicate dispatch attempt.

Each must result in **zero unauthorized Entity mutation** and a precise caller-reported rejection; do not invoke subsequent execution gates after decisive rejection.

## 6. AI27 — Skill Integration

### 6.1. Objective

Integrate selected `skill` intent using **canonical Skill** preflight, payment/cooldown candidate and explicit dispatch/outcome. Actor AI does not own Skill catalog or activation.

### 6.2. Required real pipeline

```text
AI action kind = skill
  → L4 resolves actionKey → SkillDefinition / SkillInstance
  → L4 checks selected actor/target and current ownership/rank
  → evaluateSkillActivationAdmission()
  → actual Skill Resource/Cost/Cooldown gates as accepted
  → Effect restriction contribution and action-specific preflight
  → L4 supplies SkillExecutionIntent and SkillExecutionPreflight
  → activateSkill()
      rejected → no candidate commit/dispatch
      accepted → Resource + Cooldown **candidates**, SkillExecutionRequest
  → L4 verifies freshness and authoritative candidate commit
  → L4 dispatches request through existing Skill/Combat/Effect/caller path
  → reportSkillExecutionOutcome() from **actual** execution report
  → L4 reports terminal feedback to Actor AI
```

### 6.3. Canonical distinctions

- `SkillAdmissionResult.status = admitted` ≠ activation accepted.
- `SkillActivationResult.status = accepted` ≠ execution completed.
- `SkillExecutionRequest` is **dispatch request**, not success evidence.
- `SkillExecutionOutcome.status = completed | failed` comes from actual caller execution report. Do not fabricate `completed` merely because dispatch began.
- Failed **after** an accepted/committed activation does **not** imply resource/cooldown refund; do not invent compensation policy.
- Combat-dispatch Skill must use existing Combat preflight and target validation; caller-dispatch Skill remains explicit, not silently interpreted as a Combat attack.

### 6.4. Required Skill scenarios

- Available Skill, actual dispatch completes → terminal completed.
- Skill on cooldown → canonical rejection; no dispatch.
- Insufficient resource → canonical rejection; no resource/cooldown candidate published.
- Skill not owned or insufficient rank → rejection; no dispatch.
- Actor dead or Effect-silenced → rejection; no dispatch.
- Target stale/dead/invalid → fail before effect/attack execution.
- Accepted Skill request followed by actual dispatch failure → **failed**, not completed; preserve committed resource/cooldown semantics without fabricated refund.
- Self-targeted support Skill uses actor ID; no fabricated hostile target.

Do not implement new Skill damage/effects, AoE/ground delivery, Skill ownership model, or Skill engine.

## 7. AI28 — Effect Restriction Integration

### 7.1. Objective

Apply existing Effect restriction contributions **only** through the approved L3/L4 gate composition.

### 7.2. Required public pipeline

```text
EffectLifecycleState + EffectStatusState
  → listActiveEffectRestrictions() / evaluateEffectRestrictionGate()
  → L3 policy selects blockedByRestrictionIds for this action
  → L4 computes effective availability and canonical preflight
  → Action may execute only if **all** required gates allow
```

No `AIStatusEngine`. No L2 hardcoded interpretation of `stun`, `silence`, `root`, `immune-poison`, etc. Use **opaque IDs** configured by L3.

### 7.3. AND-gate semantics

- A restriction result `allowed` **does not grant** action admission.
- A restriction result `blocked` denies this action regardless of other admission results.
- Different action kinds can have different blocked-ID policies, supplied by L3. Example: silence blocks magic Skill, not automatically Basic Attack; stun may block both.
- AI action selection could have used an earlier `available` fact; the **latest** L4 restriction check wins at execution.
- Absence of a restriction does not override insufficient resource, cooldown, target validation, Life or controller checks.
- Effect lifecycle/status companion time and membership must be aligned; malformed or stale inputs fail closed.

### 7.4. Required scenarios

- Stun configured to block Attack + Skill → neither dispatches.
- Silence configured to block Skill, not Basic Attack → Skill rejected, Basic Attack may be freshly considered.
- Restriction removed/expired through accepted canonical Effect lifecycle → later explicit fresh decision may become available.
- Unrelated restriction ID does not block an action unless L3 policy matches.
- Effect blocking occurs after AI proposal but before execution → AI proposal cannot bypass it.
- No Effect cleanup/apply/update occurs merely because Actor AI checked restriction.

      readonly status: 'completed';

    }
  | {
      readonly decisionId: string;

The proposed public validator:

```ts
export function validateActorAIActionExecutionFeedback(
  selection: ActorAIActionSelectionResult,
  feedback: ActorAIActionExecutionFeedback

```

**Preflight rule:** The `ActorAIActionSelectionResult` is the accepted AI21–AI25 result **as actually implemented**; if naming/shape differs, use exact accepted types. If no production validator is demonstrably required, provide strong installed/L4 consumer validation without introducing an extra public framework. No broad feedback engine.

### 8.3. Required correlation

The validator must verify:

1. Selection is **selected / proposed** with one existing `ActorAIActionIntent`.
2. `actorId`, `decisionId`, `actionKey` and `targetEntityId` match **exactly**.
3. `attemptId` is a nonblank caller-supplied reference, not generated by Actor AI.
4. `admission/rejected` requires a nonblank `reasonId`.
5. `execution/completed` requires `reasonId = null`.
6. `execution/failed` requires a nonblank `reasonId`.
7. Other phase/status/reason combinations reject.
8. Closed own-data record, no accessors/getters, inherited or unknown fields; return detached, frozen snapshot.
9. No feedback accepted for `no_action`, including manual-control outcomes.
10. No AI State/Combat/Skill/Effect mutation and no event dispatch.

**Do not** replace the canonical Skill `SkillExecutionOutcome` or Combat `CombatDamageApplicationResult` with this generic feedback. L4 maps actual domain outcomes into generic feedback only after checking their real meaning.

### 8.4. Outcome mapping — illustrative, L4 owns provenance

| Canonical event | AI terminal feedback | Important distinction |
| --- | --- | --- |
| Combat/Skill/Effect admission rejects | `admission / rejected` | Nothing executed |
| Combat attack executed, including dodge or zero damage | `execution / completed` | Completion does not imply hit/damage |
| Skill activation accepted but dispatch not yet finished | **No terminal feedback yet** | Accepted ≠ completed |
| Skill dispatch `reportSkillExecutionOutcome(... completed)` | `execution / completed` | Only after actual execution report |
| Skill dispatch `... failed` | `execution / failed` | No invented refund |
| L4 movement/return action actually completes | `execution / completed` | Movement source of truth is outside L2 |
| L4 movement/return action rejects or fails | `admission / rejected` or `execution / failed` | Distinguish stage |

### 8.5. Feedback trust boundary

This is an **immutable report/validation contract**, not a secure proof of execution, durable ledger, replay-prevention store, or transaction manager. L4 must verify source receipts, attempt identity, current state and duplicate handling before publication.

Do not add:

```text
lastActionStatus into ActorAIState
lastAttemptId cache in L2
execution registry
feedback event bus
exactly-once network guarantee
```

AI lifecycle/recovery transitions that consume feedback belong to v0.7.6 unless a narrowly scoped accepted AI29 contract already exists.

## 9. AI30 — Safe Fallback & Integration Closure

### 9.1. Objective

Prove that action **rejection or execution failure** is handled safely by the L4 caller, without an autonomous retry engine in Actor AI.

### 9.2. Safe fallback policy

- **Before dispatch:** If preflight rejects the selected action, do **not** execute it. Report terminal rejection; L4 may explicitly request **fresh availability + new `decisionId` + new Action Selection**.
- **After execution failure:** Use the domain-specific actual failure receipt; preserve any accepted committed side effects. L4 may request a **new** decision, not replay the same intent automatically.
- **On successful completion:** Publish completed outcome; do not automatically choose/execute another action.
- **Manual controller takeover:** Stop AI dispatch; no fallback action is selected by AI until authority returns to AI through a separately approved controller lifecycle path.
- **No fallback available:** Return `no_action / no_candidate`; do not fabricate Wait or spin a decision loop.
- **Freshness:** Confirm no stale target, restriction, cooldown or entity state; old preflight cannot authorize next attempt.

No in-L2 callback to `evaluateActorAIActionSelection()` after a failed action. Orchestration belongs to L4.

### 9.3. No double dispatch

Simulate duplicate terminal feedback / repeat attempt:

- L4 detects duplicate attempt and does not execute/commit it again.
- Stateless L2 feedback validator only confirms shape/identity; it must **not** claim duplicate prevention across invocations.
- No second resource payment, Skill cooldown start, damage application or movement for the same committed attempt.

If a test cannot prove this without creating an L4 runtime, use a minimal caller-owned attempt ledger **inside the integration fixture only**, not production Actor AI. Distinguish local fixture idempotency from distributed exactly-once.

### 9.4. Movement integration boundary

`approach_target`, `return_home` and `wait` remain structural intents:

- L4 mock/fixture may report explicit accepted/rejected/completed/failed movement outcomes.
- **No** World/Spatial/pathfinding production implementation is authorized.
- Movement is **not** a canonical RPG Core calculation and should not be simulated as Combat damage.
