## 1. Objective & features

Implement **controlled, explicit, deterministic membership changes** to an existing Encounter while preserving the canonical five-field `EncounterState` and the strict `encounter → entity` module boundary.

| Feature | Responsibility | Mandatory result |
|---|---|---|
| **EN11** | Participant Join | Validate a caller-requested Entity joining a declared side and return one immutable roster candidate |
| **EN12** | Participant Leave | Remove a member explicitly, with no implied Entity death or encounter completion |
| **EN13** | Side Membership | Inspect one participant's side and support explicit, policy-admitted transfer to another **already declared** side |
| **EN14** | Participation Eligibility | Apply explicit L3 operation/status policy and caller-provided canonical Life/World facts; separate structural errors from admission rejections |
| **EN15** | Participation Outcomes | Exact applied/rejected reasons, deterministic ordering, no silent joins, transitions or L4 commits |

**End state:** a consumer can create a prepared encounter using v0.8.0, activate it through v0.8.1, then submit **Join / Leave / Change Side** operations through one reusable Encounter API. L2 assesses and produces **state candidates**; L4 independently verifies current authority and commits.

### Expected composition

```text
L4 owns current Encounter + EntityCollection + truthful Life/World facts
                       │
                       ▼
L3 supplies explicit membership policy
                       │
                       ▼
L2 Encounter: validate state / request / policy
                       │
                admission assessment
                       │
                       ▼
         applied candidate | rejected/null
                       │
                       ▼
L4 compares current state + Entity/World revisions and commits or refuses
```

**No physical spawn, Combat admission, Skill/Effect operation, AI decision, victory/defeat, reward, World cleanup, turn scheduler or state store is implemented here.**

## 4. Ownership and immutable module boundary (L1–L4)

**L1 RPG Core:** owns calculations, not participant/side membership; no Core calculation or Core edit in this milestone.

**L2 Entity:** canonical Entity ID, EntityCollection membership and Life status (`alive`/`dead`). Encounter reads canonical values; it may not create/kill/revive Entities, invent Life states, or maintain a second Entity registry.

**L2 Encounter:** owns the *one* Encounter's immutable side/participant association, structural validation, generic membership policy assessment and proposed member changes. It does **not** own World existence, cross-encounter uniqueness, Combat relations or gameplay admission.

**L3:** owns allowable operations for `prepared`/`active`, join Life policy, World-readiness gate, team assignment requests, and game-specific capacity/party rules. No default Player/Monster faction, auto-reinforcement, score system or respawn rule. Do not add an arbitrary DSL to L2.

**L4:** owns physical spawn/despawn, current World presence, truth/freshness of Life/readiness facts, actor controller, cross-Encounter exclusivity when desired, authoritative state and membership commit, concurrency, revision/CAS checks, network/persistence, turn/realtime scheduling, and canonical action dispatch. L4 must reject a proposed roster candidate if any relevant current authority has changed.

**Module dependency graph (unchanged after v0.8.0):**

```text
entity      → []
progression → [entity]
combat      → [entity]
skill       → [entity]
effect      → [entity]
actor-ai    → [entity]
encounter   → [entity]
```

No new module registry entry in v0.8.2; v0.8.0 owns that entry. No direct `encounter → combat/skill/effect/actor-ai/world` or reverse dependency. No manager/engine/scheduler/global store, new runtime dependency, or L4 module inside `src/`.

## 5. Public API strategy — one evaluator, one candidate transition

Do **not** add separate `joinEncounterEngine` / `leaveEncounterEngine` / `switchSideEngine` or multiple independent membership stores. Prefer one discriminated request, one admission evaluator and one transition function, with a small side-inspection helper.

export type EncounterMembershipOpenStatus = 'prepared' | 'active';

## 6. EN11 — Participant Join

A join request explicitly supplies `encounterId`, `entityId`, target `sideId` and a current **caller-owned** `EncounterParticipantActivationFact` (`life` plus `worldReady`). The fact is eligibility evidence, not World admission proof.

### 6.1. Structural admission

1. Validate full current `EncounterState` against canonical `EntityCollection`, via accepted v0.8.0 `validateEncounterState`.
2. Validate complete closed policy and request (including nested Life/readiness), with exact encounter/entity correlation. No getter invocation.
3. Wrong `request.encounterId !== state.encounterId` is **TypeError** (identity binding failure), never a Join attempt in another Encounter.
4. Join fact must bind `readiness.entityId === request.entityId` and `readiness.life.entityId === request.entityId`. Malformed mismatch is **TypeError**.
5. All join fields must exist; absent Life/World fact is **TypeError** (not optimistic eligibility).

### 6.2. Domain admission — first matching reason

After all structural validation:

1. Encounter status not `prepared`/`active` → `encounter_not_open`.
2. Join not allowed in actual status by L3 policy → `operation_not_allowed`.
3. Destination `sideId` not in existing `state.sides` → `side_not_found`.
4. Existing `entityId` already participates on **any** side → `already_participating`.
5. `entityId` not found in current canonical `EntityCollection` → `entity_not_found`.
6. Caller Life status not in `policy.allowedJoinLifeStatuses` → `join_life_not_allowed`.
7. `requireWorldReadyOnJoin === true` and `readiness.worldReady === false` → `join_world_not_ready`.
8. Otherwise → `admitted`.

Status/operation/side/duplicate checks precede Life/World eligibility for deterministic diagnostics. A valid `dead` Life snapshot is structurally acceptable; it is admitted **only if L3 explicitly allows `'dead'`**. Do not automatically revive.

### 6.3. State candidate

On admission, append an existing-shape participant:

```ts
{entityId: request.entityId, sideId: request.sideId}
```

to the **end** of `state.participants`. Preserve each existing participant's exact identity/order and every declared side. **Only** `participants` differs; Encounter's `status`, `encounterId`, `definitionId`, `sides` remain semantically identical.

A join request **does not** create an Entity, change EntityCollection, physically spawn, assign AI behavior, authorize Combat, pay resources, or reserve an encounter slot in an L4 database. L4 must recheck actor's current cross-Encounter association and freshness before commit.

### 6.4. Examples

```text
Encounter forest-fight-001: active
Sides: party, enemies
Current roster: player-001 → party; monster-001 → enemies
Join: monster-002 → enemies; Life alive; worldReady true
L3 permits join while active

Result: applied candidate; participants appended monster-002 → enemies
Encounter stays active. No World spawn or new Combat action.
```

Already-participating `monster-001` cannot be joined again, even to a different side: that is **not** an implicit transfer.

## 7. EN12 — Participant Leave

A leave request has **exactly**:

```ts
{operation:'leave', encounterId:'forest-fight-001', entityId:'monster-001'}
```

No `sideId`, `readiness`, Life fact or removal reason is accepted on a leave request. These are not needed for structural membership removal; game-specific disconnect/despawn/death causes are L4 facts, not synthetic Life transitions at L2.

**Domain admission** (after complete structural validation):

1. Status outside prepared/active → `encounter_not_open`.
2. Status disallowed by `policy.leaveAllowedStatuses` → `operation_not_allowed`.
3. Participant absent → `participant_not_found`.
4. Else → `admitted` with `previousSideId` from canonical roster, `sideId:null`.

**State candidate:** remove **only** the matching participant, retaining order of everyone else, preserving `sides`, identity, definition and `status`. The related Entity stays in `EntityCollection`, remains alive/dead as before, keeps resources/AI state, and is **not** physically despawned.

**Critical EN-D05 invariant:** removing the last fighter from a side or the last participant overall leaves the same Encounter `prepared`/`active`. A temporarily empty active Encounter may be evaluated for completion **later** by EN21–EN25; v0.8.2 must not choose winner, draw, cancellation or reward. `leave` is not equivalent to `defeated`, `escaped` or `dead` without a future explicit game policy.

Repeated leave is **rejected** `participant_not_found`, never an idempotent success invented by L2. L4 may choose its own external idempotency semantics.

## 8. EN13 — Side membership inspection and explicit transfer

### 8.1. Single canonical side membership

`getEncounterParticipant(state, entities, entityId)` revalidates full state and current canonical references; returns an **independent frozen** `{entityId,sideId}` copy or `null` if not in roster. It must not depend on Entity.kind, Combat relation, Actor AI target policy or a new side-membership cache.

One Entity may occupy **at most one side in one Encounter**. That invariant was established by v0.8.0 and must remain enforced.

### 8.2. Explicit side change

A `change_side` request has `operation`, `encounterId`, `entityId`, and destination `sideId`. It does not add a new side or new participant. No implicit leave+join cascade and no second Life check is introduced; any Life/World restrictions on transfers beyond the approved generic policy remain L3/L4 responsibilities.

**Domain admission precedence:**

1. Terminal/not-open encounter → `encounter_not_open`.
2. Side change not allowed at this status → `operation_not_allowed`.
3. Participant absent → `participant_not_found`.
4. Destination side not declared → `side_not_found`.
5. Destination matches existing side → `already_on_side`.
6. Otherwise → `admitted`.

**Candidate:** replace exactly one participant's `sideId` **in its original roster position**; do not alter the participant ID, other members, side declarations, Entity or Encounter status. Return `previousSideId` and destination `sideId` for caller reconciliation.

Do **not** update Combat target relations, actor AI perception/ranking or attack eligibility automatically. At dispatch, L4 recomputes canonical relation/target admission and denies stale cross-side actions. No friendly-fire policy is inferred from side IDs.

## 9. EN14 — Explicit membership policy and eligibility

### 9.1. Status configuration

`joinAllowedStatuses`, `leaveAllowedStatuses`, `changeSideAllowedStatuses` are **ordered, unique**, closed arrays of only `'prepared'` or `'active'`. Empty arrays are allowed and mean that operation is **never permitted**. Status `'resolved'`, `'closed'`, `'cancelled'` and unknown strings are invalid **policy data** (`TypeError`), not a way to reopen terminal encounters.

`allowedJoinLifeStatuses` must be a **nonempty unique** array of canonical `EntityLifeStatus` (`'alive'|'dead'`), and `requireWorldReadyOnJoin` must be boolean. These fields are required even when the join allowed-status list is empty; no implicit defaults or truthiness coercion.

A representative L3 policy:

```ts
const policy = createEncounterMembershipPolicy({
  joinAllowedStatuses: ['prepared','active'],
  leaveAllowedStatuses: ['prepared','active'],
  changeSideAllowedStatuses: ['prepared'],
  allowedJoinLifeStatuses: ['alive'],
  requireWorldReadyOnJoin: true,
});
```

A fixed-roster turn-based game may instead configure empty active join/leave/transfer lists; dynamic-capable **L2** does not force them to be enabled.

### 9.2. Explicit admission, not authoritative access control

Every request is validated before the evaluator produces a domain result. `evaluateEncounterMembershipAdmission` is read-only and cannot imply a successful commit. L4 must enforce authoritative current controller, zone/shard ownership, game capacity, party restrictions, encounter identity uniqueness and current Life/World truth as appropriate.

The `readiness` fact from v0.8.1 is reused for join; it does **not** create a second Life snapshot owner. A caller could supply a well-formed but stale fact. The evaluator must not represent its decision as secure execution authorization.

**Well-formed but ineligible** → structured `rejected` result. **Malformed structure/correlation** → `TypeError`, before a terminal-status or duplicate outcome. This follows the accepted Encounter/Actor AI validation pattern.

### 9.3. Activation policy remains independent

Do not re-run `evaluateEncounterActivationAdmission` on every Join/Leave or require the original activation minimums to remain true forever. Activation is a historical transition from `prepared → active` using readiness facts at that time.

- Adding an eligible participant **does not** auto-activate a prepared Encounter.
- Leaving participants does **not** set active → prepared or active → closed.
- Empty active sides are allowed structurally; future completion assessment is independent.
- Initial activation policy cannot silently become permanent membership policy.
- There is no global side-capacity rule or default two-team minimum in v0.8.2.

## 10. EN15 — Admission/transition envelopes and rejection contract

### 10.1. One canonical admission evaluator

`evaluateEncounterMembershipAdmission(...)` must:

1. Validate/recapture `EncounterState` against the **current** canonical EntityCollection.
2. Capture the full closed policy and discriminated request, including nested join fact.
3. Check exact Encounter/fact/Entity ID correlation (`TypeError` if mismatched).
4. Apply the domain decision order specific to join, leave or change-side.
5. Return a detached/frozen `EncounterMembershipAdmissionResult` with exact reason and diagnostic IDs.

**No state update** or mutating an array from `EncounterState` may occur in this function.

### 10.2. One immutable transition function

`applyEncounterMembershipChange(...)` **must recompute** structural validation and admission against the supplied state, EntityCollection, policy and request. It may call the same internal evaluator. It must **not** accept or trust a caller-fabricated `EncounterMembershipAdmissionResult` as an authorization token.

- If admitted: `status:'applied'`, `reason:'none'`, new frozen/detached `EncounterState` candidate.
- If rejected: `status:'rejected'`, same exact reason/diagnostics as admission, `state:null`.
- Never return partially modified roster when rejected.
- Never adjust lifecycle `status` as a side effect.
- Every successful application changes the roster **semantically** (join appends; leave removes; change-side changes side). A same-side transfer is rejected instead of silently returning an unchanged state.
- Replaying a request against a **newly committed matching state** gets the appropriate duplicate/missing/same-side rejection; evaluating twice against the **same old snapshot** may produce identical candidates, **not** exactly-once enforcement.
- No events, timers, callbacks, resource costs, effect cleanup, waves, completion flags or action dispatch.

### 10.3. Result diagnostics and precedence

For all three operations, envelope `operation`, `encounterId` and `entityId` are copied exactly from structurally valid request. `previousSideId` reflects the current roster. `sideId` reflects requested destination for join/change-side, null for leave.

Domain check priority is fixed by Sections 6–8. **Never** sort policies, side IDs, participants or evidence by locale, JSON property order or observation order. For a well-formed conflicting case (e.g., already member + Life disallowed), the earlier domain reason wins.

No new `EntityLifeStatus`, `CombatAdmissionStatus`, Encounter outcome status or dispatch success result is created. Rejection reason strings are stable public contracts, not user-facing localized messages.

## 11. Structural, immutable and deterministic invariants

**Closed records:** exact own string keys, plain Object/null prototype, no inherited members, no extra fields, no symbol properties, no getters/setters, no arrays as records. Reject malformed requests before any domain no-op. Never invoke user getter code.

**Arrays:** dense ordinary arrays with own data indices, no holes, inherited index values, symbol/extra keys or coercion. Reject duplicate configured statuses, duplicate IDs, non-string statuses and malformed Life fields. Preserve input order of `sides`/`participants` exactly.

**Snapshot detachment:** factories, admission envelopes, read helper and transition result must be deeply frozen/detached. No shared arrays/records with caller input; caller input must remain unchanged and **not frozen by the library**.

**Canonical binding:** current Encounter participants must all still resolve through `validateEncounterState(state, entities)` before any membership operation. For a *new* join ID, membership absence in EntityCollection is an **eligibility rejection** (`entity_not_found`), not implicit Entity creation. Exact ID spelling/case/whitespace is preserved.

**Determinism:** same explicit values and current canonical EntityCollection yield identical semantic output, independent of object references, World ordering, RNG, wall-clock or hidden mutable caches. No `Date.now`, `Math.random`, timer, provider, ID generator, console/log side effects or global state in production code.

**Life owner:** never copy Life/resource/HP into EncounterState, never modify Entity Life based on Join/Leave. The join Life fact is advisory; L4 must revalidate current authority at commit.

**Replay / TOCTOU:** L2 does not promise unique commits; two concurrent candidate evaluations can be identical. L4 must own atomic compare-and-set or equivalent across Encounter roster, current Entity membership and World facts. Neither `EncounterState` nor this milestone adds a revision/cursor counter.
