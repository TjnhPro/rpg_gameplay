# 4. GF04 — Module Dependency Resolution

## 4.1. Objective

Cho phép kiểm tra các modules được lựa chọn có đủ dependencies cần thiết hay không, đồng thời xác định thứ tự dependency-first.

Dependency declarations đã tồn tại tại GF01:

```ts
interface GameplayModuleDefinition {
  readonly id: string;
  readonly optional: boolean;
  readonly dependencies: readonly string[];
}
```

GF04 chịu trách nhiệm diễn giải các dependencies này.

Không thay đổi format của `GameplayModuleDefinition`.

## 4.2. Required Public Function

Bổ sung public function tương đương:

```ts
resolveModuleDependencies(
  registry,
  configuration
)
```

Kết quả tối thiểu:

- Danh sách module IDs hợp lệ.
- Sắp xếp theo dependency-first order.
- Immutable, không chứa duplicate IDs.

Tên type/output cụ thể được thiết kế phù hợp conventions, nhưng phải thể hiện rõ đây là **resolved selection**, không phải danh sách module đã được khởi chạy.

Không cần triển khai nhiều hàm graph utilities công khai nếu một function đáp ứng đầy đủ.

## 4.3. Required Behavior

### A. Missing Dependency

Ví dụ:

```text
Registered:
  equipment → inventory

Enabled:
  equipment

Disabled:
  inventory
```

Kết quả: REJECT.

Diagnostic phải chỉ ra ít nhất:

- Module yêu cầu dependency.
- Dependency bị thiếu hoặc chưa enabled.

Không được âm thầm enable Inventory.

### B. Unknown Dependency

Ví dụ:

```text
Registered:
  equipment → unknown-module

Enabled:
  equipment
```

Kết quả: REJECT.

GF01 cho phép khai báo dependency chưa được đăng ký. GF04 phải phát hiện lỗi khi module phụ thuộc được lựa chọn.

Không tự register missing module.

### C. Valid Dependencies

Ví dụ:

```text
Registered:
  inventory
  equipment → inventory
  loot → inventory

Enabled:
  inventory
  equipment
  loot
```

Kết quả hợp lệ.

Tất cả dependencies phải xuất hiện trước module sử dụng chúng trong resolved order.

### D. Dependency Cycles

Phải phát hiện và từ chối cycles thuộc tập module đang được lựa chọn.

Ví dụ:

```text
A → B
B → C
C → A
```

Kết quả: REJECT.

Diagnostic phải cung cấp đủ thông tin để xác định cycle.

Không trả partial result như thể resolution thành công.

### E. Disabled Modules

Một module không được lựa chọn không cần kiểm tra toàn bộ dependency graph của nó tại thời điểm composition.

Ví dụ:

```text
Registered:
  inventory
  optional-feature → unknown-module

Enabled:
  inventory

Disabled:
  optional-feature
```

Resolution hợp lệ.

Lý do: L2 cho phép modules optional tồn tại mà một game không sử dụng chúng.

Tương tự, một cycle chỉ nằm trong các module không được lựa chọn không được làm một composition độc lập thất bại.

Những modules này phải được kiểm tra khi chúng thực sự được lựa chọn.

### F. Required Modules

Required modules từ GF03 phải thuộc tập được lựa chọn.

Nếu configuration không chứa required module, resolution phải reject thay vì tự bổ sung.

Điều này cũng áp dụng khi một registry mới được truyền cùng configuration snapshot cũ và xuất hiện required module chưa có trong snapshot.

Không thay đổi semantics của `configureModules()` để giải quyết vấn đề này.

### G. Invalid Configuration

GF04 phải reject cấu hình không hợp lệ, bao gồm:

- Enabled ID không tồn tại trong registry.
- Duplicate enabled IDs.
- Required module vắng mặt.
- Dữ liệu configuration không đúng contract.

Không silently ignore những trường hợp trên.

Sử dụng error semantics nhất quán với Foundation hiện tại, ưu tiên `TypeError` cho input/contract violation với diagnostic có ý nghĩa.

## 4.4. Deterministic Ordering

Resolution phải xác định và tái hiện được.

Quy tắc:

1. Dependencies xuất hiện trước dependents.
2. Module xuất hiện đúng một lần.
3. Các module độc lập hoặc đồng thời đủ điều kiện được ưu tiên theo registration order.
4. Không phụ thuộc vào thứ tự duyệt hash/object không được kiểm soát.
5. Cùng registry và configuration phải cho cùng kết quả.

Ví dụ:

```text
Registration order:
  equipment
  inventory
  loot

Dependencies:
  equipment → inventory
  loot      → inventory

Enabled:
  equipment, inventory, loot
```

Expected:

```text
inventory
equipment
loot
```

Thứ tự trong `ModuleConfiguration.enabledModuleIds` vẫn là registration order theo GF03. **Không sửa configuration đó để biến nó thành topological order.**

GF04 tạo resolved order riêng.

## 4.5. State & Mutation Safety

- Không sửa registry.
- Không sửa configuration.
- Không mutate dependency arrays.
- Không dùng module-level mutable resolver cache.
- Không giữ state giữa những lần resolution độc lập.
- Resolution thất bại không để lại partial state.
- Output không bị caller mutate để làm thay đổi input hoặc những lần resolution khác.

Có thể sử dụng temporary maps/sets nội bộ trong một function call nếu không làm rò rỉ mutable state.

## 4.6. GF04 Explicit Non-Goals

Không triển khai:

- Auto-enable dependencies.
- Optional dependency semantics mới.
- Runtime dependency injection.
- Dynamic package/module loading.
- Runtime dependency monitoring.
- Hot module activation.
- Lifecycle ordering execution.
- Event/command coordination.
- Caching framework.
- Persistent dependency graph.

GF04 chỉ xử lý dependency declarations của **selected modules**.

# 5. GF05 — Module Composition

## 5.1. Objective

Tạo một representation thống nhất, bất biến của tổ hợp gameplay modules đã được lựa chọn và resolution thành công.

Ví dụ conceptual:

```ts
const registry = registerModule(
  createModuleRegistry(),
  {
    id: "inventory",
    optional: true,
    dependencies: []
  }
);

const configuration = configureModules(
  registry,
  {enable: ["inventory"]}
);

const composition = composeModules(
  registry,
  configuration
);
```

`composition` mô tả những modules được lựa chọn và thứ tự phụ thuộc hợp lệ.

Nó không phải một runtime instance.

## 5.2. Required Public Function

Bổ sung một public function tương đương:

```ts
composeModules(
  registry,
  configuration
)
```

Function này phải:

1. Sử dụng canonical GF04 dependency resolution.
2. Reject invalid dependency graph.
3. Lựa chọn chính xác các module enabled.
4. Trả về immutable composition snapshot.
5. Giữ được resolved order.
6. Không làm thay đổi registry/configuration đầu vào.

**GF05 không được tự viết thuật toán resolution thứ hai.**

## 5.3. Composition Contract

Một composition phải cung cấp tối thiểu:

- Danh sách module IDs được lựa chọn theo dependency-first order.
- Các validated module definitions tương ứng.
- Một representation có thể dùng làm input cho Runtime Context ở v0.1.3.

Không cần:

- Module instances.
- Lifecycle hooks.
- Runtime services.
- Dependency injection container.
- Event bus.
- Command handlers.
- Clock hoặc RNG.
- Gameplay state stores.

Composition chỉ là dữ liệu mô tả một cấu hình gameplay hợp lệ.

## 5.4. Disabled Modules

Ví dụ:

```text
Registered:
  character (required)
  inventory (optional)
  equipment (optional)

Enabled:
  character
  equipment
  inventory
```

Composition chứa cả ba modules, theo dependency order.

Nếu chỉ có Character được lựa chọn:

```text
Enabled:
  character
```

Composition chỉ chứa Character.

Inventory và Equipment không được đưa vào composition mặc định.

Không tạo inactive module instances để chuẩn bị sử dụng sau.

## 5.5. Empty Composition

Một registry không có module nào và configuration rỗng phải tạo được composition rỗng hợp lệ.

Không bắt buộc một module nền tảng phải luôn tồn tại.

Không tự register `foundation`, `core` hoặc `gameplay-engine` như những module giả.

## 5.6. Composition Isolation

Các yêu cầu:

- Hai compositions tạo độc lập không ảnh hưởng nhau.
- Một composition không bị thay đổi khi có registration mới vào một registry snapshot khác.
- Configuration mới không mutate composition cũ.
- Caller không thể sửa kết quả để phá vỡ resolved order.
- Composition không chứa hidden shared mutable state.

Có thể chia sẻ references tới validated frozen definitions khi chúng thực sự immutable.

Không bắt buộc deep clone dư thừa mọi giá trị nếu không cải thiện bảo đảm hành vi.

## 5.7. No Runtime Execution

Tạo composition không được:

- Gọi module initialize.
- Gọi module start/stop.
- Tạo Gameplay Runtime.
- Phát gameplay events.
- Thực thi commands.
- Tạo Character hoặc Combat State.
- Gọi numerical calculations từ RPG Core.

Một composition thành công chỉ chứng minh các module được lựa chọn có quan hệ phụ thuộc hợp lệ.

## 7.2. Minimum Meaningful Scenarios

Agent nên thiết kế tập scenarios gọn, bao phủ các nhóm hành vi khác nhau:

### Scenario A — Valid Dependency Graph

```text
Registration:
  equipment
  inventory
  character

Dependencies:
  equipment → inventory
  inventory → character

Selection:
  character
  inventory
  equipment

Expected resolution:
  character
  inventory
  equipment
```

Chứng minh dependency-first và transitive dependencies.

### Scenario B — Invalid Selection

```text
equipment → inventory

Selection:
  equipment

Expected:
  Reject dependency inventory not enabled
```

Chứng minh không tự enable dependencies.

### Scenario C — Cycle

```text
A → B
B → C
C → A

Selection:
  A, B, C

Expected:
  Reject cycle
```

Chứng minh phát hiện cycle thuộc selected graph.

### Scenario D — Optional Isolation

```text
Registered:
  character
  optional-a → optional-b
  optional-b → optional-a

Selection:
  character

Expected:
  Valid composition containing character only
```

Chứng minh các modules không được sử dụng không làm hỏng composition khác.

### Scenario E — Immutable Composition

Tạo composition, tạo registry/configuration mới, thử thay đổi returned values.

Expected:

- Composition cũ không đổi.
- Registry/configuration cũ không đổi.
- Không có hidden global state.

Không cần nhân mọi scenario cho Text/2D/2.5D.

Những profile đó chưa tạo ra khác biệt behavior trong GF04–GF05.

## 7.3. Test Quality Requirements

Mỗi testcase mới phải trả lời:

1. Invariant nào đang được chứng minh?
2. Expected value đến từ contract nào?
3. Nếu bỏ test này, mất bằng chứng riêng biệt gì?
4. Test có thất bại khi implementation sai hay không?

Không dùng các testcase chỉ xác nhận function không throw.
