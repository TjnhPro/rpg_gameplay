## 4. AI31 — Actor & Target Death Awareness

### 4.1. Actor Life gate

Implement/reuse a **read-only life gate** for a particular Actor AI State, with authoritative `EntityLifeState` from L4. Suggested additive API:

```ts
export type ActorAILifeGateResult =
  | { readonly status: 'allowed'; readonly reason: 'none'; readonly actorId: string }
  | { readonly status: 'blocked'; readonly reason: 'actor_dead' | 'manual_control'; readonly actorId: string };

export function evaluateActorAILifeGate(
  state: ActorAIState,
  entities: EntityCollection,
  actorLife: EntityLifeState
): ActorAILifeGateResult;
```

Required:

1. Validate complete ActorAIState and canonical Entity membership via existing public Entity API.
2. Validate `actorLife.entityId === state.actorId`, status exact `alive | dead`, closed safe record.
3. `actorLife.status === 'dead'` blocks **regardless of behavior ID, target or action availability**.
4. `state.controller === 'manual'` blocks AI action decisions; manual does not imply actor dead. **Fixed precedence:** `actor_dead` before `manual_control`.
5. `alive + ai` returns allowed; **not authorization** to execute Combat/Skill.
6. Return detached immutable result; **do not modify** EntityLifeState, ActorAIState or any resources.
7. No automatic change of behaviorStateId to `disabled` (IDs are opaque L3 strings).
8. No death event processing inside Actor AI; no automatic cleanup invocation.

**Important integration rule:** L4 invokes this gate **before decision timing** and before an AI proposal becomes an executable action. L4 must recheck authoritative Life and controller at actual dispatch (TOCTOU). A prior `allowed` receipt is **not a durable capability**.

### 4.2. Target Life belongs to Entity / Perception

- L4 supplies current target Life through existing authoritative Entity and Perception inputs.
- AI09 exclusion reason `target_life_not_allowed` remains the perception-level diagnostic.
- AI15 target loss/switch handles current target that became dead/ineligible.
- AI16–AI20 FSM consumes explicit L4 trigger such as `target_lost` only **after** relevant target candidate was committed or explicitly staged.
- An AI action already selected against a dead/disappeared target **must not execute**; L4 canonical admission is authoritative.
- Do not call Combat damage or Effect cleanup merely because AI observed `dead`; source death independent from existing Effect policy.

### 4.3. Actor death and pending work

When actor dies between decision and dispatch:

```text
AI proposal selected
  → Entity canonical Life transitions to dead
  → L4 observes dead Life
  → AI Life gate blocks subsequent decision
  → L4 rechecks before pending action dispatch and rejects stale action
  → no unauthorized Combat/Skill/Movement execution
```

Never invent an Actor AI queue, cancel a scheduler, auto-refund a paid Skill or backdate events. Pending work ownership is L4.

## 5. AI32 — Explicit AI Reset & Reinitialization

### 5.1. Goal

Reset AI **structural state only**, via explicit L4 request. Reinitialize intended behavior and clear stale target without creating/reviving an Entity or changing Gameplay systems.

Proposed contract (additive; align with actual v0.7.5 APIs):

```ts
export type ActorAIResetReason = 'respawn' | 'session_reset' | 'disengage';

export interface ActorAIResetRequest {
  readonly reason: ActorAIResetReason;
  // Mandatory for respawn/session_reset; null for disengage.
  readonly resetBehaviorStateId: string | null;
}

export type ActorAIResetResult =
  | {
      readonly status: 'applied';
      readonly reason: 'none';
      readonly action: ActorAIResetReason;
      readonly state: ActorAIState;
    }
  | {
      readonly status: 'rejected';
      readonly reason: 'actor_dead';
      readonly action: ActorAIResetReason;
      readonly state: null;
    };

export function evaluateActorAIReset(
  state: ActorAIState,
  entities: EntityCollection,
  actorLife: EntityLifeState,
  behaviorPolicy: ActorAIBehaviorPolicy,
  request: ActorAIResetRequest
): ActorAIResetResult;
```

This is **not** a general-purpose FSM transition engine. The reset is a *dedicated explicit lifecycle operation*; ordinary behavior transitions continue to use AI17/AI20.

### 5.2. Reset semantics by reason

| Reason | Target | Behavior | Preconditions |
| --- | --- | --- | --- |
| `respawn` | Clear to `null` | Explicit L3 `resetBehaviorStateId` from `behaviorPolicy.stateIds` | Canonical Entity **already alive** after real revive/respawn handled elsewhere |
| `session_reset` | Clear to `null` | Explicit L3 `resetBehaviorStateId` from `behaviorPolicy.stateIds` | Canonical Entity alive, caller explicitly requests |
| `disengage` | Clear to `null` | **Preserve existing `behaviorStateId`**; caller supplies `resetBehaviorStateId: null` | Canonical Entity alive; FSM Returning handled separately by v0.7.3 |

**Always preserve:** `actorId`, `profileId`, `controller` exactly. For `disengage`, preserve behavior ID. For respawn/session reset, change only behavior ID and target. No automatic `controller='ai'` switch: Player can remain manual; reset is an explicit **L4 maintenance request**, not an AI-proposed action.

**Reason:** permits controlled Player Auto-Combat reinitialization, Monster leash disengage, Pet/Summon owner-directed resets, without creating another target authority or duplicating ordinary FSM behavior.

### 5.3. Validation / fail-closed

- Exact actor Life ID, canonical Actor/Entity presence, closed request shape, accepted FSM policy profile binding.
- For respawn/session_reset: destination must exist in `behaviorPolicy.stateIds`; no implicit default `idle`.
- For disengage: null reset destination required, current behavior unchanged.
- For dead actor: reject `actor_dead`, **even if action is disengage**; death suppression does not need resetting AI. L4 may perform explicit reset **after** revival.
- Invalid shapes or unknown state IDs throw TypeError **before** any candidate; ordinary alive/dead rejection returns `state:null`.
- Caller input remains unchanged; result state detached, frozen; no mutation of Life/Entity/Skill/Effect/Combat.
- Candidate publication is L4-owned: same entity/actor/profile/controller baseline must remain current at commit.

### 5.4. Revival / Respawn is external

```text
L4/Entity: canonical Resource/Life revival (if valid)
  → L4 verifies actor alive
  → L4 requests Actor AI respawn reset
  → Actor AI returns state candidate
  → L4 checks freshness and commits AI candidate
  → L4 initializes a NEW timing cursor explicitly
  → L4 may schedule future AI evaluation
```

No `reviveEntity()` call inside Actor AI. No HP refill, EXP grant, skill cooldown restart, effect dispel, actor spawn, network broadcast or auto-controller takeover.

**Revived actor does not automatically become active:** no decision may run merely because Life changed; L4 must initialize/enable appropriate controller, reset and timing explicitly.

## 6. AI33 — Disengage / Leash Recovery

### 6.1. Boundary

Leash distance, home position, safe zone and arrival are **World/L4 facts**. AI cannot calculate distance/path, write coordinates, or auto-move.

The approved FSM from v0.7.3 already handles configured triggers such as:

```text
engaged + disengage_requested → returning
engaged + leash_exceeded      → returning
returning + return_completed  → idle/guarding
```

**Do not implement a second FSM.** AI33 adds integrated explicit lifecycle semantics: drop stale target through the dedicated `disengage` reset, then evaluate the established FSM transition from the reset candidate, with caller-supplied trigger/policy.

### 6.2. Required L4-style composition

```text
L4 sees authoritative leash_exceeded / disengage_requested
  → verifies Actor Entity alive and current controller
  → Actor AI evaluateActorAIReset(reason=disengage)
        [clears only current target, behavior unchanged]
  → L4 evaluates existing FSM rule using resulting candidate + explicit trigger
        [e.g. engaged → returning]
  → L4 stages BOTH candidates against one authoritative baseline
  → L4 commits atomically only if baseline still current
  → later AI21–25 may propose return-home intent
  → L4 movement system executes actual return
  → L4 supplies return_completed when actually reached home
  → existing FSM may return to idle/guarding
```

No partial authoritative commit if FSM evaluation fails. Do not fabricate `return_completed` or issue movement automatically. No automatic target reacquisition while returning unless L3/L4 explicitly requests a new target-selection step and selected behavior policy permits it; **no hidden policy in L2**.

### 6.3. Important edge cases

- **Target still eligible:** leash/disengage explicit caller request may clear target anyway; this is not falsifying Perception eligibility or abusing TargetSelection; separate lifecycle purpose.
- **Target already null:** disengage reset may be an idempotent semantic no-op; output deterministic and detached.
- **No matching Returning FSM rule:** behavior remains unchanged, explicit result; L4 must not claim successful transition to Returning.
- **Actor dies between reset/FSM/commit:** discard staged candidates and stop; do not persist half-reset state.
- **Manual controller takeover:** L4 blocks AI-autonomous disengage workflow; caller-authorized AI metadata maintenance remains distinct and must not start an action.
- **Returning actor with stale target:** only a fresh explicit request can clear it, never by implicit global loop.
- **No World arrival:** stay `returning` until caller actually supplies accepted completion trigger.

## 7. AI34 — Decision Timing & Cadence

### 7.1. Goal

L3 supplies an explicit **minimum interval** between decision turns. L2 evaluates *whether the caller may start another AI decision now*, returning an immutable timing candidate. **L4 controls every invocation.**

No scheduler, no queue, no polling loop, no wall-clock access.

### 7.2. Proposed companion state

Do **not** modify the accepted five-field `ActorAIState` schema. Timing is a separate, **Actor-bound immutable L2 companion contract**, stored and committed by L4. It is not a new actor/entity authority or global store.

```ts
export interface ActorAIDecisionTimingState {
  readonly actorId: string;
  readonly observedAtMs: number;
  readonly nextEligibleAtMs: number;
}

export interface ActorAIDecisionTimingPolicy {
  readonly intervalMs: number;
}

export type ActorAIDecisionTimingResult =
  | { readonly status: 'ready'; readonly reason: 'none'; readonly state: ActorAIDecisionTimingState }
  | { readonly status: 'not_due'; readonly reason: 'interval_active'; readonly state: null }
  | { readonly status: 'blocked'; readonly reason:
      'manual_control' | 'actor_dead' | 'time_regressed' | 'time_unrepresentable'; readonly state: null };
```

Proposed operations:

```ts
export function createActorAIDecisionTimingState(
  state: ActorAIState,
  context: GameplayExecutionContext
): ActorAIDecisionTimingState;

export function evaluateActorAIDecisionTiming(
  state: ActorAIState,
  entities: EntityCollection,
  actorLife: EntityLifeState,
  timing: ActorAIDecisionTimingState,
  policy: ActorAIDecisionTimingPolicy,
  context: GameplayExecutionContext
): ActorAIDecisionTimingResult;
```

**Preflight may select the smallest equivalent API matching real v0.7.5 style.** No parallel scheduler/cooldown engine. Keep exported API tight.

### 7.3. Exact clock and readiness semantics

- **Clock source:** use only `readExecutionTime(context)` from existing Foundation. Caller supplies a valid execution context; exactly **one clock sample per actual timing evaluation**. No `Date.now`, `performance.now`, `setTimeout`, `Math.random`.
- **Initialization:** capture caller clock `t0` exactly once. Return `{actorId, observedAtMs:t0, nextEligibleAtMs:t0}` — initially ready, not automatically consumed.
- **Policy:** `intervalMs` must be finite, nonnegative and **safe integer**; zero is allowed (event/turn-driven caller), never a negative interval.
- **Timer snapshot:** exact actorId binding; times finite and nonnegative, `nextEligibleAtMs >= observedAtMs`. No unknown keys/getters.
- **Life/controller gate:** validate everything structurally, then dead actor blocks before manual; manual blocks before clock-read. No decision time consumed by blocked actor.
- **Regression:** for alive AI, if `now < timing.observedAtMs` → `blocked/time_regressed` (no candidate).
- **Not due:** if `timing.observedAtMs <= now < timing.nextEligibleAtMs` → `not_due/interval_active` (no candidate).
- **Ready:** if `now >= timing.nextEligibleAtMs`, compute `nextEligibleAtMs = now + intervalMs`. Validate finite and representable. Return `ready/none` with detached timing candidate `{actorId, observedAtMs:now, nextEligibleAtMs}`.
- **Unrepresentable time:** if the sum overflows or a positive interval does not advance representably, return `blocked/time_unrepresentable` and **no candidate**. Never wrap/saturate to zero or silently clamp.
- **Same-time:** after an accepted candidate with positive interval, re-evaluation at the same time is `not_due`. If interval `0`, next turn may be ready again; **L4 must enforce unique decision/dispatch attempts**, not L2 stateless timing.
- **No time reset on rejection:** manual/dead/not_due/regression/overflow do not create candidate or mutate timing.
- **No skipped historical work:** timing is a cadence gate, not a tick catch-up queue. If the caller advances time far beyond due, one `ready` candidate is produced; **do not auto-run N missed decisions**.
- **Commit:** L4 advances the timing cursor only after accepting/consuming the decision turn according to its explicit policy; failed admission/action must not spuriously create extra turns. The candidate is not a durable lease.

### 7.4. Freshness / invalidation

L4 must compare timing cursor against the exact authoritative baseline before commit. Two parallel evaluations from the same cursor can both be `ready`; **no distributed exactly-once claim**. Stale second candidate must be discarded by L4.

After explicit respawn/session reset: L4 must create/commit a new timing cursor or explicitly preserve it under its game policy; no implicit AI clock reset or hidden scheduling.

Timing does **not** encode: current HP, entity death, cooldowns, Skill availability, threat, World position, selected action, retry count, or controller arbitration.

## 8. AI35 — Recovery, Feedback & Continuity

### 8.1. Actual terminal feedback is mandatory

**Reuse the actual AI29 feedback contract/validator from v0.7.5.** No second receipt schema unless documented evidence shows a gap requiring Developer decision.

Terminal feedback binds the selected AI proposal to actual L4 execution outcome using accepted correlation fields. The existing canonical Skill `activateSkill()` **accepted** result is not equivalent to `reportSkillExecutionOutcome()` **completed**; Combat dodge/zero damage can be a legitimately completed attempt without HP loss.

### 8.2. Feedback does not mutate lifecycle automatically

```text
L4 obtains real terminal outcome
  → existing AI29 feedback validation
  → L4 decides whether to request a new decision (explicit)
  → AI31 Life gate
  → AI34 decision-timing gate
  → Perception / Target Selection / FSM / Action Selection
  → L4 revalidates canonical gates at dispatch
```

- Failed/rejected/no-action/wait must **not** auto-loop, re-dispatch, or advance behavior/target implicitly.
- A completed action is not permission to ignore current actor death, manual takeover, target loss, cadence or restrictions on next action.
- Already committed Resource/Cooldown/Effect state remains canonical; **do not refund automatically** following later dispatch failure.
- `decisionId` is not automatically the same as Combat `actionId` or Skill `attemptId`; L4 maintains explicit correlation.
- L4 prevents duplicate terminal feedback/dispatch as an authoritative invariant; stateless L2 cannot durably deduplicate across processes.

### 8.3. Controlled recovery scenarios

1. **Attack denied after AI selection** → no Entity mutation, truthful rejection feedback, no automatic fallback execution; later fresh decision may choose another action.
2. **Skill accepted but dispatch failed** → canonical cost/cooldown candidates remain subject to L4's actual accepted commit; feedback is failed, no automatic refund or replay.
3. **Target dies after selection** → L4 dispatch denied, subsequent perception excludes target and selection may acquire another; no target replacement by lifecycle helper.
4. **Actor dies while engaged** → AI Life gate blocks new decisions; pending L4 work invalidated. Revival and AI reset are distinct explicit operations.
5. **Manual controller takeover** → AI stops proposing/committing; manual player input uses existing L4 path, not AI.
6. **Disengage/Returning** → no forced movement or invisible reengagement; L4 tracks actual return completion.
7. **No World timer** → L4 invokes timing evaluator explicitly at each candidate turn; no autonomous scheduling.
8. **Replay across two independent sessions** → same states, clock samples, trigger sequences and feedback produce identical semantic results without shared objects.

### 8.4. No generic retry system

Do not add `retryCount`, `retryAfterMs`, `lastError`, `pendingAction`, durable execution token, action queue, or feedback history into the canonical five-field ActorAIState. These are L4 concerns or require separately approved capabilities.
