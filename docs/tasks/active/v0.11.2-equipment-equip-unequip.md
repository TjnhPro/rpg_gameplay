## 1. EQ11–EQ15 objective and ownership

| ID | Feature | Observable capability |
| --- | --- | --- |
| **EQ11 Equip Item** | Add canonical Item Instance Snapshot at the supplied occupied slot IDs, when admitted and all requested slots available |
| **EQ12 Unequip Item** | Remove one exact instance membership and return the released Item snapshot with the new Equipment candidate |
| **EQ13 Occupancy Protection** | Prevent duplicate same-instance membership, occupied-slot collisions or partially occupied multi-slot equips |
| **EQ14 Safe Replacement** | Explicitly replace one equipped instance with another and return the old item safely; never overwrite/discard it |
| **EQ15 Operation Outcomes** | Exact accepted/rejected discriminant/reason and full immutable candidate + release guarantee; invalid structure throws `TypeError` |

### System responsibility

- **Item L2:** Definition/Instance/properties/validation; no mutation/creation of Item when Equipping.
- **Inventory L2:** unequipped storage/`quantity`; Equipment does not import Inventory or transfer quantity.
- **Equipment L2:** only equipped-slot membership and pure candidate transitions, one owner.
- **Entity + Core L1:** only character stats and numeric calculations; no Equipment stat handler.
- **L3:** computes boolean eligibility for class, level, item type, slot layout, cursed item unequip and replacement policy. The generic L2 API does not infer rules from arbitrary Item property keys.
- **L4:** supplies current authoritative Item/Inventory/Equipment state; prevents duplicates across storages, checks quantity and permissions, stages candidates and commits atomically/persists. Candidate alone cannot guarantee cross-storage uniqueness or freshness.

No `EquipmentManager`, inventory transaction coordinator, event bus, ItemStore, Buff/Skill grants, item destruction, number engine, game class presets, scene/UI/VFX.

## 3. Proposed exact public API additions (NO Foundation edits)

Three runtime functions and two types. Reuse `EquipmentAdmission` from v0.11.1 and `EquipmentState`/`ItemInstanceState` from v0.11.0/Item.

```ts
export type EquipmentMutationReason =
  | 'ineligible'
  | 'already_equipped'
  | 'slot_occupied'
  | 'not_equipped'
  | 'same_instance';

export type EquipmentMutationResult =
  | {
      readonly status: 'accepted';
      readonly reason: 'none';
      readonly candidate: EquipmentState;
      readonly released: ItemInstanceState | null;
    }
  | {
      readonly status: 'rejected';
      readonly reason: EquipmentMutationReason;
      readonly candidate: null;
      readonly released: null;
    };

export function equipEquipmentItem(
  state: EquipmentState,
  context: EquipmentValidationContext,
  item: ItemInstanceState,
  slotIds: readonly string[],
  admission: EquipmentAdmission,
): EquipmentMutationResult;

export function unequipEquipmentItem(
  state: EquipmentState,
  context: EquipmentValidationContext,
  instanceId: string,
  admission: EquipmentAdmission,
): EquipmentMutationResult;

export function replaceEquipmentItem(
  state: EquipmentState,
  context: EquipmentValidationContext,
  replacedInstanceId: string,
  replacementItem: ItemInstanceState,
  replacementSlotIds: readonly string[],
  admission: EquipmentAdmission,
): EquipmentMutationResult;
```

**Purposeful `released` semantics:** Equip succeeds with `released:null`; Unequip and Replace succeed with `released:<previous canonical Item snapshot>`. Rejection **always** has both `candidate:null` and `released:null`. Never remove an equipped item without giving the consumer its Item snapshot for safe Inventory placement/another destination. This shape does **not** claim the application committed the item anywhere.

**No generic callback, transaction receipts, old/new change logs or implicit multi-item batch API.** Contract names above are proposed; reconcile actual predecessor at preflight.

## 4. Common validation, identity and immutability rules

1. **Complete existing state/context** must pass canonical `validateEquipmentState`, which uses canonical public Item Definition/Instance validation. Caller-supplied target/replacement Item must also be structurally validated against the unique matching definition in supplied context. Missing definition, invalid Item, duplicate Item definitions, mismatched `definitionId` and malformed Equipment state => `TypeError` **even when `eligible:false` or the operation will be rejected**.
2. Reuse v0.11.0 exact nonblank ID/unique slot-array validation; never trim/parse/normalize. `admission` is required exact closed `{eligible:boolean}`, with no implicit `true`. Validate all fields, including nested Item/slot values before deciding `ineligible`.
3. Only current state is authoritative input. **Do not mutate/freeze caller inputs**, call hidden providers, generate item IDs, check a global registry or interpret policy. Returned accepted full EquipmentState and `released` Item must be freshly deeply detached/frozen; outcome exact own keys; rejected returns no candidate.
4. New candidates must revalidate with **canonical** `validateEquipmentState` using the complete context. If a candidate fails due to internal construction after valid inputs, treat it as implementation error; do not suppress and return a fake denial.
5. Item/definition properties, exact IDs, `owner`, `equipmentId` and unaffected entry order must be preserved. Only requested membership/occupied slots change. No Item `isEquipped` property, `quantity`, Equipment `revision`, EquipmentItem subtype or stat mutation.
6. A valid operation which is **not permitted** (full slot, same instance, missing membership, eligible false) returns typed rejection, not TypeError. For an invalid structural input, TypeError wins over any denial reason.

## 5. Deterministic operation semantics

### EQ11 — Equip

- Evaluate same membership/slot/eligibility checks **identically to accepted** `assessEquipmentAdmission`; do not create divergent rule logic. All input structural validation happens first.
- Reason priority: `already_equipped` (incoming ID already in state) → `slot_occupied` (any requested slot occupied) → `ineligible` (explicit false) → accepted.
- On success append exactly `{item: <fresh validated canonical Item>, slotIds: <exact requested IDs>}` to ordered `entries`, preserve owner/equipmentId and all existing entries, return `{status:'accepted',reason:'none',candidate:<full state>,released:null}`.
- Even if slotIds contains two slots (allowed at data level), all must be simultaneously free. No game-specific two-hand policy is inferred; L3 decided the complete desired slot set.

### EQ12 — Unequip

- Require exact valid `instanceId`, validate full state/context/admission before membership checks.
- Reason priority: `not_equipped` (no such member) → `ineligible` (explicit false) → accepted.
- On success remove **exactly one** entry identified by Item `instanceId`, free **all** of its `slotIds`, preserve unaffected entry order, return its complete canonical ItemInstanceState as immutable `released`. No Item deletion or automatic Inventory insertion.
- `released` does not imply owner/grant; L4 selects actual destination and checks that destination accepts the item, then commits both storages.

### EQ13 — Occupancy protection

- A state with duplicate instance IDs/overlapping occupied slots is **invalid**, `TypeError` via Foundation before any operation.
- A well-formed equip/replacement request colliding with existing state is ordinary `rejected` with exact reason and **no candidate/released**; there is no partial slot occupancy/reservation.
- Same instance cannot be equipped twice, including in distinct slot IDs. A different instance with same definition is not inherently a duplicate.

### EQ14 — Replace

- Input identifies the **one** old equipped entry by `replacedInstanceId` and supplies one complete *different* replacement Item Instance plus its new `slotIds` and an explicit comprehensive eligibility decision from L3/L4.
- Validate **all structure** first. Then reason priority:

| Order | Condition | Reason |
| --- | --- | --- |
| 1 | Old `replacedInstanceId` not present | `not_equipped` |
| 2 | Replacement `item.instanceId === replacedInstanceId` | `same_instance` |
| 3 | Replacement instance ID already belongs to another equipped entry | `already_equipped` |
| 4 | Any replacement slot occupied by an entry **other than the old entry** | `slot_occupied` |
| 5 | Admission false | `ineligible` |
| 6 | Otherwise | accepted |

- On success replace old entry **at its original array position**, releasing all old slots not in replacement, occupying all requested new slots, leaving other entries/slots untouched. Return new full EquipmentState candidate **and** exact old Item snapshot in `released`.
- Existing old entry's slot IDs are treated as available during this **one targeted atomic candidate construction only**; other entries' occupied slots cannot be stolen.
- No implicit `unequip` of other entries, auto-move, forced equipment slot, stat/Effect update, Inventory return or remote commit. Same instance cannot use `replace` as an unapproved Item-property-state update shortcut; future property refresh will require an explicit separate audited capability if real game requests it.

### EQ15 — Outcomes and local semantics

```ts
// Conceptual expected result shape, not an example of persisted app state
{status:'accepted',reason:'none',candidate:<EquipmentState>,released:null} // equip
{status:'accepted',reason:'none',candidate:<EquipmentState>,released:<ItemInstanceState>} // unequip / replace
{status:'rejected',reason:'slot_occupied',candidate:null,released:null}
```

- Strict external TypeScript declaration must narrow `candidate` and `released` correctly based on `status`; nested readonly maintained.
- The same literal validated inputs return equal result data across repeated independent runs. No implicit current time, ID, RNG, event, server call or owner store.
- **No global uniqueness guarantee**: an Equipment candidate cannot prove Item absent from Inventory. L4 coordinates/synchronizes candidates and checks authority.
