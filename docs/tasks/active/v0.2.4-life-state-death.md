# 4. Life State Architecture

## 4.1. Responsibility Split

```text
L3 — Game Rules / Caller
    Select life resource
    Define valid bounds
    Decide when to evaluate defeat
    Decide revival eligibility
    Supply explicit recovery inputs
                │
                ▼
L2 — Entity / Character
    Store life state
    Evaluate life policy
    Resolve defeat/revival
    Return immutable transitions
                │
                ▼
L1 — RPG Core Kernel
    Numerical resource transitions
    Resource normalization
    Resource regeneration
```

L2 không tính lại damage/healing.

L1 không có quyền quyết định actor đã chết.

Không thay đổi ownership đã nghiệm thu.

## 4.2. Independent Life State

Life State phải độc lập với:

- `EntitySnapshot` identity/classification.
- `EntityCollection` membership.
- `EntityAttributeState`.
- `EntityStatSnapshot`.
- `EntityResourceState`.

Dùng Entity ID để liên kết dữ liệu.

Không tạo một global Entity object chứa toàn bộ game state.

Không thay đổi closed EC01–EC03 definition:

```ts
{
  id: string;
  kind: string;
}
```

Không gắn thêm `alive` hoặc `dead` vào Entity kind.

# 5. EC14 — Life State

## 5.1. Objective

Cung cấp một typed immutable state để mô tả một actor đang sống hoặc đã chết.

Public contract định hướng:

```ts
type EntityLifeStatus = "alive" | "dead";

interface EntityLifeState {
  readonly entityId: string;
  readonly status: EntityLifeStatus;
}
```

Tên có thể điều chỉnh theo conventions hiện có.

Không thêm status như:

- dying
- respawning
- knocked-down
- unconscious
- ghost
- invulnerable

Các trạng thái này có gameplay semantics riêng và chưa thuộc approved scope.

## 5.2. Life State Creation

Cung cấp public function tương đương:

```ts
createEntityLifeState(
  entity,
  {status: "alive"}
);
```

Bắt buộc:

- Entity ID hợp lệ.
- Life status explicit.
- Không tự suy ra Life State từ Entity kind.
- Không tự đọc health resource.
- Không tự phát event.
- Không gọi Kernel.
- Không tạo Runtime.
- Không tự tạo ID.
- Không đọc Clock/RNG.

Không mặc định tất cả Entity phải có Life State.

Một NPC không sử dụng cơ chế chết có thể tồn tại mà không cần Life State.

Có thể khởi tạo một actor ở trạng thái `dead` nếu caller chủ động yêu cầu, chẳng hạn dùng cho dữ liệu đã lưu.

Creation không được tự thực hiện revival hoặc defeat.

## 5.3. Life State Inspection

Cung cấp public function hoặc readonly snapshot interface để truy vấn:

- Entity ID.
- Current life status.

Nếu thêm `getEntityLifeStatus()`, không được nhân bản state authority.

Không cần nhiều convenience methods nếu status đã đọc được từ immutable snapshot.

## 5.4. Validation

Reject:

- Invalid Entity definition.
- Missing/invalid entity ID.
- Missing status.
- Unknown status.
- Malformed state.
- Unsupported extra fields ở closed input boundary.
- Accessor-based hoặc inherited state fields không phù hợp accepted validation conventions.

Không silent coercion:

```text
true → alive
false → dead
0 → dead
```

Không cho phép arbitrary string status.

## 5.5. Immutability

Life State phải:

- Immutable.
- Detached khỏi mutable caller inputs.
- Không bị thay đổi bởi caller mutation.
- Không chứa writable internal maps.
- Không có global state.
- Không có mutable state chia sẻ giữa actors.

Hai Life States cùng Entity ID có thể là hai immutable snapshots ở thời điểm khác nhau.

Không sử dụng hidden global authority để tự loại bỏ snapshot cũ.

# 6. EC15 — Defeat Resolution

## 6.1. Objective

Cho phép caller yêu cầu đánh giá một Entity có bị defeat hay không theo policy rõ ràng.

**Resource current bằng minimum không tự làm Entity chết.**

Death chỉ xảy ra khi consumer chủ động gọi Defeat Resolution.

## 6.2. Life Resource Policy

Định nghĩa policy tương đương:

```ts
interface EntityLifeResourcePolicy {
  readonly resourceId: string;
  readonly minimum: number;
  readonly maximum: number;
}
```

Đây là conceptual contract; có thể reuse những public bound contracts hiện có.

Policy xác định:

- Resource nào được dùng làm life resource.
- Minimum/maximum hiện hành.
- Điều kiện numerical state hợp lệ.

Ví dụ:

```ts
{
  resourceId: "health",
  minimum: 0,
  maximum: 100
}
```

Không hardcode `health`.

Một game có thể sử dụng resource `life`, `vitality`, `durability` hoặc một ID khác.

Minimum cũng không bắt buộc là 0.

**Trong v0.2.4 chỉ triển khai life-resource-minimum policy.** Không xây generic condition engine.

## 6.3. Required Defeat Function

Cung cấp public function tương đương:

```ts
resolveEntityDefeat(
  lifeState,
  resourceState,
  lifePolicy
);
```

Expected:

- Validate Life State.
- Validate Resource State.
- Validate policy.
- Entity IDs phải khớp.
- Life resource phải tồn tại.
- Đọc current value từ EC10.
- Đánh giá condition dựa trên explicit minimum.
- Trả Life Transition Result.

Không gọi lại `calculateResourceTransition()` để giả lập một damage action.

Không tự thay đổi Resource State.

## 6.4. Defeat Semantics

Quy tắc:

```text
Life State = alive
Life Resource current = minimum
        │
        ▼
Explicit resolveEntityDefeat()
        │
        ▼
Life State = dead
```

Nếu current lớn hơn minimum:

```text
alive → alive
```

Không phát sinh defeat.

Nếu current dưới minimum và trái với valid normalized Resource State contract, reject malformed/inconsistent input thay vì âm thầm coi là dead.

Nếu Resource State có current above maximum theo một accepted Kernel policy, không tự sửa resource. Defeat Resolver chỉ đánh giá điều kiện minimum sau khi kiểm tra những invariants cần thiết; normalization vẫn thuộc EC11.

## 6.5. Kernel `reachedMinimum`

`ResourceTransitionResult.reachedMinimum` là một numerical diagnostic:

```ts
{
  reachedMinimum: true
}
```

Không tự động chuyển thành dead.

Defeat Resolver có thể sử dụng numerical result này làm evidence phụ nếu EC12 result được truyền tường minh, nhưng phải đánh giá trạng thái resource hiện hành theo approved policy.

Không dùng `reachedMinimum` đơn lẻ làm proof rằng actor đã chết.

Không tạo riêng một damage calculator.

## 6.6. Already Dead

Nếu Life State đã `dead`:

- Defeat Resolution không được sinh transition `defeated` lần nữa.
- Không tạo duplicate defeat notification.
- Trả `unchanged` hoặc contract tương đương.
- Không mutate Life State/Resource State.

Không tự phục hồi hoặc thay đổi resource của dead Entity.

## 6.7. Multiple Actors

Mỗi Entity ID có Life State riêng.

Defeat actor A không ảnh hưởng:

- Actor B.
- Entity Collection.
- Attribute State.
- Stat Snapshot.
- Resource State của actor khác.

Không có global death manager.

## 6.8. Death Evaluation Limit

Defeat Resolution chỉ quyết định life status.

Không thực hiện:

- Loot drop.
- Reward grant.
- EXP distribution.
- Kill count.
- Monster despawn.
- Respawn scheduling.
- Equipment durability loss.
- Effect cleanup.
- Skill cancellation.
- World encounter completion.

Những chức năng này thuộc các gameplay capabilities tương ứng.

# 7. EC16 — Revival / Reset

## 7.1. Objective

Cho phép hồi sinh một Entity đã dead bằng một operation rõ ràng, có validation.

Revival không được tự xảy ra khi resource tăng lên.

Life State và Resource State vẫn là hai state domains độc lập.

## 7.2. Required Revival Function

Cung cấp function tương đương:

```ts
reviveEntity(
  lifeState,
  resourceState,
  lifePolicy
);
```

Trong đó `resourceState` phải phản ánh current resource sau recovery được caller chủ động thực hiện.

Ví dụ flow:

```text
Dead Entity
    │
    ▼
Caller explicitly restores life resource
    │
    ▼
EC11 / EC12 Resource Operation
    │
    ▼
Resource current > minimum
    │
    ▼
Explicit reviveEntity()
    │
    ▼
Life State: alive
```

Không tự gọi `transitionEntityResource()` bên trong `reviveEntity()` trừ khi public EC16 contract được thiết kế rõ một atomic combined operation và được Developer duyệt riêng.

Ở version này ưu tiên **life-only revival transition** để không tạo một resource calculator/transition owner thứ hai.

## 7.3. Revival Preconditions

Bắt buộc:

1. Life State hợp lệ.
2. Resource State hợp lệ.
3. Entity IDs khớp.
4. Policy hợp lệ.
5. Life resource tồn tại.
6. Life status hiện tại là `dead`.
7. Current life resource phải lớn hơn minimum.
8. Current phải nằm trong bounds hợp lệ cho revival.
9. Không có hidden policy hoặc implicit recovery.

Nếu resource vẫn bằng minimum:

**Reject revival hoặc trả structured rejection, không chuyển thành alive.**

Không âm thầm tạo một điểm HP.

Không tự refill lên maximum.

Không tự chọn revive percentage.

Không tạo game-specific revive amount.

## 7.4. Revival With Kernel Recovery Policy

EC12 cho phép tăng resource từ minimum nếu caller cung cấp:

```ts
allowIncreaseFromMinimum: true
```

Điều này chỉ là numerical permission.

Ví dụ:

```text
Life State: dead
Health: 0

Explicit resource increase:
  0 → 30

Life State after resource increase:
  still dead

Explicit reviveEntity():
  dead → alive
```

Không tự chuyển actor thành alive trong resource transition.

Nếu policy không cho phép increase từ minimum, caller có thể lựa chọn một explicit reset/normalization sequence hợp lệ từ EC11/EC12 hoặc thiết kế recovery capability riêng sau này.

Không viết workaround resource arithmetic trong EC16.

## 7.5. Already Alive

Nếu actor đã alive:

- Không tạo `revived` transition giả.
- Không tự refill resource.
- Trả `unchanged` hoặc explicit invalid-transition result theo một contract nhất quán.
- Không phát duplicate revival event.

Ưu tiên `unchanged` cho evaluation/no-op, còn malformed input và impossible states phải reject rõ ràng.

## 7.6. Reset Semantics

Trong v0.2.4, reset được hiểu là **một explicit recovery/reinitialization flow**, không phải respawn engine.

Caller có thể:

1. Khởi tạo Resource State mới bằng EC11 nếu đang bắt đầu một session/entity snapshot mới.
2. Dùng chính Resource State hợp lệ đó để thực hiện explicit revival.
3. Nhận một Life State mới.

Không thêm `resetEntity()` tổng quát để tự reset attributes, stats, equipment, effects hoặc progression.

Không xóa hoặc tạo lại Entity ID.

Không tự đưa actor về một vị trí trên map.

Nếu có nhu cầu reset toàn bộ character sau này, đó là một gameplay transaction có phạm vi khác.

## 7.7. Atomic State Semantics

`reviveEntity()` phải:

- Trả Life State snapshot mới khi successful.
- Không mutate old Life State.
- Không mutate Resource State.
- Không mutate Entity Collection.
- Không phát event.
- Không chạy lifecycle hooks.
- Không để lại partial mutable state khi failure.

Resource recovery và revival là hai explicit operations; chúng không được tuyên bố là một transaction atomic duy nhất.

Caller chịu trách nhiệm quyết định sử dụng kết quả nào nếu một bước của workflow thất bại.

# 8. EC17 — Life Transition Result

## 8.1. Objective

Chuẩn hóa kết quả của Defeat Resolution và Revival.

Consumer phải phân biệt:

- Actor vừa bị defeat.
- Actor vừa được revived.
- Actor không đổi Life State.

## 8.2. Result Contract

Public type định hướng:

```ts
type EntityLifeTransitionOutcome =
  | "defeated"
  | "revived"
  | "unchanged";

interface EntityLifeTransitionResult {
  readonly entityId: string;
  readonly before: EntityLifeStatus;
  readonly after: EntityLifeStatus;
  readonly outcome: EntityLifeTransitionOutcome;
  readonly state: EntityLifeState;
}
```

Có thể bổ sung resource ID/diagnostic cần thiết, nhưng không thêm arbitrary event history hoặc timestamps.

Khi `defeated`:

```text
before = alive
after = dead
```

Khi `revived`:

```text
before = dead
after = alive
```

Khi `unchanged`:

```text
before = after
```

Không được trả `defeated` hoặc `revived` nếu status thực tế không chuyển.

## 8.3. Immutable Results

- Result là immutable snapshot.
- Nested Life State immutable.
- Không chứa mutable resource references.
- Không chứa callbacks.
- Không chứa private runtime capabilities.
- Không có hidden event listener table.
- Không giữ caller-owned mutable data aliases.

Không tạo duplicate computation để dựng result.

## 8.4. Failure vs No Change

Phải phân biệt:

**Valid evaluation nhưng không có transition**

```text
alive + health > minimum → unchanged
```

**Invalid input**

```text
lifeState.entityId != resourceState.entityId
```

Phải reject rõ ràng.

Không dùng `unchanged` để che lỗi malformed input.

Không âm thầm coi resource missing là một actor bất tử.

## 8.5. Deterministic Result

Cùng:

- Life State.
- Resource State.
- Life policy.
- Explicit call.

Phải tạo cùng semantic transition result.

Không dùng Date/Clock/RNG.

Không auto-increment death counter.

Không tạo random event ID.

# 9. Integration With GF12 — Event Publication

## 9.1. Objective

Cho phép consumer sử dụng Life Transition Result để publish gameplay events qua existing Foundation Event Pub/Sub.

**Event publication phải explicit.**

Không sửa GF12/GF13 implementation.

## 9.2. Conceptual Flow

```text
EC12 Resource Transition
          │
          ▼
EC15 Defeat Resolution
          │
          ▼
EntityLifeTransitionResult
          │
          ▼
Caller chooses whether to publish
          │
          ▼
GF12 publishEvent()
          │
          ▼
Registered listeners
```

Ví dụ:

```ts
const result = resolveEntityDefeat(
  lifeState,
  resourceState,
  policy
);

if (result.outcome === "defeated") {
  publishEvent(messaging, {
    type: "entity-defeated",
    payload: {
      entityId: result.entityId
    }
  });
}
```

Đây là conceptual integration. Implementation phải dùng đúng GF12 public contract đã được nghiệm thu.

Không tự publish khi `resolveEntityDefeat()` được gọi.

## 9.3. Event Semantics

Caller có thể chọn event names:

- `entity-defeated`
- `entity-revived`

Nhưng Entity module không tự tạo event catalog bắt buộc.

Foundation không được tự biết actor là Player hay Monster để tạo event khác nhau.

Không tự phát:

- `monster-killed`
- `player-died`
- `quest-progressed`
- `reward-earned`

Chúng thuộc game-specific behavior hoặc các gameplay capabilities khác.

## 9.4. Event Ordering

Khi caller publish event, giữ nguyên GF13:

- Subscribers theo subscription order.
- Snapshot fan-out.
- Fail-fast error result.
- No implicit async queue.

Không xây Event Bus thứ hai trong Entity module.

## 9.5. Event Failure Boundary

Nếu caller publish event sau Life Transition và listener throw:

- GF12 trả event failure theo accepted contract.
- Life Transition Result đã được tạo không bị mutate.
- Không có automatic rollback.
- Không tự retry publish.

Không claim Life State và Event Publication là một transaction duy nhất.

## 9.6. No Duplicate Transition Events

Một lần `resolveEntityDefeat()` trên Life State đã dead không được trả `defeated` lại.

Một lần `reviveEntity()` trên Life State đã alive không được trả `revived` lại.

Đây là cách hỗ trợ consumer tránh phát duplicate events khi xử lý state snapshots tuần tự.

**Giới hạn:** Vì state snapshots là immutable, caller vẫn có thể cố ý gọi lại cùng old snapshot. EC17 không cung cấp global replay protection. Caller phải giữ snapshot mới nhất hoặc sử dụng một state authority phù hợp ở tầng cao hơn.

Không thêm global execution counter, event history hoặc replay guard để giải quyết vấn đề này ở v0.2.4.

# 10. Life State & Resource Consistency

## 10.1. Entity ID Association

Bắt buộc kiểm tra:

```text
LifeState.entityId == ResourceState.entityId
```

Khi mismatch:

- Reject.
- Không tạo successful transition.

## 10.2. Resource State Validation

Life operations phải sử dụng accepted EC10–EC13 validation/inspection path.

Không tin hoàn toàn vào TypeScript readonly types.

Không để forged/malformed Resource State làm Life State transition mà không được validate.

Không nhân bản toàn bộ resource validator nếu đã có canonical implementation.

Nếu EC10–EC13 thiếu một boundary cần thiết, chỉ thực hiện minimal additive reuse trong Entity owner mà không thay đổi public semantics.

Nếu không thể làm được mà cần breaking change, báo blocker.

## 10.3. Life Resource Selection

Life policy explicit xác định resource ID.

Ví dụ:

```text
Actor A:
  resourceId = health

Actor B:
  resourceId = vitality
```

Cả hai đều dùng cùng Defeat/Revival APIs.

Không hardcode `health` hoặc `hp`.

Một actor không có life resource tương ứng không được tự suy ra resource khác.

## 10.4. Different Resource Minimum

Ví dụ:

```text
resourceId = life
minimum = 10
maximum = 100
```

Nếu current = 10 và Life State đang alive:

```text
resolveEntityDefeat() → defeated
```

Không yêu cầu minimum bằng 0.

Không dùng falsy check:

```ts
if (!current) ...
```

để xác định chết.

## 10.5. Stale Resources

Nếu caller thay đổi effective maximum ở EC09 nhưng chưa normalize Resource State:

- Life operations không tự gọi Stats.
- Không tự normalize Resource State.
- Không tự điều chỉnh maximum.
- Không tự hồi resource.

Caller phải cung cấp policy/bounds nhất quán với intended operation.

Không triển khai automatic Stats → Resource → Life synchronization.
