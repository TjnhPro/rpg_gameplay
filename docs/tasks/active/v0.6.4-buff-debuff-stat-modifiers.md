| Entity effective stats | L2 Entity + Core | `calculateEntityStats()` |
| Effect Instance and Lifecycle | L2 Effect | Existing owner |




**Correct ownership:**

# 4. Verified Core Numerical Contracts

## 4.1. Modifier Operations

Core supports exactly:

```ts
type ModifierOperation =
  | "add_flat"
  | "add_percent"
  | "add_percentage_points";
```

Do not introduce new operations:

```text
multiply
divide
override
set
min
max
exponential
```

They are unsupported by the pinned numerical modifier contract.

Such requirements belong to future Core capability review, not this MVP.

## 4.2. Canonical Modifier Shape

Use actual public Core type:

```ts
interface NumericalModifier {
  readonly identity: {
    readonly source: string;
    readonly sourceInstanceId: string;
    readonly id: string;
  };

  readonly target: string;

  readonly operation: ModifierOperation;

  readonly value: number;

  readonly enabled: boolean;
}
```

Do not define a second equivalent numerical contract.

Effect may define its own **L3-facing unbound modifier specification**, but it must ultimately produce the actual Core type.

## 4.3. Verified Numerical Semantics

Core applies:

```text
totalFlat = base + sum(add_flat)

value =
  totalFlat × (1 + sum(add_percent))
  + sum(add_percentage_points)
```

Core also owns enabled filtering and canonical modifier identity behavior.

**This is documentation and test oracle information, not authorization to copy the algorithm into Effect.**

## 4.4. Existing Entity Boundary

`calculateEntityStats()` accepts an `EntityStatConfiguration` containing:

```ts
modifiers: readonly NumericalModifier[];
```

It validates configured attribute/stat targets, then calls Core numerical modifier and stat calculation APIs.

Therefore EF23 can be implemented through the existing public Entity API.

**No Entity production change is authorized.**

# 5. EF21 — Buff / Debuff Classification

## 5.1. Objective

Allow an Effect modifier snapshot to carry semantic classification independent from its numerical value.

## 5.2. Proposed Type

```ts
export type EffectClassification =
  | "buff"
  | "debuff"
  | "neutral";
```

Meaning:

- `buff`: L3 classifies the Effect as beneficial.
- `debuff`: L3 classifies the Effect as harmful.
- `neutral`: no beneficial/harmful classification.

Classification is metadata, not a numerical rule.

## 5.3. Classification Rules

Do not infer classification from:

```text
Positive modifier value
Negative modifier value
Effect ID
Source type
Skill ID
```

Examples:

```text
Effect: battle-focus
classification = buff

Effect: weakness
classification = debuff

Effect: environmental-state
classification = neutral
```

No built-in hardcoded effect catalogue.

## 5.4. Classification Does Not Imply Modifier

A Buff may have zero numerical modifiers.

A Debuff may have zero numerical modifiers.

Examples:

```text
Silence:
  classification = debuff
  numerical modifiers = []
```

This is structurally valid.

The actual Silence restriction belongs to v0.6.5.

## 5.5. No Separate Engines

Do not create:

```text
BuffState
DebuffState
BuffLifecycle
DebuffLifecycle
BuffEngine
DebuffEngine
```

Buff, Debuff and Neutral use the same Effect lifecycle.

No separate expiry, stack or refresh implementations.

## 5.6. No Effect Definition Breaking Change

Do not add `classification` to accepted:

```ts
EffectDefinition
EffectInstanceState
EffectState
```

Existing EF01–EF20 closed-record contracts remain unchanged.

Classification is captured in the modifier metadata companion when an Effect becomes active.

# 6. EF22 — Effect Modifier Snapshot

## 6.1. Objective

Capture resolved modifier values when a new Effect Instance is admitted into canonical lifecycle state.

D12:

**Effect modifier numerical values are snapshotted at application time.**

No dynamic source-stat resolution during later reads.

## 6.2. Proposed Modifier Specification

```ts
export interface EffectModifierSpec {
  readonly modifierId: string;

  readonly target: string;

  readonly operation: ModifierOperation;

  readonly value: number;

  readonly enabled: boolean;
}
```

`ModifierOperation` is imported as a type from:

```ts
@rpg/core/kernel
```

No duplicated operation union.

## 6.3. Modifier Spec Rules

Required fields are exact.

`modifierId`:

- Opaque nonblank string.
- Stable within one Effect Instance.
- Exact/case-sensitive.
- No auto-generation.

`target`:

- Opaque nonblank string.
- Must eventually match a valid Entity stat/attribute target.

`operation`:

- Must belong to Core's supported union.

`value`:

- Finite number.
- Negative and zero values allowed.
- No string coercion.
- No arbitrary balancing clamps.

`enabled`:

- Explicit boolean.
- No implicit default.

## 6.4. Target Validation Ownership

Effect validates target identity shape.

It must **not duplicate** the Entity stat/attribute target catalogue.

Example:

```text
target = attack
```

is accepted structurally as a nonblank ID.

At the stat calculation boundary, Entity validates whether `attack` is a configured target.

If unsupported:

```text
Canonical Entity TypeError
```

Do not silently ignore unknown targets.

Do not create an Effect-specific stat registry.

## 6.5. Snapshot Input

Proposed:

```ts
export interface EffectModifierCapture {
  readonly classification: EffectClassification;
  readonly modifiers: readonly EffectModifierSpec[];
}
```

L3/L4 must supply concrete resolved modifier values.

No implicit strength scaling.

No access to Skill Rank or source attributes from Effect.

If a game requires a modifier whose value depends on caster Attack, L3/L4 resolves that value before capture using approved canonical operations.

Effect stores the resolved value without recalculating it.

## 6.6. Snapshot Contract

Proposed:

```ts
export interface EffectModifierSnapshot {
  readonly effectInstanceId: string;

  readonly classification: EffectClassification;

  readonly modifiers: readonly EffectModifierSpec[];
}
```

One snapshot belongs to one canonical Effect Instance.

Even when `modifiers = []`, the snapshot records that the active instance was captured.

This prevents treating missing snapshot data as an implicit zero-modifier configuration.

## 6.7. Snapshot Identity

Numerical source identity must be:

```text
identity.source:
  effect

identity.sourceInstanceId:
  effectInstanceId

identity.id:
  modifierId
```

Example:

```ts
{
  identity: {
    source: "effect",
    sourceInstanceId: "effect-instance-001",
    id: "attack-bonus"
  },
  target: "attack",
  operation: "add_percent",
  value: 0.2,
  enabled: true
}
```

Use fixed `source: "effect"` as the namespace of the Effect module.

Do not use:

```text
source = buff
source = debuff
```

because classification is metadata, not numerical source ownership.

Do not use `sourceKey` as `sourceInstanceId`.

The canonical active Effect Instance ID identifies the numerical contribution source.

## 6.8. Duplicate Modifier ID

Within one Effect Instance snapshot:

```text
modifierId = attack-bonus
modifierId = attack-bonus
```

Expected:

```text
TypeError
```

No silent overwrite or local deduplication.

Across different Effect Instances, the same `modifierId` is valid because `sourceInstanceId` differs.

## 6.9. Snapshot Immutability

Capture must:

- Validate all nested values.
- Detach from caller arrays and records.
- Freeze snapshots deeply.
- Preserve exact numeric values.
- Preserve modifier order.
- Avoid live callbacks.
- Avoid input mutation.
- Avoid hidden global caches.

After capture, changes to L3 configuration must not affect existing instances.

```text
Exactly one EffectModifierSnapshot
```

```text
Its effectInstanceId exists in lifecycle.effectState.instances
```

- No orphaned modifier snapshots.

- Same target Entity context.

```ts
export function createEffectModifierState(
```

```text
lifecycle:
```

## 7.6. No Second Lifecycle Engine

# 8. Snapshot Capture & Lifecycle Transitions

## 8.1. Required Integration Approach

The new modifier layer must consume accepted Effect/Lifecycle/Stack transition results.

It must **not create a second application or stacking implementation**.

Proposed public API:

```ts
export function applyEffectModifierTransition(
  current: EffectModifierState,
  transition:
    | EffectLifecycleStartResult
    | EffectLifecycleTransitionResult
    | EffectStackMutationResult,
  capture?: EffectModifierCapture
): EffectModifierTransitionResult;
```

Use actual approved v0.6.3 result contracts if their final names differ.

The operation is a pure projection/association of canonical lifecycle results.

It must not reimplement their transition logic.

## 8.2. New Effect Application

Flow:

```text
L4 obtains EF09 accepted application
             ↓
L2 Effect starts/adds lifetime
             ↓
Canonical Effect transition
             ↓
L3 supplies modifier capture
             ↓
applyEffectModifierTransition()
             ↓
EffectModifierState candidate
             ↓
L4 Commit
```

Requirements:

- Exactly one new canonical instance.
- New instance has accepted lifecycle membership.
- Explicit `EffectModifierCapture` required.
- Snapshot stored against that instance ID.
- Previous snapshots unchanged.
- Returned candidate frozen.

No capture without a newly accepted instance.

## 8.3. Stack Addition

For v0.6.3:

```text
action = added
```

The new stack receives its own immutable snapshot.

Example:

```text
Stack A:
  effect-instance-A
  attack +10%

Stack B:
  effect-instance-B
  attack +10%
```

Projection must produce two distinct canonical modifiers with distinct `sourceInstanceId`.

No implicit merging of stacks into a single synthetic modifier.

## 8.4. Refresh

For:

```text
action = refreshed
```

Required:

- No new Effect Instance.
- No new modifier snapshot.
- Existing snapshot remains unchanged.
- Incoming modifier capture must not overwrite it.
- Classification remains unchanged.
- Only canonical lifetime data may change.

If caller attempts to supply new modifier payload during refresh:

```text
TypeError
```

Do not silently accept a new snapshot.

This directly enforces D09.

## 8.5. Removal / Expiration

When a canonical lifecycle transition removes an instance:

```text
Remove:
  instance A
```

The resulting modifier state must exclude A's snapshot.

No reverse numerical calculation.

No subtraction from Entity base stats.

No hidden "undo buff" operation.

## 8.6. Stack Consumption

When EF20 consumes N stacks:

- Remove precisely those instance snapshots.
- Preserve unaffected stacks.
- Preserve surviving numerical values.
- Preserve snapshot order.
- No partial cleanup.

## 8.7. Group Removal

When EF20 removes an entire group:

- Remove every snapshot whose instance was removed.
- Leave unrelated groups untouched.
- Do not scan for or remove unrelated modifiers based on `effectId` alone.

## 8.8. Timeline Advancement

An EF13 advancement may:

- Change only observed time.
- Remove expired instances.
- Preserve persistent instances.

The modifier companion must follow the returned canonical lifecycle exactly.

No independent expiration calculation inside modifier synchronization.

## 8.9. Transition Validation

Before accepting a transition:

1. Validate current EffectModifierState fully.
2. Validate supplied canonical transition result shape.
3. Verify Entity identity is unchanged.
4. Verify unaffected instances are unchanged.
5. Verify existing modifier snapshots remain associated with the same instance IDs.
6. Verify the membership delta matches the reported transition action.
7. Reject unexpected additions without capture.
8. Reject missing capture on new application.
9. Reject capture on refresh/removal/expiration.
10. Reject silent replacement of existing snapshots.

No trusting a transition merely because its status says `applied`.

The supplied result is still a caller-provided value, not a durable authorization token.

L4 retains authoritative freshness and commit responsibility.

## 8.10. Rejection Semantics

Malformed inputs:

```text
TypeError
```

Valid rejected canonical lifecycle/stack result:

```text
status = rejected
state = null
```

Do not partially update modifier snapshots.

No fabricated success result.

# 9. EF23 — Entity Stat Integration

## 9.1. Objective

Expose canonical numerical modifiers from currently active Effect snapshots so they can be passed directly to Entity.

## 9.2. Public Projection API

Proposed:

```ts
export function listActiveEffectModifiers(
  state: EffectModifierState
): readonly NumericalModifier[];
```

Return the actual Core numerical modifier shape.

Do not create:

```text
EffectiveEffectModifier
BuffValue
ComputedStatBonus
FinalBuffStat
```

as a competing numerical result.

## 9.3. Projection Rules

For each active instance in canonical lifecycle order:

1. Find its one matching snapshot.
2. Read captured `modifiers`.
3. Project each modifier to Core's `NumericalModifier`.
4. Bind identity.source to `effect`.
5. Bind identity.sourceInstanceId to exact Effect Instance ID.
6. Bind identity.id to captured modifierId.
7. Preserve target/operation/value/enabled.
8. Return frozen detached array and nested objects.

No numerical reduction.

No filtering based on Buff/Debuff classification.

No automatic multiplication by stack count.

No duplicate contribution insertion.

## 9.4. Disabled Modifiers

If a snapshot contains:

```ts
{
  modifierId: "attack-bonus",
  target: "attack",
  operation: "add_percent",
  value: 0.2,
  enabled: false
}
```

The projection preserves `enabled: false`.

Core owns enabled filtering.

Effect must not silently rewrite it or turn it into a zero-valued modifier.

## 9.5. Calculation Consumer

Expected:

```ts
const effectModifiers =
  listActiveEffectModifiers(effectModifierState);

const stats = calculateEntityStats(
  entityAttributeState,
  {
    ...existingStatConfiguration,
    modifiers: effectModifiers
  }
);
```

This is the existing canonical Entity calculation path.

No production helper is required to wrap `calculateEntityStats()`.

## 9.6. Pending Expiration

If lifecycle has due-but-unresolved expirations at its current observed timestamp, projection must fail closed rather than silently emit stale contributions.

Caller must complete canonical lifecycle advancement first.

Do not silently expire instances inside `listActiveEffectModifiers()`.

This preserves future D15 tick-before-expire ordering.

## 9.7. Base Stats Unchanged

Example:

```text
Entity Base Attack:
  100

Buff:
  +20%

Effective Attack:
  120
```

The Entity base value remains:

```text
100
```

After the Buff expires:

```text
Effective Attack:
  100
```

No state rollback arithmetic.

# 10. EF24 — Multi-Source Modifier Composition

## 10.1. Objective

Verify that Effect modifiers coexist with other canonical modifier sources.

Examples:

```text
Effect
Equipment
Item
Environment
Other gameplay systems
```

No Equipment or Item production module is required.

External consumer fixtures may provide their numerical modifier records directly.

## 10.2. Composition Ownership

L4 prepares one complete modifier input:

```ts
const modifiers = [
  ...equipmentModifiers,
  ...itemModifiers,
  ...listActiveEffectModifiers(effectModifierState)
];

const stats = calculateEntityStats(
  entityAttributes,
  {
    ...statConfiguration,
    modifiers
  }
);
```

This is consumer orchestration, not a new production modifier aggregator.

## 10.3. Source Namespace Isolation

Effect records use:

```text
source = effect
```

Equipment fixtures use:

```text
source = equipment
```

Other sources must use their own stable namespaces.

Do not rewrite another source's identity.

Do not generate a synthetic common `buff` source.

L4 is responsible for preventing unauthorized source namespace reuse.

## 10.4. Canonical Identity Collision

Core modifier identity is:

```text
source
sourceInstanceId
id
```

If two records share this tuple, canonical Core resolver determines whether they are equivalent or conflicting.

Do not implement alternate last-wins, first-wins or sum-on-duplicate behavior in Effect.

Do not silently rename duplicate IDs.

## 10.5. Independent Source Example

Entity:

```text
Base Attack = 100
```

Equipment:

```text
+5 flat
```

Buff:

```text
+20%
```

Debuff:

```text
-10 flat
```

Expected canonical result:

```text
(100 + 5 - 10) × 1.2 = 114
```

All values passed into `calculateEntityStats()`.

Effect must not compute `114` itself.

## 10.6. No Global Ordering Policy

The Core resolver owns modifier selection and calculation semantics.

L4 supplies source contributions and their identities.

Effect must not add its own ranking system:

```text
Equipment before Buff
Buff before Debuff
Strongest source wins
Last applied wins
```

Those behaviors are not part of the current Core modifier contract.

## 10.7. Unknown Numerical Targets

## 11.1. Objective

## 11.2. Required Invariant

```text

  → Snapshot exists
  → Canonical modifiers projected

  → Snapshot removed from current companion state
  → No canonical modifiers projected
```

```text

```


## 11.9. Persistent Effect

Persistent equipment-style Effect:

```text

```

No automatic equipment watcher.

```text
         ↓

         ↓
```

The new modifier companion is a view of the same lifecycle progression, not a replacement Effect runtime.
