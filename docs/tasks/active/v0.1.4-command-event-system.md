## 1. Objective

Triển khai Command & Event System để các gameplay modules có thể nhận yêu cầu, xử lý command và trao đổi gameplay events thông qua các public contracts thống nhất.

Các modules không cần import implementation nội bộ của nhau để thực hiện giao tiếp thông thường.

Version này gồm:

| ID | Feature | Responsibility |
|---|---|---|
| GF10 | Command Registration & Dispatch | Đăng ký command handlers và định tuyến command đến đúng owner |
| GF11 | Command Result Contract | Chuẩn hóa kết quả thành công, từ chối, không có handler và lỗi xử lý |
| GF12 | Event Publish / Subscribe | Cho phép modules publish events và đăng ký listeners |
| GF13 | Event Ordering & Subscription Lifecycle | Bảo đảm thứ tự xử lý, unsubscribe, cleanup và failure semantics |

**Kết quả mong muốn:**

Consumer có thể sử dụng public functions để:

1. Đăng ký command handler thuộc một selected module.
2. Gửi command và nhận result có cấu trúc.
3. Đăng ký listeners cho gameplay events.
4. Publish một event đến những listeners đã đăng ký.
5. Hủy subscriptions một cách rõ ràng.
6. Quan sát được thứ tự xử lý và lỗi.
7. Sử dụng nhiều command/event contexts độc lập.

Đây là **synchronous, headless, in-process coordination layer**.

Không xây dựng Event Sourcing, distributed message bus, background worker hoặc gameplay application.

# 4. General Design Contracts

## 4.1. Function-First

Public functionality phải sử dụng functions.

Ví dụ định hướng:

```ts
const messaging = createGameplayMessaging(composition);

registerCommandHandler(messaging, ...);

dispatchCommand(messaging, ...);

subscribeEvent(messaging, ...);

publishEvent(messaging, ...);
```

Đây là ví dụ conceptual, không bắt buộc giữ đúng tên hoặc signature.

Agent được lựa chọn cấu trúc dữ liệu và internal helpers phù hợp nhưng không được tạo class-based Gameplay Engine hoặc generic messaging framework.

## 4.2. Explicit Ownership

Mỗi command handler phải có một module owner rõ ràng.

Mỗi event subscription phải xác định module owner hoặc consumer scope rõ ràng.

Các module owners được khai báo phải thuộc composition hợp lệ.

Không đăng ký command handler hoặc module-owned subscription cho:

- Unknown module.
- Disabled module.
- Module không có trong composition.

Không tự enable hoặc register module để command/event hoạt động.

## 4.3. Isolation

Mỗi messaging context phải có state riêng.

Không sử dụng global mutable event bus.

Không sử dụng global command handler registry.

Không chia sẻ registrations/subscriptions giữa hai contexts nếu caller không chủ động cấu hình riêng.

Internal mutation capabilities phải được đóng gói, không được lộ qua public object properties, symbols hoặc public declarations.

Lưu ý bài học từ v0.1.3: `Object.freeze()` không đủ để bảo vệ internal state nếu caller vẫn có thể truy xuất mutable internals bằng JavaScript reflection.

## 4.4. Synchronous Execution

Ở v0.1.4:

- Command handlers chạy synchronous.
- Event listeners chạy synchronous.
- Không Promise orchestration.
- Không async queues.
- Không timers.
- Không tự chạy background tasks.
- Không implicit scheduler.

Nếu callback trả Promise/thenable, không được xem là xử lý thành công.

Error/result phải thể hiện việc synchronous contract bị vi phạm.

# 5. GF10 — Command Registration & Dispatch

## 5.1. Objective

Cho phép caller gửi một gameplay command qua public API mà không cần gọi trực tiếp implementation của một gameplay module.

Command là **yêu cầu thực hiện một hành động**.

Ví dụ conceptual:

```ts
const command = {
  type: "skill-use",
  payload: {
    skillId: "skill-100",
    targetId: "enemy-20"
  }
};
```

Đây chỉ là dữ liệu minh họa.

Foundation không kiểm tra skill, target hoặc combat rules.

## 5.2. Command Contract

Command contract tối thiểu:

- Command type/identity.
- Caller-supplied payload.
- Không chứa engine-specific objects.
- Không bắt buộc clock timestamps.
- Không bắt buộc global command IDs.

TypeScript phải hỗ trợ command payloads qua unknown/generic contracts phù hợp mà không ép một game-specific schema.

Invalid command identity phải bị reject rõ ràng.

Không dùng free-form routing conventions ngầm để đoán owner từ command string.

## 5.3. Command Handler Registration

Cung cấp API tương đương:

```ts
registerCommandHandler(messaging, {
  moduleId: "skill",
  commandType: "skill-use",
  handler: command => {
    // Caller-owned gameplay implementation.
  }
});
```

Yêu cầu:

1. Command handler có owner module ID.
2. Owner phải thuộc selected composition.
3. Command type hợp lệ.
4. Handler phải callable.
5. Mỗi command type có đúng một active handler trong một messaging context.
6. Duplicate command handler registration bị reject.
7. Invalid registration không ghi đè handler hiện có.
8. Không tự động đăng ký handlers chỉ vì module đã được selected.
9. Không dynamic import implementation.

Không cần một generic dependency injection container.

## 5.4. Dispatch Behavior

Cung cấp public function tương đương:

```ts
dispatchCommand(messaging, command);
```

Bắt buộc:

- Route đúng handler đã đăng ký.
- Chỉ gọi một handler cho một command.
- Không gọi tất cả modules.
- Không tự tạo handler nếu không tìm thấy.
- Không gọi implementation của disabled modules.
- Không phụ thuộc registration order của các module để chọn handler khi command identity đã rõ ràng.
- Không tự thay đổi ModuleComposition hoặc Runtime Lifecycle.
- Không tự publish event khi command hoàn thành.

Một command không có handler phải trả một kết quả xác định, không silently report success.

## 5.5. Execution Context

Command handler chỉ nhận explicit data/dependencies từ caller và các metadata thuộc coordination contract.

Foundation không tự cung cấp:

- Game State.
- Character.
- Inventory.
- Skill execution rules.
- Database.
- Network.
- Renderer.
- Clock.
- RNG.

Không tạo global service locator để handler truy cập dependencies.

Nếu một gameplay module cần state, adapter/services, việc đó thuộc module implementation hoặc caller-owned ports được truyền tường minh.

## 5.6. Command Handler Errors

Nếu handler throw:

- Dừng dispatch.
- Không gọi handler khác.
- Trả structured failure result.
- Diagnostic chỉ rõ command type và module owner.
- Không báo success.
- Không tự retry.
- Không tự rollback external side effects.

Nếu handler trả unsupported async value, kết quả phải thể hiện lỗi synchronous contract.

Không swallow errors để hệ thống có vẻ hoạt động thành công.

# 6. GF11 — Command Result Contract

## 6.1. Objective

Chuẩn hóa cách caller phân biệt các kết quả của một command.

Không để mỗi gameplay module tự định nghĩa các kết quả hoàn toàn khác nhau ở tầng Foundation.

## 6.2. Required Result States

Hỗ trợ tối thiểu bốn kết quả:

| Status | Meaning |
|---|---|
| `success` | Handler đã xử lý command thành công |
| `rejected` | Handler chủ động từ chối command theo rule của nó |
| `unhandled` | Không có handler được đăng ký cho command type |
| `failed` | Handler gặp lỗi hoặc vi phạm callback contract |

Ví dụ conceptual:

```ts
type CommandResult =
  | {status: "success"; value?: unknown}
  | {status: "rejected"; reason: string}
  | {status: "unhandled"; commandType: string}
  | {status: "failed"; failure: CommandFailure};
```

Có thể điều chỉnh schema để đủ diagnostic và type safety, nhưng phải giữ sự khác nhau giữa bốn trạng thái.

Không dùng `boolean` đơn thuần làm public command result.

## 6.3. Handler Result Validation

Bắt buộc:

- Handler success phải được biểu diễn rõ ràng.
- Handler rejection phải được biểu diễn rõ ràng.
- Invalid handler result không được chuyển thành success ngầm.
- Rejection không được tự động đổi thành technical failure.
- Unhandled không được tự động đổi thành successful no-op.
- Thrown errors trở thành structured failure.
- Result metadata được bảo vệ khỏi caller mutation ngoài ý muốn.

Nếu business payload là object do caller sở hữu, không bắt buộc deep clone arbitrary game-specific data.

Documentation phải nêu rõ quyền sở hữu payload và giới hạn immutability.

## 6.4. Domain Separation

Foundation chỉ sở hữu kết quả điều phối.

Ví dụ:

```text
Command: USE_SKILL
Result: REJECTED
Reason: INSUFFICIENT_MANA
```

`INSUFFICIENT_MANA` là game/module-defined reason.

Foundation không tự kiểm tra mana hoặc áp đặt domain reason catalog.

Không tạo gameplay error codes thuộc Skill/Combat/Item tại GF11.

# 7. GF12 — Event Publish / Subscribe

## 7.1. Objective

Cho phép modules phản ứng với gameplay events mà không cần import trực tiếp implementation của module phát event.

Event là **thông báo một sự kiện đã xảy ra**.

Ví dụ:

```ts
{
  type: "skill-executed",
  payload: {
    skillId: "skill-100",
    actorId: "player-1"
  }
}
```

Foundation không quyết định một event như vậy phải xảy ra khi nào.

## 7.2. Event Contract

Event contract tối thiểu:

- Event identity/type.
- Caller-supplied payload.
- Không chứa implicit execution policy.
- Không bắt buộc timestamp hoặc sequence từ global clock.

Event type phải có validation và định danh xác định.

Không bắt buộc event type phải khớp tên concrete gameplay module.

## 7.3. Subscription

Cung cấp public function tương đương:

```ts
const subscription = subscribeEvent(messaging, {
  moduleId: "effect",
  eventType: "skill-executed",
  handler: event => {
    // React to event.
  }
});
```

Bắt buộc:

- Module-owned subscription chỉ thuộc selected module.
- Một event type có thể có nhiều subscribers.
- Một module có thể subscribe nhiều event types.
- Subscription có identity/token để unsubscribe.
- Invalid subscriber/owner bị reject.
- Không tự tạo module.
- Không đăng ký global listeners.
- Không dùng renderer hoặc Node EventEmitter như một bắt buộc public runtime dependency.

Có thể sử dụng native language collections nội bộ nhưng không mở chúng ra public API dưới dạng writable state.

## 7.4. Publish

Cung cấp public function tương đương:

```ts
publishEvent(messaging, event);
```

Expected:

- Event được gửi đến những active subscribers của đúng event type.
- Subscribers của event type khác không bị gọi.
- Zero subscribers là một trường hợp hợp lệ.
- Không tự động đăng ký subscriber.
- Không tự chạy lifecycle hooks.
- Không bắt buộc một event phải có subscriber.

Không tự tạo automatic event từ command result.

Caller hoặc gameplay module chủ động quyết định khi nào publish event.

## 7.5. Event Payload Ownership

Foundation không được mutate event payload.

Không deep-freeze arbitrary payload objects do caller sở hữu nếu có nguy cơ thay đổi behavior của consumer.

Nếu cần readonly metadata, chỉ bảo vệ metadata thuộc Foundation.

Callback nhận payload theo contract rõ ràng.

Không biến Event System thành gameplay state store.

# 8. GF13 — Event Ordering & Subscription Lifecycle

## 8.1. Deterministic Ordering

Subscribers của cùng event type được gọi theo **subscription registration order**.

Ví dụ:

```text
Subscriptions:

1. listener-A → event-x
2. listener-B → event-x
3. listener-C → event-y
4. listener-D → event-x
```

Publish `event-x`.

Expected trace:

```text
listener-A
listener-B
listener-D
```

Không gọi listener-C.

Không tự sắp xếp subscribers theo module dependency order. GF04 chỉ quyết định dependency ordering cho module composition, không phải thứ tự fan-out của từng event.

## 8.2. Unsubscribe Contract

Cung cấp function tương đương:

```ts
unsubscribeEvent(messaging, subscription);
```

Bắt buộc:

1. Hủy đúng subscription.
2. Không hủy subscriptions khác cùng event type.
3. Không ảnh hưởng event types khác.
4. Hủy subscription trước publish tiếp theo khiến handler không còn được gọi.
5. Subscription thuộc context A không được phép mutate context B.
6. Repeated unsubscribe có kết quả rõ ràng, an toàn cho cleanup.
7. Invalid/cross-context token không được âm thầm hủy một subscription khác.

Có thể chọn boolean result hoặc explicit status, nhưng contract phải nhất quán và được kiểm chứng.

## 8.3. Module-Owned Cleanup

Cung cấp một cơ chế rõ ràng để cleanup tất cả subscriptions do một module owner đăng ký.

Ví dụ conceptual:

```ts
unsubscribeModuleEvents(messaging, "effect");
```

Có thể thực hiện bằng module-scoped subscription handles thay vì bắt buộc một public function mới.

Mục tiêu:

- Không phải lưu một global list các subscriptions.
- Cleanup của module A không ảnh hưởng module B.
- Module bị dispose không để lại active subscriptions trong context được cleanup.
- Cleanup không cần event bus riêng cho từng gameplay module.

## 8.4. Lifecycle Integration Boundary

Tích hợp với GF07 bằng explicit lifecycle bindings.

Ví dụ:

```text
Initialize/start module:
  Register relevant subscriptions

Stop/dispose module:
  Cleanup subscriptions owned by module
```

Task phải có functional evidence cho một trường hợp module lifecycle gọi cleanup qua public API.

**Không được tuyên bố cleanup tự động theo Runtime Lifecycle nếu implementation không thực sự làm điều đó.**

Nếu caller phải tự wiring cleanup trong lifecycle hook, tài liệu phải nói rõ trách nhiệm đó.

Không âm thầm sửa GF07 để tự động attach event bus vào Runtime Context.

Không tạo Runtime Lifecycle Engine thứ hai.

## 8.5. Subscription Changes During Publish

Cần quy định hành vi xác định:

- Mỗi publish sử dụng danh sách active subscribers chụp tại thời điểm bắt đầu publish.
- Subscribe/unsubscribe trong callback không thay đổi iteration của publish hiện tại.
- Những thay đổi đó có hiệu lực từ publish tiếp theo.
- Không iterate trực tiếp trên mutable registry theo cách gây skip/duplicate callbacks không xác định.

Không cần xây một event queue để xử lý tình huống này.

## 8.6. Listener Failure

Nếu một listener throw hoặc trả unsupported Promise/thenable:

1. Publish không được báo success hoàn toàn.
2. Diagnostic xác định event type và subscriber/module lỗi.
3. Những listeners đã hoàn thành trước lỗi phải được ghi nhận.
4. Những listeners sau lỗi không được gọi.
5. Không tự retry hoặc rollback caller-owned side effects.
6. Không tiếp tục bỏ qua lỗi như thể event đã được xử lý đầy đủ.

Chọn **fail-fast** cho v0.1.4.

Publish result phải thể hiện tối thiểu:

- Success/failure.
- Số listeners đã hoàn thành.
- Failure location khi có lỗi.

Không bắt buộc persistent event history.

## 8.7. Reentrancy Boundary

Không tạo recursive automatic event propagation.

Đối với việc một callback gọi lại dispatch/publish trên cùng messaging context, implementation phải có chính sách xác định và không làm corruption internal subscription state.

Ưu tiên fail-closed cho unsupported reentrant execution trong phiên bản này, thay vì ngầm tạo event queue hoặc nested scheduler.

Nếu callback thực hiện nested operation bị từ chối, failure phải observable; không silently drop events.

Không tạo async scheduler để giải quyết reentrancy.

# 9. Command/Event Relationship

GF10 và GF12 là hai cơ chế khác nhau.

**Command**

```text
Caller
   │
   ▼
Command Dispatch
   │
   ▼
Exactly one registered handler
   │
   ▼
Structured Command Result
```

**Event**

```text
Publisher
   │
   ▼
Event Publish
   │
   ├── Listener A
   ├── Listener B
   └── Listener C
```

Command biểu diễn intent/request.

Event biểu diễn thông báo đã có hành vi xảy ra.

Không đánh đồng hai khái niệm.

## Example — Future Gameplay Module

Conceptual flow:

```text
USE_SKILL command
       │
       ▼
Skill Module handler
       │
       ├── Validate gameplay preconditions
       │
       ├── Execute authorized gameplay behavior
       │
       ▼
Command Result: SUCCESS
       │
       ▼
Explicit publication:
SKILL_EXECUTED
       │
       ├── Effect subscriber
       └── Combat subscriber
```

GF10–GF13 chỉ cung cấp routing và publication primitives.

Không thực hiện validation, Skill Execution, Effect Application hoặc Combat Calculation ở version này.

Không tự động publish `SKILL_EXECUTED` khi một command type có tên `USE_SKILL`.

# 10. Ownership & Architecture

## 10.1. Canonical Owner

GF10–GF13 thuộc một canonical Foundation coordination owner.

Cấu trúc tham khảo:

```text
src/
  foundation/
    modules/     # GF01–GF05
    runtime/     # GF06–GF09
    messaging/   # GF10–GF13
  index.ts
```

Có thể tách internal command/event files nếu cần, nhưng chỉ có một ownership authority cho command registrations và một ownership authority cho event subscriptions trong mỗi messaging context.

Không tạo generic `EventBus` package riêng hoặc `GameplayEngine`.

## 11.2. Scenario A — Command Routing

Command handlers:

```text
inventory-use → Inventory handler
skill-use     → Skill handler
```

Dispatch `skill-use`.

Expected:

- Skill handler được gọi đúng một lần.
- Inventory handler không được gọi.
- Command result phản ánh đúng handler outcome.

Các module chỉ tồn tại dưới dạng test fixtures/probes. Không triển khai Inventory hoặc Skill System.

## 11.3. Scenario B — Command Result Semantics

Các tình huống:

```text
Valid handler returns success → SUCCESS

Handler rejects             → REJECTED

No handler exists           → UNHANDLED

Handler throws              → FAILED
```

Expected statuses và diagnostics phải phân biệt được.

Không dùng cùng một generic `false` cho mọi tình huống.

## 11.4. Scenario C — Event Fan-out

Subscriptions:

```text
Listener A → event-x
Listener B → event-x
Listener C → event-y
Listener D → event-x
```

Publish `event-x`.

Expected trace:

```text
A
B
D
```

Không gọi C.

## 11.5. Scenario D — Unsubscribe & Cleanup

- Subscribe A, B, C.
- Unsubscribe B.
- Publish event.
- Cleanup module owner của A.
- Publish lại.

Expected:

- Sau unsubscribe B: chỉ A/C được gọi nếu cùng event type.
- Sau cleanup owner của A: A không còn được gọi.
- C không bị ảnh hưởng.

Kết quả phải được chứng minh bằng callback trace, không chỉ inspect subscription count.

## 11.6. Scenario E — Listener Failure

Subscriptions:

```text
A → success
B → throws
C → success
```

Publish.

Expected:

- A hoàn thành.
- B gây failure.
- C không được gọi.
- Publish result ghi nhận chính xác completed deliveries và module/subscriber lỗi.
- Không rollback A.

## 11.7. Scenario F — Isolation

Tạo hai messaging contexts từ cùng composition.

Đăng ký handlers/subscribers khác nhau.

Expected:

- Context A không dispatch qua handler B.
- Publish trong A không gọi subscriber của B.
- Cleanup A không ảnh hưởng B.
- Không có global registration leakage.

## 11.8. Scenario G — Lifecycle Integration

Sử dụng public GF07 lifecycle hooks và GF12/GF13 subscription APIs.

Expected:

1. Lifecycle hook đăng ký subscription.
2. Publish event gọi subscriber.
3. Stop/dispose hook thực hiện explicit cleanup.
4. Publish tiếp theo không còn gọi subscriber đã cleanup.
5. Không thay đổi GF07 transition model.

Nếu implementation chỉ hỗ trợ manual cleanup, test phải thể hiện đúng manual integration; không claim automatic lifecycle binding.
