# 4. EC04 — Entity Collection

## 4.1. Objective

Tạo một collection chứa các Entity snapshots hợp lệ.

Collection quản lý:

- Entity membership.
- Unique entity IDs trong phạm vi collection.
- Stable insertion order.
- Entity lookup.
- Entity removal.

Không quản lý:

- Runtime Lifecycle.
- Entity AI.
- Combat.
- Game World.
- Network sessions.
- Persistence.

## 4.2. Required Public Functions

Cung cấp public functions tương đương:

```ts
createEntityCollection()

addEntity(collection, entity)

getEntity(collection, entityId)

hasEntity(collection, entityId)

listEntities(collection)

removeEntity(collection, entityId)
```

Có thể điều chỉnh tên nếu phù hợp codebase, nhưng phải giữ đầy đủ behavior.

Ưu tiên một canonical `EntityCollection` type thay vì tách nhiều collection engines.

## 4.3. Collection Contract

Ví dụ public contract định hướng:

```ts
interface EntityCollection {
  readonly entities: readonly EntitySnapshot[];
}
```

Đây là cấu trúc đề xuất, không bắt buộc implementation sử dụng đúng representation này.

Bắt buộc:

- Collection được tạo bằng public function.
- Empty collection hợp lệ.
- Chứa chỉ Entity snapshots đã validate.
- Không có duplicate IDs.
- Enumeration order xác định.
- Không expose writable internal state.
- Không sử dụng global mutable singleton.

## 4.4. Creating a Collection

```ts
const collection = createEntityCollection();
```

Expected:

- Collection rỗng.
- Không tự tạo player/monster.
- Không tự đăng ký module.
- Không tạo Runtime Context.
- Không đọc Clock/RNG.
- Không gọi Kernel.
- Không phát Event.

Tạo nhiều collections phải hoàn toàn độc lập.

## 4.5. Adding Entities

Ví dụ:

```ts
const player = createEntity({
  id: "player-1",
  kind: "player"
});

const monsters = addEntity(
  createEntityCollection(),
  player
);
```

`addEntity()` phải trả collection snapshot mới.

Bắt buộc:

1. Validate entity đầu vào bằng canonical EC03 semantics.
2. Thêm entity vào cuối collection.
3. Không mutate collection cũ.
4. Không mutate entity đầu vào.
5. Reject duplicate ID trong cùng collection.
6. Không silently overwrite existing entity.
7. Invalid input không thay đổi collection cũ.

Không tạo một validator thứ hai với semantics khác `createEntity()`.

Có thể gọi canonical creation/validation function nội bộ để bảo toàn contracts.

## 4.6. Identity Uniqueness

Uniqueness chỉ thuộc collection hiện tại.

Ví dụ:

```text
Collection A:
  player-1
  monster-1

Collection B:
  player-1
```

Hợp lệ.

Nhưng:

```text
Collection A:
  player-1
  player-1
```

Phải reject.

Entity IDs được so sánh chính xác, không trim, lowercase hoặc normalize.

Cùng ID nhưng khác kind vẫn bị xem là duplicate trong cùng collection.

## 4.7. Lookup

```ts
getEntity(collection, "player-1");

hasEntity(collection, "player-1");
```

Expected:

- `getEntity()` trả snapshot tương ứng hoặc `undefined` nếu không tìm thấy.
- `hasEntity()` trả `true`/`false`.
- Lookup không mutate collection.
- Lookup không tạo entity.
- Lookup không dùng object-reference identity.
- Không có database hoặc lazy loading.

Malformed lookup IDs phải reject rõ ràng.

Unknown nhưng hợp lệ ID không phải exception đối với lookup.

## 4.8. Enumeration

`listEntities()` phải:

- Trả danh sách theo insertion order.
- Không chứa duplicates.
- Không làm lộ writable backing array.
- Không cho caller mutate collection qua returned list.
- Cùng collection snapshot trả cùng enumeration.

Không tự sort theo ID/kind.

## 4.9. Removal

Ví dụ:

```ts
const next = removeEntity(
  collection,
  "monster-1"
);
```

Expected:

- Chỉ entity có ID được chỉ định bị xóa.
- Các entity khác không đổi.
- Relative order của những entity còn lại không đổi.
- Collection cũ vẫn giữ monster.
- Collection mới không chứa monster.

Trong v0.2.1, xóa ID không tồn tại phải reject rõ ràng bằng `TypeError`, tránh silently báo một transition đã thực hiện.

Không cascade sang inventory/equipment/effects hoặc game-world state.

Removal không tự phát event hay gọi lifecycle hooks.

# 5. EC05 — Entity State Snapshot

## 5.1. Objective

Xác định rõ collection và entity snapshots là dữ liệu gameplay bất biến, không phải live mutable storage.

Mỗi lần add/remove/replace phải tạo một version mới của collection.

Ví dụ:

```ts
const empty = createEntityCollection();

const withPlayer = addEntity(
  empty,
  createEntity({
    id: "player-1",
    kind: "player"
  })
);
```

Expected:

```text
empty:
  []

withPlayer:
  [player-1]
```

`empty` không bị thay đổi.

## 5.2. Snapshot Guarantees

- Collection object immutable.
- Entity snapshots immutable.
- Collection membership immutable.
- Enumeration immutable.
- Old snapshots không thay đổi khi tạo version mới.
- Caller không thể mutate kết quả để thay đổi các collection snapshots khác.
- Không có mutable state được chia sẻ ngoài ý muốn.

Có thể reuse references đến các already-validated frozen Entity snapshots.

Không bắt buộc clone lại immutable entities nếu không mang thêm bảo đảm.

## 5.3. Deterministic Ordering

Định nghĩa:

- Add: append.
- Replace: giữ vị trí cũ.
- Remove: xóa phần tử, giữ thứ tự tương đối của phần còn lại.
- Remove rồi add lại cùng ID: entity mới nằm cuối collection.

Cùng chuỗi operations từ cùng initial collection tạo cùng observable results.

Không sinh sequence number/timestamp tự động.

## 5.4. Snapshot vs Future Gameplay State

Tại v0.2.1:

**Entity snapshot** chỉ chứa identity/classification đã được nghiệm thu.

**Collection snapshot** chứa membership và snapshots tương ứng.

Không thêm ngay:

```ts
state: Record<string, unknown>
```

để làm generic state bag.

EC07–EC17 sau này sẽ thiết kế typed state contracts phù hợp cho attributes/resources/life state.

Task v0.2.1 không được tự quyết định trước cách tổ chức toàn bộ tương lai, ví dụ ép mọi gameplay state phải là một object duy nhất hoặc phải tồn tại trong một global Entity Store.

Chỉ xây ownership và immutable collection behavior thực sự cần thiết hiện tại.

# 6. EC06 — State Isolation & Updates

## 6.1. Objective

Cho phép một entity đã tồn tại trong collection được thay thế bằng snapshot hợp lệ mới thông qua controlled operation.

Không mutate entity trực tiếp.

## 6.2. Required Function

Cung cấp function tương đương:

```ts
replaceEntity(collection, entity)
```

Đây là **explicit full-snapshot replacement**, không phải generic partial patch.

Ví dụ:

```ts
const updated = replaceEntity(collection, {
  id: "actor-1",
  kind: "companion"
});
```

Yêu cầu:

- Entity `actor-1` phải đang tồn tại.
- `id` giữ nguyên logical identity.
- `kind` có thể thay đổi theo caller intent.
- Input phải thỏa EC03 validation.
- Replacement giữ nguyên vị trí entity trong collection.
- Old entity snapshot không đổi.
- Old collection không đổi.
- New collection chứa replacement snapshot.

Việc thay `kind` là một thao tác phân loại lại do caller chủ động, **không ngầm thay đổi quyền combat, AI, attributes hoặc life policy**.

Không có automatic side effects.

## 6.3. Replacement Semantics

Bắt buộc:

1. Không dùng `upsert`.
2. Không tự add nếu ID chưa tồn tại.
3. Không đổi Entity ID dưới dạng một update ngầm.
4. Không partial merge arbitrary fields.
5. Không bỏ qua invalid replacement.
6. Không giữ mutable references từ caller input.
7. Invalid replacement không làm thay đổi collection ban đầu.

Nếu muốn đổi identity, consumer phải thực hiện removal/addition rõ ràng; không thực hiện rename hoặc chuyển ownership ngầm.

## 6.4. Branching / Snapshot Isolation

Ví dụ:

```ts
const base = addEntity(
  createEntityCollection(),
  createEntity({
    id: "actor-1",
    kind: "npc"
  })
);

const branchA = replaceEntity(base, {
  id: "actor-1",
  kind: "companion"
});

const branchB = removeEntity(base, "actor-1");
```

Expected:

```text
base:
  actor-1 → npc

branchA:
  actor-1 → companion

branchB:
  empty
```

Không có mutation giữa ba snapshots.

Đây là một functional invariant quan trọng hơn việc tạo một generic state engine.

## 6.5. Failure Atomicity

Các lỗi cần xử lý:

- Replacement ID chưa tồn tại.
- Duplicate add.
- Invalid entity definition.
- Malformed collection.
- Invalid lookup/removal IDs.

Expected:

- Fail rõ ràng.
- Không partial changes.
- Không ảnh hưởng snapshot cũ.
- Không có global side effects.

Không cần transaction manager, lock manager hoặc rollback engine vì collection operations là synchronous immutable transformations.

- Branch A không ảnh hưởng branch B.
- Không có hidden shared state.
- `listEntities()` không cung cấp writable mutation path.

- Collection không chấp nhận dữ liệu vượt contract.

- Không silent conversion hoặc partial mutations.
