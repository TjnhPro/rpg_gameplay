## 4. AI36 — End-to-End Integration

### 4.1. Objective

Demonstrate genuine composition of the **actual** AI01–AI35 public contracts and the **actual canonical** gameplay module APIs from an L4-style consumer. The consumer is test code only, not a new gameplay application or production manager.

### 4.2. Mandatory complete composition

An integrated **AI-controlled Monster vs Player** scenario must prove:

```text
L4: construct real canonical EntityCollection and Resource/Life states
L4: inject World observation and explicit time through Foundation Clock
  ↓
AI06–AI10: perception snapshot and eligibility assessment
  ↓
AI11–AI15: choose target; L4 accepts immutable target candidate
  ↓
AI16–AI20: L4 supplies accepted trigger; FSM proposes Engaged; L4 commits
  ↓
AI31/AI34: life + decision timing gate is ready
  ↓
AI21–AI25: choose Basic Attack / Skill / Approach / Wait via L3 rule order
  ↓
L4: revalidate controller, actor/target currentness, Life and action conditions
  ↓
L4: canonical Effect restriction gate AND Combat/Skill/World preflight
  ↓
L4: existing canonical execution path; only actually accepted result candidates committed
  ↓
AI29: L4 derives terminal feedback from real canonical outcome; exact correlation
  ↓
AI35: explicit recovery/no-autoretry; next decision allowed only through fresh gates
```

Each boundary must be individually asserted. Do **not** skip admission/target validation, simulate Combat success by setting a boolean, or fabricate a Skill completed result from its activation result.

### 4.3. Canonical Combat path

For real Basic Attack resolution, L4-style test must use:

```text
AI-selected intent
  → createCombatActionContext
  → evaluateCombatActionAdmission
  → evaluateCombatTargetValidation
  → resolveCombatAttack with deterministic Foundation context and literal inputs
  → applyCombatAttackDamage with canonical Entity state
  → L4 commit accepted Entity candidates
  → terminal AI feedback correlated to actual completed attempt
```

Required distinctions:

- `source_dead` / `source_ineligible` blocks before target/resolution.
- Rejected target relation or Life blocks execution.
- Dodge is a **completed attack attempt** with zero damage; do not report failed merely because it dodged.
- Zero damage can be a completed attempt.
- A lethal hit updates Life only through canonical Entity/Combat path; target death influences subsequent AI through fresh observations.
- No extra `AIHitCalculator`, `AIDamageCalculator` or duplicate `resolveEntityDefeat`.

Numerical test oracles must be literal and independently checked against existing Kernel contracts. Never derive expected values by calling the same function under test. If a numerical scenario is sensitive to RNG, inject explicit deterministic sample sequence.

### 4.4. Canonical Skill path

L4-style consumer must demonstrate:

```text
Selected Skill intent / L4 actionKey→SkillInstance binding
  → actual evaluateSkillActivationAdmission
  → canonical resource/cooldown/preflight assessment
  → activateSkill
  → L4 explicitly commits accepted resource/cooldown candidates
  → dispatch via existing SkillExecutionRequest
  → actual reportSkillExecutionOutcome
  → AI terminal feedback mapping
```

**Essential cases:**

1. Admission rejection (dead actor, unowned/rank-ineligible Skill, etc.) → no execution.
2. Insufficient Resource → canonical rejection; no speculative payment.
3. Cooldown active → canonical rejection; no dispatch.
4. Skill activation accepted but execution pending → **NO terminal `completed` feedback**.
5. Dispatch actually completed → `execution/completed` feedback.
6. Dispatch failed → `execution/failed` feedback; **no automatic refund** of genuinely committed resource/cooldown changes.
7. Accepted Skill with Combat dispatch must recheck actual Combat target/admission through existing owners; no shortcut.

No invented Skill engine, Skill instance, cooldown or Resource state inside AI.

### 4.5. Canonical Effect restrictions

Use real Effect lifecycle/status/restriction snapshots and existing `evaluateEffectRestrictionGate` through the installed public API where possible.

- L3 specifies which restriction IDs block which action categories.
- L4 combines `Effect restriction allowed` **AND** canonical Combat/Skill/World admission.
- `silence` blocks only actions configured to be blocked by the matching restriction; do not globally forbid Basic Attack by assumption.
- A `stun`-like restriction cannot be interpreted as automatically applying to every action without explicit L3 mapping.
- Expired/removed restrictions do not remain active in later fresh decisions.
- Restriction assessment is not an execution token; L4 rechecks before dispatch.
- Effects stay canonical; do not copy active status arrays into ActorAIState.

### 4.6. Movement/World boundary

`approach_target`, `return_home` and `wait` remain **structural intents**. Closure may demonstrate L4 **caller-owned** test adapters that validate target/destination availability and explicitly report movement status.

**Do not claim** the repository contains a production World/Spatial/Movement engine, pathfinding, line-of-sight or movement physics. Report these as **external integration contracts demonstrated through L4-style fixtures only**.

### 4.7. No hidden orchestration

Tests may compose public APIs in a function local to the consumer test. They may use a small local fixture store/attempt ledger to demonstrate L4 authority. Such helpers must not become production `@rpg/gameplay` exports. No monolithic lifecycle orchestrator, event bus or new persistent runtime.

### 5.3. Profile B — Aggressive

```yaml
profileId: aggressive-melee
states: [idle, engaged, returning]
triggers:
  idle + target_acquired -> engaged
  engaged + target_lost -> returning
  returning + return_completed -> idle
actionOrder:
  engaged: [primary-skill, basic-attack, approach-target, wait]
  returning: [return-home]
  idle: [wait]
```

Expected:

- Eligible target acquired via AI11–AI15 under L3 target policy.
- L4 commits the target candidate before emitting `target_acquired`.
- FSM enters engaged through exact L3 rule; action selector follows ordered fallback.
- Primary Skill unavailable → Basic Attack, if available; Basic Attack unavailable → Approach if available.
- Target death/loss → L4 fresh target selection → explicit `target_lost` → Returning.
- L4 reports World `return_completed` only after its external movement authority says so; returning transitions to idle.
- No actual spatial movement implementation required.

### 5.4. Profile C — Guard

```yaml
profileId: guarding-defensive
states: [guarding, engaged, returning]
triggers:
  guarding + provoked -> engaged
  engaged + leash_exceeded -> returning
  engaged + target_lost -> returning
  returning + return_completed -> guarding
actionOrder:
  guarding: [wait]
  engaged: [basic-attack, approach-target]
```

Expected:

## 6. AI38 — Deterministic Replay & Failure Injection

### 6.1. Independent replay sessions

Build **two fully independent** caller-owned fixture sessions with:

- Fresh canonical Entity collections, AI/Resource/Life/Skill/Cooldown/Effect snapshots.
- Fresh L3 profile/policy records and separate policy arrays.
- Fresh Foundation execution contexts and explicit clock/RNG/ID providers.
- Identical literal input sequence: observedAtMs; perception facts; target ranking; behavior triggers; action availability; canonical action inputs; Skill outcomes; failure/retry decisions; time advances.
- Separate local L4 attempt ledgers/commit history; **no shared mutable references**.

At every step assert **same semantic trace** (status, reason, actor/decision/attempt IDs, target, behavior, action, canonical HP/resource/cooldown/Life/effects where applicable) and distinct snapshot object identity. No nondeterministic scheduling or wall-clock dependencies.

A separate session with intentionally different inputs should produce the explicitly expected different outcome (negative control). Do not merely compare function output to itself.

### 6.2. Trace contract — fixture only

Tests may capture an **L4-owned** trace such as:

```text
stepIndex | observedAtMs | actorId | decisionId | targetId
behaviorBefore/After | selectedActionKey | canonicalGate
attemptId | canonicalOutcome | terminalFeedback | committedCandidates
```

This is **test evidence**, not a new public event schema or production event ledger. Each row derives from the actual public operation and real caller commit choice; do not invent success receipts.

### 6.3. Mandatory failure timelines

| Scenario | Expected boundary |
| --- | --- |
| Manual takeover after target/action selection | L4 rejects stale AI dispatch/commit; no new AI attempt, no old intent execution |
| Actor death before new decision | Canonical Life gate blocks; no extra action/cadence commit |
| Actor death between selection and commit | L4 rejects stale candidate/dispatch; no fabricated successful action |
| Target death after selection | Fresh canonical target admission rejects; target selection later classifies loss/replacement |
| Duplicate attempt/feedback | Local L4 ledger rejects duplicate commit; never second resource payment, damage or cooldown start; L2 stateless validator **does not** claim durable dedupe |
| Skill activation accepted, dispatch fails | Actual Skill execution report = failed; accepted committed costs/cooldown are **not** automatically refunded |
| Skill activation accepted but pending | No completed terminal AI feedback before real completion |
| Combat dodge / zero damage | Completed attack, no invented damage or failure |
| Effect restriction changes between preflight and dispatch | L4 fresh gate determines admission; old `available=true` is not authorization |
| Perception stale while World target disappears | No stale target execution; L4 refreshes snapshots explicitly |
| Returning without `return_completed` | Remains Returning; no instant arrival or automatic position reset |
| Decision not due / regressed time | AI34 blocks candidate; no attempt, timing mutation or catch-up loop |
| Two concurrent ready evaluations of same timing cursor | Only L4 authoritative compare/commit accepts one; L2 does not claim lease/exactly-once |
| Reset/revival | Entity revival is separate; AI reset/cadence cursor is caller-controlled and must not auto-enable AI |
| No action available | Existing no-action result; no implicit Wait and no busy retry loop |

### 6.4. Deterministic timing details

Reuse **accepted** AI34 timing contracts; do not invent a new scheduler or timing state. Test:

- Exact due boundary (`now == nextEligibleAtMs`).
- Not due (`now < nextEligibleAtMs`).
- Time regression (`now < observedAtMs`).
- Large jump produces **one** decision opportunity, not catch-up burst.
- Valid zero interval does not generate an autonomous loop; L4 decides how often to invoke.
- If accepted AI34 rejects unrepresentable time, assert that exact accepted outcome.
- Explicit Foundation Clock is sampled only as required by accepted timing gate; no `Date.now`, `performance.now`, `setTimeout`, `setInterval`.

### 6.5. Negative controls — actual failures, then restore

Required injected faults and independently verified rejection:

1. Remove or corrupt one Actor AI public export → installed consumer fails.
2. Invalidate actor/decision/action/attempt correlation in terminal feedback → fail closed.
3. Flip actual Skill `failed` feedback to `completed` without real receipt → L4 provenance fixture rejects; do not misrepresent stateless AI validator as secure proof.
4. Re-run committed attempt → no second L4 commit.
5. Permit stale manual-controlled dispatch → test must fail.
6. Permit dead actor to act → test must fail.
7. Admit stale/dead target → canonical target checks must reject.
8. Ignore active Effect restriction → AND-gate test must fail.
9. Bypass Skill resource/cooldown/canonical admission → test must fail.
10. Reverse L3 action priority → selected action oracle fails.
11. Change FSM first-match rule order unexpectedly → literal FSM outcome fails.
12. Suppress lifecycle/timing gate → extra decision/attempt detected.
13. Allow a second timing-candidate commit from stale cursor → test fails.
14. Corrupt installed `.d.ts` or root export map → strict consumer fails.
15. Skip integrated test or zero assertions → verification runner fails.
16. Drift actual installed `dist` bytes from pack artifact → integrity test fails.
17. Change protected module/Core pin/registry → boundary check fails.
18. Omit one required execution/feedback scenario → coverage manifest check fails.

**Fault injections must restore files/fixture state in `finally`, leaving a clean working tree.** Negative tests must be observable failures; recording marker strings without a real failing assertion is insufficient.
