# 5. EC10 — Entity Resources

## 5.1. Objective

Cung cấp typed immutable Resource State cho mỗi Entity.

Một Entity có thể có nhiều resources:

```ts
{
  health: 100,
  mana: 50,
  stamina: 75
}
```

Đây chỉ là ví dụ.

Resource IDs là caller-defined.

Có thể sử dụng:

- `health`
- `mana`
- `energy`
- `rage`
- `shield`
- `spirit`
- Những IDs tùy biến khác

Không hardcode resource vocabulary.

Không bắt buộc mọi Entity có HP/MP.

NPC có thể không có resource nào.

## 5.2. Resource State Contract

Public contract định hướng:

```ts
interface EntityResourceState {
  readonly entityId: string;
  readonly current: Readonly<Record<string, number>>;
}
```

Tên cuối cùng có thể điều chỉnh cho nhất quán với EC07 Attribute State.

Bắt buộc:

- Resource State gắn với một Entity ID.
- `current` chứa các resource IDs và current values.
- State là immutable snapshot.
- Không chứa global state references.
- Không chứa Clock, Runtime, Messaging hoặc Engine.
- Không tự quyết định Entity sống/chết.
- Không chứa modifier resolver hoặc game rules.

## 5.3. Why Store Current Only?

**Current resource value là gameplay state thuộc L2.**

Minimum/maximum và calculation policies được cung cấp tại operation boundary bởi caller.

Ví dụ:

```text
Entity:
  health.current = 80

Current effective stats:
  maximum health = 100

Later:
  maximum health = 120
```

Resource State không tự cập nhật current hoặc maximum khi Stats thay đổi.

Consumer phải yêu cầu normalization hoặc transition rõ ràng với maximum mới.

Cách này tránh lưu một maximum đã lỗi thời và tránh tạo hệ thống đồng bộ Stats → Resources ngầm.

Nếu v0.2.2 đã thiết kế một canonical typed state carrier phù hợp, agent có thể dùng lại cấu trúc đó, nhưng không được thay đổi contracts hoặc tạo competing state authorities.

Không lưu một bản cached effective stats vào Resource State.

## 5.4. Resource Identity

Resource ID:

- Nonblank string.
- Exact string identity.
- Không trim/normalize.
- Không bắt buộc kebab-case.
- Không tự thêm prefix.
- Không tự suy diễn resource ID từ Entity kind.

Resource IDs phải duy nhất trong một Resource State.

Các tên đặc biệt như `constructor` hoặc `__proto__` không được gây prototype pollution hoặc mất dữ liệu.

Không sử dụng resource name để tự quyết định life/death.

## 5.5. Resource Inspection

Cung cấp public function tương đương:

```ts
getEntityResourceCurrent(resourceState, resourceId)
```

Expected:

- Resource tồn tại → trả current numeric value.
- Resource không tồn tại → trả `undefined`.
- Không tạo resource mới.
- Không mutate state.
- Không gọi Kernel.
- Không đọc Clock/RNG.

Malformed resource ID phải reject.

Unknown nhưng valid resource ID không phải exception khi chỉ lookup.

## 5.6. Fixed Resource Key Set

Resource IDs được xác định tại initialization.

Ở v0.2.3:

- Không tự thêm resource khi gọi transition.
- Không tự xóa resource.
- Không tự đổi resource ID.
- Không tự tạo resource mặc định.

Một actor mới có thể được khởi tạo với resource schema khác.

Không cần public add/remove resource schema APIs nếu không có requirement riêng.

# 6. EC11 — Resource Initialization & Normalization

## 6.1. Objective

Khởi tạo Entity Resource State bằng các resource definitions do caller cung cấp và sử dụng canonical Kernel normalization.

## 6.2. Resource Initialization Contract

Ví dụ:

```ts
const resources = createEntityResourceState(entity, {
  health: {
    minimum: 0,
    maximum: 100,
    current: 80
  },
  mana: {
    minimum: 0,
    maximum: 50
  }
});
```

Expected:

```ts
{
  entityId: "actor-1",
  current: {
    health: 80,
    mana: 50
  }
}
```

Đối với `mana`, caller không cung cấp current nên Kernel normalization khởi tạo bằng maximum.

Không được tự implement logic:

```ts
current ?? maximum
```

ở L2 như một calculator riêng.

Phải gọi `normalizeResource()`.

## 6.3. Initialization Behavior

Bắt buộc:

1. Validate Entity identity theo accepted EC01–EC03 contract.
2. Validate resource definition map.
3. Validate resource IDs.
4. Validate numeric bounds.
5. Validate optional current khi được cung cấp.
6. Gọi `normalizeResource()` cho từng resource.
7. Tạo immutable Resource State.
8. Không mutate caller inputs.
9. Không tạo resource mặc định.
10. Không gọi lifecycle/events.

Empty resource map hợp lệ.

## 6.4. Numeric Preconditions

L2 chịu trách nhiệm validate những scalar preconditions mà Kernel yêu cầu caller cung cấp hợp lệ.

Bắt buộc:

- Minimum là finite number.
- Maximum là finite number.
- `minimum <= maximum`.
- Current, nếu có, là finite number.
- Không ép numbers thành integers.
- Không tự đặt minimum bằng 0.
- Không tự chọn maximum.
- Không chấp nhận `NaN`, `Infinity`, `-Infinity`.
- Không sử dụng truthy/falsy fallback khiến current `0` bị thay bằng maximum.

Current ngoài bounds được cho phép ở normalization input nếu vẫn finite, vì chính Kernel normalization sẽ xử lý việc clamp.

Không tính lại clamp sau Kernel.

## 6.5. Explicit Normalization

Cung cấp function tương đương:

```ts
normalizeEntityResource(
  resourceState,
  resourceId,
  {
    minimum: 0,
    maximum: 120
  }
);
```

Operation phải:

- Đọc current từ Resource State.
- Đọc explicit bounds.
- Gọi `normalizeResource()` của Kernel.
- Trả immutable next state.
- Trả normalization diagnostics.

Kết quả public tương đương:

```ts
{
  state: nextResourceState,
  calculation: {
    resource: "health",
    before: 80,
    after: 80,
    initialized: false
  }
}
```

Tên `calculation` hoặc `normalization` có thể điều chỉnh.

Không thêm một `initialized` flag tự tính nếu Kernel đã cung cấp.

## 6.6. Maximum Changes

Ví dụ:

```text
Before:
  health.current = 100

Caller updates effective maximum:
  maximum = 80
```

Caller explicit yêu cầu normalization.

Expected:

```text
Before = 100
After  = 80
```

Old Resource State phải giữ health = 100.

New Resource State giữ health = 80.

Không tự thực hiện normalization chỉ vì một Stat Snapshot mới xuất hiện.

Không tạo listener hoặc scheduler theo dõi Stats.

## 6.7. Initialization Failure

Nếu bất kỳ resource nào invalid:

- Không trả partial Resource State.
- Không mutate Entity.
- Không mutate caller input.
- Không tạo side effects.
- Reject rõ ràng.

Không báo initialization success khi một Kernel call thất bại.

Không tạo transaction engine để đạt atomicity; chỉ công bố snapshot sau khi toàn bộ input đã hợp lệ và quá trình tính hoàn tất.

# 7. EC12 — Resource Increase / Decrease

## 7.1. Objective

Thay đổi current resource qua canonical Kernel transition.

Required public function tương đương:

```ts
transitionEntityResource(
  resourceState,
  resourceId,
  {
    operation: "decrease",
    amount: 25,
    maximum: 100,
    rule: {
      minimum: 0,
      currentAboveMaximum: "reject",
      allowIncreaseFromMinimum: true
    }
  }
);
```

Có thể điều chỉnh API shape nhưng các input phải explicit.

## 7.2. Supported Operations

Chỉ hỗ trợ:

- `increase`
- `decrease`

Đây là numerical transition primitives.

L2 không tự gọi chúng là:

- Damage.
- Heal.
- Mana cost.
- Shield absorption.
- Life steal.
- Revive.

Những gameplay semantics đó được xác định bởi caller hoặc các capability khác.

## 7.3. Transition Result

Kernel trả:

```ts
{
  resource,
  before,
  after,
  applied,
  reachedMinimum
}
```

L2 trả result tương đương:

```ts
{
  state: nextResourceState,
  transition: kernelTransitionResult
}
```

Bắt buộc bảo toàn chính xác:

- `resource`
- `before`
- `after`
- `applied`
- `reachedMinimum`

Không tự recompute `applied`.

Không tự đổi `reachedMinimum` thành `dead`.

Không bỏ diagnostic chỉ để trả `after`.

## 7.4. Resource Transition Preconditions

Bắt buộc validate:

- Existing resource ID.
- Valid operation.
- Finite nonnegative amount.
- Finite maximum.
- Finite minimum.
- Ordered bounds.
- Finite current.
- Current không dưới minimum ở transition boundary.
- Complete and valid Kernel rule.
- Valid `currentAboveMaximum` policy.

Các invalid inputs phải fail rõ ràng.

Không mutate state khi validation hoặc Kernel calculation fail.

Không silently clamp invalid input trong L2.

## 7.5. Above-Maximum Policy

Kernel cho phép caller chọn:

```ts
currentAboveMaximum: "allow" | "reject"
```

L2 phải bảo toàn cả hai semantics.

Đặc biệt, trong một số trường hợp:

```text
current = 120
maximum = 100
minimum = 0
operation = increase
amount = 10
currentAboveMaximum = allow
```

Kernel có thể trả:

```text
after = 100
applied = -20
```

**Đây là accepted numerical behavior của Kernel**, không phải lỗi để L2 tự sửa.

Tương tự, khi giảm resource đang above maximum, `applied` có thể khác độ lớn thay đổi ròng giữa before và after.

L2 phải trả nguyên giá trị authoritative từ Kernel.

Không suy diễn:

```ts
applied = Math.abs(after - before);
```

Không chuyển negative applied thành 0 nếu Kernel đã trả kết quả đó cho valid input.

## 7.6. Minimum Recovery Policy

Kernel có:

```ts
allowIncreaseFromMinimum: boolean
```

L2 phải chuyển chính xác policy này vào calculation.

Ví dụ:

```text
current = 0
minimum = 0
amount = 20
operation = increase
allowIncreaseFromMinimum = false
```

Expected: resource giữ nguyên minimum theo Kernel.

Nếu policy cho phép increase, Kernel quyết định giá trị mới.

**Không diễn giải điều này thành revive actor.**

Life State thuộc v0.2.4.

## 7.7. Zero and Boundary Cases

Phải xử lý đúng:

- Amount = 0.
- Current = minimum.
- Current = maximum.
- Current above maximum với allowed policy.
- Resource có minimum khác 0.
- Fractional values.
- Current equals maximum equals minimum.

Không dùng các integer-only assumptions.

Không tự làm tròn transition result.

## 7.8. No Automatic State Coupling

Khi health giảm:

- Không phát `damage-applied`.
- Không phát `entity-dead`.
- Không cập nhật combat state.
- Không tự gọi Effect System.
- Không tự cập nhật Skill cooldown.
- Không tự thay đổi Actor kind.

Resource transition chỉ đổi resource current value và trả numerical result.

# 8. EC13 — Resource Regeneration

## 8.1. Objective

Cho phép tăng current resource theo rate và elapsed time do caller cung cấp.

Không cần game loop hoặc scheduler.

Required function tương đương:

```ts
regenerateEntityResource(
  resourceState,
  "health",
  {
    minimum: 0,
    maximum: 100,
    ratePerSecond: 2,
    elapsedSeconds: 2.5,
    eligible: true,
    precision: {
      decimalPlaces: 12
    }
  }
);
```

## 8.2. Kernel Delegation

Bắt buộc gọi:

`calculateResourceRegeneration()`

Không tự implement:

```ts
current + ratePerSecond * elapsedSeconds
```

Không tự round/clamp bằng một helper ở Entity module.

L2 chỉ chuẩn bị input, gọi Kernel và tạo next state.

## 8.3. Regeneration Inputs

Caller cung cấp:

- Resource ID.
- Current đã lưu.
- Minimum.
- Maximum.
- Rate per second.
- Elapsed seconds.
- Eligibility.
- Decimal precision.

Requirements:

- Không tự lấy elapsed time từ system clock.
- Không tự lấy elapsed time từ Runtime Context.
- Không tự gọi `readExecutionTime()` ngầm.
- Không tự tạo default regeneration rate.
- Không tự chọn precision mặc định.
- Không tự quyết định `eligible` dựa trên alive/dead.
- Không tự suy ra HP/MP regeneration rules.

Caller có thể sử dụng GF14 Clock để tính elapsed duration bên ngoài rồi truyền vào operation.

## 8.4. Regeneration Validation

Khi `eligible = true`, validate các scalar preconditions:

- Current đã được normalized trong bounds hiện hành.
- Minimum/maximum finite và có thứ tự hợp lệ.
- Rate per second là finite nonnegative number.
- Elapsed seconds là finite nonnegative number.
- Precision decimalPlaces là integer từ 0 đến 100.
- Không chấp nhận invalid resource IDs.

Không sửa số học Kernel.

Khi `eligible = false`, giữ nguyên no-op semantics của Kernel. Không tự chạy calculation hoặc consume clock để tạo elapsed time giả.

Mọi getter/callback side-effect trên caller-owned inputs phải được xem xét tại validation boundary; không đưa thêm hidden reads/retries vượt quá accepted contract.

## 8.5. Expected Calculation

Ví dụ:

```text
current = 30
maximum = 100
ratePerSecond = 2
elapsedSeconds = 2.5
eligible = true
```

Expected:

```text
after = 35
applied = 5
```

Chỉ dùng kết quả này làm independent test oracle.

Production calculation bắt buộc delegate Kernel.

## 8.6. Ineligible Regeneration

Nếu:

```ts
eligible: false
```

Expected:

- Current không đổi.
- `applied = 0`.
- Không tự ép Eligible thành true.
- Không retry.
- Không phát event.
- Không đọc clock.
- Không làm Entity sống lại.

Nếu current đã ngoài bounds vì maximum thay đổi, caller phải quyết định normalization hoặc chọn operation phù hợp; không tự tạo hidden normalization trước một regeneration.

## 8.7. No Scheduler

Không triển khai:

- Automatic regeneration tick.
- Fixed time step.
- Background timer.
- World update loop.
- Character update loop.
- Regen accumulator.
- Offline recovery.
- Cooldown timer.
- Regen subscriptions.

EC13 chỉ cung cấp một synchronous explicit transition.

# 9. Resource State Immutability & Isolation

Các operations EC10–EC13 phải trả immutable results.

Bắt buộc:

1. Old Resource State không đổi.
2. New Resource State giữ đúng Entity ID.
3. Chỉ requested resource được cập nhật.
4. Các resources khác giữ nguyên.
5. Caller input không bị mutate/freeze.
6. Không có writable backing maps bị expose.
7. Không có module-global current resource store.
8. Không có implicit collection synchronization.
9. Không có cross-entity state leakage.
10. Không sử dụng hidden cache hoặc snapshot mutation.

Ví dụ:

```text
State A:
  actor-1
  health = 80
  mana = 50

Transition health -20

State B:
  actor-1
  health = 60
  mana = 50

State A remains:
  health = 80
  mana = 50
```

Một Entity khác có thể có cùng resource keys nhưng current values độc lập.

Hai independent operation sequences với cùng inputs và policies tạo cùng semantic results.

# 10. Integration With Attributes & Stats

## 10.1. Explicit Maximum Source

Khi EC08 tính được effective stats, caller có thể chọn một stat làm resource maximum.

Ví dụ:

```text
Effective Stats:
  maximumHealth = 120

Resource State:
  health.current = 80
```

Caller explicit truyền:

```ts
maximum: 120
```

vào normalization/transition/regeneration.

**Entity Resource module không tự đoán `maximumHealth` tương ứng với `health`.**

Không hardcode:

- `maxHp`
- `maxMana`
- `maximumHealth`
- `maxEnergy`
- `vitality`
- `intelligence`

Mapping thuộc L3/caller.

## 10.2. Maximum Changed

Expected flow:

```text
Attribute update
       │
       ▼
Explicit stat recalculation (EC09)
       │
       ▼
Consumer chooses resource maximum
       │
       ▼
Explicit resource normalization (EC11)
       │
       ▼
New Resource State
```

Không tự đồng bộ maximum với current.

Không tự refill HP khi maximum tăng.

Không tự preserve HP percentage khi maximum thay đổi.

Không auto-restore resources từ stat changes.

Các policy đó có thể được thiết kế sau nếu game thực sự cần.

## 10.3. Collection Membership

Resource State gắn với Entity ID.

Không sửa `EntityCollection` để tự quản lý resources.

Khi Entity bị remove khỏi Collection, Resource State không tự bị xóa hoặc invalidate trên toàn hệ thống.

Caller/integration layer chịu trách nhiệm lifecycle của những state snapshots liên quan.

Không tạo global Entity Resource Manager.

# 11. Life State Boundary

**EC10–EC13 chỉ quản lý numerical resources.**

Chưa triển khai:

- Alive.
- Dead.
- Defeated.
- Revived.
- Respawned.

Kernel `reachedMinimum` chỉ là numerical transition information.

Ví dụ:

```text
health: 10 → 0
reachedMinimum: true
```

Đây chưa phải kết luận actor chết.

v0.2.4 sẽ quyết định:

- Resource nào được xem là life resource.
- Khi nào Entity chết.
- Dead entity có thể nhận recovery hay không.
- Revival policy.
- Life transition result/events.

Không cài sẵn life rules vào v0.2.3 để tránh phải sửa lại khi triển khai v0.2.4.

# 14. Minimum Meaningful Scenarios

## Scenario A — Resource Initialization

Input:

```text
Entity: player-1

health:
  minimum = 0
  maximum = 100
  current = 80

mana:
  minimum = 0
  maximum = 50
  current omitted
```

Expected:

```text
health = 80
mana = 50
```

Không tự tạo energy hoặc resource khác.

## Scenario B — Decrease / Increase

Initial:

```text
health = 80
minimum = 0
maximum = 100
```

Decrease 25.

Expected:

```text
before = 80
after = 55
applied = 25
reachedMinimum = false
```

Sau đó increase 15 với policy cho phép.

Expected:

```text
before = 55
after = 70
applied = 15
```

Old snapshots không đổi.

## Scenario C — Above Maximum

Initial state có current 120, maximum mới 100.

Chứng minh hai accepted Kernel behaviors:

- `increase 10`, above-max allow: after 100, applied -20.
- `decrease 10`, above-max allow: after 100, applied 10.

Nếu policy reject above-max, operation phải fail theo canonical contract.

Không tự tính lại `applied` từ before/after.

## Scenario D — Minimum Recovery

Current = minimum = 0.

Increase 20:

- Policy cấm increase from minimum → vẫn 0.
- Policy cho phép → Kernel quyết định recovery result.

Không tự chuyển Life State.

## Scenario E — Explicit Normalization

Current health = 100.

Caller đổi maximum thành 80.

Expected:

```text
Before normalization: 100
After normalization:   80
```

Không tự tạo transition khi Stats được tính lại.

## Scenario F — Regeneration

Initial:

```text
health = 30
ratePerSecond = 2
elapsedSeconds = 2.5
maximum = 100
eligible = true
```

Expected:

```text
after = 35
applied = 5
```

Với `eligible = false`, current phải giữ nguyên.

## Scenario G — Entity Isolation

Hai actor:

```text
player-1: health 80, mana 50
monster-1: health 30
```

Transition player health -20.

Expected:

```text
player-1 health = 60
player-1 mana = 50
monster-1 health = 30
```

Không chia sẻ mutable state.

## Scenario H — Existing Stats Integration

1. Tạo Entity.
2. Tạo Base Attributes.
3. Tính Effective Stats bằng EC08.
4. Caller lấy một stat làm maximum.
5. Gọi Resource Normalization/Transition với maximum explicit.

Expected:

- Value lấy đúng từ calculated Stat Snapshot.
- Resource operation dùng đúng maximum được truyền.
- Không tự mapping attribute names hoặc resource policies.
- Existing Stat Snapshot không bị mutate.
