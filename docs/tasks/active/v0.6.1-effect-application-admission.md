# 1. Objective

Triển khai **Effect Application & Admission**, cho phép các hệ thống gameplay yêu cầu áp dụng Effect lên một Entity thông qua một reusable, source-agnostic API.

Effect Application phải:

1. Nhận Effect Instance đã được định danh bởi EF01–EF05.
2. Validate Definition/Instance/Target associations.
3. Validate Entity/System source identity.
4. Kiểm tra Entity source existence khi applicable.
5. Kiểm tra target existence, life state và caller-supplied eligibility.
6. Reject duplicate Effect Instance IDs trong target state.
7. Tạo immutable Effect State candidate khi accepted.
8. Trả deterministic application outcome.
9. Không tự commit hoặc thực hiện gameplay side effects.

| ID | Feature | Responsibility |
|---|---|---|
| EF06 | Effect Apply Request | Generic request contract, reusable across Skill/Item/Equipment/Environment |
| EF07 | Source & Target Validation | Canonical Entity lookup, identity consistency, explicit life state |
| EF08 | Effect Apply Admission | Source/target eligibility, caller policy, deterministic rejection |
| EF09 | Effect Application | Accepted immutable Effect State candidate, no partial mutation |
| EF10 | Application Outcomes & Verification | Rejections, duplicate identity, replay, installed package and regression |

## Expected Consumer Flow

```text
Effect Definition
       ↓
Effect Instance
       ↓
Effect Apply Request
       ↓
Source / Target Validation
       ↓
Application Admission
       ↓
Accepted / Rejected
       ↓
Immutable Effect State Candidate
       ↓
L4 — Authoritative Commit
```

**Accepted application chỉ xác nhận Effect Instance đã vượt qua các gates và có thể được ghi vào candidate Effect State.**

Chưa đồng nghĩa với:

- Timed/persistent lifecycle đã được kích hoạt.
- Duration đã bắt đầu.
- Active modifiers đang tác động.
- Stack đã được tăng.
- DoT/HoT đã chạy.
- Gameplay effect đã thực thi.

Những khả năng này thuộc các milestones sau.

# 5. EF06 — Effect Apply Request

## 5.1. Objective

Tạo generic Effect Apply Request cho mọi source.

Không giới hạn Effect Application cho Skill.

## 5.2. Proposed Contract

```ts
export interface EffectApplyRequest {
  readonly instance: EffectInstanceState;
}
```

Request tham chiếu canonical Effect Instance.

Không tạo thêm duplicate identity fields như:

```text
skillId
itemId
equipmentId

effectId
effectInstanceId
sourceId
targetEntityId
```

vì tất cả Effect identities đã tồn tại trong `EffectInstanceState`.

## 5.3. Example — Skill Source

```ts
{
  instance: {
    effectInstanceId: "effect-instance-001",
    effectId: "poison",
    source: {
      kind: "entity",
      sourceId: "player-1",
      sourceKey: "player-1/skill-instance-001"
    },
    targetEntityId: "monster-1"
  }
}
```

Không bắt buộc truyền `SkillInstanceState` hoặc Skill Admission Result vào Effect.

Skill ownership đã được đánh giá bởi canonical Skill owner và L4 trước đó.

## 5.4. Example — Equipment Source

```ts
{
  instance: {
    effectInstanceId: "effect-instance-002",
    effectId: "frost-shield",
    source: {
      kind: "entity",
      sourceId: "player-1",
      sourceKey: "equipment/armor-instance-001"
    },
    targetEntityId: "player-1"
  }
}
```

Không triển khai Equipment Inventory.

`sourceKey` được L4 cung cấp.

## 5.5. Example — Environment Source

```ts
{
  instance: {
    effectInstanceId: "effect-instance-003",
    effectId: "poison",
    source: {
      kind: "system",
      sourceId: "swamp-zone",
      sourceKey: "swamp-zone/poison-area-001"
    },
    targetEntityId: "player-1"
  }
}
```

Không tạo fake Entity cho `swamp-zone`.

## 5.6. No Runtime Invocation

Creating an Effect Apply Request không:

- Call Skill.
- Read time.
- Generate instance ID.
- Create Effect Definition.
- Modify Effect State.
- Resolve target relations.
- Start Effect lifecycle.

Không tạo riêng một Effect Request Factory nếu plain validated request được xử lý tại admission boundary.

# 6. EF07 — Source & Target Validation

## 6.1. Objective

Reuse canonical Entity identity/lookup và validate consistency của application inputs.

Không tạo Combat Target Validator thứ hai.

## 6.2. Required Entity APIs

Reuse:

```ts
createEntity()
getEntity()
```

Existing types:

```ts
EntityCollection
EntityLifeState
EntityLifeStatus
```

Effect không được scan hoặc sửa private Entity collections.

## 6.3. Entity Source

Nếu:

```text
source.kind = entity
```

Effect phải kiểm tra source tồn tại trong supplied `EntityCollection` qua `getEntity()`.

Nếu source không tồn tại:

```text
rejected / source_not_found
```

Không tự thêm source Entity.

Không tự tạo Entity Collection mới.

Không bắt buộc source phải alive ở L2 Effect.

**D17:** Source chết không đồng nghĩa effect đã apply bị hủy. Với new application, caller-supplied `sourceEligible` quyết định các điều kiện như source death hoặc gameplay eligibility.

Không đọc/copy Skill Life Admission.

## 6.4. System Source

Nếu:

```text
source.kind = system
```

Không gọi `getEntity()` cho system source ID.

Không require System/Environment phải là Entity.

Structural Source Reference vẫn phải hợp lệ.

Caller/L4 bảo đảm source identity đó thực sự được phép phát sinh application.

Nếu policy cho biết source không eligible:

```text
rejected / source_ineligible
```

## 6.5. Target Entity

Target phải là canonical Entity reference.

Lookup:

```ts
getEntity(entities, instance.targetEntityId)
```

Nếu không tồn tại:

```text
rejected / target_not_found
```

Không tự create target.

Không thay target ID khi mismatch.

## 6.6. Target Life State

Input:

```ts
EntityLifeState
```

Required:

```text
targetLife.entityId == instance.targetEntityId
```

Nếu mismatch:

```text
TypeError
```

Target Life State phải sử dụng canonical Entity semantics:

```text
alive
dead
```

Không tự định nghĩa một Effect-specific Life enum.

### Target Life Policy

L3/caller cung cấp allowed life statuses.

Ví dụ:

```text
Poison:
  allowed = [alive]
```

hoặc một future dead-target effect:

```text
allowed = [dead]
```

Không hardcode mọi Effect phải nhắm target alive.

Nếu target hiện tại không nằm trong allowed statuses:

```text
rejected / target_life_not_allowed
```

Không tự revive target.

## 6.7. Target Relations

Effect không tự quyết định:

```text
self
ally
enemy
neutral
```

Existing Combat admission/target validation tiếp tục là canonical owner cho Combat actions.

L4 có thể dùng Combat preflight hoặc game-specific relation policy trước khi cấp:

```text
targetEligible = true / false
```

Effect chỉ tiêu thụ explicit caller assessment.

Không thêm `effect → combat` dependency.

Không copy `evaluateCombatTargetValidation()`.

## 6.8. Structural Mismatch

Definition:

```text
effectId = poison
```

Instance:

```text
effectId = burning
```

Expected:

```text
TypeError
```

Đây là malformed cross-contract association, không phải ordinary gameplay rejection.

Tương tự:

```text
state.entityId != instance.targetEntityId
```

Expected:

```text
TypeError
```

Không tự rebind instance sang Entity khác.

# 7. EF08 — Effect Apply Admission

## 7.1. Objective

Tạo pure Effect Application Admission assessment với explicit policies.

Không tạo authorization/permission store.

## 7.2. Proposed Policy

```ts
export interface EffectApplyPolicy {
  readonly sourceEligible: boolean;
  readonly targetEligible: boolean;
  readonly allowedTargetLifeStatuses:
    readonly EntityLifeStatus[];
}
```

All fields required.

Không có implicit defaults.

### sourceEligible

Được L3/L4 resolve trước.

Có thể phản ánh:

```text
Source permission
Source gameplay state
Equipment availability
System/environment availability
Application-specific restrictions
```

Không tạo một generic requirements engine để tính `sourceEligible`.

### targetEligible

Được L3/L4 resolve trước.

Có thể phản ánh:

```text
Self/ally/enemy relation
Target class/type
Effect eligibility
Gameplay-specific target restrictions
```

Không tự triển khai immunities hoặc active status queries tại v0.6.1.

EF26–EF30 sẽ cung cấp restriction contributions sau.

### allowedTargetLifeStatuses

Required nonempty unique array.

Allowed entries:

```text
alive
dead
```

Không silently deduplicate hoặc default `[alive]`.

## 7.3. Proposed Admission Status

```ts
export type EffectApplyAdmissionStatus =
  | "admitted"
  | "rejected";
```

## 7.4. Proposed Rejection Reasons

```ts
export type EffectApplyAdmissionReason =
  | "none"
  | "source_not_found"
  | "target_not_found"
  | "target_life_not_allowed"
  | "source_ineligible"
  | "target_ineligible"
  | "instance_already_present";
```

Không dùng generic:

```text
invalid
not_allowed
failed
```

nếu có thể trả exact reason.

## 7.5. Proposed Result

```ts
export interface EffectApplyAdmissionResult {
  readonly request: EffectApplyRequest;

  readonly status: EffectApplyAdmissionStatus;
  readonly reason: EffectApplyAdmissionReason;
}
```

Invariant:

```text
status = admitted
  ↔ reason = none

status = rejected
  ↔ reason != none
```

Returned request phải là detached immutable snapshot.

Không giữ mutable caller input.

## 7.6. Public API

```ts
export function evaluateEffectApplyAdmission(
  definition: EffectDefinition,
  request: EffectApplyRequest,
  state: EffectState,
  entities: EntityCollection,
  targetLife: EntityLifeState,
  policy: EffectApplyPolicy
): EffectApplyAdmissionResult;
```

Assessment phải:

1. Validate complete input contracts.
2. Validate Definition/Instance identity.
3. Validate Effect State association.
4. Validate Target Life identity.
5. Validate policy.
6. Check Entity/System source.
7. Check target existence.
8. Check target life policy.
9. Check source eligibility.
10. Check target eligibility.
11. Check duplicate instance identity.
12. Return admitted/rejected assessment.

Không mutate state.

Không tạo Effect Instance mới.

Không perform application.

Không gọi Clock hoặc RNG.

## 7.7. Rejection Priority

**Full structural validation luôn xảy ra trước ordinary rejection selection.**

After validation:

```text
1. source_not_found
2. target_not_found
3. target_life_not_allowed
4. source_ineligible
5. target_ineligible
6. instance_already_present
7. none
```

Priority không phụ thuộc field enumeration order.

Nếu policy malformed và source không tồn tại:

```text
TypeError
```

Không trả `source_not_found` trước khi hoàn tất structural validation.

## 7.8. Caller Assertion Boundary

`sourceEligible` và `targetEligible` là caller-supplied assertions.

Không phải security credentials.

Admission Result không phải durable authorization token.

L4 phải resolve authoritative source/target state và policy tại appropriate commit boundary.

Không claim chống concurrent changes.

# 8. EF09 — Effect Application

## 8.1. Objective

Tạo accepted immutable Effect State candidate bằng cách thêm một Effect Instance reference vào target state.

Không ghi vào global store.

## 8.2. Public API

```ts
export function applyEffect(
  definition: EffectDefinition,
  request: EffectApplyRequest,
  state: EffectState,
  entities: EntityCollection,
  targetLife: EntityLifeState,
  policy: EffectApplyPolicy
): EffectApplyResult;
```

## 8.3. Proposed Result

```ts
export type EffectApplyResult =
  | {
      readonly status: "applied";
      readonly reason: "none";
      readonly admission: EffectApplyAdmissionResult;
      readonly state: EffectState;
    }
  | {
      readonly status: "rejected";
      readonly reason: Exclude<
        EffectApplyAdmissionReason,
        "none"
      >;
      readonly admission: EffectApplyAdmissionResult;
      readonly state: null;
    };
```

No partial state.

No nullable ambiguity in accepted branch.

## 8.4. Implementation Sequence

```text
Validate complete inputs
          ↓
Evaluate Effect Apply Admission
          ↓
    admitted?
       │
    ┌──┴───┐
    │      │
   NO     YES
    │      │
    ▼      ▼
 Rejected  Construct next Effect State
 state=null        │
    │              ▼
    │       Validate/freeze candidate
    │              │
    ▼              ▼
 Return         Applied Result
```

Reuse `evaluateEffectApplyAdmission()`.

Không triển khai admission logic thứ hai trong `applyEffect()`.

Không cho phép caller tự đưa forged `EffectApplyAdmissionResult` vào để bypass eligibility.

## 8.5. Successful Application

Initial:

```text
Effect State:
  entityId = monster-1
  instances = []
```

Apply:

```text
effectId = poison
effectInstanceId = effect-instance-001
target = monster-1

source:
  entity / player-1
  sourceKey = player-1/skill-instance-001
```

Policy:

```text
sourceEligible = true
targetEligible = true
allowedTargetLifeStatuses = [alive]
```

Expected:

```text
status = applied
reason = none

candidate Effect State:
  entityId = monster-1
  instances:
    - effect-instance-001
```

Original state:

```text
instances = []
```

vẫn unchanged.

## 8.6. Accepted State Semantics

v0.6.1 thêm structural instance vào candidate.

Không thêm:

```text
appliedAt
expiresAt
remainingDurationMs
currentStacks
nextTickAt
```

Không tự khởi động lifecycle.

Future EF11–EF15 sẽ thiết kế duration/lifecycle representation trong canonical Effect module, không được tạo active store thứ hai hoặc sửa accepted EF01–EF10 semantics tùy tiện.

**Không mô tả `EffectState.instances` là authoritative active-timed effects ở v0.6.1.**

## 8.7. Rejected Application

Nếu admission rejected:

```text
status = rejected
reason = specific reason

state = null
```

Không:

- Append instance.
- Remove previous instance.
- Modify target Entity.
- Start timer.
- Create stack.
- Emit events.
- Apply modifiers.

## 8.8. Application Order

Với accepted applications:

```text
instance-a
instance-b
instance-c
```

Expected state order:

```text
instance-a
instance-b
instance-c
```

Preserve existing order, append new instance.

Không sort theo Effect ID, Source Key hoặc Instance ID.

## 8.9. No Automatic Commit

`applyEffect()` chỉ trả candidate.

L4 có thể:

```ts
const outcome = applyEffect(
  definition,
  request,
  effectState,
  entities,
  targetLife,
  policy
);

if (outcome.status === "applied") {
  // L4 rechecks authoritative state/freshness
  // and decides whether to commit outcome.state.
}
```

Không triển khai production L4 code.

Không claim atomic transaction giữa Effect và Resource/Combat.

# 9. EF10 — Duplicate Application & Outcomes

## 9.1. Objective

Cung cấp deterministic result khi cùng Effect Instance ID được apply nhiều lần.

Không tạo persistent idempotency store.

## 9.2. Duplicate Instance Identity

Current state:

```text
effect-instance-001
```

Apply again:

```text
effect-instance-001
```

Expected:

```text
rejected / instance_already_present
state = null
```

Áp dụng cho cả:

- Exact same request retry.
- Same instance ID with different effect/source payload.

Không silently overwrite.

Không tự đổi ID.

Không tạo second instance.

## 9.3. Duplicate Scope

Uniqueness được kiểm tra trong supplied target `EffectState`.

Không claim global uniqueness across all Entity states.

L4 sở hữu application-wide identity allocation và authoritative retry semantics.

## 9.4. No Automatic Idempotent Success

Không trả `applied` chỉ vì retry giống application trước đó.

Không fabricate historical receipt.

Không giữ global processed-request map.

Nếu L4 cần exactly-once hoặc idempotent network processing, triển khai ở đúng runtime owner với task riêng.

## 9.5. Same Effect, Different Instance IDs

Current:

```text
effect-instance-001 → poison
```

New request:

```text
effect-instance-002 → poison
```

Expected structurally:

```text
applied
```

nếu source/target/policies đều valid.

Không áp stack/maxStacks limits tại v0.6.1.

EF16–EF20 sẽ quyết định grouping/stack admission.

## 9.6. Rejection Is Not Lifecycle

`instance_already_present` không tương đương:

```text
max_stacks_reached
effect_already_active
effect_immune
effect_duration_active
```

Không tạo các reasons này trước milestone tương ứng.
