# 5. CB21 — Damage Application Contract

## 5.1. Objective

Định nghĩa operation áp dụng kết quả damage đã resolve lên một target Resource/Life State.

## 5.2. Public Function

Đề xuất:

```ts
applyCombatAttackDamage(
  attack: CombatAttackResolutionResult,
  resources: EntityResourceState,
  life: EntityLifeState,
  policy: CombatDamageApplicationPolicy
): CombatDamageApplicationResult
```

Chỉ một canonical public entrypoint.

Không tạo:

```text
applyRawDamage()
applyMonsterDamage()
applyPlayerDamage()
dealCombatDamage()
damageHealthDirectly()
```

nếu chỉ duplicate cùng operation.

## 5.3. Required Inputs

Operation nhận:

**Attack**

Actual v0.4.3 result.

**Resources**

Current target `EntityResourceState`.

**Life**

Current target `EntityLifeState`.

**Policy**

Caller-supplied life-resource mapping và current-above-maximum behavior.

Không yêu cầu:

- Entity Attribute State.
- Skill Rank.
- Skill Definition.
- Target Stats.
- Combat Session.
- Encounter State.
- RNG.
- Clock.

Attack đã được tính ở v0.4.3.

## 5.4. Damage Application Policy

Conceptual:

```ts
interface CombatDamageApplicationPolicy
  extends EntityLifeResourcePolicy {

  readonly currentAboveMaximum:
    "allow" | "reject";
}
```

Example:

```ts
{
  resourceId: "health",
  minimum: 0,
  maximum: 100,
  currentAboveMaximum: "reject"
}
```

Đây là ví dụ, không phải default.

## 5.5. Resource ID Is Caller-Owned

Không hardcode:

```text
hp
health
life
vitality
```

Caller chỉ định resource nào đại diện cho life resource.

Ví dụ:

```text
resourceId = "health"
```

hoặc:

```text
resourceId = "vitality"
```

Combat dùng cùng `resourceId`, `minimum`, `maximum` cho Resource Transition và Death Evaluation.

Không có hai numerical bounds policies độc lập cho cùng operation.

## 5.6. No Hidden Policy Defaults

Không tự chọn:

- Health Resource ID.
- Minimum.
- Maximum.
- Above-maximum behavior.
- Damage rounding.
- Minimum damage.
- Damage multiplier.
- Damage reduction.
- Invulnerability.

Các phép tính damage đã hoàn tất tại v0.4.3.

Nếu game có invulnerability, restriction phải được giải quyết trước hoặc thông qua explicit gameplay policy phù hợp.

Không tự thêm damage modifiers tại application stage.

# 6. CB21 — Input & Identity Validation

## 6.1. Attack Preconditions

Attack result phải:

- Có valid accepted v0.4.3 shape.
- Có canonical Combat Action Context.
- Có supported outcome discriminant.
- Có finite nonnegative finalDamage.
- Có consistent outcome and diagnostics.
- Có exact target identity.

Không nhận raw number thay cho actual attack result.

Không tự tạo fake attack result để gọi Entity.

## 6.2. Identity Matching

Bắt buộc:

```text
attack.context.target.entityId
==
resources.entityId
==
life.entityId
```

Nếu mismatch:

`TypeError`

Không update resource của actor khác.

Không silently rewrite Entity IDs.

## 6.3. Attack Result Validation

Đối với dodged attack:

- Outcome phải tương ứng actual CB20 dodge result.
- Final damage phải bằng 0.
- Không có fabricated landed-stage diagnostics.

Đối với landed attack:

- Final damage phải finite và nonnegative.
- Damage phải nhất quán với actual v0.4.3 result structure.
- Nếu result chứa mitigation diagnostics, `finalDamage` phải khớp canonical value được v0.4.3 công bố.

Không tính lại B0/B1/Mitigation.

Không gọi RPG Core numerical damage calculators lần thứ hai.

## 6.4. Structural Validation

Reject:

- Missing fields.
- Unknown fields.
- Malformed attack result.
- Getter-based fields.
- Invalid nested data.
- Inherited required properties.
- Invalid target identity.
- Invalid Resource State.
- Invalid Life State.
- Invalid policy.
- Negative/nonfinite damage.
- Invalid bounds.
- Unknown resource ID.

Malformed input phải throw `TypeError`.

Không trả một successful application result cho malformed attack.

## 6.5. Stage Result Trust Boundary

Actual attack result được xem là caller-supplied calculation receipt.

Structural validation không chứng minh receipt được tạo bởi một trusted runtime executor.

Không tạo:

- Cryptographic attack token.
- Persistent attack ledger.
- Global receipt registry.
- Authenticated Combat Session.

Document rõ:

**Caller phải cung cấp actual trusted current snapshots và results.**

Không claim protection chống intentional forged structurally valid receipts.

## 6.6. No New Actor/Target Admission

v0.4.4 không tự:

- Re-evaluate Actor Admission.
- Re-evaluate Target Relation.
- Re-evaluate target existence.
- Re-evaluate Dodge/Critical.
- Recalculate Attack Damage.

Các stages đó đã có canonical owners.

Application chỉ validate consistency của supplied result và target states.

# 7. CB22 — Resource Damage Application

## 7.1. Objective

Áp positive calculated damage lên target resource bằng:

`transitionEntityResource()`

Không tạo một damage subtraction algorithm khác.

## 7.2. Canonical Operation

Conceptual call:

```ts
transitionEntityResource(
  resources,
  policy.resourceId,
  {
    maximum: policy.maximum,
    amount: attack.finalDamage,
    operation: "decrease",
    rule: {
      minimum: policy.minimum,
      currentAboveMaximum:
        policy.currentAboveMaximum,
      allowIncreaseFromMinimum: false
    }
  }
);
```

`allowIncreaseFromMinimum: false` là giá trị cố định cho một operation chỉ giảm resource; không mở ra caller-configured regeneration/revival behavior.

Actual implementation phải dùng accepted Entity API contract.

Không copy resource subtraction formula.

## 7.3. Positive Damage

Nếu:

```text
attack.outcome = landed
finalDamage > 0
```

Combat gọi canonical Entity Resource Transition đúng một lần.

Không:

- Gọi normalize trước một cách ngầm.
- Trừ HP trực tiếp.
- Apply damage hai lần.
- Tự clamp HP.
- Tự round applied damage.

## 7.4. Immutable State

Entity Resource Transition trả:

- New Resource State.
- Resource transition diagnostics.

Combat không mutate resource state cũ.

Không update:

```ts
resources.current.health -= damage;
```

Không viết vào mutable global resource map.

## 7.5. Multiple Resources

Ví dụ:

```text
health = 100
mana = 50
stamina = 30
```

Damage application với:

```text
resourceId = health
```

chỉ cập nhật health.

Expected:

```text
health = 70
mana = 50
stamina = 30
```

Không tự consume mana hoặc stamina.

Không tự áp resource cost.

## 7.6. Current Above Maximum

Phải bảo toàn actual Entity/Core behavior.

Policy:

```text
currentAboveMaximum = allow
```

không đồng nghĩa Combat tự normalize health trước khi trừ damage.

Gọi canonical Entity Resource Transition với policy đã cung cấp.

Nếu:

```text
currentAboveMaximum = reject
```

và current resource vượt maximum:

Operation phải reject theo accepted Entity behavior.

Không silently clamp rồi apply.

# 8. CB22 — Dodge & Zero Damage

## 8.1. Dodged Attack

Nếu attack outcome là:

```text
dodged
```

Expected:

- Calculated damage = 0.
- Applied damage = 0.
- Không gọi `transitionEntityResource()`.
- Không gọi `resolveEntityDefeat()`.
- Không tự normalize HP.
- Không đổi Life State.
- Không phát event.

Return structured no-op result.

Không tạo fake Resource Transition.

Không tạo fake Life Transition.

## 8.2. Landed With Zero Damage

Nếu:

```text
outcome = landed
finalDamage = 0
```

Expected:

- No resource transition.
- No defeat evaluation.
- Applied damage = 0.
- No state mutation.
- Explicit `zero_damage` outcome.

Không gọi Entity Resource API chỉ để tạo một transition bằng 0.

Điều này tránh việc một zero-damage action vô tình normalize above-maximum resources.

## 8.3. Already at Minimum

Phân biệt với zero calculated damage.

Ví dụ:

```text
Current HP = 0
Calculated Damage = 50
```

Đây là positive-damage processing attempt.

Nếu caller đã cho phép target ở trạng thái này qua previous stages:

- Gọi canonical Resource Transition.
- Applied damage có thể bằng 0.
- Sau đó gọi canonical `resolveEntityDefeat()`.

Không đồng nhất:

```text
calculatedDamage > 0
```

với:

```text
appliedDamage > 0
```

Nếu caller Life State đang alive nhưng HP đã ở minimum, Entity có thể trả defeat outcome dù applied damage bằng 0. Phải giữ actual Entity semantics, không tự phủ nhận bằng một Combat condition khác.

# 9. CB23 — Applied Damage Accounting

## 9.1. Objective

Phân biệt ba giá trị:

1. Calculated Damage.
2. Applied Damage.
3. Resource Current Difference.

Không mặc định chúng bằng nhau.

## 9.2. Calculated Damage

Lấy từ actual:

```text
CombatAttackResolutionResult.finalDamage
```

Ví dụ:

```text
calculatedDamage = 150
```

Không tính lại mitigation.

## 9.3. Applied Damage

Lấy trực tiếp từ canonical:

```ts
resourceTransition.transition.applied
```

Ví dụ:

```text
Before HP = 100
Calculated Damage = 150
Minimum = 0

After HP = 0
Applied Damage = 100
```

Overkill không làm applied damage vượt lượng HP thực tế được tính bởi canonical transition.

## 9.4. Do Not Reconstruct Applied

**Bắt buộc không dùng:**

```ts
const appliedDamage =
  beforeHealth - afterHealth;
```

Lý do: Kernel `ResourceTransitionResult.applied` là authoritative applied magnitude.

Trong above-maximum cases, `applied` có thể khác resource before/after delta.

Ví dụ:

```text
Before HP = 140
Maximum = 100
Minimum = 0
Damage = 20
currentAboveMaximum = allow
```

Theo pinned Kernel:

```text
After HP = 100
Applied Damage = 20
Before - After = 40
```

Expected Combat result:

```text
calculatedDamage = 20
appliedDamage = 20
```

Không ghi:

```text
appliedDamage = 40
```

Không sửa Kernel để ép hai đại lượng bằng nhau.

## 9.5. Applied Damage Rules

Đối với positive landed attack:

- Dùng actual Entity `transition.applied`.
- Không clamp lại.
- Không round lại.
- Không suy ra từ health delta.

Đối với dodged/zero-damage no-op:

```text
appliedDamage = 0
```

Đây là no-op outcome, không phải fabricated Entity transition.

## 9.6. Result Diagnostics

Preserve:

- Resource ID.
- Before.
- After.
- Applied.
- Reached minimum.

Bảo toàn canonical transition values.

Không thêm second numerical diagnostics calculator.

# 10. CB24 — Death Resolution

## 10.1. Objective

Sau successful positive-damage Resource Transition, evaluate Entity Life State bằng canonical:

`resolveEntityDefeat()`

## 10.2. Required Order

```text
Calculated Damage
       │
       ▼
transitionEntityResource()
       │
       ▼
Updated Resource State
       │
       ▼
resolveEntityDefeat()
       │
       ▼
Updated Life State
```

Bắt buộc dùng updated resource snapshot.

Không dùng original Resource State để evaluate death sau khi damage đã apply.

## 10.3. Canonical Call

Conceptual:

```ts
resolveEntityDefeat(
  life,
  resourceResult.state,
  {
    resourceId: policy.resourceId,
    minimum: policy.minimum,
    maximum: policy.maximum
  }
);
```

Không dùng:

```ts
if (hp <= 0) {
  target.dead = true;
}
```

Không tạo custom defeat evaluator.

## 10.4. Nonlethal Damage

Ví dụ:

```text
Before HP = 100
Damage = 30
After HP = 70

Before Life = alive
```

Expected:

```text
Life after = alive
Life outcome = unchanged
```

Không tạo death event.

## 10.5. Lethal Damage

Ví dụ:

```text
Before HP = 100
Damage = 150
After HP = 0

Before Life = alive
```

Expected:

```text
Life after = dead
Life outcome = defeated
```

Không tự tạo corpse/loot/EXP.

Không cập nhật Encounter status.

## 10.6. Already Dead Target

v0.4.2 cho phép caller-defined policy nhắm vào dead targets.

Do đó v0.4.4 không được tự thêm một blanket rule:

```text
dead target cannot receive damage
```

Nếu previous stages chấp nhận target và actual Entity Resource Transition hợp lệ:

- Giữ canonical Entity Life semantics.
- Không tự revive.
- Không tự chuyển dead thành alive.
- Không phát defeat lần thứ hai nếu Entity trả `unchanged`.

Không tạo special undead/double-death mechanics.

## 10.7. Defeat Is a Transition

Phải phân biệt:

```text
Life after = dead
```

với:

```text
Life transition outcome = defeated
```

Nếu target đã dead trước operation:

```text
before = dead
after = dead
outcome = unchanged
```

Đây không phải một defeat transition mới.

Không báo:

```text
newlyDefeated = true
```

chỉ vì life status cuối là dead.

## 10.8. Resource Minimum vs Death

Không sử dụng riêng:

```text
resourceTransition.reachedMinimum
```

làm authoritative death result.

Entity Life Transition mới quyết định:

- `defeated`
- `unchanged`
- `revived`

Combat chỉ project actual canonical outcome.

Không gọi `reviveEntity()` trong v0.4.4.

# 11. CB25 — Combat Damage Application Result

## 11.1. Objective

Cung cấp một structured immutable result đủ để:

- Consumer cập nhật authoritative snapshots.
- Theo dõi calculated/applied damage.
- Phân biệt dodge, zero damage và processed damage.
- Phát hiện defeat transition.
- Tích hợp Encounter/Events sau này.

## 11.2. Result Status

Đề xuất:

```ts
export type CombatDamageApplicationOutcome =
  | "dodged"
  | "zero_damage"
  | "processed";
```

Ý nghĩa:

**dodged**

Attack không trúng, không thực hiện Entity transitions.

**zero_damage**

Attack landed nhưng finalDamage bằng 0, không thực hiện Entity transitions.

**processed**

Positive calculated damage được đưa qua canonical Entity Resource/Life transitions.

`processed` không khẳng định appliedDamage lớn hơn 0.

## 11.3. Result Contract

Conceptual:

```ts
type CombatDamageApplicationResult =
  | {
      readonly context: CombatActionContext;
      readonly outcome: "dodged" | "zero_damage";

      readonly calculatedDamage: 0;
      readonly appliedDamage: 0;

      readonly resourceResult: null;
      readonly lifeResult: null;
    }
  | {
      readonly context: CombatActionContext;
      readonly outcome: "processed";

      readonly calculatedDamage: number;
      readonly appliedDamage: number;

      readonly resourceResult:
        EntityResourceTransitionResult;

      readonly lifeResult:
        EntityLifeTransitionResult;
    };
```

Tên fields có thể điều chỉnh theo accepted v0.4.3 conventions.

Phải giữ một discriminated result rõ ràng.

## 11.4. No-Op Results

Đối với dodge/zero damage:

```text
resourceResult = null
lifeResult = null
```

Caller tiếp tục giữ current Resource/Life States.

Không tạo duplicated unchanged snapshots chỉ để giả lập transition chưa chạy.

Tuy nhiên, phải validate target state identity và policy inputs trước khi trả no-op result.

## 11.5. Processed Result

Processed result phải chứa:

- Detached immutable Combat Action Context.
- Calculated damage.
- Actual applied damage.
- Actual Entity Resource Transition Result.
- Actual Entity Life Transition Result.

Resource State trong result là next authoritative snapshot do Entity tạo ra.

Life State trong result là next authoritative snapshot do Entity tạo ra.

Không tạo một Resource/Life state riêng từ Combat.

## 11.6. Defeat Diagnostics

Không cần second Death Engine.

Consumer có thể đọc:

```text
lifeResult.outcome = defeated
```

Nếu bổ sung convenience field như:

```text
newlyDefeated
```

phải derive trực tiếp từ canonical Life Transition và không tạo authority riêng.

Ưu tiên không bổ sung field nếu không cần thiết.

## 11.7. Immutability

Bắt buộc:

- Root result frozen.
- Embedded context frozen/detached.
- Resource result frozen.
- Nested Resource State frozen.
- Resource current map frozen.
- Resource transition frozen.
- Life result frozen.
- Nested Life State frozen.

Không mutate caller inputs.

Không giữ writable aliases.

Không gọi freeze trên caller-owned original objects như side effect.

# 12. Transaction & Failure Boundaries

## 12.1. Immutable Combined Operation

Successful positive-damage processing tạo:

1. New Resource State.
2. Resource Transition.
3. New Life State.
4. Life Transition.
5. Combined Combat Application Result.

Nếu validation hoặc Entity operation thất bại:

- Không trả partial successful Combat result.
- Không mutate original snapshots.
- Không publish event.
- Không ghi persistent store.

## 12.2. No Database Transaction Claim

Đây là immutable result construction.

Không phải:

- Durable transaction.
- Database commit.
- Network synchronization.
- Exactly-once damage application.
- Concurrent-write conflict resolver.

Caller phải áp dụng next Resource/Life snapshots cùng nhau tại authoritative game runtime.

Không tự lưu vào Global Combat State.

## 12.3. Replay Limitation

Nếu caller dùng cùng Attack Result trên nhiều snapshot branches, Combat không có global memory để nhận biết đã apply trước đó.

Không xây Attack Ledger ở v0.4.4.

Document:

- Caller owns latest snapshots.
- Caller owns replay/idempotency control.
- Caller owns action authorization.
- Combat only returns deterministic transitions for supplied inputs.

Không claim chống double damage khi caller cố tình replay cùng receipt.

## 12.4. No Hidden Side Effects

Không:

- Update Entity Collection.
- Change Skill State.
- Change Progression State.
- Grant EXP.
- Grant Loot.
- Publish events.
- Update Encounter.
- Trigger AI.
- Schedule another attack.
