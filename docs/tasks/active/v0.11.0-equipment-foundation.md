## 4. Proposed stable public API (exact shapes subject to accepted predecessor compatibility)

**Two runtime functions and five public types.** No extras/aliases. If actual accepted Item API prevents using `ItemInstanceState`/`ItemDefinition` as proposed, **STOP with evidence** and request a contract correction; don't reimplement Item.

```ts
export interface EquipmentOwnerReference {
  readonly ownerKind: string;
  readonly ownerId: string;
}
export interface EquippedEntry {
  readonly item: ItemInstanceState;
  readonly slotIds: readonly string[];
}
export interface EquipmentState {
  readonly equipmentId: string;
  readonly owner: EquipmentOwnerReference | null;
  readonly entries: readonly EquippedEntry[];
}
export interface EquipmentItemContext {
  readonly definition: ItemDefinition;
}
export interface EquipmentValidationContext {
  readonly items: readonly EquipmentItemContext[];
}
export function createEquipmentState(
  input: EquipmentState,
  context: EquipmentValidationContext,
): EquipmentState;
export function validateEquipmentState(
  state: EquipmentState,
  context: EquipmentValidationContext,
): EquipmentState;
```

**State/validation semantics (normative):**

1. `equipmentId` and `ownerKind/ownerId` are exact, nonblank opaque strings. `owner: null` valid. Preserve case/whitespace; never auto-generate, trim or infer from Entity.
2. `entries` is a required ordered dense array; zero entries valid. Each `item` is the **accepted** ItemInstanceState, validated with full matching ItemDefinition supplied through context. **One `item.instanceId` at most once** within the EquipmentState, regardless of slot IDs. Cross-storage global uniqueness is outside L2.
3. `slotIds` is a required **nonempty dense ordered array** of exact nonblank opaque strings. No duplicate ID within an entry, **no slot occupied in two entries**. No default slot, capacity, fixed weapon/armor vocabulary or automatic slot reservation inferred from item category. Slot array order preserved, but no gameplay priority is inferred from it.
4. `context.items` is a required array of closed `{definition}` records with full canonical validated ItemDefinitions. **One definition per exact `definitionId`**; duplicates (even equal duplicates) reject. Unused definitions allowed (for operation preloading). Missing definition for any equipped item rejects; ItemDefinition/ItemInstance binding validated using canonical public Item `validateItemInstance`. Context itself never saved to EquipmentState.
5. All Equipment public inputs must be own-data records of exact shape, with no extra fields, symbol fields, accessors, custom prototypes, inherited required fields or cycles. Reject invalid arrays (sparse/extra indexed metadata) and malformed nested Item values using Item validators **without executing user getters**. Nonempty IDs required; `slotIds` are IDs (different from arbitrary property dictionary keys).
6. Malformed inputs/duplicate IDs/occupied-slot conflicts in a **supplied snapshot** => deterministic `TypeError`. There are no ordinary operation `rejected` outcomes yet: create/validate return snapshots or throw.
7. Every successful call returns a **fresh detached deeply frozen** EquipmentState, with **no aliases into caller objects** and no modifying/freezing caller inputs. Validation and creation may accept nonempty input (for rehydration/testing) but do not claim an Item was legally moved/equipped in an authoritative game.
8. No `quantity`, `slotLayout`, `itemDefinition`, `statModifiers`, `isEquipped`, `transactionId`, `revision`, `itemOwner`, `timestamp`, `equipmentType` or runtime provider added to canonical state. Use Item Instance `instanceId` for one local membership identity; do not invent a redundant equipment-entry ID.

### Literal example fixture (test-only)

```ts
const swordDefinition = createItemDefinition(
  createItemDefinitionReference({ definitionId: 'def-sword' }),
  { categoryId: 'weapon', tagIds: [], rarityId: null, properties: {} },
);
const sword = createItemInstance(swordDefinition, {
  instanceId: 'item-sword-1', properties: {},
});
const context = {items:[{definition:swordDefinition}]};
const empty = createEquipmentState({
  equipmentId:'equip-player-1', owner:{ownerKind:'entity',ownerId:'hero-1'}, entries:[],
}, context);
// exact empty.entries.length === 0
const loaded = validateEquipmentState({
  equipmentId:'equip-player-1', owner:{ownerKind:'entity',ownerId:'hero-1'},
  entries:[{item:sword,slotIds:['weapon_main']}],
}, context);
// one entry, same exact Item identity/data, slotIds ['weapon_main']; deeply frozen.
```

`weapon_main`/`hero-1` are **only test IDs**. No Player/Entity type in Equipment. Future two-handed state with `['hand_left','hand_right']` may be **validated as data** in Foundation; no equip gameplay rule or Item modifier occurs here.
