## 1. Objective and feature inventory

Make an **active Encounter's participant and side membership** a reusable, explicit **scope gate** for Combat, Skill and Actor AI integrations, while preserving **all canonical owners**. The Encounter module checks **who belongs to this encounter and what side each member belongs to**; it does **not** decide whether a Combat attack, Skill activation, Effect gate or AI proposal will execute successfully.

| ID | Feature | Required outcome |
| --- | --- | --- |
| **EN16** | Encounter Action Participation Gate | Validate that the encounter is `active` and the source Entity is a current participant; otherwise reject. |
| **EN17** | Encounter Target Membership & Side Scope | Validate current target membership, explicit targetless intents and same-side/other-side/self associations without replacing Combat's canonical relation gate. |
| **EN18** | Combat / Skill / Effect Coordination | L4 installed consumer composes Encounter scope with real canonical admission, target validation, cost/cooldown, execution and feedback paths. No Encounter-owned execution. |
| **EN19** | Actor AI Coordination | L4 consumes actual AI proposal, verifies exact identity/target/action correlation, current controller/Life/timing and Encounter scope, then dispatches only after canonical gates. |
| **EN20** | Scope Outcomes & Integration Verification | Deterministic, immutable, fail-closed scope results; current-state/duplicate/race controls in L4; full installed and historical regressions. |

### Expected gameplay-facing outcome

```text

Status: active
Sides: party, enemies
Participants:
  player-001  -> party
  monster-001 -> enemies

Monster AI proposes Basic Attack on player-001:
```

Only canonical mathematical resolution: Hit/Dodge/Critical, damage/mitigation, stat/resource calculations. v0.8.3 adds no new formulas, RNG, threat score, target prioritization or Core code.

### L2 — Encounter (this milestone)

- Check that the encounter is active.
- Read **current snapshot** of participant→side association.
- Check exact actor/source membership and optional target membership.
- Derive purely structural `self` / `same_side` / `other_side` membership association.
- Produce a **detached immutable eligibility/rejection assessment**, not a transition, authorization token, Combat relation or execution receipt.

- **Entity:** stable Entity identities, collection membership and Life/resources. Encounter must not mirror HP/MP/Stats/Life or declare an Entity dead.

## 5. EN16–EN17 public API proposal — minimal advisory gate

### 5.1. Scope design decisions

An Encounter scope gate answers only:

1. Is this **exact Encounter** active?
2. Is the proposed **source Entity** a participant here?
3. Is the action caller-configured as **targetless** or as requiring a participant target?
4. If targeted, is that exact target in **this Encounter**?
5. If targeted, is the source–target **membership-side association** allowed by L3 policy?

It never accepts an `Entity.kind` whitelist, never looks up a World map, never treats `other_side` as synonymous with canonical Combat `enemy`, and never executes gameplay. The targetless mode is for actions such as explicit AI `wait`/`return_home` **if L3/L4 chooses that action contract**. Basic Attack and Entity-targeted Skill must use participant-target mode.

**Important scope limitation:** v0.8.3 intentionally does **not** support cross-Encounter targeted actions. If a game later needs a projectile or Skill affecting targets in another Encounter, obtain a separate approved targeting contract; do not add an undocumented opt-out or take a `target_not_participant` as permission to execute.

### 5.2. Proposed public types

```ts
export type EncounterActionTargetMode = 'none' | 'participant';

/** Encounter side membership, NOT Combat's self/ally/enemy/neutral relation. */
export type EncounterSideMembershipRelation =
  | 'self'
  | 'same_side'
  | 'other_side';

/** L3 policy for one action binding; no defaults and no policy registry. */
export interface EncounterActionScopePolicy {
  readonly targetMode: EncounterActionTargetMode;
  readonly allowedSideRelations: readonly EncounterSideMembershipRelation[];
}

/** L4 binds canonical action/intent identity to one scope assessment. */
export interface EncounterActionScopeRequest {
  readonly encounterId: string;
  readonly actionId: string;
  readonly sourceEntityId: string;
  readonly targetEntityId: string | null;
}

export type EncounterActionScopeRejectionReason =
  | 'encounter_not_active'
  | 'source_not_participant'
  | 'target_required'
  | 'unexpected_target'
  | 'target_not_participant'
  | 'side_relation_not_allowed';

export type EncounterActionScopeResult =
  | {
      readonly status: 'eligible';
      readonly reason: 'none';
      readonly encounterId: string;
      readonly actionId: string;
      readonly sourceEntityId: string;
      readonly targetEntityId: string | null;
      readonly sourceSideId: string;
      readonly targetSideId: string | null;
      readonly sideRelation: EncounterSideMembershipRelation | null;
    }
  | {
      readonly status: 'rejected';
      readonly reason: EncounterActionScopeRejectionReason;
      readonly encounterId: string;
      readonly actionId: string;
      readonly sourceEntityId: string;
      readonly targetEntityId: string | null;
      readonly sourceSideId: string | null;
      readonly targetSideId: string | null;
      readonly sideRelation: EncounterSideMembershipRelation | null;
    };
```

**Type delta target:** six types. Reuse equivalent accepted types if present and do not create separate `EncounterCombatAdmission`, `EncounterSkillAdmission` and `EncounterAIAdmission` engines/types.

Policy rules:

- `targetMode:'none'`: **must** have `allowedSideRelations:[]`; `targetEntityId` **must** be `null` to be eligible.
- `targetMode:'participant'`: `allowedSideRelations` must be **nonempty** and contain unique values from exactly the three named membership relations. `targetEntityId` must be a nonblank exact string to be eligible.
- Do not silently repair contradictory policy or missing/unknown keys. Identical relation content in a different array order is semantically equivalent; no selection priority is embedded in this list.
- `actionId` is an **opaque correlation value**, not globally unique by L2 and **not** an execution authorization, idempotency key automatically persisted, or receipt. L4 must choose its exact correspondence to an AI decision, Combat action or direct Skill/World request and own duplicate control.
- IDs preserve case, spaces and exact spelling under existing identity validation; no normalizing/sorting.

### 5.3. Proposed public functions

```ts

  input: EncounterActionScopePolicy,

export function createEncounterActionScopeRequest(
```

## 6. Validation, reason precedence and semantics

### 6.1. Structural validation always first

Before returning *any* normal outcome (including inactive encounter):

1. Validate the whole Encounter State and canonical Entity Collection through existing Encounter/Entity APIs. Reject malformed roster/sides, duplicated participants, missing roster Entity references, wrong shape or malformed status with `TypeError`.
2. Capture and validate complete `EncounterActionScopePolicy`: closed own-data record, exact discriminants, no extra or inherited fields, no getters evaluated, complete dense arrays, valid unique relations, policy mode/relation compatibility.
3. Capture and validate `EncounterActionScopeRequest`: exact closed own-data properties, valid nonblank `encounterId`/`actionId`/`sourceEntityId`, `targetEntityId` null or valid ID. Reject accessors, symbols, arrays, unknown keys and inherited fields.
4. Require `request.encounterId === state.encounterId`; mismatch is **TypeError** (wrong encounter binding), not a domain-rejection alias.
5. Only then evaluate the domain gates below.

A well-formed **nonparticipating** source/target ID is a **domain rejection**, not malformed input. A wrong active-state snapshot cannot claim authoritative current membership; L4 supplies/rechecks freshness.

### 6.2. Deterministic first reason wins

After valid structural input:

| Order | Condition | Result reason |
| --- | --- | --- |
| 1 | `state.status !== 'active'` | `encounter_not_active` |
| 2 | Source does not participate | `source_not_participant` |
| 3 | `targetMode:'participant'` with null target | `target_required` |
| 4 | `targetMode:'none'` with non-null target | `unexpected_target` |
| 5 | Required target is not in this encounter | `target_not_participant` |
| 6 | Existing participant-target relationship is not permitted by L3 list | `side_relation_not_allowed` |
| 7 | Otherwise | `eligible / none` |

Use the current `state.participants` snapshot only. `sourceSideId` is null until source membership is established. For an existing but disallowed target, return its actual `targetSideId` and computed `sideRelation` as diagnostics. For targetless action, return `targetSideId:null` and `sideRelation:null`.

### 6.3. Exactly defined relation mapping

```text
sourceEntityId == targetEntityId            -> self
sourceEntityId != targetEntityId,
  source.sideId == target.sideId             -> same_side
sourceEntityId != targetEntityId,
  source.sideId != target.sideId             -> other_side
```

These are **membership associations**, not tactical relationships. Combat still evaluates independently the current caller-supplied `CombatTargetRelation` and `CombatTargetPolicy`; target of `other_side` is **not automatically enemy**, and `same_side` is **not automatically ally**. L3/L4 must not convert those values without a concrete, externally supplied relation policy.

### 6.4. Immutability and result contract

- Never mutate Encounter State, participant arrays, EntityCollection, source/target Entity, Life/resources, policy, request or any World/AI/Combat/Skill/Effect state.
- Return new fully detached/frozen own-data result and factories; no exposure of caller-owned nested mutable arrays.
- Do not add `lastAction`, `currentTurn`, `actionCount`, `lastAttacker`, `winner`, `combatState`, `HP`, `updatedAt`, `revision`, `receipt`, `lock`, `cooldown` or global store to Encounter State.
- Repeated identical input values yield identical semantic results and independent objects. No implicit `Date.now`, `Math.random`, ID provider, event bus or timer.
- Two scope assessments may return `eligible` from the same baseline. This gives **zero** authority to execute twice: L4 must perform a fresh atomic compare-and-commit and explicit duplicate prevention.

### 6.5. Negative meaning of `eligible`

`eligible` means **only Encounter membership and side scope are satisfied**. It does not establish current World existence, current Entity Life, single controller, line of sight, actor admission, Skill ownership, cooldown/resource balance, Effect restrictions, Combat hit, applied damage, action scheduling, success or persistence. Every such gate remains the responsibility of its canonical module and L4.

## 7. EN16 — Encounter Action Participation Gate

### 7.1. Active-only source

An active encounter with a known source participant may pass the source gate. A `prepared`, `resolved`, `closed` or `cancelled` encounter cannot admit an action scope, even when it still contains a valid participant roster. `activateEncounter()` from v0.8.1 is the only accepted transition to `active`; v0.8.3 cannot flip status.

### 7.2. Empty and dynamic roster

An `active` encounter with zero members stays `active` under accepted membership semantics; all source-gated requests reject `source_not_participant`. No victory/draw/cancellation inferred.

After accepted v0.8.2 explicit leave/change-side/join is **committed by L4**, a fresh assessment uses the updated participant snapshot. A proposal created before a leave may have been eligible then, but **must not** remain dispatchable merely due to stale assessment. L4 re-reads current membership just before canonical admission and just before any commit susceptible to reentrancy.

### 7.3. Two encounters / one Entity

Encounter scope is **encounter-local**, not a global ownership registry. A source in Encounter A is not automatically authorized in B. A simultaneous membership conflict across A/B, if prohibited by a game, must be enforced by L4's cross-Encounter authoritative roster/World rules. Do not claim v0.8.3 provides global uniqueness or transactional isolation.

## 8. EN17 — Encounter Target Membership & Side Scope

### 8.1. Basic Attack / targeted Skill

For Basic Attack and an Entity-targeted Skill, caller-supplied policy is typically:

```ts
const enemySideMember = createEncounterActionScopePolicy({
  targetMode: 'participant',
  allowedSideRelations: ['other_side'],
});
```

This does **not** replace Combat's `enemy` relation. L4 must provide an actual current Combat relation and evaluate the canonical Combat target policy. For neutral, party-v-party, friendly fire or temporary alliance scenarios, L3 supplies the correct policy and canonical relation evidence; no encounter-side hardcoding.

### 8.2. Self-support / same-side Skill

```ts
const support = createEncounterActionScopePolicy({
  targetMode: 'participant',
  allowedSideRelations: ['self', 'same_side'],
});
```

A self Skill targets the source Entity ID (not null). Skill eligibility still belongs to Skill; Effect and L4 still gate status/restrictions. Same-side association cannot grant heal/benefit admission to a forbidden target.

### 8.3. Targetless advisory action

```ts
const noTarget = createEncounterActionScopePolicy({
  targetMode: 'none',
  allowedSideRelations: [],
});
```

Only a `targetEntityId:null` request can pass. This is structurally compatible with certain AI intents like `wait`/`return_home`. **L4 decides whether a targetless action may be dispatched and who owns its World effect**; Encounter does not pathfind, move, schedule, enter a turn or process wait.

### 8.4. Cross-Encounter/unknown/dead target

A target ID absent from current Encounter roster rejects `target_not_participant` regardless of whether that ID exists in another World/Encounter. A dead Entity **still listed as a participant** can pass the **membership-only** check; canonical Life and Combat/Skill target admission must block dead targets when appropriate. No Encounter inference that dead means auto-leave or auto-resolve.

## 9. EN18 — Combat / Skill / Effect integration, executed only in L4 consumer

The **production Encounter module must not import** Combat, Skill, Effect or Actor AI. Test-only L4 composition imports them through the **installed package's root export** and performs real canonical operations.

### 9.1. Combat pipeline (test-only L4 composition)

```text
L4 current Encounter State + EntityCollection
  -> evaluateEncounterActionScope (eligible or reject)
  -> verify actual current controller / actor Life / target Life / World facts
  -> createCombatActionContext (existing Combat request)
  -> evaluateCombatActionAdmission (Combat owner)
  -> evaluateCombatTargetValidation (Combat owner)
  -> resolveCombatAttack (Combat + pinned Kernel)
  -> applyCombatAttackDamage (Combat calls canonical Entity Resource/Life)
  -> L4 compare-and-commit authoritative candidate
  -> report terminal execution outcome to originating AI when relevant
```

L4 must match **exact** action correlation: scope `actionId` ↔ current request ID, `sourceEntityId` ↔ `CombatActionContext.sourceEntityId`, `targetEntityId` ↔ canonical `target.entityId`. Do not trust an old scope result after target/source/side membership changes. A malicious mismatch is rejected **before** canonical execution; this is an L4 assertion, not a new Encounter engine.

Prove actual numerical results through the existing Combat+Kernel public API (e.g., a deterministic fixture with HP 100 and actual applied 20 produces HP 80 if hit/mitigation policy yields 20). Dodge/zero-damage may still be **completed** with applied 0. A source absent from Encounter does not cause any Combat RNG call or HP change.

### 9.2. Skill pipeline (test-only L4 composition)

```text
L4 actionKey -> SkillInstance/definition binding
  -> current Encounter scope
  -> current Skill ownership / rank / resource / cooldown / target gates
  -> current Effect restriction interpretation via L3/L4
  -> canonical Skill activation and payment/cooldown transitions
  -> L4 canonical dispatch + terminal execution report
```

Canonical Skill API names/signatures must be read from actual current source; examples include existing Skill admission/cost/cooldown/activation/report functions. Do not create a second resource/cooldown calculator or an Encounter Skill eligibility engine.

**Critical D04:** Skill activation **accepted** is not proof of execution completion. If dispatch returns pending, terminal AI feedback must remain pending/absent; only an actual execution outcome allows `completed` or `failed`. If canonical Skill already committed cost/cooldown before a later failure, do not invent a refund/retry. If Encounter scope rejects, there must be **zero payment, cooldown start, Effect application or Skill dispatch**.

### 9.3. Effect restrictions (test-only L4 composition)

L4 evaluates current actual Effect status/restrictions and composes them as an **AND gate** alongside current Encounter scope and canonical Combat/Skill admission. Encounter `eligible` must **never override** a restrictive Effect or current cooldown/resource rejection. Encounter `rejected` must not be overridden by Effect `allowed` or Combat-target `accepted`.

### 9.4. No direct Combat/Skill production dependency

Use existing `@rpg/gameplay` installed public APIs in the consumer fixture, **not** imports in `src/modules/encounter/index.ts`. Do not edit protected Combat/Skill/Effect modules to make the fixture pass. If a true canonical capability is missing, record a minimal reproduction and escalate; **do not** replace it with a shortcut.

```ts
  sourceEntityId: aiIntent.actorId,
  targetEntityId: aiIntent.targetEntityId,
});
```

L4 first validates that `aiIntent` is an **actual current** AI proposal and uses the correct `actionKey`→scope policy and canonical action mapping. An attacker-supplied matching `decisionId` alone is not authorization; L4 must bind AI state/profile/controller, decision and target to current authoritative records, and maintain attempt/decision freshness/idempotency under its own runtime.

`actionId` is **not required by L2 to equal decisionId universally**. This example is one explicit L4 mapping. For non-AI manual actions L4 binds its own canonical action identity.

### 10.3. Current gating and dispatch

Before sending any Combat/Skill/Movement/Wait action, L4 must:

1. Read current authoritative Encounter status/roster and current Entity/AI controller/Life state.
2. Re-evaluate Encounter scope using **current membership**, not stale perception, not prior selection evidence.
3. Verify AI controller is still `ai`, current actor Life is allowed, current decision cadence/turn is valid and original intent is still current (no manual takeover, actor death, stale decision or target switch).
4. Evaluate canonical Combat/Skill/Effect/World requirements for the action.
5. Execute exactly once according to L4 commit/attempt policy; record actual outcome.
6. Produce **terminal feedback only when supported by actual execution**, with exact actor/decision/action/target/attempt bindings. Never mark a `proposed` or Skill `accepted` action completed.

No automatic retry, priority reselection, movement, AI state transition, timer scheduling or target mutation is added by Encounter. Subsequent AI decisions and behavior transitions remain caller-explicit.

### 10.4. No-AI composition

Encounter + Entity + Combat must work **without** Actor AI enabled. An Encounter target scope must never require an AI profile/behavior state. Manual controller actions still pass through Encounter membership and canonical admission when L4 dispatches them.

## 11. EN20 — Scope outcomes, rejection, failure atomicity

### 11.1. Outcomes

| Input | Required outcome | Canonical continuation |
| --- | --- | --- |
| Active encounter; member source; member target; relation permitted | `eligible / none` | L4 **still** executes canonical gates |
| `prepared/resolved/closed/cancelled` | `rejected / encounter_not_active` | No dispatch |
| Source absent from roster | `rejected / source_not_participant` | No dispatch |
| Targeted policy + target null | `rejected / target_required` | No dispatch |
| Targetless policy + target non-null | `rejected / unexpected_target` | No dispatch |
| Target ID outside roster | `rejected / target_not_participant` | No dispatch |
| Both participants but forbidden side association | `rejected / side_relation_not_allowed` | No dispatch |
| Valid Encounter scope, Combat target policy rejects | Encounter result remains eligible; Combat rejects | No damage |
| Valid Encounter scope, Skill cooldown or Effect blocks | Encounter result remains eligible; owner rejects | No Skill dispatch/payment beyond canonical rules |
| Scope eligible then source/target leaves or switches before dispatch | L4 fresh scope rejects or authority CAS rejects | No stale action or partial commit |
| Scope eligible twice from one baseline | Two advisory results allowed | L4 permits **at most one** authoritative attempt/commit |
| Structural violation, mismatched Encounter ID | `TypeError` | No result/candidate/partial write |

### 11.2. Structural errors vs domain rejections

Preserve exact `TypeError` for malformed source data, wrong Encounter identity, unknown schema fields, inherited/accessor/symbol keys, conflicting target policy and wrong EntityCollection. Domain rejection reasons apply only to well-formed requests evaluated against a valid Encounter snapshot.

### 11.3. Rejection does not mutate

A rejection never updates Encounter membership/status, Entity resources/Life, AI state/target/timing, Skill cooldowns, Effects, World position or caller action ledger. Scope API only returns immutable data. Tests must assert **negative side effects** with real pre/post snapshots and provider-call counts, not merely `status:'rejected'` strings.

### 11.4. L4 commit authority

L2 does not supply durable compare-and-swap, receipt issuance, distributed exactly-once guarantees or a storage transaction. L4 fixture may demonstrate a **session-local** revision/decision/attempt ledger, fresh snapshots and atomic candidate acceptance; label the limitation accurately. Do not claim production durability from test-only fixtures.
